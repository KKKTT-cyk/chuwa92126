# Homework 17 – Observability

## 1. How many time series does the histogram create?

Each label combination creates 11 series: 8 finite buckets, the +Inf bucket, the sum, and the count. That gives 100 × 20 × 4 × 11 = **88,000 series**. If every combination occurs for every user, adding user_id raises the count to 88,000 × 50,000 = **4.4 billion series**.

Active series and their indexes use RAM. Writing samples needs CPU, disk space, and disk I/O. Queries that combine many series also take longer.

1. In application code, keep user IDs in logs or traces and use bounded metric labels such as status.
2. In HTTP instrumentation, label requests by route template, such as /videos/{id}, so all video IDs share one route.
3. At the collector, filter out unexpected high-cardinality metrics before they reach storage.

## 2. Can we average the p99 latency of two instances?

The combined p99 depends on the 990th request when all 1,000 latencies are sorted from fastest to slowest (nearest-rank method). A's p99 of 20 ms and B's p99 of 600 ms tell us too little about that ordering. Neither the simple average (310 ms) nor the traffic-weighted average (136 ms) gives a reliable combined p99.

| Method | Across instances | Accuracy and cost |
|---|---|---|
| Client-side summary | Precomputed p99 values cannot be merged. | Estimates selected percentiles with a configured rank error. Each instance spends CPU and memory computing them. |
| Fixed-bucket histogram | Add matching bucket counts, then estimate p99. | Precision depends on bucket width. More buckets give finer resolution and create more series. |
| Mergeable sketch | Merge compatible sketches, then estimate p99. | A sketch such as DDSketch bounds relative value error. Tighter accuracy generally needs more memory. |

For a 200 ms objective, a bucket ending at 200 ms tells us exactly how many requests met the target. Nearby boundaries help estimate percentiles around it.

## 3. How much memory does tail sampling need?

2,000 traces/s × 20 s × 8 spans/trace × 400 bytes/span = **128,000,000 bytes (128 MB, about 122 MiB)** for span data. A real sampler also needs memory for queues and trace metadata.

Route all spans with the same trace ID to one node so it can make one keep-or-drop decision for the whole trace. Otherwise one node might miss the span that recorded an error.

With uniformly distributed hashes, growing from 4 to 5 nodes changes the destination for **80%** of traces under hash(trace_id) modulo N. Across 20 consecutive hash values, only 4 keep the same remainder. With balanced consistent hashing, the new node takes about **1/5 (20%)** of the keys and the rest stay in place.

## 4. What does the traceparent header mean?

| Field | Value | Meaning |
|---|---|---|
| Version | 00 (1 byte) | Header format version. |
| Trace ID | 4bf92f3577b34da6a3ce929d0e0e4736 (16 bytes) | Identifies the whole trace. |
| Parent ID | 00f067aa0ba902b7 (8 bytes) | Identifies the caller's span for this request. |
| Trace flags | 00 (1 byte) | The sampled bit is off. |

A service using parent-based sampling follows the incoming unsampled decision and propagates it downstream. For its outgoing request, it keeps the trace ID and sets the parent ID to its own outgoing span's ID. The next service can then identify its direct parent.

## 5. How fast is the error budget being used?

The allowed error ratio is 100% − 99.95% = 0.05%. Over 30 days, the time budget is 30 × 24 × 60 × 0.0005 = **21.6 minutes**.

| Burn rate | Error ratio | Share of the 30-day budget used | Action for this exercise |
|---|---|---|---|
| 14.4× for 1 hour | 14.4 × 0.05% = 0.72% | 14.4 × 1 / 720 = 2% | Page the on-call engineer for the fast burn. |
| 6× for 6 hours | 6 × 0.05% = 0.30% | 6 × 6 / 720 = 5% | Open a ticket for prompt investigation of the slower burn. |

At a steady 6×, a full budget lasts **30 / 6 = 5 days**. Require both windows to exceed the threshold. The long window confirms significant budget loss, and the short window confirms the problem is still happening.

## 6. How can monitoring keep working safely during an outage?

The application puts telemetry into a bounded queue without waiting. A background worker exports batches to a collector with timeouts and limited retries. If the queue fills, the application drops telemetry and continues serving requests.

| Option | Where to use it and what it costs |
|---|---|
| Buffering | A bounded exporter or collector queue absorbs short outages. It uses memory or disk and eventually fills. |
| Dropping | The SDK or collector discards records when full. This protects the application but leaves gaps. |
| Sampling | The SDK or collector keeps a subset of traces. This reduces volume but may miss rare events. |
| Rate limiting | The collector caps incoming or outgoing traffic. This protects capacity but loses detail during bursts. |

At-least-once delivery retries unacknowledged records and may create duplicates. At-most-once delivery avoids redelivery but can lose records after a failure.

Run alerting in a separate failure domain so a service outage cannot also silence its alerts. Send a regular heartbeat through the alerting path to an independent receiver. A watchdog alerts when that heartbeat stops, including when the monitoring or notification path itself breaks.
