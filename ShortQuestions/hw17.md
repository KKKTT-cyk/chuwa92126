# java-observability-homework

## Q1
Logs record individual events. Each entry includes a timestamp, a severity level, and a message. Log volume grows with the number of events and logs show what happened at a specific time.

Metrics record a timestamp and a numeric value for each sample and help detect trends and trigger alerts. At a fixed sampling interval, metric volume grows with the number of label combinations.

Traces show the path of a request and each span records an operation, its timing, and its parent span ID if it has a parent. Trace volume grows with the number of traced requests and the number of spans per request and traces show where delays or errors occur.

A telemetry pipeline is a distributed system that continuously collects and stores data from many services. Reads mainly come from dashboards, alerts, and troubleshooting, so they are less frequent but can spike during incidents.


## Q2
Full-text inverted index maps each term to the log entries that contain it. Building and storing the index adds work and uses extra space at write time. Keyword searches are fast, but common terms can return many entries to process. Indexing high-cardinality fields like request IDs adds many unique terms and makes the index larger.

Label index indexes labels such as service and stores the full logs in compressed chunks in object storage. At write time, the system indexes the labels and compresses the logs. Queries by service and time can quickly locate the relevant chunks, but keyword searches require reading, decompressing, and scanning those chunks. Using request IDs as labels creates many small streams and chunks, increasing overhead.

For a high-volume platform where most queries ask for one service’s logs from the last 15 minutes, I would choose the label index. The service label and time range can locate the relevant chunks while keeping indexing costs low.


## Q3
In pull-based collection, the collector uses service discovery to find targets and fetches their metrics at a set interval. A failed scrape tells the collector that a target is unreachable. The collector controls the collection rate and uses timeouts to limit the impact of a slow target. However, it needs network access to each target, and a short-lived batch job may finish before the next scrape.

In push-based collection, applications send metrics to a known collector endpoint. The collector does not need to discover each application before receiving data. Push works well for short-lived jobs that can send metrics before exiting and for applications behind firewalls that allow outbound connections. Applications control how often they send data, so a misbehaving application can overwhelm the collector unless it enforces rate limits.
