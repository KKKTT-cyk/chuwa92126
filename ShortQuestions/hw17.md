# HW17 – Observability

## Question 1.

The three signals are three different data models. **Logs** are discrete events, **metrics** are aggregated numbers over time, and **traces** describe the causal structure of one request.

| Aspect | Logs | Metrics | Traces |
|---|---|---|---|
| One record contains | One event: a timestamp and arbitrary fields or free text, e.g. `ERROR payment declined order=981 code=51` | One sample of a time series: a timestamp and one 64-bit value, identified by a name and a label set, e.g. `http_requests_total{service="checkout",status="500"} 1873` | One span: part of a tree for one request, linked to its parent by a parent id (e.g. `checkout` > `payment.charge` > `bank.api`) |
| Volume grows with | Number of events, so with traffic | Number of distinct label combinations (active series), not traffic | Number of requests times spans per request, so with traffic and with the size of the call tree |
| Cost per unit | Highest: bytes of text per event | Lowest: about 1 to 2 bytes per sample after compression | Medium: hundreds of bytes per span |
| Best at | Explaining exactly what happened | Detecting that something is wrong, trends, alerting | Locating where in a call graph time or errors originate |
| Query pattern | Search by text or field over a time range | Aggregate over time and labels | Fetch by trace id; search by attributes |

Metrics cost depends on label cardinality, while logs and traces cost depends on traffic. A metrics system with a fixed set of series costs the same at 10 requests per second and at 100,000, but logs and traces grow with every request. For one instance serving 50 requests per second, logs are about 40 KB/s, metrics about 300 bytes/s, and 1% sampled traces about 2 KB/s. Metrics grow multiplicatively with label values: 200 instances x 50 endpoints x 5 statuses x 13 series is 650,000 series, and adding a user-id label multiplies that again.

In practice, use **metrics** to notice a problem ("is checkout slow?"), **traces** to find which service in the call chain is slow for a request, and **logs** to see why that request failed. Metrics cannot explain individual requests, and logs have no structure across services.

A telemetry pipeline is itself a distributed system with an unusual workload: the write rate is very high and continuous from every process, while reads are low and bursty (dashboards, alert rules, incident investigations), so it is heavily write-dominated. The value of data is highest in the first minutes and drops sharply with age, consistency needs are weak (slightly late or missing samples are acceptable), but availability needs are very high because the platform is needed most during an outage. It must also never slow down or crash the application. This is why the architecture uses append-oriented storage, buffering queues, tiered retention, aggressive compression, sampling, and telemetry code that never blocks the request path.

## Question 2.

**Family 1** is a full-text inverted index (Elasticsearch, built on Lucene): every token of every log line is indexed. **Family 2** is a label index plus compressed chunks in object storage (Loki): only a small set of labels (service, environment, level) is indexed, and log text is compressed into chunks that are scanned at query time. The fundamental trade-off is paying at write time (building an index) or at read time (scanning).

| Dimension | Full-text inverted index | Label index plus chunks |
|---|---|---|
| Paid at write time | High: tokenize every line, update the index, write segments, merge segments (write amplification) | Low: group lines by label set, append and compress, write chunks, index only the label set |
| Paid at read time | Low: look up tokens and intersect lists | High: select chunks by labels and time, then scan their contents |
| Storage | Index often comparable to or larger than raw data, usually on fast disks | Small index; compressed data on cheap object storage |
| Arbitrary text search over large ranges | Fast | Slow: scans every selected chunk |
| Narrowed by labels and a short time range | Fast | Fast |
| Hurt by high cardinality | Field mappings can explode with many distinct field names | Label cardinality explodes the index and creates tiny chunks |
| Suitable scale | Moderate volume with heavy search needs | High volume with predictable access paths |

The full-text index makes any text query fast, but you pay for it on every line written, even though most lines are never read. The label-index design keeps writes cheap and the index small, but a query is only fast when labels and the time window narrow the data before scanning. In both families high cardinality is harmful when it lands in the index: many distinct field names in the first, many distinct label values in the second (which also splits the data into tiny chunks). Keep unbounded values such as user ids out of labels and in the log text.

**Choice: label index plus compressed chunks in object storage.** Logs are read far less often than they are written, so shifting the cost to read time reduces total cost at high volume. The stated workload is "this service, last 15 minutes", which is exactly a known service plus a short time window: labels select a few chunks and only those are scanned, so queries stay fast. Meanwhile the platform avoids the write amplification and the index-size cost of tokenizing a very high volume of logs, and stores the data on cheap object storage. A full-text index would only be justified if frequent, unpredictable searches across all logs were required, which this platform does not have.

## Question 3.

In **pull** collection the collector requests data from each target (a Prometheus-style server scrapes `/metrics` at a fixed interval). In **push** collection the producer sends data to the collector.

| Aspect | Pull (scrape) | Push |
|---|---|---|
| Service discovery | Needed: the collector needs the current list of targets (Kubernetes API, DNS, cloud APIs, static files) | Not needed: producers know the collector address |
| Detecting a dead target | A failed scrape is an explicit signal (`up = 0`), generated by the server without the target's cooperation | Absence of data is ambiguous: dead or just idle? |
| Short-lived batch jobs | Hard: the job may exit between scrapes | Natural: send before exit |
| Firewalls and topology | Collector must be able to reach every target | Outbound connections only from the producer |
| Who controls the rate | The collector controls the rate and time of collection | The producers do |
| Misbehaving application | The collector can reject or truncate an overloaded target (limit labels per target or samples per scrape) | Producers can overwhelm the collector |

With pull, service discovery is what lets autoscaled and short-lived instances appear and disappear automatically, and applications keep no export state and need no network client. The server decides the scrape time, so all samples of a target share a timestamp and the server controls its own load. A job that finishes before the next scrape cannot be pulled, so the usual solution is to push its final metrics to an intermediary gateway that the server scrapes; this works for a few jobs but is not a general push path.

With push, the collector must cope with whatever the producers decide to send, so a misbehaving application (for example one that suddenly emits far more data) can overload it, and silence from a producer cannot by itself be told apart from a producer with nothing to report. In return, push works well for ephemeral workloads and restricted networks, because only outbound connections are needed.

Neither model is universally better. Pull fits long-running services where discovery is available, because it gives the collector control over load and a built-in health signal. Push fits short-lived jobs and restricted networks. Many production setups use both: scrape long-running services and push from batch jobs through a gateway.
