## Question1:Why does the thread-per-request model waste resources for I/O-bound work?
The traditional thread-per-request model, commonly used in Spring MVC, assigns a worker thread to handle each incoming HTTP request. The thread typically remains occupied until the request has been processed and a response has been returned.
This approach can be inefficient for I/O-bound applications because threads spend much of their time waiting for external operations, such as database queries or HTTP requests, rather than performing actual computation.

## Question2: Describe the Reactor pattern: the roles of the demultiplexer, the event loop, the acceptor and the handlers. Explain why blocking an event loop thread is so harmful.
The Reactor pattern is an event-driven architectural design pattern that enables applications to handle multiple I/O operations efficiently using a small number of threads.
Instead of assigning a dedicated thread to each client connection, the Reactor pattern monitors multiple connections and dispatches events to the appropriate handlers when they are ready for processing.

Four main components
1. Demultiplexer
The demultiplexer monitors multiple I/O channels or connections and identifies which ones are ready for operations such as accepting connections, reading data, or writing data.
In Java NIO, Selector is an example of an I/O demultiplexer.
2. Event Loop
The event loop continuously waits for I/O readiness events and dispatches them to the appropriate handlers.
A single event loop can manage many connections because it does not wait synchronously for each I/O operation to finish.
3. Acceptor
The acceptor handles new incoming client connections. When a new connection is established, it accepts the connection and registers it for further processing.
4. Handlers
Handlers contain the application logic required to process specific events.
For example, a handler might read an HTTP request, decode its contents, initiate an asynchronous database query, or write an HTTP response.

Why blocking an event loop thread is harmful?
An event loop is designed to execute short, non-blocking tasks. If an event loop thread executes a blocking operation, such as Thread.sleep(), a synchronous JDBC query, or a blocking HTTP call, it cannot process other events while waiting.

## Question3: Explain the four Reactive Streams interfaces, signal sequence, and request(n).
It contains four primary interfaces.
Interface	Responsibility
Publisher<T>	Produces data and allows subscribers to subscribe
Subscriber<T>	Receives data, completion notifications, and errors
Subscription	Manages demand and cancellation
Processor<T, R>	Acts as both a Subscriber and a Publisher

1. Publisher
   A Publisher is responsible for providing data to subscribers.
2. Subscriber
   A Subscriber receives signals from a publisher through four methods:
   void onSubscribe(Subscription subscription);
   void onNext(T item);
   void onError(Throwable error);
   void onComplete();

- onSubscribe() receives the subscription and enables the subscriber to request data.
- onNext() receives an emitted item.
- onError() receives a terminal error signal.
- onComplete() indicates successful completion.

3. Subscription
   A Subscription represents the relationship between a publisher and a subscriber.
   It provides two methods:
   void request(long n);
   void cancel();

request(n) communicates how many additional elements the subscriber is prepared to receive, and cancel() terminates the subscription.

4. Processor
   A Processor<T, R> implements both Subscriber<T> and Publisher<R>. It can receive data from an upstream publisher, process it, and publish transformed data to downstream subscribers.

Sequence of signals
The subscriber first subscribes, receives a Subscription, and requests two elements. The publisher can then emit up to two elements in response to that request.

Role of request(n)
The request(n) mechanism provides backpressure, preventing a publisher from overwhelming a slower subscriber.
This allows the subscriber to control its outstanding demand rather than requesting the entire stream immediately.

## Question4: Explain Mono, Flux, lazy execution, and Mono.just() versus Mono.fromCallable().
Mono vs. Flux
Characteristic	Mono<T>	Flux<T>
Number of emitted elements	0 or 1	0 to N
Successful completion	onComplete()	onComplete()
Error handling	onError()	onError()
Common use case	Retrieve one customer	Retrieve multiple customers
Example	Mono.just("Alice")	Flux.just("A", "B", "C")

What does "nothing happens until you subscribe" mean?
Reactive pipelines are generally lazy. Defining a reactive pipeline creates a description of the work to perform, but it does not automatically execute its deferred operations.
The callable is invoked when the Mono is subscribed to, not when the pipeline is constructed.
In Spring WebFlux, the framework normally subscribes to publishers returned from controller methods. Therefore, developers generally should not manually call subscribe() inside controllers or services.

Difference between Mono.just() and Mono.fromCallable()
Consider:
Mono<Report> mono = Mono.just(buildReport());
Here, buildReport() is executed immediately when the Mono is constructed.
The result is then stored as a value inside Mono.just().
If buildReport() throws an exception, the exception occurs immediately during pipeline construction.

Now consider:
Mono<Report> mono = Mono.fromCallable(() -> buildReport());
Here, the method is not executed when the Mono is constructed. Instead, the callable executes when a subscriber subscribes.
If buildReport() throws an exception during subscription, Reactor converts that exception into an onError signal.

## Question5:Compare map, flatMap, concatMap, and flatMapSequential.
In Project Reactor, map, flatMap, concatMap, and flatMapSequential are operators used to transform elements in reactive pipelines.
1. map()
   The map() operator transforms each element synchronously using a function that returns a regular value rather than another publisher.
   The function executes for each element and preserves the order of the source.
map() does not introduce concurrency by itself.
2. flatMap()
   The flatMap() operator transforms each source element into an inner Publisher and merges their results into one output stream.
It is especially useful for asynchronous operations, such as calling external services.

Example:
Flux.just(1, 2, 3)
.flatMap(id -> webClient.get()
.uri("/users/{id}", id)
.retrieve()
.bodyToMono(User.class)
);

This example initiates asynchronous HTTP requests for multiple users.
The inner publishers can execute concurrently, and results are emitted as they become available.
If the third request finishes first, its result may be emitted before the results of the first and second requests.
Therefore, flatMap() does not guarantee source ordering.

3. concatMap()
   The concatMap() operator is similar to flatMap(), but it processes inner publishers sequentially.
   Example:
   Flux.just(1, 2, 3)
   .concatMap(id -> webClient.get()
   .uri("/users/{id}", id)
   .retrieve()
   .bodyToMono(User.class)
   );

The behavior is:
1. Start the HTTP request for user 1.
2. Wait for the first inner publisher to complete.
3. Start the HTTP request for user 2.
4. Wait for completion.
5. Start the HTTP request for user 3.
   The output order is guaranteed to follow the source order.

However, this can be slower than flatMap() because independent operations cannot overlap.

4. flatMapSequential()
   The flatMapSequential() operator combines the concurrency of flatMap() with the ordering guarantee of concatMap().
   Example:
   Flux.just(1, 2, 3)
   .flatMapSequential(id -> webClient.get()
   .uri("/users/{id}", id)
   .retrieve()
   .bodyToMono(User.class)
   );
   All three HTTP requests can run concurrently, subject to concurrency limits, but their results are emitted in the original order.
   The flatMapSequential() operator temporarily buffers results that arrive out of order until earlier publishers have completed.

## Question6:Why doesn't try/catch catch errors from a reactive pipeline? Explain Reactor error-handling operators.
In traditional imperative Java programming, try/catch handles exceptions thrown during synchronous execution.
However, reactive pipelines usually execute later, when a subscriber subscribes to the publisher. Errors occurring during that execution are delivered as onError signals rather than being thrown directly to the code that constructed the pipeline.
When the publisher is subscribed to, the computation executes, and the error is propagated as an onError signal.
A try/catch can still catch synchronous exceptions during pipeline construction. It simply cannot catch an asynchronous error that occurs after the try block has finished.

Reactor provides several operators for handling these errors.
1. onErrorReturn()
   onErrorReturn() replaces an error with a predefined fallback value.
2. onErrorResume()
   onErrorResume() handles an error by switching to an alternative publisher.
3. onErrorMap()
   onErrorMap() transforms one exception into another exception.
4. retryWhen()
   retryWhen() automatically resubscribes to the source after an error, according to a configured retry strategy.
5. timeout()
   The timeout() operator limits how long a publisher can wait for a signal.

## Question7:Explain publishOn, subscribeOn, and the correct scheduler for blocking JDBC.
In Project Reactor, publishOn() and subscribeOn() control where reactive operations execute.
Both use schedulers, but they affect different parts of a reactive pipeline.
subscribeOn()
The subscribeOn() operator specifies which scheduler should handle subscription and the upstream source execution.
Example:
Flux.range(1, 3)
.map(i -> {
System.out.println(
"Map: " + Thread.currentThread().getName()
);
return i * 10;
})
.subscribeOn(Schedulers.boundedElastic())
.subscribe();

In this example, the source and the map() operation typically execute on a boundedElastic worker thread.
The subscribeOn() operator generally affects the subscription process for the entire upstream chain, regardless of where it appears, unless another operator imposes its own scheduling behavior.

publishOn()
The publishOn() operator changes the scheduler used to process downstream signals from the point where it appears.
Example:
Flux.range(1, 3)
.map(i -> {
System.out.println(
"Before: " + Thread.currentThread().getName()
);
return i;
})
.publishOn(Schedulers.parallel())
.map(i -> {
System.out.println(
"After: " + Thread.currentThread().getName()
);
return i * 10;
})
.subscribe();

In this example, the first map() executes on the upstream execution thread, while the second map() executes on a worker from Schedulers.parallel().

Which scheduler should wrap a blocking JDBC call?
The appropriate scheduler is:
Schedulers.boundedElastic()

This scheduler is intended for blocking I/O operations and uses a bounded worker pool or supported virtual-thread implementation.

## Question8:Explain backpressure, request(n), and handling a source that cannot slow down.
Backpressure is a mechanism used in reactive programming to prevent a fast publisher from overwhelming a slower subscriber.
Without backpressure, messages can accumulate in memory, potentially causing excessive memory usage, increasing latency, and eventually leading to application failure.

How subscribers express demand
Reactive Streams provides the Subscription.request(n) method.
A subscriber uses this method to tell the publisher how many additional elements it can accept.

What happens with Flux.interval()?
Flux.interval() generates values periodically.
Unlike a demand-driven database query, a periodic timer cannot arbitrarily postpone each scheduled tick until the subscriber is ready.
In Reactor, Flux.interval() can emit an overflow error when a scheduled tick occurs without sufficient downstream demand.
Several strategies are available to handle such situations.
1. Buffering
   Flux.interval(Duration.ofMillis(100))
   .onBackpressureBuffer(100);


onBackpressureBuffer() temporarily stores items when the consumer cannot process them immediately.

The buffer should have a reasonable capacity because unlimited buffering can exhaust memory. A bounded buffer can fail with an overflow error when full.
2. Dropping elements
   Flux.interval(Duration.ofMillis(100))
   .onBackpressureDrop();


onBackpressureDrop() discards items when downstream demand is insufficient.

This strategy is useful when processing the latest information matters more than processing every individual event.

For example, a real-time monitoring dashboard may not need every intermediate CPU usage reading.
3. Keeping only the latest element
   Flux.interval(Duration.ofMillis(100))
   .onBackpressureLatest();


onBackpressureLatest() retains the latest available item while downstream processing is delayed.

Older unconsumed items are replaced as new items arrive.

This approach is suitable for applications such as live device telemetry or user interface updates.
4. Applying an error strategy
   Flux.interval(Duration.ofMillis(100))
   .onBackpressureError();


onBackpressureError() generates an error if downstream demand is insufficient to accept incoming elements.

This can be appropriate when data loss is unacceptable and the application should fail explicitly rather than silently dropping data.

## Question9:Explain cold and hot publishers, duplicate WebClient requests, cache(), and share().
In reactive programming, publishers can be classified as cold or hot based on how they produce and distribute data.

Cold publishers
A cold publisher starts a new execution for each subscriber.
Every subscription receives its own sequence of events.
Cold publishers commonly represent deferred database queries, HTTP requests, or other operations that execute independently for each subscription.

Hot publishers
A hot publisher shares data production among multiple subscribers.
Unlike a typical cold publisher, it does not necessarily restart the source for each subscriber.
For example, a live stream of stock prices may continuously emit new prices that multiple subscribers receive.
Subscribers joining later generally do not receive historical events unless the publisher supports replay or caching.

Why does subscribing twice to a WebClient Mono send two HTTP requests?
The WebClient publisher is cold.
The first subscription triggers an HTTP request, and the second subscription independently triggers another HTTP request.
Therefore, two HTTP requests are sent to the server.

How cache() changes this behavior
Mono<String> response =
webClient.get()
.uri("/products/123")
.retrieve()
.bodyToMono(String.class)
.cache();

response.subscribe(System.out::println);
response.subscribe(System.out::println);


The first subscription triggers the HTTP request and stores the terminal result.
The second subscription receives the cached result without making another HTTP request.
By default, Mono.cache() also caches completion and error signals, which may be undesirable for transient failures.

A time-limited cache can be configured:
.cache(Duration.ofMinutes(5))
This allows the cached signal to expire after five minutes.

How share() changes this behavior
The share() operator allows multiple subscribers to share a source subscription.
When multiple subscribers subscribe to this shared Mono, they can receive the same result from a single underlying HTTP operation.

For Mono.share(), the source begins when the first subscriber subscribes. If all subscribers cancel while the operation is still running, the shared source is cancelled and a later subscription can restart it.

Unlike Mono.cache(), which retains its cached signal independently of subscriber cancellation, Mono.share() focuses on sharing a common task.

For Flux.share(), subscribers share an active stream, and late subscribers generally do not receive previously emitted items.

Conclusion: Cold publishers restart work for each subscription, while hot publishers share data production. cache() is suitable for reusing previously completed results, while share() is useful for sharing a common source subscription.

## Question10:Compare Spring MVC and Spring WebFlux. When is Spring MVC with virtual threads a better choice?
Spring MVC and Spring WebFlux are both web frameworks within the Spring ecosystem, but they use different concurrency and programming models.
Spring MVC follows a primarily imperative, traditionally blocking programming model, while Spring WebFlux supports asynchronous and non-blocking reactive processing.

Comparison
Feature	Spring MVC	Spring WebFlux
Programming model	Primarily imperative	Reactive
Typical return type	User, ResponseEntity<User>	Mono<User>, Flux<User>
Request handling	Servlet request processing	Non-blocking, event-driven processing
Thread usage	Traditionally one worker per active request	Small event loop worker pool
Blocking I/O	Naturally supported	Should be avoided on event loops
Database integration	JDBC, Spring Data JPA	R2DBC, reactive repositories
Common server	Tomcat	Reactor Netty by default

Spring MVC with virtual threads
Java 21 introduced virtual threads as a standard feature.
Virtual threads are lightweight JVM-managed threads that allow applications to support large numbers of concurrent tasks without requiring a matching number of operating-system threads.
With a compatible Servlet container, incoming Spring MVC requests can be processed using virtual threads.
When a virtual thread waits during a supported blocking operation, the JVM can suspend it and free the underlying carrier thread to perform other work.
This allows programmers to retain straightforward imperative code while improving concurrency efficiency for many blocking workloads.

When Spring MVC with virtual threads is a better choice
Spring MVC with virtual threads may be preferable in the following situations:
1. Existing blocking dependencies: Applications rely heavily on Spring Data JPA, Hibernate, JDBC, or synchronous third-party APIs.
2. Simpler programming model: Developers want to retain familiar imperative Java code without introducing reactive operators.
3. Legacy application compatibility: An existing Spring MVC application would require substantial refactoring to migrate to WebFlux.
4. I/O-bound workloads: The application spends significant time waiting for database queries or external network calls, making lightweight virtual threads beneficial.
5. Maintainability: The team is more experienced with synchronous Java and wants simpler debugging, exception handling, and transaction management.

However, virtual threads do not make the underlying database or network operation non-blocking. Database connection pools and downstream service capacity still limit throughput.

When WebFlux is preferable
Spring WebFlux may be a better choice when an application:
- Must handle large numbers of concurrent requests or streaming connections.
- Uses non-blocking drivers and reactive APIs end to end.
- Performs many independent asynchronous operations.
- Needs reactive backpressure and streaming.
- Can tolerate the additional complexity of reactive programming.
  Conclusion: Spring MVC with virtual threads is often a practical choice for applications using blocking database access and traditional Java libraries. WebFlux is particularly valuable when an application can use a genuinely non-blocking architecture throughout its request-processing pipeline.
