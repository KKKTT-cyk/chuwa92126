1. Comparison of logs, metrics and traces
A log contains an event, and its volume grows with the number of events increase. Logs could best answer the questions 
that need to be explained exactly what happened.
Metrics contain samples of a time series, and its volume grows with the number of distinct label combinations without
traffic grows. Metrics could answer the questions that could detect something is wrong, or questions about trending or
alerting.
Traces contain span which is a part of a trace tree, and its volume grows with the number of request times span per 
request grows, Traces could answer the questions that need locate where in a call graph time or errors originate.
A telemetry pipeline collects many logs, metrics and traces from many different services and machines. It needs to handle
a great amount of data thus it needs high throughput and performs frequent writes. Reads are less frequent and mainly 
focus on dashboard, troubleshooting and alerts. Besides, collection, processor and storage are spread across multiple
machines, makes it a distributed system.
2. A full-text inverted index has a high write cost in tokenization, index updates and segment merges at write time, and
also has a high storage cost in index plus data, usually on fast disk at read time. In both query by arbitrary text over 
large range and query narrowed by labels and a short time range, the full-text inverted index is fast. And if it hurt by
high cardinality, field mappings can explode with many distinct field names.
A label-index plus compressed chunks in object storage has a low write cost in appending and compressing at write time, 
and has a low read cost in compressed data on object storage at read time. In query by arbitrary text over large range 
the label-index plus compressed chunks in object storage is slow while for query narrowed by labels and a short time 
range, it is fast. And if it hurt by high cardinality, label cardinality explodes the index and creates tiny chunks.
I will choose the label-index plus compressed chunks in object storage, because labels narrow down the relevant chunks
while compression and object storage cost low at high volumes.
3. Push-based collection do not need to discover target because producers know the collector's address. Push-based 
collection could not know whether the data is dead or idle and for short-lived jobs, it could send them before exit which
is not hard. For firewalls and network topology, push collection only outbound from the producers and producers will
control the collector. When the application misbehaves, push requires more protection against application sending too much data.
Pull-based collection needs a list of targets. A failed scrape is an explicit signal that the target is down, but it is 
hard to handle short-lived jobs, they may exit between scrapes. For firewalls and network topology, collectors must reach
every target in pull collection and the collector also controls the rate and time of collection. When the application 
misbehaves, pull gives the collector more control over incoming traffic.
