## 1. Time-Series Cardinality

### Series Count

Each histogram exports:
- 8 finite buckets
- 1 +Inf bucket
- 1 sum
- 1 count

Total series per label combination:

8 + 1 + 1 + 1 = 11

Original number of series:

100 × 20 × 4 × 11 = 88,000

After adding the user_id label with 50,000 distinct values, the worst-case series count is:

100 × 20 × 4 × 50,000 × 11 = 4,400,000,000

Therefore, the cardinality increases by 50,000 times, resulting in 4.4 billion time series.

### Impact on Time-Series Database Resources

- Memory: More active series, labels, indexes, and chunks must be maintained in memory.
- CPU: More computation is required for ingestion, indexing, compression, and query execution.
- Disk: More samples, metadata, indexes, and write-ahead logs must be stored.
- Network: More telemetry data must be transferred between applications, collectors, and storage systems.
- Query performance: Aggregating a large number of series increases query latency.

### Three Cardinality Control Techniques

1. Label normalization at the application instrumentation layer:
   Replace dynamic URLs such as /users/12345 with /users/{id}. Avoid using user_id, request_id, and trace_id as metric labels.

2. Label filtering at the collector or ingestion layer:
   Remove unnecessary high-cardinality attributes or drop unwanted metrics before they reach the database. Aggregate series appropriately when removing labels to avoid conflicting samples.

3. Cardinality limits at the collector or storage backend:
   Enforce limits on the number of distinct time series accepted from each application or tenant.

High-cardinality information should generally be stored in logs or traces instead of metric labels.

## 2. Percentiles, Histograms, and Sketches

### Why Percentiles Cannot Be Averaged

Instance A:
- Requests: 800
- P99: 20 ms

Instance B:
- Requests: 200
- P99: 600 ms

The arithmetic average is:

(20 + 600) / 2 = 310 ms

The weighted average is:

(800 × 20 + 200 × 600) / 1000 = 136 ms

Neither value necessarily represents the combined P99.

A percentile describes a position within a distribution rather than an arithmetic average. The combined P99 depends on the distribution of all 1,000 requests.

For example, suppose all 800 requests from instance A take 20 ms, while 100 requests from instance B take 20 ms and the remaining 100 take 600 ms.

The combined distribution contains:

- 900 requests at 20 ms
- 100 requests at 600 ms

The combined P99 is 600 ms.

Therefore, the exact combined P99 cannot be calculated using only the individual percentiles and request counts.

### Comparison

| Feature | Client-Side Summary | Fixed-Bucket Histogram | Sketch |
|---|---|---|---|
| Aggregation | Quantiles cannot be aggregated | Can aggregate matching buckets | Compatible mergeable sketches can be aggregated |
| Accuracy | Depends on quantile algorithm | Depends on bucket boundaries | Depends on approximation algorithm |
| CPU cost | Client-side quantile computation | Bucket counter updates | Sketch updates |
| Memory cost | Depends on quantile configuration | Increases with bucket count | Depends on sketch configuration |
| Storage cost | Usually relatively low | Increases with bucket count | Generally compact |
| Examples | Prometheus Summary | Prometheus Histogram | DDSketch, t-digest |

Client-side summaries calculate quantiles directly in the application. Their precomputed quantiles cannot generally be aggregated across instances, although their counts and sums can be aggregated.

Fixed-bucket histograms record the number of observations within predefined buckets. Bucket counts from different instances can be aggregated if their boundaries are identical.

Sketches maintain compressed representations of distributions. Compatible mergeable sketches can be combined across instances to estimate global percentiles.

### Bucket Boundary Selection

Bucket boundaries should be concentrated around the latency objective because histogram percentile estimation depends on bucket width.

For example, if the latency SLO requires 95% of requests to complete within 200 ms, suitable bucket boundaries are:

10 ms, 50 ms, 100 ms, 150 ms, 200 ms, 250 ms, 500 ms, 1000 ms, +Inf

Including a boundary at exactly 200 ms allows the system to calculate the percentage of requests satisfying the SLO directly.

Example PromQL query:

```promql
sum(rate(http_request_duration_seconds_bucket{le="0.2"}[5m]))
/
sum(rate(http_request_duration_seconds_count[5m]))
```

Smaller bucket intervals near the latency objective improve percentile estimation accuracy in that region.

## 3. Tail-Based Sampling and Consistent Hashing

### Memory Calculation

Given:

- Incoming traces: 2,000 traces per second
- Spans per trace: 8
- Average span size: 400 bytes
- Decision window: 20 seconds

Number of buffered traces:

2,000 × 20 = 40,000 traces

Number of buffered spans:

40,000 × 8 = 320,000 spans

Required memory:

320,000 × 400 = 128,000,000 bytes

Therefore, the required memory is 128 MB, or approximately 122.07 MiB.

This represents the raw span payload size. Actual memory consumption will be higher because of object overhead, metadata, indexes, and processing buffers.

### Why All Spans Must Reach the Same Sampler

Tail-based sampling makes sampling decisions after collecting information about the entire trace.

For example, a sampling policy may retain a trace if:

- Any span contains an error.
- The overall request latency exceeds a threshold.
- The trace contains an important business operation.

If spans belonging to the same trace are distributed across different sampler nodes, each node sees only a partial trace.

This may result in:

- Incomplete traces.
- Incorrect latency calculations.
- Missed errors.
- Inconsistent sampling decisions.

Therefore, all spans with the same trace ID must be routed to the same sampler node.

### Modulo Hashing

Before scaling:

node = hash(trace_id) % 4

After scaling:

node = hash(trace_id) % 5

For uniformly distributed hashes, the fraction of traces that remain on the same node is:

1 / 5 = 20%

The fraction of traces that move is:

1 - 20% = 80%

Therefore, approximately 80% of traces are reassigned when the number of nodes increases from 4 to 5.

### Consistent Hashing

Consistent hashing places sampler nodes and trace IDs on a logical hash ring.

When a new node is added, only traces belonging to the hash ranges taken over by the new node need to move.

Assuming a balanced hash ring, the fraction of traces that move is:

1 / 5 = 20%

Therefore, approximately 20% of traces are reassigned.

### Comparison

| Feature | Modulo Hashing | Consistent Hashing |
|---|---|---|
| Traces moved | 80% | Approximately 20% |
| Implementation | Simple | More complex |
| Scaling stability | Poor | Good |
| Load balancing | Generally uniform | Improved with virtual nodes |
| Tail-based sampling suitability | Lower | Higher |

Consistent hashing is preferred because it minimizes reassignment when sampler nodes are added or removed.

However, membership changes can still split in-flight traces. Graceful draining or stable routing during the decision window may be required.

## 4. W3C Trace Context

Given the following header:

```http
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-00
```

### Meaning and Size of Each Field

| Field | Value | Size | Meaning |
|---|---|---|---|
| Version | 00 | 1 byte (8 bits) | Trace Context protocol version |
| Trace ID | 4bf92f3577b34da6a3ce929d0e0e4736 | 16 bytes (128 bits) | Unique identifier of the entire distributed trace |
| Parent ID | 00f067aa0ba902b7 | 8 bytes (64 bits) | Identifier of the upstream span |
| Trace Flags | 00 | 1 byte (8 bits) | Flags containing sampling information |

### Meaning of the Last Field

The last field is the trace flags field.

Its least significant bit represents the sampled flag.

- 00: The sampled flag is not set.
- 01: The sampled flag is set.

In this example, the value is 00, indicating that the upstream context marks the trace as not sampled.

With a parent-based sampling policy, the receiving service should normally respect the upstream decision and avoid recording and exporting the span.

However, it should continue propagating the trace context to downstream services.

The sampled flag is a recommendation rather than an absolute protocol requirement. A service may override it under an appropriate sampling policy.

### Maintaining Consistent Sampling Decisions

The sampling decision is propagated through the traceparent header.

Each downstream service reads the sampled flag and inherits the upstream sampling decision when using a parent-based sampler.

For example:

API Gateway (sampled = 00)
    |
    v
Order Service (sampled = 00)
    |
    v
Payment Service (sampled = 00)

This prevents services from independently making conflicting sampling decisions under a parent-based sampling policy.

### Outgoing Parent ID

When forwarding a request, the service should place its current outgoing span ID in the parent-id field.

Suppose the outgoing span ID is:

a1b2c3d4e5f67890

The outgoing header becomes:

```http
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-a1b2c3d4e5f67890-00
```

The trace ID remains unchanged, while the parent ID changes to represent the current upstream span.

## 5. SLO, Error Budget, and Burn Rate

### Error Budget Calculation

Given:

- Availability SLO: 99.95%
- Measurement period: 30 days

Allowed error ratio:

100% - 99.95% = 0.05% = 0.0005

Total minutes in 30 days:

30 × 24 × 60 = 43,200 minutes

Error budget:

43,200 × 0.0005 = 21.6 minutes

Therefore, the error budget is 21.6 minutes, or 21 minutes and 36 seconds.

This assumes time-based availability. For request-based availability, the error budget is 0.05% of total requests.

### Error Ratio at Burn Rate 14.4

The burn rate formula is:

Burn Rate = Actual Error Ratio / Allowed Error Ratio

Therefore:

Actual Error Ratio = Burn Rate × Allowed Error Ratio

14.4 × 0.0005 = 0.0072 = 0.72%

The alert threshold is an error ratio of 0.72%.

### Error Ratio at Burn Rate 6

6 × 0.0005 = 0.003 = 0.30%

The alert threshold is an error ratio of 0.30%.

### Error Budget Consumed After 1 Hour at Burn Rate 14.4

Total hours in the measurement period:

30 × 24 = 720 hours

Budget fraction consumed:

Burn Rate × Elapsed Time / SLO Period

14.4 × 1 / 720 = 0.02 = 2%

Equivalent downtime:

21.6 × 0.02 = 0.432 minutes

Therefore, 2% of the total error budget is consumed after one hour.

### Error Budget Consumed After 6 Hours at Burn Rate 6

6 × 6 / 720 = 0.05 = 5%

Equivalent downtime:

21.6 × 0.05 = 1.08 minutes

Therefore, 5% of the total error budget is consumed after six hours.

### Time Until Budget Exhaustion at Burn Rate 6

Time to exhaustion = SLO Period / Burn Rate

30 / 6 = 5 days

Therefore, the entire error budget will be exhausted after 5 days, assuming the full budget is initially available and the burn rate remains constant.

### Multi-Window Alerting

A good alert uses both a long window and a short window.

The long window determines whether the error rate is sustained and significant.

The short window determines whether the problem is still occurring.

For example:

| Alert | Burn Rate | Long Window | Short Window |
|---|---|---|---|
| Fast Burn | 14.4 | 1 hour | 5 minutes |
| Slower Burn | 6 | 6 hours | 30 minutes |

An alert fires only when both windows exceed the corresponding burn rate threshold.

This approach reduces false positives caused by temporary error spikes and prevents alerts from continuing unnecessarily after the service has recovered.

### Paging vs. Ticketing

Under a simplified two-tier alerting policy:

- Burn rate 14.4: Page the on-call engineer because the error budget is being consumed rapidly and immediate investigation is required.
- Burn rate 6: Create a high-priority ticket because the issue is developing more slowly.

However, in the standard Google SRE multi-window, multi-burn-rate alerting approach, both burn rates of 14.4 and 6 are commonly paging alerts. Lower burn rates, such as 1 sustained over several days, are more suitable for ticket-based alerts.

### Summary

| Metric | Burn Rate 14.4 | Burn Rate 6 |
|---|---|---|
| Error ratio | 0.72% | 0.30% |
| Measurement window | 1 hour | 6 hours |
| Budget consumed | 2% | 5% |
| Time to exhaust full budget | 50 hours | 120 hours |

## 6. Telemetry Pipeline Reliability

### Preventing Backend Outages from Affecting the Application

The telemetry pipeline should be decoupled from the application's critical request-processing path.

The application should not synchronously wait for telemetry data to be written to a remote backend.

A typical architecture is:

```text
Java Application
       |
       | Non-blocking enqueue
       v
Bounded In-Memory Queue
       |
       v
Asynchronous Background Exporter
       |
       v
OpenTelemetry Collector
       |
       v
Telemetry Backend
```

The following techniques should be implemented:

- Asynchronous exporting: Telemetry is exported by background threads instead of application request threads.
- Bounded queues: Limit memory consumption during backend outages.
- Batching: Send multiple telemetry records together to reduce network overhead.
- Timeouts: Prevent exporters from waiting indefinitely for backend responses.
- Limited retries: Retry temporary failures using exponential backoff.
- Circuit breakers: Temporarily stop sending requests to an unavailable backend.
- Resource isolation: Separate telemetry worker threads and resource limits from application resources.
- Load shedding: Drop telemetry when queues are full rather than blocking the application.

Example Java implementation:

```java
import java.util.concurrent.ArrayBlockingQueue;
import java.util.concurrent.BlockingQueue;
import java.util.concurrent.atomic.LongAdder;

public class TelemetryBuffer {

    private final BlockingQueue<String> queue =
            new ArrayBlockingQueue<>(10000);

    private final LongAdder droppedEvents = new LongAdder();

    public void record(String event) {
        boolean accepted = queue.offer(event);

        if (!accepted) {
            droppedEvents.increment();
        }
    }

    public String take() throws InterruptedException {
        return queue.take();
    }

    public long getDroppedEvents() {
        return droppedEvents.sum();
    }
}
```

The offer() method attempts to insert an event without waiting for queue capacity.

If the queue is full, it returns false and the event is dropped.

Unlike offer(), the put() method may block the application thread until queue capacity becomes available.

A background worker can retrieve events using take() and export them independently.

Telemetry still introduces some CPU and memory overhead. Resource limits are necessary to prevent backend outages from indirectly degrading application performance.

### Overload Options and Tradeoffs

| Technique | Where Applied | Advantages | Disadvantages |
|---|---|---|---|
| Buffering | SDK, collector, message queue | Absorbs temporary spikes and outages | Consumes memory or disk and increases latency |
| Dropping | SDK, collector, backend | Protects application availability | Causes permanent telemetry loss |
| Sampling | SDK, collector | Reduces telemetry volume and storage cost | Some traces are not recorded |
| Rate limiting | SDK, collector, backend | Prevents producers from overwhelming the pipeline | Excess telemetry may be rejected, delayed, or dropped |

### Overload Strategy at Each Stage

Application SDK:
- Use bounded queues.
- Use non-blocking enqueue operations.
- Apply head-based sampling.
- Drop telemetry when queues are full.

Background exporter:
- Batch telemetry records.
- Configure network timeouts.
- Apply limited retries and exponential backoff.
- Use circuit breakers.

Collector:
- Apply memory limits.
- Buffer telemetry temporarily.
- Perform tail-based sampling.
- Apply rate limiting and load shedding.

Message queue:
- Configure bounded retention.
- Enforce disk quotas.
- Apply producer rate limits.

Storage backend:
- Enforce ingestion quotas.
- Apply cardinality limits.
- Reject excessive traffic.
- Use load shedding during overload.

Buffering is useful for temporary outages. However, during prolonged outages, buffers eventually become full. The pipeline must then drop, sample, or rate-limit telemetry rather than allocate unlimited resources.

### At-Least-Once vs. At-Most-Once Delivery

At-least-once delivery means that each accepted event is delivered one or more times under the delivery guarantee.

The sender retries events until successful delivery is acknowledged.

If the backend receives an event but the acknowledgment is lost, the sender may retry the same event, resulting in duplicate telemetry.

At-most-once delivery means that each event is delivered zero or one time.

The sender does not retry failed delivery attempts. This avoids retry-induced duplicates but may result in data loss.

| Feature | At-Least-Once | At-Most-Once |
|---|---|---|
| Delivery | One or more times | Zero or one time |
| Retries | Yes | No delivery retry |
| Duplicate events | Possible | Not under the delivery guarantee |
| Data loss | Avoided under guarantee assumptions | Possible |
| Resource cost | Higher | Lower |
| Implementation complexity | Higher | Lower |
| Suitable use case | Important operational events | High-volume, loss-tolerant telemetry |

At-least-once delivery requires sufficient durable storage and retry mechanisms. A bounded in-memory queue with limited retries cannot provide an unconditional at-least-once guarantee.

The backend can use unique event IDs, deduplication, or idempotent processing to handle duplicate events.

### Separate Failure Domains for Alerting

A failure domain is a group of components that may fail together because they share infrastructure or dependencies.

If the monitoring system and the monitored application run in the same failure domain, an infrastructure outage may disable both systems simultaneously.

For example, if an application and Alertmanager run in the same Kubernetes cluster, a cluster-wide outage may prevent Alertmanager from sending notifications.

To avoid this problem, the monitoring and alerting systems should operate in an independent failure domain, such as:

- A separate Kubernetes cluster.
- A different availability zone.
- A different cloud region.
- A separate cloud account.
- An independent notification provider.

Example architecture:

```text
Failure Domain A:
    Java Application
           |
    Telemetry Collector
           |
           v
Failure Domain B:
    Monitoring Backend
           |
       Alertmanager
           |
           v
    On-Call Notification
```

This ensures that the monitoring system can remain operational even when the monitored infrastructure fails.

The monitoring system should also detect missing telemetry and failed external health checks.

### Watchdog Alert (Dead-Man's Switch)

A watchdog alert is an alert that is expected to fire continuously or send periodic heartbeat notifications.

Example Prometheus alerting rule:

```yaml
groups:
  - name: watchdog
    rules:
      - alert: Watchdog
        expr: vector(1)
        labels:
          severity: none
        annotations:
          summary: "Monitoring pipeline heartbeat"
```

The expression vector(1) always produces a value, so the alert remains active while Prometheus is functioning.

Alertmanager periodically sends this alert to an independent external monitoring service.

If the external service stops receiving heartbeat notifications within the expected interval, it generates an alert.

A watchdog can detect failures along the heartbeat delivery path, including:

- Prometheus failure.
- Alertmanager failure.
- Alert-rule evaluation failure.
- Network connectivity problems.
- Notification delivery failure.
- Infrastructure outages affecting the monitoring pipeline.

A normal alert detects problems in the monitored application, while a watchdog detects problems in the monitoring and alerting system itself.
