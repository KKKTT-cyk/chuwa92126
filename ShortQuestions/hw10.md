# Homework 10 - Spring AOP

## 1. What Is a Cross-Cutting Concern? Explain Tangling and Scattering.

A cross-cutting concern is a function needed across multiple methods or classes, such as logging, timing, or transaction management.

Using a simplified OrderService example, createOrder() checks stock and saves an order. If timing code is mixed into this method, that is **tangling**: business logic and timing logic are mixed together. If the same timing code is repeated in createOrder(), cancelOrder(), and payOrder(), that is **scattering**: the same concern is spread across different methods.

AOP lets us manage the timing logic in an aspect and apply it to selected methods. The business logic, such as checkStock() and saveOrder(), stays in OrderService.

## 2. Define Aspect, Join Point, Pointcut, Advice, Target, and Proxy.

- **Aspect:** A module that groups a cross-cutting concern, such as a TimingAspect for timing methods.
- **Join point:** A point in program execution where advice can apply. In Spring AOP, it always represents a method execution.
- **Pointcut:** A rule that selects which method executions receive advice, such as methods whose names start with create.
- **Advice:** The extra action performed before, after, or around a selected method execution, such as recording execution time.
- **Target:** The original object containing the business logic, such as an OrderService that checks stock and saves orders.
- **Proxy:** An object created by Spring that intercepts method calls and applies matching advice when delegating to the target.

## 3. Compare the Five Advice Types.

| Advice | When it runs |
| --- | --- |
| `@Before` | Before the target method executes. |
| `@AfterReturning` | After the target method returns normally. |
| `@AfterThrowing` | When the target method exits by throwing an exception. |
| `@After` | After the method exits, whether normally or with an exception, like finally. |
| `@Around` | Around the method invocation; it controls whether execution continues and what value is returned. |

`@Around` can replace the return value. Calling `proceed()` gets the result from the remaining invocation chain. Returning that result preserves it; returning a different compatible value replaces it. For example, the target may return "Order created", while the advice returns "Success" to the caller.

`@AfterReturning` can inspect the result but cannot replace the returned value. Reassigning its local parameter does not change what the caller receives. It can modify fields of a mutable returned object, which is different from replacing the object.

`@Around` can skip the target by not calling `proceed()`. `@Before` can also prevent target execution by throwing an exception, but cannot supply an alternative normal return value. The after advice types run after the target has already exited, so they cannot prevent that execution.

## 4. Describe Three Common Mistakes in Around Advice.

1. **Forgetting to call proceed():** The target method never runs. For example, the caller may receive "Success" even though no order was saved. Skipping proceed() is only appropriate when intentional, such as returning a cached result.
2. **Not returning the correct result:** Calling proceed() but returning null discards the target's result. The caller receives null instead; a primitive return type can cause an error. Normally, return the result from proceed() unless intentionally replacing it with a compatible value.
3. **Swallowing an exception:** Catching an exception and returning "Success" hides the failure from the caller. If the advice only needs to log the error, log it and rethrow the exception with throw e.

## 5. Explain the Pointcut Expressions.

- `execution(* com.example.orders.service.*.*(..))`: Matches method executions in types directly in the com.example.orders.service package, excluding subpackages. Return type, method name, and parameters can be anything.
- `execution(* com.example.orders..*.*(..))`: Matches method executions in types in com.example.orders and all its subpackages, with any return type, method name, and parameters.
- `execution(* *(Long, ..))`: Matches methods with any return type or name whose first declared parameter is java.lang.Long, followed by zero or more parameters of any type. A Long only in the second position does not match.
- `@annotation(com.example.orders.aop.LogExecutionTime)`: Matches executions of methods carrying the specified LogExecutionTime annotation. The annotation marks the method; matching advice provides the timing behavior.

These expressions select method executions; advice still depends on calls passing through a Spring AOP proxy and the method being interceptable by that proxy.

## 6. How Does Spring Apply Advice Through Proxies?

Spring creates a proxy for a bean that needs AOP. Other beans receive this proxy through dependency injection. Calls through it run the matching advice chain and then the target method, unless advice stops execution. Being a proxy does not mean every method matches every advice.

In the normal bean lifecycle, Spring creates the target, injects its dependencies, and runs initialization callbacks. The auto-proxy creator, a BeanPostProcessor, normally wraps it during postProcessAfterInitialization before it is exposed for use. Early proxy references can be involved in circular-dependency handling.

Use AopUtils.isAopProxy() to check the injected object. For example, inside the controller constructor:

```java
public OrderController(OrderService orderService) {
    this.orderService = orderService;
    System.out.println(AopUtils.isAopProxy(orderService));
}
```

Import org.springframework.aop.support.AopUtils. A result of true means the object is a Spring AOP proxy; it does not prove that a particular timing pointcut matches every method.

## 7. Why Does Self-Invocation Skip Advice, and How Can It Be Fixed?

Spring AOP uses proxies. Once execution reaches the target, a call to another method through this, explicitly or implicitly, stays inside that target and bypasses the proxy. The called method still runs, but its @LogExecutionTime advice or, in the default proxy mode, its @Transactional advice is not triggered by that internal call. An existing outer transaction may still apply.

Two fixes are:

1. **Move the method to another Spring bean.** Inject that bean and call its method through the injected proxy. This is usually the preferred approach. Creating it manually with new does not provide Spring AOP.
2. **Call through a self proxy reference.** Inject a reference to the bean's proxy, for example with a correctly configured @Autowired @Lazy self reference, and call self.saveOrder() instead of this.saveOrder(). This requires care with self-dependencies and is generally a fallback.

Changing this.saveOrder() to saveOrder() alone does not fix the problem; both are self-invocation.

### Fix 1: Move the Method to Another Spring Bean

These are two alternative examples, not classes to register together. Both assume Spring AOP is enabled, these services are component-scanned, and the existing LogExecutionTime annotation and matching timing advice are configured. The print statement stands in for the actual order-saving logic.

**OrderWriter.java**

```java
package com.example.orders.service;

import com.example.orders.aop.LogExecutionTime;
import org.springframework.stereotype.Service;

@Service
public class OrderWriter {

    @LogExecutionTime
    public void saveOrder() {
        System.out.println("Saving order");
    }
}
```

**OrderService.java**

```java
package com.example.orders.service;

import org.springframework.stereotype.Service;

@Service
public class OrderService {

    private final OrderWriter orderWriter;

    public OrderService(OrderWriter orderWriter) {
        this.orderWriter = orderWriter;
    }

    public void placeOrder() {
        orderWriter.saveOrder();
    }
}
```

Spring injects the OrderWriter proxy. Calling orderWriter.saveOrder() goes through that proxy, so the timing advice runs. Do not replace injection with new OrderWriter().

```text
Caller -> OrderService.placeOrder()
       -> OrderWriter proxy -> timing advice -> OrderWriter.saveOrder()
```

### Fix 2: Call Through a Lazily Injected Self Reference

As an alternative, keep both methods in OrderService and call through a Spring-provided self reference. Use this version instead of the OrderService above.

**OrderService.java**

```java
package com.example.orders.service;

import com.example.orders.aop.LogExecutionTime;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.context.annotation.Lazy;
import org.springframework.stereotype.Service;

@Service
public class OrderService {

    @Autowired
    @Lazy
    private OrderService self;

    public void placeOrder() {
        self.saveOrder();
    }

    @LogExecutionTime
    public void saveOrder() {
        System.out.println("Saving order");
    }
}
```

At the injection point, @Lazy supplies a lazy-resolution proxy and delays resolving the self dependency until it is used. It does not provide timing behavior by itself. The call through self reaches the bean's AOP proxy, which applies the matching advice.

```text
this.saveOrder() -> target directly -> no timing advice for this call
self.saveOrder() -> lazy reference -> AOP proxy -> timing advice -> target
```

Call placeOrder() on the Spring-managed bean after initialization, not from its constructor. The separate-bean approach is usually clearer; self injection is a fallback.

The same proxy-call principle applies to @Transactional in its default proxy mode, provided transaction management and the appropriate transaction manager are configured. A method-level annotation alone does not make an internal this call pass through a proxy.

## 8. What Are the Default Rollback Rules, and When Might Rollback Not Happen?

By default, @Transactional rolls back for RuntimeException and Error, but not for checked exceptions. Custom rollback rules can change this; for example, @Transactional(rollbackFor = IOException.class) includes IOException.

Three common situations are:

1. **A checked exception is thrown without a matching rollback rule.** The caller receives the exception, but the transaction may still commit.
2. **The method catches the exception and returns normally.** Logging an error does not request rollback. Unless the transaction has otherwise been marked rollback-only, it may commit. Rethrowing a RuntimeException lets the transaction advice apply its default rollback rule.
3. **Self-invocation bypasses the proxy.** If there is no outer transaction, an internal call does not activate the called method's @Transactional advice, so it cannot provide the expected transaction-wide rollback.

Throwing an exception is not the only way to request rollback: code can also mark an active transaction rollback-only. Rollback only affects participating transactional resources; it does not automatically undo ordinary Java List changes or recall sent emails.

## 9. Explain Advice Order and Compare Spring AOP with AspectJ.

A lower @Order value has higher precedence. SecurityAspect with @Order(1) wraps TimingAspect with @Order(2). If both around advice methods call proceed() once and execution completes normally, the order is:

```text
Security: before proceed()
    Timing: before proceed()
        Target method
    Timing: after proceed()
Security: after proceed()
```

If Security does not call proceed(), Timing and the target are skipped. If proceed() throws, ordinary statements after it are skipped unless the exception is handled; use finally for cleanup that must run on either outcome.

Weaving means connecting aspect behavior with the application code.

| Comparison | Spring AOP | AspectJ |
| --- | --- | --- |
| Mechanism | Runtime proxies that apply advice around calls to Spring beans. | Bytecode weaving at compile time, after compilation, or at class-loading time. |
| Join points | Method execution only. | Method execution and calls, constructor execution and calls, field reads and writes, and more. |
| Self-invocation | Direct calls within the target bypass proxy advice. | Correctly woven join points do not depend on going through an external proxy. |

Using @Aspect annotations with Spring AOP does not by itself enable AspectJ weaving; Spring can use that annotation style while still applying advice through proxies.
