# HW10 – Kafka

## Question 1.

Apache Kafka is an open-source distributed event streaming platform, used primarily to build real-time data streaming pipelines. It solves the data integration problem: a business has many applications (accounting, billing, CRM, websites) with different protocols, data formats and schemas, and direct point-to-point integrations between them become complicated. With Kafka as the integration layer, data sources publish to Kafka and target systems read from Kafka, so source streams and target systems are decoupled.

---

## Question 2.

A message (record) is one event written to a Kafka topic. It consists of:

| Element | Meaning |
|---|---|
| Key | Optional (can be null); serialized to bytes |
| Value | The content of the message; can also be null; serialized to bytes |
| Compression type | none, gzip, lz4, snappy or zstd |
| Headers | Optional key-value pairs, commonly metadata such as tracing info |
| Partition + Offset | Assigned once the message is written; topic + partition + offset uniquely identifies the message |
| Timestamp | Added either by the user or by the system |

## Question 3.

A producer is an application that sends data into Kafka topics. It decides which topic to write to, and messages are distributed to partitions by a mechanism such as key hashing. It also has to specify a level of acknowledgment (`acks`) for a write to count as successful, and it serializes keys and values into byte arrays because brokers expect bytes.

---

## Question 4.

A consumer is an application that reads messages from Kafka topics. It pulls data from brokers through a poll loop, reads from one or more partitions, and always reads in order from a lower offset to a higher offset within a partition. It deserializes the bytes back into the same format the producer used, and it commits its offsets to checkpoint its progress.

---

## Question 5.

A topic is a named, logical grouping of related messages, similar to a table in a database (for example `logs` or `purchases`). Kafka uses topics to organize related messages, so producers write related data to one topic and consumers subscribe only to the data they need. The sequence of all messages in a topic is called a data stream.

---

## Question 6.

A broker is a single Kafka server. It stores partition data on disk, handles read and write requests from producers and consumers, manages partition replication, and coordinates with other brokers. A cluster can have multiple brokers so that the partitions of a topic are distributed among them, which gives load balancing and scalability, and so that partitions can be replicated on other brokers, which prevents data loss if one broker fails.

---

## Question 7.

A topic is broken down into partitions, numbered from 0 to N-1, and messages are appended to the end of each partition. A topic may need multiple partitions for two reasons:

- **Scalability:** data is distributed across multiple brokers, so the cluster can handle more data than a single server could.
- **Parallelism:** multiple consumers can read different partitions at the same time, which increases throughput.

---

## Question 8.

An offset is an integer that Kafka adds to each message as it is written into a partition. It is the position of the message within a partition, not a global number. Numbering starts at 0 in every partition, so offset 3 in partition 0 is not the same data as offset 3 in partition 1.

---

## Question 9.

A consumer group is a set of consumers that belong to the same application and perform the same logical job, identified by the setting `group.id`. Within a group, each topic partition is assigned to only one consumer, while one consumer can be assigned several partitions. The consumers coordinate (through the group coordinator) to split the partitions, so the group reads the topic in parallel. For example, with 5 partitions and 3 consumers, Consumer 1 gets Partitions 0 and 1, Consumer 2 gets Partitions 2 and 3, and Consumer 3 gets Partition 4.

---

## Question 10.

Each message has an optional key. If the key is null, messages are distributed evenly across the partitions in a round-robin fashion. If the key is not null, all messages with the same key are always sent to and stored in the same partition (as long as the number of partitions does not change), because the default partitioner hashes the key (with murmur2) to choose the partition.

## Question 14.

No. The offset is added by Kafka when the message is written into a partition, not chosen by the producer. A consumer records its position because it needs to know how far it has read. It regularly commits the latest processed offset (stored by the brokers in the internal topic `__consumer_offsets`), so after a crash and rebalance the consumers know where to restart reading. When an offset is committed, all messages with a lower offset are also considered committed.

| Scenario | Ordering guarantee |
|---|---|
| Messages with the same key | Ordered (same partition) |
| Messages without key | Not ordered (round-robin) |
| Messages across partitions | Not ordered |

## Question 16.

At most **3** consumers can consume the topic at the same time. The maximum number of active consumers in a group equals the number of partitions, because each partition is assigned to only one consumer in the group. The other 2 consumers stay idle and receive no messages. Each of the 3 active consumers gets exactly one partition.
