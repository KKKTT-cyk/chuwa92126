# HW10 - Spring AOP

The answers follow the assignment's question order. Transaction examples assume Spring's default proxy mode and standard rollback settings.

## 1. What is a cross-cutting concern? Explain tangling and scattering using OrderService.

A **cross-cutting concern** is a responsibility needed across multiple methods or classes, such as logging, security, timing, or transaction management.

For example, `OrderService.placeOrder()` might check permissions, start a timer, save an order, and log the elapsed time. The order logic is mixed with security and timing logic. This is **tangling**: different concerns are mixed inside one method.

If similar permission checks and timing code are repeated in `cancelOrder()`, `refundOrder()`, and other services, that is **scattering**: one concern is spread across many places. A change to the logging format would require editing all those places.

AOP moves those shared concerns into aspects and uses pointcuts to select the methods they apply to, keeping the service focused on order operations.

Reference: [Spring AOP concepts](https://docs.spring.io/spring-framework/reference/core/aop/introduction-defn.html).

## 2. Define aspect, join point, pointcut, advice, target, and proxy.

| Term | Meaning |
| --- | --- |
| Aspect | A module containing a cross-cutting concern, such as a timing aspect declared with `@Aspect`. |
| Join point | A point in program execution where advice can apply. In Spring AOP, it always represents a **method execution**. |
| Pointcut | A rule that selects join points, such as all method executions in the service package. |
| Advice | The action performed at a selected join point, such as checking permission before a method runs. |
| Target | The original object whose methods are being advised, such as the `OrderService` bean. |
| Proxy | The wrapper exposed to callers that runs applicable advice and delegates to the target. |

Spring AOP intercepts method executions on Spring beans through proxies; it does not provide field-access or constructor join points.

Reference: [Spring AOP concepts](https://docs.spring.io/spring-framework/reference/core/aop/introduction-defn.html).

## 3. Compare the five advice types.

| Advice | When it runs | Can it replace the return value? | Can it prevent target execution? |
| --- | --- | --- | --- |
| `@Before` | Before the matched method. | No. | Only by throwing an exception; a normal return continues the invocation. |
| `@AfterReturning` | After normal completion, optionally binding the result. | No. | No; execution has already completed. |
| `@AfterThrowing` | After exceptional completion, optionally filtering and binding the exception. | No. | No; execution has already failed. |
| `@After` | On exit after either normal or exceptional completion, like `finally`. | No. | No; execution has already happened. |
| `@Around` | Surrounds the invocation and controls whether it continues. | Yes, by returning a compatible value. | Yes, by skipping `proceed()` or throwing an exception first. |

`@AfterReturning` can modify the state of a returned mutable object, but assigning a different reference to its advice parameter does not replace the caller's result. `@AfterThrowing` does not recover by returning a fallback; use `@Around` for that. An after advice can throw and change the exception seen by the caller, but it cannot undo execution.

Reference: [Declaring advice](https://docs.spring.io/spring-framework/reference/core/aop/ataspectj/advice.html).

## 4. Describe three common mistakes inside @Around advice and their effects.

1. **Forgetting `proceed()`.** The remaining advice chain and target method never run. This is valid for an intentional cache hit or rejection, but otherwise skips the business operation.
2. **Discarding the result of `proceed()`.** Returning `null` accidentally, or declaring the advice `void`, loses the target's result. Returning `null` for a primitive return type causes an error, and an incompatible replacement value can also fail.
3. **Catching an exception and not rethrowing it.** The caller may see a false success. If transaction advice is outside this advice and no rollback-only flag has been set, it may also commit because it never sees the failure.

A timing advice should preserve the result and exception and log elapsed time even when the method fails. For example, this method belongs inside a registered aspect:

```java
@Around("@annotation(com.example.orders.aop.LogExecutionTime)")
public Object measure(ProceedingJoinPoint joinPoint) throws Throwable {
    long start = System.nanoTime();
    try {
        return joinPoint.proceed();
    } finally {
        long elapsed = System.nanoTime() - start;
        System.out.println(joinPoint.getSignature() + " took " + elapsed + " ns");
    }
}
```

Here `@Around` and `ProceedingJoinPoint` come from `org.aspectj.lang.annotation` and `org.aspectj.lang`, respectively. The `finally` block runs on success and failure; there is no catch that swallows the target exception.

Reference: [Around advice](https://docs.spring.io/spring-framework/reference/core/aop/ataspectj/advice.html#_around_advice).

## 5. What does each pointcut expression match?

| Expression | Matches |
| --- | --- |
| `execution(* com.example.orders.service.*.*(..))` | Any return type and method name, with any arguments, on types directly in `com.example.orders.service`. It does not include subpackages such as `service.impl`. |
| `execution(* com.example.orders..*.*(..))` | Any return type and method name, with any arguments, on types in `com.example.orders` and all its subpackages. |
| `execution(* *(Long, ..))` | Any method whose first **declared parameter type** is `java.lang.Long`, followed by zero or more parameters. It matches `find(Long id)` and `find(Long id, String status)`, but not a zero-argument method or one starting with primitive `long`. |
| `@annotation(com.example.orders.aop.LogExecutionTime)` | Method executions where the method has the specified annotation. The custom annotation should target methods and use `RetentionPolicy.RUNTIME`. |

In these expressions, `*` is a wildcard and `..` allows any number of parameters or package levels, depending on its position. `execution` matches a method signature: a method declared with `Object` as its first parameter does not match the `Long` expression just because a caller passes a `Long`. These matches remain subject to Spring AOP's proxy limitations.

Reference: [Declaring a pointcut](https://docs.spring.io/spring-framework/reference/core/aop/ataspectj/pointcuts.html).

## 6. How do proxies apply advice, when are they created, and how can you check one?

A caller holding an injected proxy follows this path:

```text
Caller -> Spring proxy -> applicable advice chain -> target method
```

The proxy selects advice for the method and runs the interceptor chain. Spring Framework normally uses a **JDK dynamic proxy** when the target implements an interface, or a **CGLIB subclass proxy** otherwise. Configuration, including Spring Boot settings, can force class-based proxies. JDK proxies expose interface methods; CGLIB cannot advise private or final methods or subclass a final class.

In the normal bean lifecycle, Spring instantiates the target, injects dependencies, and runs initialization callbacks. An auto-proxy creator, implemented as a `BeanPostProcessor`, normally wraps an eligible bean in `postProcessAfterInitialization`. The container then exposes the proxy for callers. Early proxy references can also be involved in circular-reference handling, so after-initialization is the usual path rather than an absolute rule.

Check the bean reference injected into a caller, using `org.springframework.aop.support.AopUtils`:

```java
System.out.println(AopUtils.isAopProxy(orderService));
System.out.println(AopUtils.isJdkDynamicProxy(orderService));
System.out.println(AopUtils.isCglibProxy(orderService));
System.out.println(orderService.getClass().getName());
```

The utility methods are more reliable than guessing from a generated class name. Being a proxy does not by itself prove that a particular method matches a pointcut.

References: [Proxying mechanisms](https://docs.spring.io/spring-framework/reference/core/aop/proxying.html), [Bean post-processors](https://docs.spring.io/spring-framework/reference/core/beans/factory-extension.html), [AbstractAutoProxyCreator](https://docs.spring.io/spring-framework/docs/current/javadoc-api/org/springframework/aop/framework/autoproxy/AbstractAutoProxyCreator.html), [AopUtils](https://docs.spring.io/spring-framework/docs/current/javadoc-api/org/springframework/aop/support/AopUtils.html).

## 7. Why does self-invocation skip advice, and what are two ways to fix it?

When one target method calls another through `this`, including an implicit `this`, the call stays on the target object and does not re-enter the proxy. Therefore, the inner method's `@LogExecutionTime` or `@Transactional` advice is not applied in proxy mode.

For example, an external call to `orderService.placeOrder()` may enter the proxy, but `placeOrder()` calling `this.saveOrder()` does not create another proxy interception. An annotation on `saveOrder()` alone will not start a transaction. If `placeOrder()` already has an active transaction, `saveOrder()` can still run inside that transaction; its own transactional settings are simply not intercepted.

Two fixes are:

1. **Move the advised operation to a separate Spring bean.** Inject an `OrderWriter` into `OrderService` and call its public annotated method. The call crosses the injected bean's proxy. This is usually the clearest design.
2. **Call through a self-reference to the proxy.** For example, use a lazily injected self-reference and call `self.saveOrder()` instead of `this.saveOrder()`. Ensure the reference resolves to the Spring proxy, avoid an eager circular dependency, and use a method exposed by that proxy.

Simply adding another annotation to the inner method does not fix a call that bypasses the proxy.

References: [Self-invocation and proxying](https://docs.spring.io/spring-framework/reference/core/aop/proxying.html), [Transactional proxy semantics](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/annotations.html).

## 8. What are the default rollback rules, and why might a transaction not roll back?

With the standard defaults, an unhandled **`RuntimeException` or `Error`** causes rollback. A **checked exception**, such as `IOException`, does not cause rollback by default. These rules apply when the failure reaches the transaction interceptor; annotations alone do not activate transactions.

Three common situations are:

1. **A checked exception escapes the method.** Spring normally commits instead of rolling back for that exception. Use `@Transactional(rollbackFor = IOException.class)`, or another appropriate exception type, when rollback is required.
2. **The method catches the failure and returns normally.** If no other participant has marked the transaction rollback-only, the interceptor sees success and commits. Rethrow an appropriate exception or explicitly mark rollback-only. Catching an exception does not clear a rollback-only flag already set by an inner transactional call or persistence provider.
3. **The transactional call bypasses the proxy.** A self-invocation, or a call on an object created with `new`, does not activate that method's transaction advice. If there is no outer transaction, no service-level transaction exists to undo earlier committed writes. Call a Spring-managed bean through its proxy.

Explicit `rollbackFor` and `noRollbackFor` rules can change the defaults. Since Spring 6.2, a global setting such as `@EnableTransactionManagement(rollbackOn = ALL_EXCEPTIONS)` can also change the default treatment of checked exceptions.

References: [Transaction rollback rules](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/rolling-back.html), [Transactional settings and proxy mode](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/annotations.html).

## 9. Explain aspect ordering, then compare Spring AOP with AspectJ.

A lower `@Order` value has higher precedence. If both around advices call `proceed()` once and the method completes normally, the execution order is:

```text
SecurityAspect (@Order(1)): before proceed()
    TimingAspect (@Order(2)): before proceed()
        Target method
    TimingAspect: after proceed()
SecurityAspect: after proceed()
```

Security is the outer advice: it enters first and exits last. If security rejects the call without proceeding, neither timing nor the target runs. If the target throws, the exception travels back through timing and then security; their `finally` blocks run during unwinding, while ordinary statements after `proceed()` are skipped unless the exception is handled.

| Topic | Spring AOP | AspectJ |
| --- | --- | --- |
| Weaving | Runtime proxy interception; the target class's bytecode is not woven. | Weaves bytecode at compile time, after compilation, or at class loading. |
| Join points | Method executions reachable through Spring bean proxies. | A broader model including method calls and executions, constructor calls and executions, field reads and writes, and exception handlers. |
| Self-invocation and private methods | Self-invocation bypasses advice; private methods cannot be intercepted by proxies. | Matching bytecode join points can be advised, including self-invocations and private method executions. |
| Object scope | Objects exposed through Spring AOP proxies. | Can advise objects outside Spring management when their relevant classes are woven. |

Using `@Aspect` annotations with Spring AOP does not automatically enable AspectJ bytecode weaving.

References: [Advice ordering](https://docs.spring.io/spring-framework/reference/core/aop/ataspectj/advice.html#_advice_ordering), [AspectJ weaving](https://eclipse.dev/aspectj/doc/latest/devguide/ltw.html), [AspectJ join points](https://eclipse.dev/aspectj/doc/released/progguide/semantics-joinPoints.html), [Spring proxying](https://docs.spring.io/spring-framework/reference/core/aop/proxying.html).
