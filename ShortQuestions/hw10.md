# Q3.
`@before` runs before the method, can't see the return value and can't change the result,can prevent the call by throwing.  
`@AfterReturning` runs after a normal call, and can see the return value, but can't change the result, can't prevent call.
`AfterThrowing` runs after an exception, can see the exception can't change the result, can't prevent call.  
`@After` always run like finally, can't see the return value and can't change the result, can't prevent call.  
`@Around` wraps the whole call, can see the return value and change return value, and also can prevent call.


```java
public Object invoke() {
    try {
        before();                          // ① @Before
        Object result = target.method();    
        afterReturning(result);            // ② @AfterReturning
        return result;
    } catch (Exception e) {
        afterThrowing(e);                  // ③ @AfterThrowing
        throw e;
    } finally {
        after();                           // ④ @After
    }
}
```

# Q8.
1. RuntimeException (unchecked), By default, if a @Transactional method throws a RuntimeException, the transaction is rolled back. To keep the transaction committed for a specific runtime exception, use noRollbackFor.
2. Error An Error (such as OutOfMemoryError) also triggers a rollback by default, since it signals a serious problem and the application state can no longer be trusted.
3. Checked Exception By default, a checked exception (such as IOException) does not trigger a rollback. The transaction is still committed, even though the exception propagates to the caller. To roll back on checked exceptions, declare rollbackFor = Exception.class.

# Q9.
Order of execution: With @Order, a lower value means higher precedence, and the higher-precedence aspect wraps the outer layer. So SecurityAspect runs its code before proceed() first, then TimingAspect runs its code before proceed(), then the target method executes. On the way out, the order is reversed: TimingAspect finishes its after-proceed() code first, then SecurityAspect. If the security check fails, TimingAspect and the target method never run.
Spring AOP vs AspectJ: 
Spring AOP uses runtime weaving through proxies. It only works on Spring-managed beans and only supports method execution join points; 
it cannot intercept private, final, or static methods, and self-invocation bypasses the advice. 
AspectJ weaves aspects directly into bytecode at compile time, post-compile time, or load time. 
It works on any object and supports many more join points, such as constructor calls, field access, static initialization, and exception handlers, and self-invocation is intercepted as well. The trade-off is that AspectJ requires a special compiler or a Java agent and is more complex to set up.
