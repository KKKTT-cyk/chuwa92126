## Question1:
A Servlet Filter and a Spring MVC HandlerInterceptor both intercept HTTP requests and responses, but they operate at different levels of the request-processing lifecycle.
A Servlet Filter is defined by the Jakarta Servlet specification (jakarta.servlet.Filter), independently of Spring. It operates at the servlet container level, before a request reaches the DispatcherServlet. Because filters work directly with ServletRequest and ServletResponse, they can inspect or modify HTTP headers, request bodies, response bodies (using wrappers), and other low-level request information. They are commonly used for logging, authentication, CORS handling, and request validation.
A HandlerInterceptor is defined by the Spring MVC framework (org.springframework.web.servlet.HandlerInterceptor). It operates inside the DispatcherServlet, after Spring determines which handler should process the request. Unlike filters, interceptors can access the selected controller handler, including its method metadata through HandlerMethod. They are commonly used for controller-specific authorization, logging, auditing, and performance monitoring.

## Question2:
The doFilter() method is the main entry point of a Servlet Filter. It allows developers to perform operations before and after the remaining request-processing chain.
- Before chain.doFilter(): Code executes before the request proceeds to the next filter or target servlet. Common operations include logging, authentication checks, and request validation.
- During chain.doFilter(): Control is passed to the next filter or, if no filters remain, to the target servlet.
- After chain.doFilter(): Code executes as processing returns from the downstream chain. Common operations include logging completion, calculating execution time, and response processing.
  If a filter does not call chain.doFilter(), the remaining filters and target servlet are not invoked through that chain. The filter can terminate request processing, for example by returning an HTTP 401 Unauthorized response.

Two design patterns
1. Chain of Responsibility Pattern
   Each filter is responsible for processing part of a request and deciding whether to pass it to the next filter. Filters are loosely coupled and can be independently added, removed, or reordered.
2. Decorator Pattern
   Filters can add behavior around downstream processing without modifying the underlying servlet or controller. For example, a logging filter adds execution-time measurements before and after request processing. Filters can also decorate servlet requests and responses with wrappers.

## Question3:
1. Spring Boot provides multiple ways to register Servlet Filters. Two commonly used approaches are @Component and FilterRegistrationBean.
2. How filter ordering works
   Spring Boot primarily controls servlet filter order through:
- @Order or Ordered for automatically registered filter beans.
- FilterRegistrationBean.setOrder() for explicit registrations.
  A lower order value executes first on incoming requests.

3. Spring Security registers its own servlet filter through DelegatingFilterProxy, which delegates to FilterChainProxy. In a typical Spring Boot application, Spring Security's servlet filter has a default order of -100, so it executes before ordinary filters with order 0, 1, or higher.
The default order can be customized, and the order of filters within Spring Security is managed separately from the servlet filter order.

4. Accidental double registration
   A common problem occurs when a custom filter is registered both as a servlet filter and inside Spring Security's filter chain.

## Question4:
1. preHandle()
   preHandle() executes before the controller method is invoked.
   It returns a boolean value that determines whether processing should continue.
- true: Continue to the next interceptor or controller.
- false: Stop further handler processing. The controller will not execute.
  It is commonly used for authentication checks, authorization, logging, and request validation.
2. postHandle()
   postHandle() executes after the controller method successfully completes, but before Spring MVC renders a traditional view.
   It can modify the ModelAndView returned by a traditional MVC controller.
   However, it generally does not execute if the controller throws an exception, even when the exception is subsequently handled by an exception resolver.
3. afterCompletion()
   afterCompletion() executes after Spring MVC finishes processing the request, including view rendering or exception handling.
   It is commonly used for resource cleanup, logging, and performance monitoring.
   This method is invoked for interceptors whose preHandle() successfully returned true, even if a controller exception occurs.

What happens when the controller throws an exception?
Method	Normal request	Controller throws exception
preHandle()	Executes	Executes
Controller	Executes	Throws exception
postHandle()	Executes	Generally skipped
afterCompletion()	Executes	Executes for successfully entered interceptors

Why postHandle() cannot change a @RestController response body
A @RestController uses @ResponseBody semantics. Spring processes its return value using an HttpMessageConverter, such as Jackson's JSON converter, during controller handling.
By the time postHandle() executes, the response body has already been written and may already be committed. Therefore, postHandle() cannot reliably modify its contents.

## Question6:
1. The difference comes from where filters and interceptors execute relative to Spring MVC's exception-handling infrastructure.
A Servlet Filter runs outside the DispatcherServlet, so an exception thrown within the filter is not automatically processed by Spring MVC's HandlerExceptionResolver or @RestControllerAdvice.
A HandlerInterceptor, however, executes inside the DispatcherServlet. When preHandle() throws an exception, the DispatcherServlet can pass that exception to the registered exception resolvers, including those supporting @RestControllerAdvice.
2. Solution 1: Catch exceptions and write JSON directly
   A filter can catch exceptions and construct its own JSON response using HttpServletResponse.

Solution 2: Delegate to HandlerExceptionResolver
A filter can also inject Spring MVC's HandlerExceptionResolver and explicitly forward exceptions for resolution.
