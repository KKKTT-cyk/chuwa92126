# Spring AOP Homework — Questions and Answers

## Question 1
Explain what a cross-cutting concern is, and use the OrderService example from class to explain "tangling" and "scattering".

A cross-cutting concern is functionality needed across multiple parts of an application, such as logging, security, transaction management, or performance monitoring, rather than functionality belonging to one business operation. In an `OrderService`, business logic might validate and place orders, while logging, authorization, and timing code surrounds that logic. Tangling occurs when one `OrderService` method mixes order-processing code with logging, security, and timing code. Scattering occurs when the same logging or security logic is repeated across `OrderService`, `PaymentService`, and other services. Spring AOP separates these concerns into aspects so the business methods stay focused. (The homework references an in-class example but does not provide its implementation; this is an illustrative version.)

## Question 2
Define aspect, join point, pointcut, advice, target and proxy, and state what a join point always is in Spring AOP.

An aspect is a module that groups cross-cutting behavior, often a class annotated with `@Aspect`. A join point is a point in execution where advice can apply; in Spring AOP, a join point is always a method execution. A pointcut is a rule selecting which method executions should be advised. Advice is the action run at matching join points, such as logging before a method or measuring its duration. The target is the underlying object whose method is being called. A proxy is the Spring-managed wrapper around that target which intercepts eligible calls and executes the applicable advice.

## Question 3
Compare the five advice types (`@Before`, `@AfterReturning`, `@AfterThrowing`, `@After`, `@Around`): when each one runs, and which of them can change the return value or prevent the target method from running.

| Advice | When it runs | Can replace the return value? | Can skip the target? |
|---|---|---|---|
| `@Before` | Before the target executes | No | Not normally; throwing an exception prevents execution |
| `@AfterReturning` | After the target returns normally | No (it can mutate a returned mutable object) | No |
| `@AfterThrowing` | When the target exits by throwing a matching exception | No | No |
| `@After` | After the target exits, whether normally or exceptionally (finally-style) | No | No |
| `@Around` | Surrounds the target invocation | Yes | Yes, by not calling `proceed()` |

`@Around` has the most control: it can run code before and after, call `ProceedingJoinPoint.proceed()`, return a different result, or skip the invocation entirely. Other advice can throw exceptions, but cannot directly substitute a successful return value or choose whether to invoke the target.

## Question 4
Describe three mistakes that are easy to make inside an `@Around` advice and the effect of each one.

1. Forgetting `proceed()`: the target method never runs, so its business operation is silently skipped unless that was intentional.
2. Calling `proceed()` multiple times: the target runs multiple times, potentially creating duplicate orders, payments, or database writes.
3. Not returning the result of `proceed()`: returning `null` or an incorrect value changes what the caller receives and can cause failures, especially for primitive return types. Normally store and return the result, unless changing it is intentional.

A typical safe pattern is:

```java
@Around("execution(* com.example.orders.service.*.*(..))")
public Object measure(ProceedingJoinPoint joinPoint) throws Throwable {
    long start = System.nanoTime();
    try {
        return joinPoint.proceed();
    } finally {
        long elapsed = System.nanoTime() - start;
        System.out.println("Elapsed ns: " + elapsed);
    }
}
```

## Question 5
Explain what each pointcut expression matches: `execution(* com.example.orders.service.*.*(..))`, `execution(* com.example.orders..*.*(..))`, `execution(* *(Long, ..))` and `@annotation(com.example.orders.aop.LogExecutionTime)`.

- `execution(* com.example.orders.service.*.*(..))`: methods with any return type, any method name, and any arguments declared on types directly in the `com.example.orders.service` package; it does not include types in deeper subpackages.
- `execution(* com.example.orders..*.*(..))`: methods on types in `com.example.orders` and all its subpackages, with any return type, name, and argument list.
- `execution(* *(Long, ..))`: methods of any name and return type whose first parameter is `java.lang.Long` and which may have zero or more additional parameters. It does not mean any method containing a `Long` parameter in an arbitrary position.
- `@annotation(com.example.orders.aop.LogExecutionTime)`: method executions where the method carries the specified `@LogExecutionTime` annotation, subject to Spring AOP's proxy and method-visibility limitations.

## Question 6
Explain how Spring AOP applies advice through proxies, at which step of the bean lifecycle the proxy is created, and how you can check that an injected bean is a proxy.

Spring creates and initializes a target bean, and an AOP auto-proxy creator (a `BeanPostProcessor`) can wrap an eligible bean in a proxy during post-processing after initialization, before it is made available for normal use. Calls arriving through the proxy pass through an interceptor/advice chain before reaching the target. Spring commonly uses JDK dynamic proxies for interface-based proxying and CGLIB subclass proxies for class-based proxying, depending on configuration. To check an injected bean:

```java
import org.springframework.aop.support.AopUtils;

System.out.println(AopUtils.isAopProxy(orderService));
System.out.println(AopUtils.isJdkDynamicProxy(orderService));
System.out.println(AopUtils.isCglibProxy(orderService));
```

`AopUtils.isAopProxy(orderService)` is the clearest general check; inspecting `orderService.getClass()` may also show a generated proxy class.

## Question 7
Explain why calling a method annotated with `@LogExecutionTime` or `@Transactional` from another method of the same class skips the advice, and describe two ways to fix it.

Spring AOP intercepts calls that go through the proxy. When one method calls another method on the same instance (for example, `this.saveOrder()`), the call goes directly to the target instead of re-entering the proxy, so logging or transaction advice on the called method is skipped. One fix is to move the advised method into a separate Spring-managed service and inject that service, so the call crosses its proxy. Another fix is to invoke the method through a Spring-managed self-reference to the proxy (carefully injected rather than using `this`), though this couples the design to proxy behavior and is generally less desirable than extracting another service. AspectJ weaving is an additional alternative because it does not depend on proxy interception.

## Question 8
State the default rollback rules of `@Transactional`, and describe three situations in which a `@Transactional` method does not roll back even though something went wrong.

By default, Spring's `@Transactional` rolls back for unchecked exceptions (`RuntimeException`) and `Error`, but not for checked exceptions. Three common cases where rollback does not happen as expected are:

1. A checked exception escapes the method, such as `IOException`, without `rollbackFor = IOException.class`; by default Spring commits instead of rolling back.
2. The method catches an exception and returns normally without marking the transaction rollback-only; the transaction interceptor sees a successful return and normally commits.
3. The method is called through self-invocation, bypassing the transactional proxy; the annotation on the internally called method does not start its intended transaction. If an outer transaction already exists, its behavior depends on that transaction's configuration.

For example, `@Transactional(rollbackFor = Exception.class)` broadens rollback to checked exceptions, and `TransactionAspectSupport.currentTransactionStatus().setRollbackOnly()` can mark an active transaction for rollback when an error is handled internally.

## Question 9
SecurityAspect has `@Order(1)` and TimingAspect has `@Order(2)`, and both use `@Around` on the same method. Describe the order in which their code runs. Then compare Spring AOP with AspectJ in terms of weaving and the join points each one supports.

A lower `@Order` value has higher precedence, so `SecurityAspect` is the outer wrapper. Assuming each advice calls `proceed()` exactly once, execution follows:

```text
SecurityAspect: before
    TimingAspect: before
        Target method
    TimingAspect: after
SecurityAspect: after
```

The “after” lines assume the advice uses a `finally` block or the target returns normally. Spring AOP uses runtime proxies around Spring-managed beans and supports method-execution join points only, primarily when calls enter through the proxy. AspectJ can weave aspects into bytecode at compile time, post-compile time, or class-loading time. AspectJ supports a broader set of join points, including method calls and executions, constructor calls and executions, and field reads/writes; because its advice is woven into code, it can also handle self-invocation that Spring proxy-based AOP misses.
