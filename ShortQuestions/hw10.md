
# Java Spring Boot — Filter & Interceptor Homework

## 1. Difference between Servlet Filter and HandlerInterceptor

### Servlet Filter
- Defined by the Jakarta Servlet specification.
- Runs before and after `DispatcherServlet`.
- Has access to HTTP requests and responses.
- Commonly used for security, logging, and CORS.

### HandlerInterceptor
- Defined by the Spring MVC framework.
- Runs inside `DispatcherServlet` processing.
- Has access to HTTP requests, responses, and handler information.
- Commonly used for authentication, authorization, and logging.

### Request Flow

```text
Client
  ↓
Servlet Filter
  ↓
DispatcherServlet
  ↓
HandlerInterceptor
  ↓
Controller
  ↓
HandlerInterceptor
  ↓
DispatcherServlet
  ↓
Servlet Filter
  ↓
Client
```

**Key Difference:** Filters operate at the Servlet level, while Interceptors operate at the Spring MVC level.

## 2. How does chain.doFilter() work?

### Example

```java
@Override
public void doFilter(
        ServletRequest request,
        ServletResponse response,
        FilterChain chain)
        throws IOException, ServletException {

    System.out.println("Before");

    chain.doFilter(request, response);

    System.out.println("After");
}
```

### Explanation

- Before `chain.doFilter()`: Code runs before the next filter or servlet.
- `chain.doFilter()`: Passes the request to the next filter or servlet.
- After `chain.doFilter()`: Code runs when downstream processing returns normally.
- Without `chain.doFilter()`: The request stops, and the controller is not reached.

### Design Patterns

1. **Chain of Responsibility:** Each filter passes the request to the next filter.
2. **Decorator:** Filters wrap request and response processing with additional behavior.

## 3. How to register a Filter in Spring Boot?

### Method 1: Use @Component

```java
@Component
@Order(1)
public class MyFilter implements Filter {

    @Override
    public void doFilter(
            ServletRequest request,
            ServletResponse response,
            FilterChain chain)
            throws IOException, ServletException {

        chain.doFilter(request, response);
    }
}
```

### Method 2: Use FilterRegistrationBean

```java
@Bean
public FilterRegistrationBean<MyFilter> filterRegistration() {

    FilterRegistrationBean<MyFilter> registration =
            new FilterRegistrationBean<>();

    registration.setFilter(new MyFilter());
    registration.addUrlPatterns("/api/*");
    registration.setOrder(1);

    return registration;
}
```

### Filter Order

- Controlled by `@Order` or `setOrder()`.
- Lower order numbers execute first.

### Spring Security

- Spring Security uses a filter chain called `springSecurityFilterChain`.
- It is typically registered through `DelegatingFilterProxy`.
- It runs before `DispatcherServlet`.
- Its order is configured by Spring Boot and can be customized.

### Duplicate Registration

A filter can accidentally execute twice when:

- It is registered using both `@Component` and a separate `FilterRegistrationBean`.
- It is registered as a Servlet filter and also added to Spring Security's filter chain.

## 4. Explain preHandle, postHandle, and afterCompletion

### preHandle()

- Executes before the controller.
- Returns `true` to continue processing.
- Returns `false` to stop processing.

### postHandle()

- Executes after successful controller execution.
- Runs before view rendering.
- Usually does not execute when the controller throws an exception.

### afterCompletion()

- Executes after request processing finishes.
- Also executes during exception handling if `preHandle()` returned `true`.

### Normal Execution

```text
preHandle()
    ↓
Controller
    ↓
postHandle()
    ↓
afterCompletion()
```

### If the Controller Throws an Exception

- `preHandle()` has already executed.
- `postHandle()` is generally skipped.
- `afterCompletion()` runs if the interceptor's `preHandle()` returned `true` and MVC processing completes.

### Why can't postHandle() change a @RestController response body?

Because the response body is normally serialized and written by an `HttpMessageConverter` before `postHandle()` executes.

**Solution:** Use `ResponseBodyAdvice` to modify the response body.

## 5. Execution order of Interceptor A and B

Given:

- Interceptor A: order 1
- Interceptor B: order 2

### Case 1: Successful Request

```text
1. A.preHandle()
2. B.preHandle()
3. Controller executes
4. B.postHandle()
5. A.postHandle()
6. B.afterCompletion()
7. A.afterCompletion()
```

### Case 2: B.preHandle() returns false

```text
1. A.preHandle() → true
2. B.preHandle() → false
3. A.afterCompletion()
```

### Explanation

- The controller does not execute.
- Neither interceptor's `postHandle()` executes.
- `B.afterCompletion()` does not execute.
- `A.afterCompletion()` still executes.

**Remember:**

- `preHandle()` executes in forward order.
- `postHandle()` executes in reverse order.
- `afterCompletion()` executes in reverse order.

## 6. Why doesn't @RestControllerAdvice handle Filter exceptions?

### Explanation

- Filters execute outside Spring MVC's `DispatcherServlet`.
- `@RestControllerAdvice` handles exceptions through Spring MVC's exception resolution mechanism.
- Therefore, exceptions thrown in filters are not automatically handled by `@RestControllerAdvice`.
- Exceptions thrown in `preHandle()` occur inside `DispatcherServlet` processing and can be handled by Spring MVC exception resolvers.

### Solution 1: Handle exceptions inside the Filter

```java
try {
    chain.doFilter(request, response);
} catch (Exception e) {

    HttpServletResponse res =
            (HttpServletResponse) response;

    res.setStatus(500);
    res.setContentType("application/json");

    res.getWriter().write(
        "{\"error\":\"Internal server error\"}"
    );
}
```

This approach writes a JSON error response directly.

### Solution 2: Use HandlerExceptionResolver

```java
try {
    chain.doFilter(request, response);
} catch (Exception e) {

    resolver.resolveException(
        (HttpServletRequest) request,
        (HttpServletResponse) response,
        null,
        e
    );
}
```

This approach delegates exception handling to Spring MVC's exception resolver.

An appropriate resolver must be configured to handle the exception.

**Key Difference:** Filters execute outside MVC exception handling, while Interceptors execute inside it.

## 7. Difference between /api/* in Filter and Interceptor

### Servlet Filter

```java
registration.addUrlPatterns("/api/*");
```

Uses Servlet URL pattern matching.

Matches:

- `/api`
- `/api/test`
- `/api/users/123`

### Spring MVC Interceptor

```java
registry.addInterceptor(myInterceptor)
        .addPathPatterns("/api/*");
```

Uses Spring MVC path matching.

Matches:

- `/api/test`

Does not match:

- `/api/users/123`

### Match Multiple Path Levels

```java
.addPathPatterns("/api/**");
```

This matches nested API paths.

### Why should an authentication interceptor exclude /error?

Spring Boot uses `/error` to handle errors.

If an authentication interceptor also intercepts `/error`, it may reject the error dispatch or interfere with the original error response.

### Example

```java
@Override
public void addInterceptors(InterceptorRegistry registry) {

    registry.addInterceptor(authInterceptor)
            .addPathPatterns("/api/**")
            .excludePathPatterns("/error");
}
```

This allows Spring Boot to handle error responses without interference from the authentication interceptor.
