## 1. Compare the data models of logs, metrics and traces: what a single record contains, how the storage volume of each signal grows (with traffic, with the number of label combinations, or with the number of services a request touches), and which kind of question each signal answers best. Explain why a telemetry pipeline is itself a high-throughput write-heavy, low-frequency-read distributed system.
Logs describe individual events, usually with a timestamp, message, severity, and context. Their volume grows with traffic and how much the application logs. Metrics store timestamped values for named measurements and label combinations, so their size depends mainly on the number of series and collection frequency. Traces connect spans into a request’s call tree; their volume grows with request count, sampling rate, and the number of operations recorded. Logs explain what happened, metrics show overall trends, and traces show where a request slowed down or failed. The pipeline is write-heavy because applications constantly produce data, while people mainly read it through dashboards or during investigations, alongside automated alert checks.

## 2. Compare the two families of log storage: a full-text inverted index and a label index with compressed chunks in object storage. For each family describe what is paid at write time and at read time, which query patterns are fast or slow, and how each one is hurt by high cardinality. State which family you would choose for a platform with very high volume and mostly "this service, last 15 minutes" searches, and why.
full-text inverted index does more work when logs arrive, indexing terms so text searches are fast later. This costs storage, especially when indexed fields contain many unique values. Label-based storage indexes a few labels and keeps compressed log chunks in object storage. Writes are cheaper, but searches must scan the chunks selected by labels and time. High cardinality labels create too many streams and small chunks, reducing efficiency. For high-volume logs mostly searched by service over the last 15 minutes, I would choose label based storage.




## 3. Compare pull-based and push-based metrics collection. Cover service discovery, detecting that a target is down, short-lived batch jobs, firewalls and network topology, who controls the collection rate, and what happens to the collector when an application misbehaves.
With pull, the collector discovers targets and decides when to scrape them. A failed scrape signals a problem, though it could be the network rather than the application. Pull can miss short lived jobs and needs network access to each target. With push, applications send data to a known endpoint, which works better behind NAT or firewalls and lets jobs report before exiting. Missing updates need a heartbeat or freshness check to detect failure. Applications control how often they push, so a noisy producer can overload the collector unless limits are enforced. Pull gives the collector more control, but it still needs timeouts and response size limits for badly behaved targets.
