1. A request thread waits while the database and external API respond. During that time it does no useful work but still
occupies memory and a thread.
2. The demultiplexer watches for I/O readiness. The event loop dispatches ready events. The acceptor accepts new connections and registers them; handlers process each connection’s events. Blocking the event loop delays every connection assigned to it.
3. The four interfaces are Publisher, Subscriber, Subscription, and Processor. The publisher calls onSubscribe; the subscriber requests items through request(n). The publisher then sends onNext signals, followed by onComplete or onError.
4. Mono emits zero or one item; Flux emits zero to many. A pipeline usually runs only after subscription. Mono.just(buildReport()) calls buildReport() immediately; Mono.fromCallable(() -> buildReport()) calls it on subscription and turns thrown exceptions into error signals.
5. Operator	Function returns	Inner work	Output order
   map	A value	Synchronous	Source order
   flatMap	A publisher	May run concurrently	Not guaranteed
   concatMap	A publisher	One at a time	Source order
   flatMapSequential	A publisher	May run concurrently	Source order
6. A try/catch around pipeline construction catches immediate Java exceptions, not errors that happen later during subscription. onErrorReturn supplies a value; onErrorResume switches to another publisher; onErrorMap transforms the error; retryWhen retries by a policy; timeout signals an error if the deadline is exceeded.
7. subscribeOn schedules the source subscription and upstream work. publishOn changes the scheduler for downstream work after that point. Use Schedulers.boundedElastic() to wrap a blocking JDBC call.
8. Backpressure lets a subscriber tell a publisher how many items it can handle with request(n). If a source such as Flux.interval cannot slow down, you can buffer, drop items, keep only the latest item, or signal an error when demand is exceeded.
9. A cold publisher starts work separately for each subscriber. A WebClient Mono is cold, so two subscriptions usually send two requests. cache() stores and replays the result; share() lets subscribers share an active upstream subscription.
10. Spring MVC uses an imperative request-per-thread model; WebFlux supports non-blocking reactive I/O. MVC with virtual threads can be a better fit for blocking code such as JDBC when you want simpler imperative programming. WebFlux is useful when the full request path is non-blocking or needs reactive streaming.
