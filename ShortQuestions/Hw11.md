## 3. Explain chunk-oriented processing: how reading, processing and writing are organized, where the transaction boundaries are, and how the chunk size affects speed, memory and the amount of work repeated after a failure.
In chunk-oriented processing, Spring Batch reads items one at a time, processes them individually, and writes the resulting items together as a batch. Each chunk runs within a transaction, which commits after successful writing. If a failure occurs, the current chunk’s transactional changes roll back, while earlier committed chunks remain; checkpoint-based restart may therefore repeat the uncommitted chunk. A larger chunk size usually improves speed by reducing transaction and write-call overhead, but uses more memory and increases the work potentially repeated after failure. A smaller chunk size uses less memory and reduces repeated work, but adds more frequent writes and commits, which can reduce throughput.

## 4. Compare a tasklet step with a chunk-oriented step, and give a typical use for each one.
A tasklet step executes custom logic through Tasklet.execute(), repeating until it returns RepeatStatus.FINISHED or throws an exception. It suits discrete operations such as checking whether an input file exists or archiving a processed file.

A chunk-oriented step uses an ItemReader, an optional ItemProcessor, and an ItemWriter to process records in groups, committing a transaction for each chunk. It suits large, record-based workloads, such as reading thousands of CSV transactions, calculating settlement amounts, and writing the results.




## 5. Describe the contracts of ItemReader, ItemProcessor and ItemWriter: how a reader signals the end of the input, what it means when a processor returns null, and why a writer receives a whole Chunk instead of a single item.
An ItemReader returns one item per read() call and signals the end of input by returning null. An ItemProcessor transforms or validates each item; returning null filters that item out, so it is not passed to the writer this is normal filtering, not an error or exception-based skip. An ItemWriter receives a whole Chunk of output items because Spring Batch groups records before writing.


## 6. Explain the difference between filtering and skipping an item, and the difference between skip and retry, with an example of an error suited to each.
Filtering intentionally excludes an item for a business reason: the processor returns null, for example to ignore an already settled transaction. No error occurs. Skipping ignores an item after a configured skippable exception, such as an invalid amount in a CSV record, and processing continues within the skip limit. Retrying attempts a failed operation again because the problem may be temporary, such as a database deadlock.


## 7. Explain why a reader that uses #{jobParameters['inputFile']} must be declared @StepScope.
It depends on parameters supplied when a Job runs, which are unavailable when ordinary singleton beans are created at application startup. @StepScope enables late binding by delaying creation of the actual reader until the step executes, when those parameters are available.




## 8. Describe what happens when a failed job is started again with the same identifying parameters, what the reader and the writer must support for this to work, and when JobInstanceAlreadyCompleteException is thrown.
Assuming the Job is restartable, starting a failed job with the same identifying parameters reuses the JobInstance but creates a new JobExecution. By default, completed steps are skipped, and the failed step resumes from its last committed checkpoint. The reader must restore its saved position against stable input, while a stateful writer must restore its output state without overwriting committed results.


## 9. Compare a multi-threaded step with partitioning, and explain what must be true of the reader, processor and writer in a multi-threaded step.
A multi-threaded step processes chunks concurrently within one StepExecution in a single JVM, sharing the reader, processor, and writer. Partitioning divides the input into independent subsets, such as files or ID ranges, each handled by a separate worker StepExecution with its own ExecutionContext; workers can run locally or remotely. In a multi-threaded step, the reader must safely coordinate concurrent reads, the processor must be stateless or thread-safe, and the writer must safely handle concurrent writes.






## 10. Describe two pitfalls of starting batch jobs with @Scheduled in an application that runs as several instances, and how to address each one.
First, @Scheduled runs independently on every application instance, so several replicas may launch the same business job. Address this with a distributed lock or a single active scheduler, plus a shared JobRepository and stable identifying parameters, such as runDate, so duplicate triggers refer to the same JobInstance. Job identity rules. Second, executions can overlap if another trigger fires while the previous job is still running, particularly when different parameters create separate JobInstances. Prevent this with cluster-wide concurrency control that skips or defers conflicting launches.
