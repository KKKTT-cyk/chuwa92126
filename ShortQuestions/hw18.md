#### Conceptual Questions

1. **Explain the difference between an imperative command such as "start 3 copies of checkout on these hosts" and a declarative object such as "there should be 3 copies of checkout", and explain what the spec and the status of an object are used for. Then explain why Kubernetes controllers are level-triggered rather than edge-triggered: for each of these three situations, say what an edge-triggered design does and what a level-triggered design does: (a) an event is lost, (b) the controller restarts, (c) the same event is delivered twice.**

   An imperative command describes an action to perform now, including details such as which hosts should run the copies. Once the action finishes, the command alone does not keep repairing the application if a copy fails later. A declarative object describes the desired outcome, such as three replicas of checkout. Kubernetes controllers repeatedly compare this desired state with the actual cluster state and take steps to make them agree. The object's spec describes the desired configuration, such as its replica count and Pod template. Its status reports observations, such as available replicas and conditions. Status may lag behind reality, so reconciliation also uses the current state of related objects rather than treating a status field as an infallible command.

   An edge-triggered design reacts to a particular transition or event, while a level-triggered design evaluates whether the current state satisfies the desired state. If an event is lost, a purely edge-triggered controller may never perform the action associated with that event unless it has reliable replay or another recovery mechanism. A level-triggered controller can detect the remaining mismatch during a later reconciliation and repair it. This still requires another evaluation, triggered by a later notification, retry, resynchronization or relist; recovery does not happen automatically without running the loop.

   After a restart, an edge-triggered controller may need to replay event history to determine which actions it missed. A level-triggered controller can rebuild its view from the API, observe what exists now and continue reconciliation without reconstructing every past transition. If the same event arrives twice, an edge-triggered implementation may perform an action twice unless it explicitly deduplicates events. A level-triggered controller checks the state again and avoids unnecessary action once the desired state is satisfied. Reconciliation must still be designed to be idempotent and tolerate stale reads and retries; level-triggering is not an exactly-once execution guarantee. In Kubernetes, change notifications mainly identify objects that should be reconsidered, rather than act as commands that must each execute once.

2. **Explain why Kubernetes components never call each other and instead read and write objects through the API server (name at least three benefits and the main cost). Then describe how resourceVersion and optimistic concurrency handle two controllers that read the same object and both try to update it: say which update succeeds, what the other one receives, what it must do next, and why this design needs no locks. Also explain what a watching client must do when the revision it wants to resume from has already been compacted.**

   The tutorial's statement describes the main coordination model: components communicate desired and observed cluster state through API objects rather than a chain of direct commands. For example, the scheduler records a Pod's node assignment through the API, and the kubelet observes that assignment. This provides several benefits. Authentication, authorization, admission policy and auditing are applied centrally. Components share durable state without needing direct access to etcd or knowledge of its storage details. Loose coupling allows a component to restart or be replaced without requiring every other component to change. The same API and watch mechanisms also support custom resources and extension controllers. The main cost is that the API server and its backing store become a shared control-plane bottleneck and failure dependency, requiring capacity planning and high availability.

   “Never call each other” is not literally true for every Kubernetes interaction. For example, the API server contacts kubelets for logs, exec and port forwarding. The API-object model describes cluster-state coordination, not every data or management connection. [Kubernetes communication documentation](https://kubernetes.io/docs/concepts/architecture/control-plane-node-communication/).

   Suppose both controllers read the same object at resourceVersion R and submit ordinary version-checked updates based on R. The first valid update committed against that version succeeds and produces a new version. The other stale update receives HTTP 409 Conflict. That controller must read the latest object, recompute or reapply its intended change without overwriting the first controller's work, and retry using the current version. The server performs the version check atomically with the write, so controllers do not need to acquire and hold distributed locks across their read-modify-write cycles. This does not mean the storage system has no internal synchronization or consensus mechanisms.

   If a client's watch resume version is older than retained history, the server reports an expired resource version, typically HTTP 410 Gone. The client must rebuild its view with a fresh List and start watching from the resourceVersion returned with that list. Retrying the expired version cannot recover history that has already been compacted.

3. **Explain the roles of Pods, ReplicaSets, Deployments, and Services. How do these objects work together to run and maintain an application?**

   A Pod is the smallest deployable workload unit. It contains one or more closely related containers scheduled together on one node, with a shared network context and access to configured volumes. A ReplicaSet maintains the desired number of matching Pods, creating or deleting Pods as needed. A Deployment manages ReplicaSets and provides declarative updates, scaling and rollout management. Changing the Deployment's Pod template normally creates a new ReplicaSet, and the Deployment controller adjusts the old and new ReplicaSets according to the rollout strategy. A Service provides stable network access to a selected group of Pods even as individual Pod addresses change.

   For example, a checkout Deployment requests three replicas and defines the container image and Pod labels. Its controller manages a ReplicaSet, whose controller creates the required Pods. The scheduler assigns those Pods to nodes, and the kubelets start their containers. A Service selects the checkout Pods by label; EndpointSlices describe its backends, and the Service networking implementation routes traffic to eligible endpoints, normally ready Pods. If a Pod is deleted, the ReplicaSet creates a replacement and the endpoint information is updated. If the application image changes, the Deployment coordinates the rollout while the Service continues exposing the application at a stable address. A Service routes traffic; it does not create Pods or maintain the replica count itself.

4. **What is the difference between the Kubernetes control plane and data plane? What happens to existing running workloads if the control plane becomes temporarily unavailable?**

   The control plane stores cluster state and makes decisions about how to achieve the desired configuration. Its main components include the API server, etcd, scheduler and controllers. The data plane runs the workloads and carries their traffic, using worker nodes, container runtimes, node agents and networking components. The kubelet connects these concerns by observing assigned workloads and managing containers locally.

   If the control plane temporarily becomes unavailable, existing containers generally continue running on healthy nodes. Previously installed network and Service-routing rules can continue forwarding traffic, and a running kubelet can often restart failed containers using the Pod configuration it already knows. However, the cluster cannot normally accept new configuration, schedule new Pods, coordinate rollouts or scaling, or replace workloads on failed nodes. Endpoint and routing information may become stale, so continued operation is not guaranteed if backends or external dependencies fail. Applications that call the Kubernetes API directly may also be affected. When the control plane recovers, controllers observe the current state and reconcile outstanding differences. The separation preserves existing execution during an outage, but it does not preserve all cluster-wide repair and management capabilities.

5. **Describe the main stages a request goes through when a client creates a Kubernetes object. What is the difference between authentication, authorization, and admission control?**

   The client sends a create request containing the object to the API server. At a high level, the server authenticates the requester, authorizes the operation, processes the object through admission and validation, and persists the accepted object in etcd. Mutating admission can modify the object, such as adding required labels or injecting a sidecar. Schema and resource-specific validation check that the object is valid, and validating admission checks whether the final object satisfies cluster policies without modifying it. Decoding, conversion and defaulting also occur as part of request processing. If the request is accepted, the server returns the stored object and exposes the change to watchers. Controllers then react asynchronously; successfully creating a Deployment object does not mean all its Pods are already running.

   Authentication asks “Who is making this request?” and establishes an identity using credentials such as a certificate or token. Authorization asks “May this identity perform this operation on this resource in this scope?” For example, RBAC may allow creating Deployments in one namespace but deny it in another. Admission control asks “Is this proposed object or change acceptable under cluster policy, and should it be modified before storage?” An authorized user can still have a create request rejected because the object violates a security policy or resource quota. Admission evaluates the content and context of a permitted operation; it does not replace authentication or authorization.

6. **What is the purpose of the resourceVersion field in Kubernetes? How does it help prevent conflicting updates when multiple clients modify the same object?**

   resourceVersion is a server-assigned, opaque version token representing a particular stored state of an object. Clients should preserve it as a string rather than interpret it as a timestamp, numeric counter or API schema version. It supports optimistic concurrency and is also used in List and Watch operations. For a normal version-checked update, the client sends the resourceVersion it read. The server accepts the update only if that version still matches the stored object; otherwise it returns a conflict, preventing a stale client from silently replacing newer data. The client then reads the latest state and retries its change. Patch and apply operations have their own concurrency and ownership semantics, so they should not all be assumed to behave like a full-object update. 

7. **How do the List and Watch operations work together to help Kubernetes components track changes in cluster state? Why is this approach more efficient than repeatedly listing all objects?**

   A client first uses List to obtain the relevant objects and the collection's resourceVersion. It builds a local cache and starts a Watch from that version, allowing it to receive changes that occur after the snapshot without intentionally leaving a gap between the two operations. Watch events such as ADDED, MODIFIED and DELETED update the cache, while optional bookmarks indicate progress without representing an object change. Informers commonly manage this process for controllers and enqueue affected object keys for reconciliation. The cache is an eventually updated view, so controller logic must tolerate it being briefly stale.

   If the connection closes, the client can reconnect using its last successfully processed resourceVersion while that version remains available. If history has expired, it must relist, replace or reconcile its cached view, and resume watching from the new snapshot version. Compared with repeatedly transferring every object, List followed by Watch sends a full snapshot primarily during initialization or recovery and then streams incremental changes. This reduces network traffic, serialization work and repeated API-server processing while detecting changes promptly. Watch still has connection and event-processing costs, and a relist is still necessary when the client can no longer resume reliably.
