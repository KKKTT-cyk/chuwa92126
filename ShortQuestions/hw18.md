1. A request-duration histogram has 8 finite buckets, 1 +Inf bucket, 1 sum series, and 1 count series. Therefore, each label combination produces 11 time series.

The original number of label combinations is:

100 instances × 20 endpoints × 4 status values = 8,000 combinations

Total series:

8,000 × 11 = 88,000 time series

After adding a user_id label with 50,000 distinct values, the worst-case number of combinations is:

8,000 × 50,000 = 400,000,000 combinations

Total series:

400,000,000 × 11 = 4,400,000,000 time series

High cardinality increases memory use for active series and indexes, CPU use during ingestion and queries, and storage needs for samples and metadata. It can also slow queries and exhaust database resources.

Three ways to control cardinality:
1. Avoid unbounded labels. Do not add user_id; use a bounded label such as user tier instead. Apply this in application instrumentation.
2. Drop or rewrite labels before ingestion. Remove user_id in the scrape configuration or telemetry collection pipeline.
3. Aggregate measurements before storing them. Combine data across users and keep only useful dimensions, such as endpoint and status. Apply this in a collector or with recording rules.

2. The average p99 is (20 + 600) / 2 = 310 ms, but percentiles cannot be averaged to get the combined p99. It depends on the distribution of all 1,000 requests; the two p99 values alone are insufficient.

Summaries: Accurate per instance, but quantiles generally cannot be aggregated; moderate client CPU and memory cost.

Histograms: Bucket counts can be aggregated when instances share boundaries; quantiles are approximate, with accuracy depending on bucket width; cost grows with the number of buckets.

Sketches: Usually mergeable across instances; provide approximate quantiles with algorithm-dependent error; compact, but require computation.

Place histogram boundaries around the latency objective. A boundary at the SLO lets you count requests that meet it directly.

3. The buffer holds 2,000 × 20 = 40,000 traces. Each trace is 8 × 400 = 3,200 bytes, so the spans require 128,000,000 bytes, or about 128 MB (122 MiB), excluding overhead.

All spans from one trace must reach the same sampler so it can make a tail-sampling decision using the complete trace.

When scaling from 4 to 5 nodes, hash(trace_id) modulo N remaps about 80% of traces. Consistent hashing moves about 20%—the share assigned to the new node—and leaves the rest in place.

4. The traceparent format is version-trace-id-parent-id-trace-flags.
- 00 — version: 2 hex characters (1 byte).
- 4bf92f3577b34da6a3ce929d0e0e4736 — trace ID: 32 hex characters (16 bytes), identifying the whole trace.
- 00f067aa0ba902b7 — parent ID: 16 hex characters (8 bytes), identifying the caller’s span.
- 00 — trace flags: 2 hex characters (1 byte). The sampled bit is unset, so the service should not sample this trace.
  The service propagates the sampling decision in the outgoing trace flags so downstream services can follow the same decision. In the next service’s header, the parent ID is the current service’s span ID.

5. The 30-day period contains 43,200 minutes. At 99.95% availability, the error budget is 0.05% × 43,200 = 21.6 minutes.
- Burn rate 14.4: Triggering error ratio = 14.4 × 0.05% = 0.72%. It consumes 2% of the budget in 1 hour.
- Burn rate 6: Triggering error ratio = 6 × 0.05% = 0.30%. It consumes 5% of the budget in 6 hours and exhausts it in 5 days.
  A long window detects sustained budget burn; a short window confirms the problem is still happening and helps avoid alerts for brief, resolved spikes. The 14.4 burn-rate alert should page because it signals rapid budget loss. The 6 burn-rate alert should create a ticket for less urgent follow-up.

6. Send telemetry asynchronously through a bounded queue so backend failures do not block the app. Buffering absorbs brief outages but can fill up; dropping loses data; sampling reduces volume but may miss rare events; rate limiting protects the backend but delays or drops excess data.

At-least-once delivery retries but may create duplicates. At-most-once avoids duplicates but may lose data.

Run alerting in a separate failure domain so the same outage cannot disable monitoring and alerts. A watchdog alert detects a missing expected heartbeat.
