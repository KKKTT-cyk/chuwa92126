# HW18 – Observability (Part 2)

## Question 1.

A histogram exports 8 finite buckets + 1 `+Inf` bucket + sum + count = **11 series** per label combination.

Series = 100 instances x 20 endpoints x 4 status values x 11 = **88,000**.

Adding `user_id` with 50,000 distinct values raises the worst case to 88,000 x 50,000 = **4,400,000,000** (4.4 billion) series. Even if only a fraction of the combinations ever occur, the series count now grows with the number of users, not with the number of metric types.

Resources of a time-series database that are hurt:

| Resource | Effect of more series |
|---|---|
| Memory | Every active series keeps state in the head block (kilobytes per series) |
| Index size | Postings lists grow and intersections get slower |
| Ingestion | Every series is a separate append target |
| Queries | A query that selects many series reads many chunks |

Three techniques that keep cardinality under control:

| Technique | Where it is applied |
|---|---|
| Never use unbounded values (user id, request id, full URL) as labels, and normalize values (URL template instead of raw path) | Instrumentation or framework |
| Drop or rewrite noisy labels, and limit labels per target or samples per scrape | Collector |
| Per-tenant series limits | Platform |

Per-user detail should move to logs or traces, which scale with traffic and not with label cardinality.

## Question 2.

A percentile is a property of a whole distribution, so it cannot be recovered from the percentiles of parts. The simple average of the two values is (20 + 600) / 2 = 310 ms, but this ignores that A handled 800 requests and B only 200. The combined 99th percentile is the value that 1% of the 1,000 requests (the 10 slowest) exceed, and that depends on the full distribution of both instances; neither 310 ms nor a request-weighted average (800 x 20 + 200 x 600) / 1,000 = 136 ms is that value.

| Approach | Aggregatable across instances | Accuracy | Cost |
|---|---|---|---|
| Client-side summary (precomputed p50, p99) | No | Accurate for that instance only | One series per quantile |
| Histogram with fixed buckets | Yes: add the bucket counts across instances, then estimate | Limited by bucket layout: error up to the bucket width | One series per bucket per label combination |
| Sketch (t-digest, DDSketch) or exponential histogram | Yes: sketches can be merged | Bounded relative error (a design parameter) | Small, but needs backend support |

A quantile is estimated by finding the bucket that contains the target rank and interpolating inside it, so the error is bounded by the width of that bucket and the estimate is most accurate near a boundary. Bucket boundaries should therefore be chosen around the latency objective (for example just below and just above the SLO threshold), so that the question "are we under the objective?" is answered where the estimate is most accurate. More buckets give more accuracy but cost one more series per label combination.

## Question 3.

Memory = 2,000 traces/s x 20 s x 8 spans x 400 bytes = 128,000,000 bytes = **128 MB** held at any moment (across the whole sampler tier).

A sampler can judge a trace only if it sees all of its spans, because the decision uses the outcome (any error, total duration, an attribute). Spans of one trace are produced by different services and arrive at different collector instances, so they must be routed by trace id to the same sampler node. Otherwise each node sees a partial trace and could keep or drop it for the wrong reason.

| Routing | Fraction of traces that change node when going from 4 to 5 nodes |
|---|---|
| hash(trace id) modulo N | 1 - 1/5 = **80%** |
| Consistent hashing | about 1/5 = **20%** |

With modulo N, the destination of most traces changes when N changes, so traces in flight are split between old and new nodes and lose their decisions. Consistent hashing places nodes on a ring and sends each trace to the next node clockwise, so a new node only takes over the range of traces it owns. Even so, traces in flight during a change are affected, so the decision window is also a window of vulnerability to topology changes.

## Question 4.

`traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-00`

| Field | Value | Size | Meaning |
|---|---|---|---|
| version | `00` | 1 byte | Format version |
| trace-id | `4bf92f3577b34da6a3ce929d0e0e4736` | 16 bytes (128 bits) | Identifies the whole trace |
| parent-id | `00f067aa0ba902b7` | 8 bytes (64 bits) | The span id of the caller's span (the receiver's parent) |
| trace-flags | `00` | 1 byte | Bit 0 is the sampled flag |

The last field is `00`, so the sampled flag is not set: the caller did not record this trace, and the service should follow that and not record spans for it. The decision is made once at the start of the trace (head-based sampling) in the first service and travels in the trace context, so every downstream service follows it without deciding again. Each service copies the flags into the header it sends on, which keeps the decision consistent for all services of the trace.

When the service calls the next service, it keeps the same trace-id and puts the span id of its own outgoing client span in the parent-id field, not the parent-id it received.

## Question 5.

For a 30-day objective, the window is 30 x 24 x 60 = 43,200 minutes. The error budget is 1 - 0.9995 = 0.05%, so the budget is 0.0005 x 43,200 = **21.6 minutes**.

Burn rate 1 uses the whole budget in 30 days. The trigger error ratio is burn rate x 0.05%, and the budget consumed in a window is burn rate x window / 720 hours.

| Burn rate | Window | Error ratio that triggers | Budget consumed in that window |
|---|---|---|---|
| 14.4 | 1 hour | 14.4 x 0.05% = 0.72% | 14.4 x 1 / 720 = 2% |
| 6 | 6 hours | 6 x 0.05% = 0.30% | 6 x 6 / 720 = 5% |

At burn rate 6 the budget is exhausted after 30 / 6 = **5 days**.

An alert that looks only at a long window stays firing long after the problem is fixed, and an alert that looks only at a short window flaps on brief blips. A good alert requires both to exceed the threshold (the short window is about 1/12 of the long one). The long window confirms the severity, so it is quick to fire, and the short window shows recovery, so it clears quickly.

The burn rate 14.4 alert (the budget would be gone in 2 days) is a fast burn and should page someone. The burn rate 6 alert (5 days) is a slower burn and should create a ticket for working hours.

## Question 6.

**Never blocking the application.** The application writes telemetry to a bounded in-memory queue, a separate exporter thread takes batches and sends them to the agent or collector, and when the queue is full the producer drops the item, increments a "dropped" counter and continues. If the send fails, the exporter retries with backoff and then drops the batch. The request thread never waits for the network, so a backend outage can only cause data loss, not latency. The collector in the middle also buffers and retries, so the application hands off quickly.

**Overload options** when a downstream stage is slower than the upstream stage:

| Option | Behavior | Tradeoff |
|---|---|---|
| Buffering | Hold data in memory or on disk | Absorbs short bursts; fails when the buffer fills |
| Dropping | Discard some data | Bounded resources; visible data loss |
| Sampling (shed by priority) | Keep a fraction, or drop low-value data first (debug logs, health-check traces) | Keeps the most important signals; needs classification and loses detail |
| Rate limiting | Cap volume per source or tenant (quotas) | Protects shared stages; the excess is lost or the source is rejected |

Blocking the producer is also possible, but it is unacceptable on the request path. A durable buffer such as a log-structured message broker between the collection tier and storage decouples ingestion speed from storage speed.

**Delivery semantics.** At-most-once means each item is delivered zero or one times (send without retry), so any failure loses data. At-least-once means each item is delivered one or more times (retry until acknowledged), so duplicates are possible and consumers must tolerate them. Most telemetry uses at-least-once between pipeline stages with duplicate-tolerant storage, and accepts at-most-once at the edge, where the application drops when overloaded.

**Separate failure domain.** The observability platform is most needed when something else is failing, so the alerting path should run in a separate cluster, account or region with an independent notification channel. If it shared a failure domain with the monitored system, the same outage (or an overloaded pipeline or service mesh) would stop the alerts at the moment they are needed.

**Watchdog (dead-man's switch).** It is an always-firing alert that is sent continuously to an external receiver. The external system pages when the watchdog stops arriving, so it detects that the alerting system itself (or the path to it) has stopped working, which silence from normal alerts could never show.
