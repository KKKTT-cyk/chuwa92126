### Question 1.

Each label combination creates `8 + 1 + 1 + 1 = 11` series, so the baseline is `11 * (100 * 20 * 4) = 88,000` and the worst case with `user_id` is `88,000 * 50,000 = 4.4 billion`. That drives up active-series memory, index size, ingest work, and query fan-out. I'd keep unbounded IDs out of instrumentation, aggregate away unwanted dimensions before storage, and enforce per-tenant series limits at the backend.

### Question 2.

A p99 is a range, so averaging local p99s, even weighted by traffic, cannot give the fleet p99. Client-side summary quantiles cannot be merged. Histograms merge by adding matching buckets, and sketches merge their distribution state. I'd put a bucket boundary at the latency objective so I can measure compliance directly.

### Question 3.

At steady state, a 20-second window holds `2,000 * 20 = 40,000` traces, or `40,000 * 8 = 320,000` spans. The raw buffer is `320,000 * 400 = 128,000,000 bytes = 128 MB`, plus runtime overhead. Route by trace ID so one sampler sees all spans and makes one decision. Scaling from four nodes to five moves 80% of trace IDs with modulo routing and about 20% with balanced consistent hashing.

### Question 4.

`traceparent` contains a 1-byte version, 16-byte trace ID, 8-byte parent span ID, and 1-byte flags field. Flags `00` mean the sampled bit is clear. A parent-based sampler inherits and propagates that decision. For the next call, keep the trace ID and put the outgoing client span's ID in `parent-id`.

### Question 5.

A 99.95% availability objective allows a 0.05% error fraction. Over 30 days, the time-equivalent error budget is `30 * 24 * 60 * 0.0005 = 21.6 minutes`.
Burn rate is the observed error radio divided by the allowed error ratio. The alert threshold is `burn rate * 0.05%`, and the fraction consumed at a sustained burn is `burn rate * elapsed hours / 720`.

- burn rate = 14.4: Error ratio = `14.4 * 0.05% = 0.72%`. Budget consumed after 1 hour = `14.4 * 1 / 720 = 2%`.

- burn rate = 6: Error ratio = `6 * 0.05 = 0.30%`. Budget consumed after 6 hours = '6 \* 1 / 720 = 5%'. At this rate, a full budget would last 30 / 6 = 5 days.

I'd require both windows to breach and , for this two-tier policy, page at 14.4x and ticket at 6x.

### Question 6.

Telemetry export runs asynchronously off the request path. The application offers telemetry to a bounded queue without waiting, and a background worker exports it with timeouts and bounded retries. If a backend outage fills the queue, telemetry is dropped so requrests keep moving.

The application uses small buffers and early sampling. Collectors can buffer to memory or disk, rate-limit noisy sources, and sample complete traces. The backend can use durable queue and per-tenant limits. Buffering buys time but costs resources and delays delivery. Dropping creates gaps, campling can miss rare events, and rate limiting protects shared capacity by rejecting excess traffic.

At-least-once delivery retries unacknowledged data and can produce duplicates. At-most-once delivery avoids redelivery and can lose data.

Alerting runs in a separate failure domain so the same outage cannot take down both the service and its alerting path. A watchdog sends a periodic heartbeat through that path to an independent receiver. If the heartbeat stops, the receiver alerts that the alerting path itself may be broken.
