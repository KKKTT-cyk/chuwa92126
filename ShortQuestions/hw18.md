1. The number of series: 88,000, worst case series count with user_id: 4,400,000,000
Each label combination produces: 8+1+1+1=11 series
Origin count = 100*4*2*11=88,000
Worst case: 88000*50000= 4,400,000,000
Database impact: More active series consume memory for metadata and indexes, disk space for samples and the write-ahead log, and CPU 
and I/O for ingestion, compaction, and queries.
Three techniques:
 At the application instrumentation layer, omit user_id from metric labels and keep it in logs or traces for debugging.
 In the HTTP metrics middleware, use route templates such as /orders/{id} as endpoint labels so all order IDs share the 
same label value.
 In the collection pipeline, drop unnecessary high-cardinality metrics before they reach storage, for example with 
Prometheus metric_relabel_configs.

2. The combined p99 is the latency at around the 990th position after sorting all 1,000 requests together. A’s p99 of 
20 ms and B’s p99 of 600 ms give us where that cutoff falls within each instance, but they don’t give us how the two 
sets of latencies overlap. Even a request-weighted average of the two p99s can’t recover the combined p99.
    Client-side summaries estimate percentiles locally, often with a configurable error in rank. They keep the number of 
exported values small but require CPU and memory on each instance. The exported percentiles can’t be merged into a global p99.
    Fixed-bucket histograms can be aggregated by adding bucket counts across instances that use the same boundaries. 
Percentile accuracy depends on bucket width. More buckets give finer resolution but increase the number of time series 
and storage cost.
    Sketches combine compact representations of each instance’s latency distribution. Accuracy depends on the algorithm 
and its settings, with higher precision generally requiring more memory, bandwidth, and processing.

Put a bucket boundary at the latency objective. If the goal is “99% of requests finish within 200 ms,” a bucket at 
200 ms gives you the exact fraction that met it. Narrower buckets nearby also improve the p99 estimate when it falls 
close to that threshold.

3. The memory needed to buffer the spans: 128MB
2000*20*8*400=128,000,000 bytes

All spans with the same trace ID need to reach the same sampler, so it can make one decision based on the whole trace. 
If the spans are split across nodes, one sampler might miss an error span and drop a trace it would otherwise keep.

When the tier grows from 4 to 5 nodes, hash(trace_id) % N moves about 80% of traces because only 1 in 5 hashes keeps 
the same node assignment. Consistent hashing moves about 20% on a well-balanced ring because only the traces assigned 
to the new node need to move.

4. 00 is the version, 1 byte (2 hex characters).
   4bf92f3577b34da6a3ce929d0e0e4736 is the trace ID, 16 bytes (32 hex characters). It identifies the entire trace.
   00f067aa0ba902b7 is the parent ID, 8 bytes (16 hex characters). It identifies the upstream span.
   00 is the trace flags field, 1 byte (2 hex characters). Its sampled bit is clear, so the upstream decision is unsampled.

With parent-based sampling, the service honors that decision and forwards the sampled bit unchanged. Each downstream 
service follows the same rule, so the decision stays consistent across the trace.

The outgoing header keeps the same trace ID and puts the ID of the local span making the outgoing call in the parent-id field.

5. Error budget in minute: 21.6 minutes
A 99.95% availability target leaves a 0.05% error budget. Thus, over 30 days, that's 30*24*60*0.05%=21.6 minutes
   14.4× burn rate: The alert threshold is 14.4 × 0.05% = 0.72% errors. One hour at that rate consumes 
14.4 × 1 / 720 = 2% of the budget.
   6× burn rate: The alert threshold is 6 × 0.05% = 0.30% errors. Six hours at that rate consumes 
6 × 6 / 720 = 5% of the budget. At a sustained 6× burn, a full budget runs out in 30 / 6 = 5 days.

Require both windows to cross the threshold. The long window shows that the incident has burned a meaningful amount of 
budget, and the short window confirms it’s still happening so the alert clears quickly after recovery.

If the exercise expects one page and one ticket, page at 14.4× and create a ticket at 6×. A common SRE policy pages on 
both of these thresholds and reserves tickets for slower burns.

6. Keep telemetry off the application’s request path. The app hands data to a bounded, non-blocking queue, and a 
background worker exports it in batches with timeouts and backoff. If the backend stays down and the queue fills, the 
app drops telemetry and keeps serving requests.
    At the application, sample traces early or drop telemetry when the queue fills. Sampling reduces processing and 
network costs but can miss rare events. Dropping is cheap and immediate, but you lose data during the incident.
    At the collector, use bounded memory or disk buffers to ride out short outages. Buffers preserve data temporarily 
but cost memory or disk and can fill up. Rate-limit noisy sources to protect shared capacity, at the cost of losing some
data from those sources.
    At the backend, enforce ingestion limits and reject excess traffic. The collector can retry within its buffer and 
retry limits, then drop what it can no longer hold.
    At-least-once delivery retries unacknowledged data, so the backend may receive duplicates. At-most-once delivery 
avoids duplicates, but data can be lost if a send fails.

Run alerting in a separate failure domain so the outage it needs to report does not also disable notifications. A 
watchdog which stands for dead-man’s switch, sends a regular heartbeat through the alerting path. An independent 
receiver raises an alert when the heartbeat stops arriving, detecting a silent failure somewhere along that path.
