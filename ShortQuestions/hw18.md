## 1. Imperative vs. Declarative Design and Level-Triggered Controllers

### Imperative vs. Declarative Design

An imperative command specifies what actions the system should perform and how to perform them.

For example:

"Start 3 copies of checkout on these hosts."

The user explicitly tells the system what operation to execute. If one instance crashes afterward, the original command does not automatically restore it unless additional recovery logic exists.

A declarative object specifies the desired state rather than the exact operations required to achieve it.

For example:

"There should be 3 copies of checkout."

Kubernetes continuously compares the desired state with the actual state and performs the necessary operations to eliminate the difference.

If one instance crashes, Kubernetes attempts to create another instance to restore the desired number of replicas.

Example Kubernetes Deployment:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: checkout
spec:
  replicas: 3
  selector:
    matchLabels:
      app: checkout
  template:
    metadata:
      labels:
        app: checkout
    spec:
      containers:
        - name: checkout
          image: checkout:1.0
```

The user specifies that three replicas should exist without specifying which machines should run them.

### Spec and Status

Most Kubernetes workload objects contain two important sections: spec and status.

- spec: Describes the desired state of the object, usually configured by the user.
- status: Describes the observed state of the object, usually updated by Kubernetes controllers.

For example:

```yaml
spec:
  replicas: 3

status:
  replicas: 2
  readyReplicas: 2
```

The desired number of replicas is 3, but only 2 replicas currently exist.

The controller detects this difference and attempts to create another replica.

This process is called reconciliation.

### Level-Triggered vs. Edge-Triggered Controllers

An edge-triggered controller responds to specific events or state transitions.

A level-triggered controller examines the current state and compares it with the desired state, regardless of which events occurred previously.

Kubernetes controllers use level-triggered reconciliation because events may be lost, duplicated, or delivered out of order.

#### Situation A: An Event Is Lost

Edge-triggered design:

If an event indicating that a Pod was deleted is lost, the controller may never create a replacement Pod because it depends on receiving that specific event.

Level-triggered design:

During a subsequent reconciliation, the controller observes that only 2 replicas exist while 3 replicas are desired. It creates another Pod even though the original event was lost.

#### Situation B: The Controller Restarts

Edge-triggered design:

The controller may lose its previous event-processing state. Events that occurred while the controller was unavailable may not be processed unless an event replay mechanism exists.

Level-triggered design:

After restarting, the controller lists the current objects from the API server and compares their actual states with their desired states.

It can reconstruct its understanding of the cluster without replaying every historical event.

#### Situation C: The Same Event Is Delivered Twice

Edge-triggered design:

The controller may execute the same operation twice, potentially creating duplicate resources unless explicit deduplication or idempotency mechanisms are implemented.

Level-triggered design:

The controller checks the current state during each reconciliation.

If the desired state has already been achieved, no additional operation is necessary.

For example:

- Desired replicas: 3
- Actual replicas: 3
- Result: No action required.

### Comparison

| Situation | Edge-Triggered | Level-Triggered |
|---|---|---|
| Event lost | May miss the required operation | Corrects the state during subsequent reconciliation |
| Controller restarts | May require event replay | Reconstructs state from the API server |
| Duplicate event | May repeat an operation | Rechecks state before acting |
| Main focus | State transitions | Desired state versus actual state |
| Recovery | Depends on event history | Based on current cluster state |

Level-triggered controllers are more resilient because they continuously work toward the desired state instead of depending on reliable delivery of every individual event.

Controllers should also implement idempotent reconciliation logic so that repeated execution does not create unintended side effects.

## 2. API Server, Optimistic Concurrency, and Watch Compaction

### Communication Through the API Server

Kubernetes control-plane components primarily coordinate by reading and writing Kubernetes objects through the API server instead of directly invoking one another.

The API server provides a centralized interface for accessing and modifying cluster state.

For example:

```text
kubectl -----------+
                   |
Deployment         |
Controller --------+
                   |
Scheduler ---------+---- API Server ---- etcd
                   |
ReplicaSet         |
Controller --------+
                   |
Kubelet -----------+
```

etcd stores the persistent cluster state.

For example, when a Deployment is created:

1. The client submits the Deployment to the API server.
2. The Deployment controller observes the Deployment and creates a ReplicaSet through the API server.
3. The ReplicaSet controller observes the ReplicaSet and creates Pods.
4. The scheduler observes unscheduled Pods and assigns them to nodes.
5. The kubelet observes Pods assigned to its node and starts their containers.

These components coordinate through shared objects rather than directly instructing one another.

Strictly speaking, Kubernetes components can communicate directly for certain operations, such as retrieving container logs or executing commands. However, shared cluster-state coordination primarily occurs through the API server.

### Benefits

1. Loose coupling

   Components do not need to know the internal implementation or network address of other controllers.

   Each component independently observes and modifies Kubernetes objects.

2. Fault tolerance

   If a controller becomes unavailable, other components can continue operating.

   When the failed controller restarts, it can reconstruct its state from the API server.

3. Consistent cluster state

   The API server provides a centralized interface to the authoritative cluster state stored in etcd.

   Components coordinate using the same object model.

4. Security and access control

   Authentication, authorization, admission control, and auditing can be enforced centrally through the API server.

5. Extensibility

   New controllers and operators can be added without modifying existing Kubernetes components.

   Custom Resource Definitions (CRDs) allow developers to introduce new resource types.

### Main Cost

The main cost is additional communication overhead and eventual consistency.

Instead of directly invoking another component, a controller writes an object to the API server and waits for another component to observe and process the change.

This introduces:

- Additional network requests.
- API server processing overhead.
- Storage operations.
- Reconciliation delays.
- Potential API server bottlenecks.

The API server and etcd therefore require high availability and sufficient capacity.

### resourceVersion and Optimistic Concurrency

Every persisted Kubernetes object has a metadata.resourceVersion field.

It identifies a version of the object and allows Kubernetes to detect conflicting updates.

Consider the following object:

```yaml
metadata:
  name: checkout
  resourceVersion: "100"
spec:
  replicas: 3
```

Suppose two controllers read the same object at resourceVersion 100.

Controller A wants to change the number of replicas to 5.

Controller B wants to change the number of replicas to 4.

The following sequence occurs:

```text
Controller A reads version 100
Controller B reads version 100

Controller A submits an update using version 100

API Server:
- Current version is 100
- Update succeeds
- Object receives a new resourceVersion, for example 101

Controller B submits an update using version 100

API Server:
- Current version is now 101
- Submitted version is stale
- Update is rejected with HTTP 409 Conflict
```

The first valid update committed by the API server succeeds.

The second update receives:

```text
HTTP 409 Conflict
```

Controller B must then:

1. Retrieve the latest version of the object.
2. Reevaluate the desired operation using the latest state.
3. Apply the necessary changes.
4. Submit the update using the latest resourceVersion.
5. Retry if another conflict occurs.

This prevents lost updates caused by clients overwriting changes made by other clients.

### Why No Distributed Locks Are Required

This mechanism is called optimistic concurrency control.

Controllers do not need to acquire distributed locks before reading or modifying an object.

Instead, the API server and storage layer atomically verify that the submitted version matches the current version before accepting a conditional update.

If a conflict occurs, the outdated update is rejected.

This allows multiple controllers to operate concurrently while preventing stale updates from silently overwriting newer changes.

The storage layer still requires atomic operations internally, but clients do not need to coordinate through explicit distributed locks.

### Watch Revision Compaction

Kubernetes clients can use Watch operations to receive changes to objects.

For example:

```text
Watch objects starting from resourceVersion 100
```

However, etcd and the Kubernetes watch cache do not retain historical revisions indefinitely.

Old revisions may be compacted or become unavailable.

If a client attempts to resume a watch from an expired revision, the API server may return:

```text
HTTP 410 Gone
```

The client must:

1. Perform a new List operation.
2. Replace or rebuild its local cache using the returned objects.
3. Obtain the resourceVersion returned by the List response.
4. Start a new Watch from that resourceVersion.

Example:

```text
Watch from resourceVersion 100
              |
              v
       HTTP 410 Gone
              |
              v
       Perform new List
              |
              v
       Rebuild local cache
              |
              v
       Obtain resourceVersion 500
              |
              v
       Watch from version 500
```

This allows the client to recover even when historical events are no longer available.

## 3. Pods, ReplicaSets, Deployments, and Services

### Pod

A Pod is the smallest deployable unit in Kubernetes.

A Pod contains one or more containers that share:

- Network namespace.
- IP address.
- Port space.
- Volumes when configured.
- Lifecycle and scheduling location.

Containers within the same Pod can communicate using localhost.

Example:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: checkout-pod
  labels:
    app: checkout
spec:
  containers:
    - name: checkout
      image: checkout:1.0
      ports:
        - containerPort: 8080
```

A standalone Pod is not automatically recreated by a workload controller if the Pod itself is deleted or its node permanently fails.

For production applications, Pods are usually managed by higher-level controllers.

### ReplicaSet

A ReplicaSet ensures that a specified number of matching Pod replicas exist.

For example, if the desired replica count is 3 and one Pod is deleted, the ReplicaSet controller creates a replacement Pod.

```yaml
apiVersion: apps/v1
kind: ReplicaSet
metadata:
  name: checkout-rs
spec:
  replicas: 3
  selector:
    matchLabels:
      app: checkout
  template:
    metadata:
      labels:
        app: checkout
    spec:
      containers:
        - name: checkout
          image: checkout:1.0
```

The main responsibilities of a ReplicaSet are:

- Maintaining the desired number of Pods.
- Creating replacement Pods when necessary.
- Removing excess Pods.
- Managing Pods using label selectors.

### Deployment

A Deployment is a higher-level workload object that manages ReplicaSets.

It provides declarative application management, including:

- Application deployment.
- Scaling.
- Rolling updates.
- Rollbacks.
- Version management.

Example:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: checkout
spec:
  replicas: 3
  selector:
    matchLabels:
      app: checkout
  template:
    metadata:
      labels:
        app: checkout
    spec:
      containers:
        - name: checkout
          image: checkout:1.0
          ports:
            - containerPort: 8080
```

When the application image changes from checkout:1.0 to checkout:2.0, the Deployment controller creates a new ReplicaSet and gradually replaces the old Pods according to its rollout strategy.

For example:

```text
Before update:

Deployment
    |
    +-- ReplicaSet v1
          |
          +-- Pod v1
          +-- Pod v1
          +-- Pod v1

During rolling update:

Deployment
    |
    +-- ReplicaSet v1
    |     |
    |     +-- Pod v1
    |
    +-- ReplicaSet v2
          |
          +-- Pod v2
          +-- Pod v2

After update:

Deployment
    |
    +-- ReplicaSet v2
          |
          +-- Pod v2
          +-- Pod v2
          +-- Pod v2
```

### Service

A Service provides a stable network endpoint for accessing a group of Pods.

Pods are temporary resources. Their IP addresses may change when they are recreated.

A Service provides a stable virtual IP address and DNS name, depending on its configuration.

Example:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: checkout-service
spec:
  selector:
    app: checkout
  ports:
    - port: 80
      targetPort: 8080
  type: ClusterIP
```

The Service selects Pods with the label app: checkout.

Clients can access the application through:

```text
http://checkout-service
```

The Service data plane routes requests to eligible backend Pods using endpoint information maintained by Kubernetes.

Common Service types include:

- ClusterIP: Exposes the Service inside the cluster.
- NodePort: Exposes the Service through a port on cluster nodes.
- LoadBalancer: Requests an external load balancer from a supported infrastructure provider.
- ExternalName: Maps the Service to an external DNS name.

### How These Objects Work Together

```text
                   Deployment
                        |
                   ReplicaSet
                        |
            +-----------+-----------+
            |           |           |
          Pod 1       Pod 2       Pod 3
            ^           ^           ^
            |           |           |
            +-----------+-----------+
                        |
                     Service
                        |
                      Client
```

The Deployment manages the application version and rollout strategy.

The ReplicaSet maintains the desired number of Pods.

The Pods run the application containers.

The Service provides stable network access to the Pods.

If a Pod is deleted, the ReplicaSet creates a replacement Pod. Kubernetes updates the Service's endpoint information so traffic can be routed to the available backend Pods.

If a new application version is deployed, the Deployment manages the transition between ReplicaSets.

### Comparison

| Object | Main Responsibility |
|---|---|
| Pod | Runs one or more application containers |
| ReplicaSet | Maintains the desired number of Pods |
| Deployment | Manages ReplicaSets, updates, scaling, and rollbacks |
| Service | Provides stable network access to application Pods |

## 4. Kubernetes Control Plane vs. Data Plane

### Control Plane

The control plane manages the overall state of the Kubernetes cluster.

It is responsible for making scheduling decisions, processing API requests, storing cluster state, and reconciling desired state with actual state.

The main control-plane components are:

#### kube-apiserver

The API server exposes the Kubernetes API.

It processes client requests, performs authentication and authorization, applies admission control, and provides access to cluster objects.

#### etcd

etcd is a distributed key-value database that stores persistent Kubernetes cluster state.

Examples of stored objects include:

- Deployments.
- Pods.
- Services.
- ConfigMaps.
- Secrets.

#### kube-scheduler

The scheduler identifies Pods that have not been assigned to a node and selects suitable nodes for them.

Scheduling decisions consider:

- CPU and memory requirements.
- Node capacity.
- Node affinity.
- Pod affinity and anti-affinity.
- Taints and tolerations.
- Other scheduling constraints.

#### kube-controller-manager

The controller manager runs Kubernetes controllers that continuously reconcile actual state with desired state.

Examples include:

- Deployment controller.
- ReplicaSet controller.
- Node controller.
- Job controller.

#### cloud-controller-manager

The cloud controller manager integrates Kubernetes with supported cloud infrastructure.

It may manage cloud-specific resources such as load balancers, nodes, and networking routes.

### Data Plane

The data plane consists of the worker-node components and application workloads that execute the actual application traffic.

The main components include:

#### Kubelet

The kubelet is an agent running on each worker node.

It ensures that the containers belonging to Pods assigned to that node are running according to their specifications.

#### Container Runtime

The container runtime is responsible for running containers.

Examples include:

- containerd.
- CRI-O.

#### kube-proxy or Equivalent Networking Implementation

kube-proxy maintains networking rules that implement Kubernetes Service connectivity.

Some Kubernetes networking implementations replace kube-proxy with an alternative data plane, such as an eBPF-based implementation.

#### CNI Plugin

The Container Network Interface plugin configures Pod networking and connectivity.

Examples include:

- Calico.
- Cilium.
- Flannel.

#### Application Pods

Application Pods contain the actual workloads that process user requests.

### Architecture

```text
                 CONTROL PLANE

+------------------------------------------+
|                                          |
|  API Server <----------> etcd            |
|      ^                                   |
|      |                                   |
|  Scheduler                               |
|  Controller Manager                      |
|                                          |
+---------------------+--------------------+
                      |
                      |
                 DATA PLANE

+---------------------+--------------------+
|                                          |
| Worker Node 1       Worker Node 2        |
|                                          |
| Kubelet             Kubelet              |
| Container Runtime   Container Runtime    |
| Networking          Networking           |
|                                          |
| Pod A               Pod C                |
| Pod B               Pod D                |
|                                          |
+------------------------------------------+
```

### What Happens If the Control Plane Becomes Unavailable?

Existing running workloads generally continue operating because their containers are already running on worker nodes.

Previously configured networking rules can also continue routing traffic to existing Pods.

However, operations requiring control-plane coordination become unavailable or degraded.

For example:

- New Pods cannot be scheduled normally.
- Deployments cannot be updated.
- Scaling operations cannot be performed normally.
- Deleted Pods cannot be replaced by controllers.
- Failed nodes cannot be handled through normal rescheduling.
- Service endpoint updates may stop.
- Cluster configuration changes cannot be processed normally.

The kubelet can generally continue managing already-known Pods and may restart failed containers according to their restart policies.

However, it cannot independently replace a failed node or create new controller-managed Pods.

If the control-plane outage continues, application availability may gradually degrade as Pods or nodes fail.

### Comparison

| Feature | Control Plane | Data Plane |
|---|---|---|
| Responsibility | Manages cluster state | Runs application workloads |
| Scheduling | Makes scheduling decisions | Executes assigned workloads |
| Components | API server, etcd, scheduler, controllers | Kubelet, runtime, networking, Pods |
| Application traffic | Generally not directly involved | Processes application traffic |
| Control-plane outage | Management operations stop or degrade | Existing workloads generally continue running |

## 5. Kubernetes API Request Lifecycle

When a client creates a Kubernetes object, the request passes through several stages before the object is persisted.

For example:

```bash
kubectl create deployment checkout --image=checkout:1.0
```

The kubectl client sends an HTTP request to the Kubernetes API server.

### Request Lifecycle

```text
Client / kubectl
       |
       v
HTTPS Request
       |
       v
Authentication
       |
       v
Authorization
       |
       v
Request Decoding and Defaulting
       |
       v
Mutating Admission Control
       |
       v
Object Validation
       |
       v
Validating Admission Control
       |
       v
Persist Object in etcd
       |
       v
Return HTTP Response
       |
       v
Controllers Observe Object
```

The exact internal processing details depend on the resource type and API implementation, but this represents the main stages.

### Stage 1: Authentication

Authentication determines the identity of the client making the request.

It answers the question:

"Who are you?"

Kubernetes supports authentication mechanisms such as:

- Client certificates.
- Bearer tokens.
- Service account tokens.
- OpenID Connect (OIDC).
- Authentication webhooks.

For example, a request may contain:

```http
Authorization: Bearer <token>
```

The API server verifies the token and identifies the associated user or service account.

If authentication fails, the request may be rejected with:

```text
HTTP 401 Unauthorized
```

### Stage 2: Authorization

Authorization determines whether the authenticated identity has permission to perform the requested operation.

It answers the question:

"Are you allowed to perform this operation?"

Kubernetes commonly uses Role-Based Access Control (RBAC).

For example, the following Role allows users or service accounts bound to it to read Pods in a namespace:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader
  namespace: default
rules:
  - apiGroups: [""]
    resources: ["pods"]
    verbs: ["get", "list", "watch"]
```

This Role does not grant permission to create or delete Pods.

If an identity has no other applicable permissions and attempts to create a Pod, the API server rejects the request with:

```text
HTTP 403 Forbidden
```

### Stage 3: Request Decoding and Defaulting

The API server decodes the submitted JSON or YAML representation into the appropriate Kubernetes object.

It may also apply default values to fields that were not explicitly specified.

For example, a Deployment that does not specify replicas normally defaults to one replica.

### Stage 4: Mutating Admission Control

Mutating admission controllers can modify an incoming object before it is persisted.

Examples include:

- Adding default resource requests and limits.
- Injecting sidecar containers.
- Adding required labels.
- Applying security-related configuration.

For example, a service mesh may automatically inject a proxy sidecar into a Pod.

The submitted Pod initially contains one application container.

After mutation, the Pod may contain both the application container and a proxy sidecar.

### Stage 5: Object Validation

The API server validates the object against the applicable resource schema and validation rules.

For example:

- Required fields must exist.
- Field values must have valid types.
- Replica counts cannot be negative.
- Deployment selectors must match the Pod template labels.

An invalid object may be rejected with:

```text
HTTP 422 Unprocessable Entity
```

Malformed requests may instead receive HTTP 400 Bad Request.

### Stage 6: Validating Admission Control

Validating admission controllers inspect the object and decide whether it should be accepted or rejected.

Unlike mutating admission controllers, validating admission controllers do not modify the object.

Examples include:

- Rejecting privileged containers.
- Rejecting images from untrusted registries.
- Enforcing required resource limits.
- Enforcing namespace security policies.

For example, a security policy may reject a Pod containing:

```yaml
securityContext:
  privileged: true
```

Even if the user has permission to create Pods, admission control can reject the object because it violates cluster policy.

### Stage 7: Persistence

If the request passes authentication, authorization, admission control, and validation, the API server persists the object in etcd.

The object receives metadata such as:

- UID.
- resourceVersion.
- creationTimestamp.

The API server then returns a successful response, typically:

```text
HTTP 201 Created
```

### Stage 8: Controller Reconciliation

After the object is persisted, relevant controllers observe the new object through List and Watch mechanisms.

For example:

1. The Deployment controller observes the new Deployment.
2. It creates a ReplicaSet.
3. The ReplicaSet controller creates Pods.
4. The scheduler assigns Pods to worker nodes.
5. The kubelet starts the containers.

Creating a Deployment object successfully does not mean that its application containers are already running.

The remaining operations occur asynchronously through reconciliation.

### Authentication vs. Authorization vs. Admission Control

| Mechanism | Main Question | Purpose | Example |
|---|---|---|---|
| Authentication | Who are you? | Verifies identity | Validate a service account token |
| Authorization | Are you allowed to do this? | Checks permissions | RBAC permits creating Pods |
| Admission Control | Is this object acceptable? | Enforces object and cluster policies | Reject privileged containers |

Authentication verifies the identity of the requester.

Authorization verifies whether the requester has permission to perform the operation.

Admission control verifies whether the requested object satisfies cluster policies and may modify or reject it.

## 6. Purpose of resourceVersion

The resourceVersion field is an opaque version identifier maintained by Kubernetes for persisted objects.

Example:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: checkout
  resourceVersion: "12345"
spec:
  replicas: 3
```

The resourceVersion field is used for:

- Optimistic concurrency control.
- Detecting stale object updates.
- Tracking changes to objects.
- Starting and resuming Watch operations.
- Maintaining consistent local caches.

Clients should treat resourceVersion as an opaque string rather than assuming that it is a numeric counter that can be incremented or compared manually.

### Preventing Conflicting Updates

Consider a Deployment with the following state:

```yaml
metadata:
  resourceVersion: "100"
spec:
  replicas: 3
```

Two clients retrieve the object simultaneously.

Client A wants to change replicas from 3 to 5.

Client B wants to change replicas from 3 to 4.

Both clients initially have resourceVersion 100.

Client A submits:

```yaml
metadata:
  resourceVersion: "100"
spec:
  replicas: 5
```

The API server checks the submitted resourceVersion against the current version.

Because they match, the update succeeds.

The updated object becomes:

```yaml
metadata:
  resourceVersion: "101"
spec:
  replicas: 5
```

Client B then submits:

```yaml
metadata:
  resourceVersion: "100"
spec:
  replicas: 4
```

The API server detects that Client B is using an outdated resourceVersion.

The update is rejected with:

```text
HTTP 409 Conflict
```

Client B must retrieve the latest object, reevaluate its intended modification, and retry the update using the current resourceVersion.

### Without Optimistic Concurrency

Without version checking, the following situation could occur:

```text
Initial replicas = 3

Client A reads replicas = 3
Client B reads replicas = 3

Client A writes replicas = 5
Client B writes replicas = 4

Final replicas = 4
```

Client B silently overwrites Client A's update.

This is called a lost update.

### With Optimistic Concurrency

```text
Initial state:
replicas = 3, resourceVersion = 100

Client A reads version 100
Client B reads version 100

Client A updates using version 100
Result: Success

Current state:
replicas = 5, resourceVersion = 101

Client B updates using version 100
Result: HTTP 409 Conflict

Client B reads the latest object
Client B reevaluates its intended update
Client B retries if necessary
```

This prevents stale conditional updates from silently overwriting newer changes.

Different Kubernetes update and patch mechanisms have different conflict-handling semantics. A resourceVersion precondition can be used when an operation requires protection against stale updates.

### resourceVersion vs. generation

These fields serve different purposes.

| Field | Purpose |
|---|---|
| resourceVersion | Identifies the persisted version of an object and supports concurrency control and watches |
| generation | Tracks changes to the desired state for resource types that support it |
| observedGeneration | Indicates which generation a controller has processed, when provided in status |

For example:

```yaml
metadata:
  generation: 3
  resourceVersion: "105"

status:
  observedGeneration: 2
```

This indicates that the desired state has reached generation 3, but the controller has only processed generation 2.

A status update can change resourceVersion without necessarily changing generation.

## 7. List and Watch Operations

Kubernetes components need to continuously track changes in cluster state.

Repeatedly requesting every object from the API server would consume significant CPU, memory, and network resources.

Kubernetes solves this problem using the List and Watch mechanism.

### List Operation

A List operation retrieves a collection of objects and a resourceVersion representing the returned collection snapshot.

For example:

```bash
kubectl get pods
```

The corresponding API request may be:

```http
GET /api/v1/namespaces/default/pods
```

Example response:

```json
{
  "kind": "PodList",
  "metadata": {
    "resourceVersion": "100"
  },
  "items": [
    {
      "metadata": {
        "name": "pod-a"
      }
    },
    {
      "metadata": {
        "name": "pod-b"
      }
    }
  ]
}
```

The client stores the returned objects in a local cache.

Initial cache:

```text
pod-a
pod-b
```

The client also records the collection resourceVersion, which is 100 in this example.

### Watch Operation

A Watch operation establishes a streaming connection with the API server to receive object changes.

For example:

```http
GET /api/v1/namespaces/default/pods?watch=true&resourceVersion=100
```

The client receives events representing changes after the listed snapshot.

Common Watch event types include:

- ADDED: A new object has been added to the watched collection.
- MODIFIED: An existing object has changed.
- DELETED: An object has been removed from the watched collection.
- BOOKMARK: Indicates progress to a particular resourceVersion.
- ERROR: Indicates a problem with the Watch operation.

Example event:

```json
{
  "type": "ADDED",
  "object": {
    "metadata": {
      "name": "pod-c",
      "resourceVersion": "101"
    }
  }
}
```

After receiving this event, the client updates its local cache:

```text
pod-a
pod-b
pod-c
```

Suppose another event arrives:

```json
{
  "type": "DELETED",
  "object": {
    "metadata": {
      "name": "pod-a",
      "resourceVersion": "102"
    }
  }
}
```

The updated cache becomes:

```text
pod-b
pod-c
```

### How List and Watch Work Together

```text
Kubernetes Controller
          |
          | 1. List objects
          v
      API Server
          |
          | 2. Return current objects
          |    and resourceVersion
          v
      Local Cache
          |
          | 3. Start Watch using
          |    returned resourceVersion
          v
      API Server
          |
          | 4. Stream object changes
          v
      Local Cache
          |
          | 5. Trigger reconciliation
          v
      Controller Logic
```

The complete process is:

1. The client performs a List operation.
2. The API server returns the current objects and a collection resourceVersion.
3. The client initializes its local cache.
4. The client starts a Watch from the returned resourceVersion.
5. The API server streams subsequent object changes.
6. The client updates its local cache.
7. Relevant changes trigger controller reconciliation.

Using the resourceVersion returned by List helps avoid missing changes that occur between the List response and the establishment of the Watch connection.

### Handling Watch Disconnections

A Watch connection may disconnect because of:

- Network failures.
- API server restarts.
- Connection timeouts.
- Temporary infrastructure failures.

The client records the latest resourceVersion it has successfully processed.

If the connection is interrupted, it attempts to resume watching from that version.

If the version is no longer available, the API server may return:

```text
HTTP 410 Gone
```

The client must perform a new List operation, rebuild its local cache, and start a new Watch using the new collection resourceVersion.

### Why List and Watch Are More Efficient Than Polling

Suppose a cluster contains 10,000 Pods.

A polling client retrieves all 10,000 Pods every 5 seconds.

The number of polling requests per minute is:

60 / 5 = 12 requests

The total number of object representations transferred per minute is:

10,000 × 12 = 120,000 objects

If only 100 Pod change events occur per minute, the Watch mechanism needs to transfer approximately 100 change events per minute after the initial List.

The reduction in steady-state object transfer volume is approximately:

120,000 / 100 = 1,200 times

This simplified example excludes the initial List, reconnections, relisting, bookmarks, and protocol overhead.

### Comparison

| Feature | Repeated List / Polling | List and Watch |
|---|---|---|
| Data transferred | Entire object collection repeatedly | Initial collection followed by changes |
| Network usage | Higher | Lower |
| API server workload | Higher | Generally lower |
| Update latency | Depends on polling interval | Near real-time |
| Local cache | Rebuilt or refreshed repeatedly | Updated incrementally |
| Scalability | Lower | Higher |
| Recovery | Perform another List | Resume Watch or relist if necessary |

### Kubernetes Informers

Kubernetes controllers commonly use informers to implement the List and Watch pattern.

An informer provides:

- Initial object listing.
- Continuous watching.
- Local caching.
- Event notification.
- Watch reconnection and recovery.
- Efficient sharing of cached objects among controllers.

A typical controller architecture is:

```text
API Server
    |
List and Watch
    |
Reflector
    |
Informer / Local Cache
    |
Event Handler
    |
Work Queue
    |
Reconciliation Loop
    |
API Server
```

The informer receives changes and updates its local cache.

Event handlers enqueue object identifiers into a work queue.

The controller retrieves identifiers from the queue and reconciles the current state against the desired state.

This combines event-driven notifications with level-triggered reconciliation.

Events tell the controller when it should reconcile, but the current object state determines what action should be taken.
