## Question1:Compare the data models of logs, metrics, and traces. Explain why a telemetry pipeline is a high-throughput, write-heavy, low-frequency-read distributed system.
1. Data models of logs, metrics, and traces
   Logs: Discrete events
Logs record individual events occurring within an application. A single log record typically contains a timestamp, severity level, message, and optional contextual fields such as a service name, order ID, or error code.
Logs provide the highest level of event detail and are particularly useful for explaining exactly what happened during an operation.
For instance, when a payment fails, logs can reveal the specific exception, error message, or business rule responsible.
The main limitation is that logs are expensive to store and search at scale. Furthermore, individual log records do not automatically establish relationships among multiple services involved in a distributed request.

Metrics: Aggregated numerical time series
Metrics represent numerical measurements collected over time. A time series is identified by a metric name and a combination of labels, while each sample contains a timestamp and numerical value.
Common metric types include counters, gauges, and histograms. Metrics are particularly effective for monitoring system health, identifying performance trends, and triggering alerts.
Unlike logs, metrics aggregate information rather than recording every individual event. Consequently, they can efficiently answer questions such as whether the error rate has exceeded 1%, but they cannot explain why one particular payment failed.

Traces: Causal structures of distributed requests
A distributed trace represents the execution path of a request across multiple operations or services.
A trace contains multiple spans, where each span represents an individual operation. A span typically includes a trace ID, span ID, parent span ID, operation name, timestamps, duration, and optional attributes.
The parent-child relationships between spans create a causal structure showing how operations are connected.
However, distributed tracing requires context propagation across services and threads. Traces are also frequently sampled to control storage costs, meaning detailed traces may not be available for every request.

2. How storage volume grows

| Property  |                	Logs                                 |                Metrics                   | Traces |
| --- | --- | --- | --- |
| Basic data unit    | Event | Time-series sample | Span   |

metrics storage depends primarily on label cardinality, whereas logs and traces grow primarily with traffic.

3. Why a telemetry pipeline is a distributed system
   A telemetry pipeline is itself a distributed system because it must continuously collect, process, transport, and store data generated by many application instances running across multiple hosts and services.
   High-throughput and continuous writes: Every application instance can generate telemetry continuously, even when nobody is actively querying it. Thousands of applications may generate millions of events and samples, creating substantial ingestion traffic.
   Low-frequency and bursty reads: Compared with the continuous ingestion workload, interactive reads are usually less frequent. Engineers primarily query detailed logs and traces during incident investigations, while dashboards and alerting rules perform more regular metric queries. Overall, the system remains heavily write-dominated.

## Question2:Compare the two families of log storage: full-text inverted indexes and label indexes with compressed chunks in object storage.
1. Full-text inverted index
   A full-text inverted index is designed to support fast searches across log messages. In this architecture, the storage engine tokenizes searchable log text and creates an index mapping each term to the log documents containing it.

Write-time costs: In a full-text indexing system, substantial processing occurs during ingestion. Each incoming log must be tokenized, indexed, and written to storage. Index updates and background segment merges introduce additional CPU, memory, and disk I/O overhead, a phenomenon known as write amplification.
The index can occupy storage space comparable to or greater than the original log data. Consequently, maintaining a full-text index for billions of log records can become expensive.

Read-time costs: The major benefit is efficient arbitrary text searching. Because searchable terms are already indexed, the system can quickly locate logs containing specific error messages, exception names, or keywords.

High-cardinality problems: High cardinality can increase the number of distinct indexed terms and associated postings data. In addition, dynamically generated field names can create excessive field mappings, increasing index complexity, memory consumption, and storage overhead.

2. Label index with compressed chunks in object storage
   The second architecture, used by Grafana Loki, minimizes indexing overhead by indexing only a selected set of labels instead of every word in each log message.
   Logs sharing the same label combination are grouped into streams. The log contents are compressed into chunks and stored in object storage, such as Amazon S3.
The index maps label combinations to references identifying the relevant chunks.

Write-time costs: This architecture primarily performs stream grouping, appending, compression, and object-storage writes. Because it does not build a complete full-text index, ingestion is generally less CPU-intensive, and the resulting index is substantially smaller.
Compressed chunks can also be stored in relatively inexpensive object storage, reducing the cost of retaining very large log volumes.

Read-time costs: Queries first use labels and time ranges to identify the relevant chunks. The query engine then reads, decompresses, and scans the selected log contents.

High-cardinality problems: Label cardinality is a major concern in this architecture.
For example, adding a unique transactionId as an indexed label could create a separate stream for every transaction.
This would produce excessive stream metadata, a larger label index, and numerous small chunks that compress inefficiently.
Therefore, Loki-style systems should use stable labels with relatively few distinct values, such as service name, environment, or application level, rather than unbounded identifiers such as user IDs or transaction IDs.

3. Recommended architecture for a high-volume platform
   For a platform generating extremely high log volumes where most searches follow the pattern of one known service within the last 15 minutes, I would choose the label-index architecture with compressed chunks in object storage.
There are several reasons for this decision.
First, the query pattern is predictable. Engineers usually already know which service they are investigating and the approximate time of the incident. Label-based filtering can efficiently narrow the query to a relatively small set of chunks.
Second, the write volume is significantly higher than the read volume. Building and maintaining a full-text index for every log is expensive when the majority of records may never be searched. Shifting some processing costs from ingestion to query time can therefore reduce overall system costs.
Third, compressed object storage provides better cost efficiency at large scale. Since most searches focus on recent logs, the platform can also apply tiered retention policies, keeping recent data readily accessible while moving older data to less expensive storage.
I would additionally use node agents to collect application logs, a durable message broker to absorb ingestion bursts, and separate storage and query components so that expensive searches do not interrupt ingestion.

## Question3:Compare pull-based and push-based metrics collection, including service discovery, failure detection, batch jobs, network topology, collection rate, and collector overload.
1. Pull-based metrics collection
   In a pull-based architecture, the monitoring server initiates the collection process. Prometheus is a common example.
Applications expose a metrics endpoint, and Prometheus periodically sends HTTP requests to retrieve the current measurements.
   Prometheus controls when scraping occurs, which targets are scraped, and how frequently samples are collected.
   With this configuration, Prometheus requests the application's metrics every 15 seconds.
The centralized control, automatic target discovery, and scrape-based failure detection as major advantages of this model.
2. Push-based metrics collection
      In a push-based model, the application or its telemetry exporter initiates communication with a collection endpoint.
For example, a Spring Boot application may use an OpenTelemetry SDK to send metric measurements to an OpenTelemetry Collector.
   The application generally controls its export schedule, while the collector handles receiving, processing, and forwarding telemetry to the storage backend.
This approach is particularly useful when applications are short-lived or operate in environments where the monitoring system cannot directly reach their metrics endpoints.
The tutorial also describes the OpenTelemetry Collector's receiver–processor–exporter architecture, which separates data ingestion, transformation, and backend transmission.

3. Comparison across the six required dimensions
   A. Service discovery
   In pull-based collection, the monitoring server must maintain a list of targets to scrape.
For example, a Kubernetes application may scale from five pods to twenty pods. Prometheus can use Kubernetes service discovery to identify the current application instances.
This provides automatic adaptation to changes in the deployment topology without manually registering every instance.

In push-based collection, applications generally do not need to be discovered as scrape targets because they already know the collector's address.
The application sends telemetry to the configured collector endpoint. However, the exporter still requires an appropriate destination configuration and network connectivity.

Therefore, pull-based collection places the service-discovery responsibility on the monitoring system, whereas push-based collection primarily requires senders to know where to export data.

B. Detecting when a target is down
Pull-based collection provides a built-in mechanism for detecting unsuccessful scraping.
Prometheus generates a metric named up, which indicates the result of a scrape attempt.
If an application crashes or its metrics endpoint becomes unreachable, Prometheus can detect the failed scrape without requiring the application to report its own failure.

In push-based collection, the absence of data is more ambiguous.
If a service stops exporting metrics, the collector cannot immediately determine whether the application crashed, lost connectivity, or is simply not producing new measurements.
Additional mechanisms, such as heartbeats or missing-data alerts, may therefore be required.

A failed scrape is a direct indication of a monitoring problem with that target, although it does not always prove that the underlying application itself has crashed.

C. Short-lived batch jobs
Pull-based collection is less suitable for very short-lived applications.
For example, consider a Spring Batch job that runs for only ten seconds while Prometheus collects metrics every 15 seconds.
The job could start and finish between two scrape attempts, causing Prometheus to miss its measurements entirely.
Push-based collection avoids this limitation because the batch job can report its final metrics before terminating.

D. Firewalls and network topology
Pull-based collection requires the monitoring server to establish connections to every target it scrapes.
This can become difficult when applications operate behind firewalls, network address translation (NAT), or restricted private networks.
For example, a central Prometheus server might not be able to reach application instances inside a private corporate network.

Push-based collection can simplify this scenario because the application only needs an allowed outbound connection to the collector.

E. Who controls the collection rate?
In a pull-based architecture, the monitoring server controls the scrape schedule.

In a push-based architecture, the producer or exporter generally determines how frequently telemetry is transmitted.
This provides flexibility but makes centralized rate control more challenging.
The collector may enforce limits, but it must still handle incoming requests initiated by producers.

Therefore, pull-based collection provides stronger centralized control over collection frequency and workload.

F. What happens when an application misbehaves?
A misbehaving application may expose an excessive number of metrics, generate high-cardinality labels, respond slowly, or continuously send telemetry at an unexpectedly high rate.

In a pull-based system, the collector controls when each request occurs. This makes it easier to bound collection work using scrape intervals, timeouts, and sample limits.

In a push-based system, a misconfigured application might export metrics much more frequently than expected.

Because the producer initiates requests, the collector could receive excessive traffic from multiple applications simultaneously.

This may cause queue saturation, high CPU utilization, memory pressure, or rejected ingestion requests.
