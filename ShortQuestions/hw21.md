1.a A client can use its full quota just before one window ends and again just after the next begins. Both windows stay within the limit, but the requests form a burst. This follows from the fixed-window rule itself, so changing code inside the class cannot eliminate it. Fixed windows are suitable for limits defined per calendar period, such as requests per day.
b.Two threads can read the same count, both accept a request, and both write back the same incremented count. One update is lost. A plain HashMap does not make these operations thread-safe. Version 1 is appropriate for single-threaded use or when access is synchronized externally.
c.ConcurrentHashMap.compute performs the computation and update atomically for one key. Operations on other keys in the same hash bin may also be blocked. Version 2 is thread-safe because concurrent requests for the same key cannot lose count updates.
d.Injecting a LongSupplier lets tests control time without waiting for the real clock. Production code passes a system clock, such as System::currentTimeMillis. Tests pass a controllable fake clock.
2.a. Version 3 removes request timestamps outside the last window, then checks how many remain. If the count is below the limit, it accepts the request and records its timestamp; otherwise, it rejects it. Because the window moves with the current time, requests just before a fixed boundary still count just after it.
b.The log stores a timestamp for every request still in the sliding window, so its memory per key grows with the request limit. A fixed window counter stores only a window identifier and a count per key. The log is appropriate when exact enforcement matters and its memory cost is acceptable.
c.Version 4 adds the current window’s count to a weighted part of the previous window’s count. If a fraction \(f\) of the current window has elapsed, its estimate is
\(\text{current count}+(1-f)\times\text{previous count}\).
This assumes requests in the previous window were spread roughly evenly over time.
d.The estimate is too loose when previous-window requests occurred near the end of that window: more of them are still in the sliding window than the formula estimates, so it may accept too many requests. It is too strict when they occurred near the beginning: fewer are still in the sliding window than estimated, so it may reject requests unnecessarily. Version 4 is appropriate when low memory use matters and small inaccuracies are acceptable.
3.a While a client is idle, tokens accumulate up to the bucket’s capacity. It can then spend those tokens on a burst, even if a fixed or sliding window limit would reject some requests. The bucket capacity sets the maximum burst; the refill rate sets the long-term average rate.
b.When a request arrives, the class calculates how much time has passed since the last refill and adds the corresponding number of tokens, up to capacity. No background timer is needed. A short burst can use tokens accumulated earlier as well as newly refilled tokens.
c.Unlike a token bucket, Version 6 does not save up permission for an idle client to send a burst. It spaces accepted requests according to the leak interval. Its actual accepted rate also depends on when requests arrive: idle time cannot be used to accept extra requests later. Each key needs only a timestamp representing its next allowed time; the passage of time accounts for leaking without a timer or a separate leak update.

2. Version 3 — Sliding window log. It enforces an exact limit of five attempts in any 60-second period.
3. Version 4 — Sliding window counter. It uses little memory per key, and the requirement allows a small estimation error.
4. Version 5 — Token bucket. Set the capacity to at least 20 tokens and the refill rate to 5 tokens per second, so a full bucket can handle the page-load burst.
5. Version 6 — Leaky bucket. Set the interval to 200 ms to space accepted calls apart.

4.a.Memory usage depends on the number of distinct keys ever seen, not just the number of currently active clients. Since entries are never removed, even a one-time request leaves state behind. IP addresses and session IDs are risky because many different values can appear over time, including values generated by an attacker.
b.An entry can be removed when treating the key as new would produce exactly the same future decisions. For a leaky bucket, this means its next-allowed-time state no longer imposes any wait. A sweep might read an expired entry, then a request updates that entry and is accepted, and then the sweep removes it based on its earlier read. The next request sees a new key and may be accepted too soon. Version 7 checks expiry and removes the entry atomically with respect to updates for that key, using compute or computeIfPresent.

d.Each instance has its own counter. A user who sends requests to multiple instances can receive a separate allowance from each one and exceed the intended service-wide limit. Version 8 is still appropriate when the service runs on one instance, or when the limit is intentionally defined per instance rather than across the whole service.
e.The shared store must provide an atomic increment for a counter. A separate read and write can lose updates when two instances read the same value. The class uses wall-clock milliseconds so instances can identify the same time window; each counter has a time to live so old windows expire from the store. Every request now requires a store operation, adding network latency and dependence on store availability. The system must decide in advance whether a store failure should fail open (allow requests) or fail closed (reject them). Version 9 also brings back the fixed-window boundary burst from Version 2.
