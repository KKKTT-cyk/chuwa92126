1. 
a) A fixed window can allow a burst because the counter resets at each boundary. A client can use its full limit just
before the reset and again right after it. Changing the counter code won’t remove this; the effect comes from how fixed 
windows work. Fixed windows are useful for simple quotas, like requests per hour or day, when brief bursts are acceptable. 
b) In a hashmap, when two threads both accept the request, they saw the same count, and then both of them update the count,
but in the last only one record was recorded, which cause the lost update issue. Version 1 use hashmap to store the count,
which is safe for single thread, not for multiple threads that may cause race condition. But when there is single thread,
for example for simple quotas, like requests per day, version 1 is still a right choice.
c) Because ConcurrentHashMap.compute(key,func) is an atomic operation that combine the get() and put() methods for multiple
threads and will not allow other threads working with the same key override the results. Other keys that hash to the same
bin may also be blocked briefly. In Version 2, compute makes the read, update, and write happen as one atomic operation,
which makes the shared map updates thread-safe.
d) The classes receive time through a LongSupplier so their behavior is easy to test. Production passes 
System::currentTimeMillis, while tests pass a controllable clock, such as AtomicLong::get, and advance it to test window
resets without waiting.

2. 
a) The sliding window log stores the timestamp of each accepted request. For a new request, it removes timestamps 
older than the window, then accepts the request if fewer than the limit remain. Because it checks the most recent time 
interval, requests before and after a fixed boundary are counted together.
b) The log stores one timestamp per accepted request, so memory grows with the limit. A fixed window counter stores only 
a count and the current window, so its state per key stays constant. The log is a good choice when you need an accurate 
limit and the request volume is manageable.
c) The sliding window counter adds the current window’s count to a weighted portion of the previous window’s count:
estimate = current count + previous count × (1 − fraction of current window elapsed)
It assumes requests were evenly distributed across the previous window.
d) If requests cluster near the end of the previous window, the estimate can be too low: it discounts requests that are 
still in the sliding window, so too many may be accepted. If they cluster near the beginning, the estimate can be too 
high: it counts some requests that have already expired, so valid requests may be rejected. Version 4 is useful when you
want lower memory use than the log and can accept an approximate limit.

3. 
a) A token bucket stores unused tokens while the client is idle, so it can allow a burst later. The capacity sets the 
maximum burst; the refill rate sets the long-term rate.
b) No timer is needed. When a request arrives, the limiter uses the time since the last request to calculate how many 
tokens to add, up to capacity. A short burst can exceed the refill rate because it can use tokens saved while idle.
c) A token bucket saves tokens for later bursts. A leaky bucket tracks incoming requests as water that drains over time;
if it fills up, new requests are rejected. Sparse traffic may leave capacity unused, while bursts may fill the bucket
and cause rejections, so the accepted rate depends on the arrival pattern. Each key stores its water level and last 
update time. The limiter calculates the leak from elapsed time when the next request arrives, so no timer is needed.
d) 
Fixed window counter — the limit resets at one midnight.
Sliding window log — accurately enforces five attempts in any rolling minute.
Sliding window counter — uses little memory per key and allows a small estimation error.
Token bucket — set capacity to 20 and refill to 5 tokens per second.
Leaky bucket — set capacity to one call and leak at five calls per second to enforce the 200 ms gap.

4. 
a) Memory depends on the number of distinct keys stored, not on the total number of requests. IP addresses and 
session IDs can have high or attacker-controlled variety, so the map may grow without bound and exhaust memory.
b) An entry can be removed when its state is equivalent to a fresh entry. For a leaky bucket, that is when its water 
level is zero.
A race can happen if the sweeper reads an empty bucket, a request then fills it, and the sweeper removes it based on the
old value. The next request creates a fresh bucket and gets another full capacity. Version 7 checks and removes the entry
atomically with compute, so it cannot remove state that a request has just updated.
c) A rejected request gets HTTP 429 Too Many Requests with a Retry-After header. The header gives the wait in seconds.
d) Each instance has its own counter, so a user’s total allowance can multiply across instances. Version 8 is still 
suitable when the service runs on one instance, or when a separate limit per instance is intentional.
e) The shared store must provide an atomic increment. A separate read and write can lose updates when concurrent requests
read the same count.
The class uses wall-clock milliseconds to calculate the same fixed-window key across instances. Each counter gets a TTL 
so old window keys are removed. Every request now requires a network call to the shared store.
In the tutorial, if the store is down, tryAcquire rejects the request (fails closed). The system should decide in advance
whether store failures should fail open or closed. This fixed-window approach also brings back Version 2’s boundary-burst
problem.
