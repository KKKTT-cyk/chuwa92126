### 1. Fixed Window Counter

(a). Each fixed window has an independent allowance, so a caller can spend one allowance just before the reset and another just after it. The burst follows from the reset rule, so changing the implementation alone cannot eliminate it. A fixed window counter is appropriate when the quota explicitly resets at a scheduled boundary, such as 1,000 calls per day with a reset at midnight.

(b). Two threads can read the same count, both accept, and overwrite each other's increment. Version 1 is suitable for a limiter confined to one thread.

(c). `compute` serializes updates for the same key and can briefly block updates to other keys in the same bin. Version 2 is thread-safe because the whole check-and-update happens inside that atomic operation.

(d). The limiter takes a `LongSupplier` so it can read the current time as a `long` whenever a request arrives, while letting the caller choose the time source. Production passes `System::nanoTime` for elapsed-time limits, and tests pass a manually controlled clock, such as `testClock::get` on an `AtomicLong`, so they can advance time and test window boundaries without sleeping.

### 2. Sliding Window Rate Limiters

(a). The sliding log removes accepted-request timestamps at or before `now - windowLength`. It accepts the new request and records its timestamp if fewer than `limit` entries remain. Because the interval moves with each request, timestamps from just before a fixed boundary still count just after it.

(b). The log can store up to one timestamp per allowed request, so its worst-case memory per key grows with the limit. A fixed counter stores only a window ID and count per key, regardless of the limit. The log is a good choice when the limit is small and must be exact, such as five login attempts in any minute.

(c). It adds the entire current-window count to the previous-window count multiplied by the fraction of that previous window that still overlaps the rolling interval. It accepts if the estimate plus one is within the limit. The estimate assumes requests were spread evenly across the previous window.

(d). It is too loose when previous requests cluster near the end of their window, inside the overlap, because the estimate counts only a fraction of them. It is too strict when they cluster near the beginning, outside the overlap, because the estimate still counts some of them. Version 4 fits large limits across many keys when some overcounting or undercounting is acceptable and constant memory per key matters.

### 3. Token Bucket and Leaky Bucket

(a). While the client is idle, tokens accumulate up to the bucket's capacity. Fixed and sliding windows do not carry forward unused allowance from idle periods, so they may reject part of the sme burst. Token bucket capacity sets the largest immediate burst from a full bucket, and the refill rate sets the sustainable long-term rate.

(b). On arrival, it multiplies elapsed time since the last update by the refill rate, adds those tokens up to capacity, and spends one taken if available. A short interval can use tokens already in the bucket plus tokens generated during that interval. That is why it can admit more requests than the refill rate alone would suggest.

(c). Each accepted request adds one unit to the leaky bucket, and a request that would overflow it is rejected. The tutorial uses capacity 1 to enforce spacing, while its token bucket uses larger capacity to admit bursts. At 5 units per second, capacity 1 requires a 200 ms gap. If requests arrive every 110 ms, only every other request passes, so the actual rate is below 5 per second. The only per-key state is `emptyAt`. The limiter calculates the remaining drain time as `max(0, emptyAt - now)`, so leaking requires no background update.

(d).

- 1. V2 atomic fixed window. Each calendar day gets a separate counter aligned to midnight in the intended time zone.

- 2. V3 sliding window log. It enforces the exact limit over the latest 60 seconds using at most five timestamps per key.

- 3. V4 sliding window counter. It approximates the rolling count with constant memory per key.

- 4. V5 token bucket. Capacity 20 allows the burst when full, and a refill rate of 5 tokens per second limits sustained traffic.

- 5. V6 leaky bucket. Capacity 1 and a leaky rate of 5 per second enforce at least 200 ms between accepted calls for the same quota.

### 4. Memory Management and Distributed Rate Limiting

(a). The map retains one entry per distinct key ever seen. Memory depends on that historical key count and the amount of state each entry holds. The entry count is independent of the current request rate or how many times existing keys have made requests. IP addresses and session IDs are risky because new values can keep creating entries even if each appears only once.

(b). A key can be removed when its state would produce the same future decisions as a new key. For a leaky bucket, that means it has drained completely. With capacity 1, a sweeper can read an empty bucket, a request can fill it, and the sweeper can then delete the updated entry. An immediate second request sees a fresh bucket and passes too. Version 7 checks and removes the entry atomically with `computeIfPresent`, so the check and deletion cannot be separated by an update from `tryAcquire`.

(c). It returns `0` on acceptance and, on rejection, the number of nanoseconds until enough water drains for another request to fit. The HTTP response uses `429 Too Many Requests` and puts the delay in `Retry-After` as a whole number of seconds rounded up. For example, 180 ms becomes `Retry-After: 1`.

(d). Each instance keeps its own state, so a user whose requests reach multiple instances can spend a separate allowance on each and exceed the intended service-wide limit. Version 8 is appropriate when the service runs on one instance or when the limit is intended to protect each instance independently.

(e). The store must atomically increment the named counter and return its new value. With a separate read and write, two instances could read the same count, overwrites each other's increment, and both admit a request. Wall-clock miliseconds let instances with aligned clocks calculate the same window ID. Each counter gets a TTL so old windows do not accumulate. Every request costs a store round trip, including requests that exceed the limit. `tryAcquire` throws `IllegalStateException` when the store is unavailable. The service must decide in advance whether to fail open and allow requests or fail closed and reject them. The fixed-window boundary burst from Version 2 returns because adjacent windows still have separate allowances.
