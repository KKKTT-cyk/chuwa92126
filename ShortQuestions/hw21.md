# HW21 – Rate Limiter

## Question 1.

**(a)** The fixed window counter restarts the count at every window boundary. A client can use a full allowance at the end of one window and another full allowance at the start of the next. In the tutorial's example, requests 1-5 at 900-980 ms and requests 6-10 at 1000-1080 ms are all accepted: ten requests in 180 ms with a limit of 5 per second, so up to 2 x limit requests can pass within one second. This follows from counting per fixed window, so no change inside the class removes it. The fixed window is still the right choice when the limit is defined per calendar period, such as 1,000 calls per day that reset at midnight, because there the fixed window is the requirement.

**(b)** `tryAcquire` reads the count, compares it and writes it back as separate steps. Thread A reads 4, thread B reads 4, A sees 4 < 5 and writes 5 and accepts, then B sees 4 < 5 and writes 5 and accepts. Two requests were accepted but the count rose by only one. A plain `HashMap` and plain fields give nothing that stops this, so Version 1 is not thread-safe. In the real run (limit 1,000,000, 16 threads x 200,000 calls) Version 1 accepted 3,200,001 in every run, 3.2 times the limit. Version 1 is still the right choice when a single thread makes all the calls, for example a batch job that throttles its own requests.

**(c)** `compute(key, function)` runs the function for that key while no other thread can run a function for the same key. Other keys are not locked, except the few that share the same bin of the map. In Version 2 the read, the comparison and the write all happen inside `compute`, so two threads can no longer read the same count. The same 16-thread run accepted exactly 1,000,000 in all 5 runs.

**(d)** The classes receive a `LongSupplier` so that they do not depend on the system clock, and a test can control time. Production code passes `System::nanoTime`. A test passes a clock that it moves by hand (for example an `AtomicLong`), so no test has to sleep.

## Question 2.

**(a)** Version 3 keeps the timestamp of every accepted request of the last second. A new request first drops the timestamps that are older than one second, and it is accepted if fewer than 5 remain. The interval that is counted now ends at the current request, wherever that falls, so there is no boundary. In the 14-request run, requests 6-10 are rejected because the five timestamps from 900 to 980 ms are still inside the last second.

**(b)** The state of one key is no longer two numbers; it is up to `limit` timestamps, so memory grows with the limit. Measured on JDK 21: fixed window 123 bytes per key, sliding log 306 bytes (limit 5), 2,975 bytes (limit 100) and 29,182 bytes (limit 1,000). With a limit of 100 and one million active keys the logs take about 3 GB. The log is still the right choice when the limit is small and must hold exactly, such as 5 login attempts per minute.

**(c)** Version 4 keeps two counters per key: the count of the current fixed window and the count of the previous one. The estimate is the whole current count plus the share of the previous count that still lies inside the last second. For a request at 1150 ms: 5 x 0.85 + 0 = 4.25, and 4.25 + 1 > 5, so it is rejected. The estimate rests on the assumption that the previous window's requests were spread evenly over that window.

**(d)** Too loose: request 12 at 1500 ms. The five previous-window requests (900-980 ms) all lie at the end of their window, inside the last second, but the estimate counts only half of the previous window. Version 3 rejects it (5 in the interval), Version 4 accepts it (6 in the interval). Too strict: five requests from 0 to 80 ms and a sixth at 1100 ms. The previous-window requests lie at the start of their window, so the last second contains none of them, but the estimate still counts 90% of the previous window. Version 3 accepts the request at 1100 ms, Version 4 rejects it. Version 4 is still the right choice when the limit is large, there are many keys, and a small error is acceptable, such as 600 requests per minute per API key.

## Question 3.

**(a)** A token bucket has a rate and a capacity; a client that was idle has a full bucket and may send `capacity` requests at once. Window limiters count per interval, so a client idle for ten seconds that sends 8 requests within 70 ms gets 5 accepted and 3 rejected in Versions 2, 3 and 4. Token bucket with capacity 5 gives the same result, but with capacity 10 it accepts 8 and rejects 0. The capacity sets the burst that passes; the rate (5 per second) sets the long-term rate.

**(b)** No timer adds tokens. Each call works out how many tokens accumulated since the previous call for that key (elapsed time x refill rate), adds them up to `capacity`, and stores the new time. A request then takes one token or is rejected if less than one is left. In any interval of length t, up to capacity + rate x t requests can pass, so the burst comes on top of the rate. Example: a client sends one request every 10 ms for one second with capacity 5 and refill 5 per second; 9 of 100 are accepted, 5 of them in the first 40 ms.

**(c)** In the token bucket an idle client may burst up to the capacity. The leaky bucket adds one unit of water per accepted request, water leaks at the rate, and a request that would overflow is rejected; with a capacity of 1 accepted requests are at least 200 ms apart at 5 per second. In the same one-request-every-10-ms run, Version 6 accepts 5 of 100 at 0, 200, 400, 600 and 800 ms. On the 14-request trace Version 6 accepts only 4 (at 900, 1150, 1500 and 1950 ms), because a request is accepted only after the previous unit has leaked out, and rejected requests add no water. The whole state of a key is one number: the time at which its bucket will be empty. The level at any moment is that time minus now, so the leaking itself needs no update.

**(d)**

| Requirement | Version | Reason |
|---|---|---|
| 1,000 calls per calendar day, reset at midnight | Version 2 (fixed window) | The limit is defined per calendar period, so the fixed window is the requirement. |
| 5 login attempts in any minute | Version 3 (sliding log) | The limit is small and must hold exactly. |
| 600 requests per minute per API key, many keys, small error acceptable | Version 4 (sliding counter) | The limit is large, there are many keys, and a small error is acceptable; state is three numbers per key. |
| A page sends 20 calls at once on load, 5 per second on average | Version 5 (token bucket), capacity 20, rate 5 per second | Capacity is set to the burst that should pass; the rate stays the average. |
| A third-party API rejects a second call within 200 ms | Version 6 (leaky bucket, capacity 1, leak 5 per second) | Accepted requests are at least 200 ms apart, which the protected system needs. |

## Question 4.

**(a)** The memory depends on how many different keys were ever seen, not on the current traffic. For example, one million users who send one request each and never return leave 1,000,000 entries after one hour, about 123 MB at 123 bytes per key. When the key is an IP address or a session id, new keys keep arriving, and a client can create them on purpose, so the map can grow without a bound.

**(b)** A key can be removed when its state is the same as the state of a key that was never seen; then removing it cannot change any later decision. For the leaky bucket that state is an empty bucket. With a `get` followed by a `remove`, the sweep reads an empty bucket, then a request fills the bucket, and then the remove deletes what that request wrote. The next request sees a new key with an empty bucket and is accepted, so the key is accepted more than `capacity` times. In the stress run, 27 of 60,000 keys were accepted more than capacity (most for one key: 6). Version 7 does the check and the removal inside `computeIfPresent`, the same atomic per-key step that `tryAcquire` uses, so no request can run in between (0 of 60,000).

**(c)** Version 8 adds `acquireOrWaitNanos`, which returns 0 for an accepted request and otherwise the nanoseconds until a request will be accepted; the bucket level says when one more unit will fit. In the trace, request 2 at 920 ms is told to wait 180 ms, which is 1100 ms, the moment the bucket is empty. In an HTTP service the rejection is status 429 (Too Many Requests), and the wait goes into the `Retry-After` header, in whole seconds, rounded up.

**(d)** The state lives in the memory of one process, and each instance has its own map. A user who sends 40 requests (one every 50 ms for two seconds) handed to four instances in turn is accepted 40 of 40, versus 10 of 40 with one instance: each instance sees a request every 200 ms and accepts all of them, so the user gets 20 per second through a limit of 5. Version 8 is still the right choice when the service runs as a single instance, or when the limit is meant to protect each instance separately.

**(e)** The store must offer one operation: add one to a named counter and return the new value, as a single atomic step inside the store (Redis `INCR`). A read followed by a write is not enough because two instances could both read 4 and both write 5; the atomic increment means that can never happen. The class takes wall-clock milliseconds because the window number must be the same on every instance, while the starting point of `System.nanoTime()` differs from process to process. Every counter gets a time to live so that old counters disappear; the tutorial uses 2 x the window length, since a counter is used only during its own window. Every request now costs a round trip to the store, which adds latency to the request and load to the store (40 store calls for 40 requests in the run). When the store is down, `tryAcquire` throws `IllegalStateException: store unavailable`. The service must decide in advance whether it then accepts every request or rejects every request. The boundary burst of Version 2 is back, because this is the fixed window counter again.
