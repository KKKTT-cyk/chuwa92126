# Rate Limiter — Conceptual Questions

## 1. Fixed Window Counter

### (a) Why can a fixed window counter allow a burst across a window boundary?

A fixed window counter divides time into non-overlapping intervals and maintains a request counter for each interval.

For example, suppose the rate limit is 100 requests per minute.

A client sends:

- 100 requests at 12:00:59.
- 100 requests at 12:01:00.

Both requests belong to different fixed windows:

- Window 1: 12:00:00 to 12:00:59.
- Window 2: 12:01:00 to 12:01:59.

Each window satisfies the limit of 100 requests, but the client sends 200 requests within approximately one second.

This is called the fixed-window boundary burst problem.

```text
Window 1                 Window 2
|------------------------|------------------------|
                   100 requests
                         | 100 requests
                         |
                    Window boundary
```

No implementation change that preserves the fixed-window counting semantics can completely eliminate this problem because it is caused by the algorithm itself.

The algorithm only considers requests within the current fixed window. It does not consider requests immediately before the window boundary.

To eliminate this behavior, the rate-limiting semantics must change, for example by using a sliding window.

Fixed window counters are still appropriate for limits defined by specific accounting periods, such as:

- 1,000 API calls per calendar day.
- 10,000 requests per billing month.
- Daily usage quotas that reset at midnight.

In these situations, the window boundary is part of the business requirement rather than an implementation problem.

---

### (b) Why is Version 1 not thread-safe?

Version 1 uses a plain HashMap to store the current window and request count for each key.

Suppose the limit is 5 requests and the current count is 4.

Two threads attempt to acquire permission simultaneously.

```text
Initial count = 4
Limit = 5

Thread A reads count = 4
Thread B reads count = 4

Thread A checks 4 < 5: true
Thread B checks 4 < 5: true

Thread A writes count = 5
Thread B writes count = 5

Thread A accepts the request.
Thread B accepts the request.

Final stored count = 5
Actual accepted requests = 6
```

Both threads accept a request, but one increment is lost because both threads write the same updated value.

This is called a lost update.

Version 1 is not thread-safe for two reasons:

1. HashMap does not support unsynchronized concurrent modification safely.
2. Reading, checking, and updating the counter is a compound operation that is not atomic.

Even replacing HashMap with ConcurrentHashMap would not solve the second problem if get() and put() were still called separately.

Version 1 is appropriate when:

- The rate limiter is used by only one thread.
- All access is serialized through an event loop.
- External synchronization protects every access.
- The implementation is used for learning or simple single-threaded applications.

---

### (c) How does ConcurrentHashMap.compute() make Version 2 thread-safe?

ConcurrentHashMap.compute(key, function) atomically computes and updates the mapping associated with a particular key.

For example:

```java
map.compute(key, (k, state) -> {
    // Check the current window.
    // Check the current count.
    // Update the count if the request is accepted.
    return state;
});
```

For the same key, concurrent compute operations cannot independently modify the mapping at the same time.

Suppose the current count is 4 and the limit is 5.

```text
Thread A enters compute(key).

Thread A reads count = 4.
Thread A accepts the request.
Thread A updates count = 5.
Thread A completes compute().

Thread B enters compute(key).

Thread B reads count = 5.
Thread B rejects the request.
Thread B completes compute().
```

The check-and-update operation is atomic for that key.

This prevents the lost update problem from Version 1.

However, ConcurrentHashMap does not necessarily provide a completely independent lock for every key.

Updates to other keys that occupy the same internal hash bin may also be blocked while the computation is running.

Updates to unrelated keys in different bins can generally proceed concurrently.

Therefore, the compute function should be short and should not perform expensive operations such as:

- Network requests.
- Database queries.
- Long-running calculations.
- Blocking I/O.

Version 2 is thread-safe as long as all relevant state mutations occur through the protected atomic operation and mutable state is not modified unsafely elsewhere.

---

### (d) Why use LongSupplier instead of directly reading the system clock?

LongSupplier is a Java functional interface that supplies a long value.

Its method is:

```java
long getAsLong();
```

A rate limiter can receive its clock through constructor injection.

```java
import java.util.function.LongSupplier;

public class RateLimiter {

    private final LongSupplier clock;

    public RateLimiter(LongSupplier clock) {
        this.clock = clock;
    }

    public long currentTime() {
        return clock.getAsLong();
    }
}
```

This is an example of dependency injection.

The rate limiter does not need to know how the current time is obtained.

### Production Code

For a local rate limiter that measures elapsed time in milliseconds, production code can use a monotonic clock:

```java
RateLimiter limiter = new RateLimiter(
    () -> System.nanoTime() / 1_000_000L
);
```

For a limiter that requires calendar-based or shared wall-clock windows, production code can use:

```java
RateLimiter limiter = new RateLimiter(
    System::currentTimeMillis
);
```

The clock and the rate limiter must agree on the time unit.

System.nanoTime() is suitable for measuring elapsed time because it is monotonic and is not affected by normal wall-clock adjustments.

System.currentTimeMillis() is suitable when the algorithm requires an actual wall-clock timestamp.

### Test Code

A test can pass a manually controlled clock.

```java
import java.util.concurrent.atomic.AtomicLong;

AtomicLong fakeClock = new AtomicLong(0);

RateLimiter limiter = new RateLimiter(fakeClock::get);

fakeClock.set(1000);
fakeClock.addAndGet(500);
```

This allows tests to simulate time passing without calling Thread.sleep().

Benefits include:

- Deterministic tests.
- Faster execution.
- Easier testing of window boundaries.
- Easier testing of token refilling.
- Easier testing of expiration and cleanup.
- Reduced dependence on the real system clock.

## 2. Sliding Window Rate Limiters

### (a) How does the sliding window log of Version 3 work?

A sliding window log stores the timestamps of previously accepted requests for each key.

It considers a continuously moving time interval instead of fixed time windows.

Suppose the limit is 5 requests in any 60-second interval.

When a new request arrives at time now:

1. Calculate the beginning of the sliding window.

   windowStart = now - windowSize

2. Remove timestamps that are outside the current window.

3. Count the remaining timestamps.

4. If the count is below the limit, accept the request and append its timestamp.

5. Otherwise, reject the request.

Example Java-style pseudocode:

```java
while (!timestamps.isEmpty()
        && timestamps.peekFirst() <= now - windowSize) {

    timestamps.pollFirst();
}

if (timestamps.size() < limit) {
    timestamps.addLast(now);
    return true;
}

return false;
```

This example uses the interval (now - windowSize, now].

### Example

Suppose the limit is 3 requests per 60 seconds.

```text
Request at second 10: Accepted
Request at second 20: Accepted
Request at second 30: Accepted
Request at second 40: Rejected
Request at second 71: Accepted
```

At second 71, the request from second 10 has expired.

Only the requests at seconds 20 and 30 remain inside the current window.

The new request can therefore be accepted.

### Why It Avoids Boundary Bursts

The sliding window log considers every request within the most recent windowSize interval.

It does not reset the counter at an arbitrary fixed boundary.

For example, if a client sends 100 requests at 12:00:59, those requests remain inside the sliding window at 12:01:00.

The client cannot immediately send another 100 requests simply because the minute changed.

Therefore, the sliding window log enforces an exact rolling-window limit.

---

### (b) Why does sliding window log memory grow with the limit?

The sliding window log stores one timestamp for each accepted request that remains relevant to the current window.

If the limit is L requests per window, a key may need to store up to L timestamps.

Therefore:

```text
Sliding window log memory per key = O(L)
```

If there are K keys:

```text
Worst-case total memory = O(K × L)
```

For example:

```text
Number of keys = 100,000
Limit = 1,000 requests per window

Maximum timestamps = 100,000 × 1,000
                   = 100,000,000
```

If each timestamp uses 8 bytes, the raw timestamp storage alone is:

```text
100,000,000 × 8 = 800,000,000 bytes
```

This is approximately 800 MB, excluding Java object, collection, and map overhead.

In contrast, a fixed window counter only needs to store:

- The current window identifier.
- The current request count.

Therefore:

```text
Fixed window memory per key = O(1)
Total memory = O(K)
```

### Time Complexity

A sliding window log may remove multiple expired timestamps during one request.

However, each accepted timestamp is inserted once and removed at most once.

Using an efficient deque, the amortized processing cost is generally O(1) per request, excluding map contention and other overhead.

### When Is the Sliding Window Log the Right Choice?

The sliding window log is appropriate when:

- Exact rolling-window enforcement is required.
- The request limit is relatively small.
- The number of keys is manageable.
- Incorrect acceptance or rejection has significant consequences.

Examples include:

- Login attempt limits.
- Password reset requests.
- Verification code requests.
- Sensitive security operations.

---

### (c) How does the sliding window counter of Version 4 estimate requests?

The sliding window counter combines two adjacent fixed-window counters:

- The previous window count.
- The current window count.

It estimates how many requests from the previous window remain inside the current sliding interval.

The formula is:

```text
Estimated count =
    currentCount
    + previousCount × remainingPreviousWindowFraction
```

The remaining fraction is:

```text
remainingPreviousWindowFraction =
    1 - elapsedTimeInCurrentWindow / windowSize
```

### Example

Suppose:

```text
Window size = 60 seconds
Previous window count = 80
Current window count = 30
Elapsed time in current window = 15 seconds
```

The fraction of the previous window that overlaps the sliding window is:

```text
1 - 15 / 60 = 0.75
```

The estimated request count is:

```text
30 + 80 × 0.75 = 90
```

If the limit is 100, another request can be accepted because:

```text
90 + 1 <= 100
```

### Illustration

```text
Previous window            Current window
|-------------------------|-------------------------|
       |                  |       |
       +--------------------------+
          Current sliding window
```

Only part of the previous fixed window overlaps the current sliding window.

### Main Assumption

The algorithm assumes that requests in the previous window were distributed uniformly throughout that window.

Under this assumption, if 75% of the previous window overlaps the current sliding interval, approximately 75% of its requests should still count.

However, real requests may arrive in bursts instead of being uniformly distributed.

Therefore, the sliding window counter provides an approximation rather than an exact rolling-window count.

---

### (d) When is the sliding window counter too loose or too strict?

The sliding window counter estimates the number of relevant requests from the previous window without storing their exact timestamps.

This creates two possible estimation errors.

Suppose:

```text
Window size = 60 seconds
Previous window count = 100
Elapsed time in current window = 30 seconds
Current window count = 0
```

The estimated count is:

```text
100 × (1 - 30 / 60) = 50
```

### Case 1: The Estimate Is Too Loose

Suppose all 100 requests occurred near the end of the previous window.

```text
Previous window             Current window
|--------------------------|--------------------------|
                    XXXXXXX              ^
                    Requests             Now
```

All 100 requests may still be inside the actual sliding window.

However, the algorithm estimates that only 50 requests remain.

```text
Actual count = 100
Estimated count = 50
```

The estimate is too low.

As a result, the limiter may accept additional requests even though the exact rolling-window limit has already been reached.

This is called underestimation.

### Case 2: The Estimate Is Too Strict

Suppose all 100 requests occurred near the beginning of the previous window.

```text
Previous window             Current window
|--------------------------|--------------------------|
 XXXXXXX                                 ^
 Requests                                Now
```

All 100 requests may already be outside the actual sliding window.

However, the algorithm still estimates that 50 requests remain.

```text
Actual count = 0
Estimated count = 50
```

The estimate is too high.

As a result, the limiter may reject requests earlier than necessary.

This is called overestimation.

### When Is Version 4 the Right Choice?

The sliding window counter is appropriate when:

- There are many users or API keys.
- Memory efficiency is important.
- Approximate rolling-window enforcement is acceptable.
- Request traffic is reasonably distributed.
- Occasional estimation errors are tolerable.

It uses O(1) memory per key because it only stores a small number of counters and window information.

It is commonly suitable for general API rate limiting.

However, it is less suitable for security-sensitive limits that require exact enforcement.

## 3. Token Bucket and Leaky Bucket

### (a) Why can a token bucket allow bursts after a client has been idle?

A token bucket maintains a collection of available tokens.

Each accepted request consumes one token.

Tokens are replenished at a configured rate until the bucket reaches its maximum capacity.

The two main parameters are:

- Capacity: Maximum number of tokens that can be stored.
- Refill rate: Number of tokens added per unit of time.

Suppose:

```text
Bucket capacity = 20 tokens
Refill rate = 5 tokens per second
```

If the client remains idle long enough, the bucket becomes full.

```text
Available tokens = 20
```

When the client sends 20 requests simultaneously, all 20 requests can be accepted because enough tokens have accumulated.

After the burst:

```text
Available tokens = 0
```

The client must wait for tokens to refill before additional requests can be accepted.

### Burst Capacity

The bucket capacity determines the maximum immediate burst when the bucket is full.

```text
Maximum immediate burst = Bucket capacity
```

### Long-Term Rate

The refill rate determines the sustainable long-term acceptance rate.

```text
Long-term rate = Token refill rate
```

For example, a bucket with capacity 20 and refill rate 5 requests per second allows:

- An immediate burst of up to 20 requests.
- A sustainable long-term rate of approximately 5 requests per second.

Fixed and sliding window limiters do not normally accumulate unused request allowances across windows.

If they are configured to allow 5 requests per second, they may reject part of a 20-request burst even after a long idle period.

The token bucket is therefore suitable when occasional bursts should be allowed while maintaining an average rate limit.

---

### (b) Why does the token bucket need no timer?

The token bucket can calculate refilled tokens lazily when a request arrives.

It does not need a background thread or scheduled task that periodically adds tokens.

Each key stores:

- The current number of tokens.
- The timestamp of the last refill calculation.

When a new request arrives:

```text
elapsedTime = now - lastRefillTime

newTokens = elapsedTime × refillRate

availableTokens =
    min(capacity, previousTokens + newTokens)
```

If at least one token is available, the request is accepted and one token is consumed.

### Example

Suppose:

```text
Capacity = 10 tokens
Refill rate = 2 tokens per second
Current tokens = 3
Elapsed time = 2 seconds
```

The number of refilled tokens is:

```text
2 × 2 = 4
```

The new token count is:

```text
min(10, 3 + 4) = 7
```

After accepting one request:

```text
Remaining tokens = 6
```

### Java-Style Pseudocode

```java
double elapsedSeconds =
    (now - state.lastRefillTime) / 1000.0;

state.tokens = Math.min(
    capacity,
    state.tokens + elapsedSeconds * refillRate
);

state.lastRefillTime = now;

if (state.tokens >= 1.0) {
    state.tokens -= 1.0;
    return true;
}

return false;
```

This assumes timestamps are measured in milliseconds and the refill rate is expressed in tokens per second.

Fractional tokens can be retained so that small refill intervals do not lose accumulated credit.

### Why Can the Short-Term Accepted Rate Exceed the Refill Rate?

The refill rate controls how quickly new tokens become available.

However, requests can also consume tokens that were accumulated before the current interval.

Suppose:

```text
Capacity = 20
Refill rate = 5 tokens per second
Initial tokens = 20
```

The client can immediately send 20 requests even though the refill rate is only 5 requests per second.

Over an interval of duration T, the theoretical acceptance bound is:

```text
Accepted requests <= Initial available tokens
                     + refillRate × T
```

For a bucket that starts full:

```text
Accepted requests <= Capacity + refillRate × T
```

This explains why the short-term rate can exceed the refill rate while the long-term average remains bounded by it.

---

### (c) How does the leaky bucket of Version 6 differ from the token bucket?

The leaky bucket implementation described in the question appears to be a strict-spacing rate limiter rather than a queued traffic-shaping implementation.

It controls how frequently requests can be accepted.

Unlike the token bucket, it does not accumulate unused burst capacity during idle periods.

Suppose the configured rate is 5 requests per second.

The minimum interval between accepted requests is:

```text
1 second / 5 = 0.2 seconds = 200 ms
```

After accepting a request, the limiter does not accept another request until at least 200 ms has passed.

### Example

```text
Request at 0 ms:   Accepted
Request at 50 ms:  Rejected
Request at 100 ms: Rejected
Request at 200 ms: Accepted
Request at 250 ms: Rejected
Request at 400 ms: Accepted
```

### Token Bucket vs. Leaky Bucket

Suppose 20 requests arrive simultaneously after a long idle period.

A token bucket with capacity 20 can accept all 20 requests.

A strict-spacing leaky bucket accepts one request and rejects the remaining 19 requests because they arrive too early.

A different leaky bucket implementation may queue requests and release them at a controlled rate. However, Version 6 appears to use immediate acceptance or rejection without maintaining such a queue.

### Why Can the Long-Run Accepted Rate Depend on the Arrival Pattern?

The configured leak rate defines the maximum permitted acceptance rate.

It does not guarantee that requests arrive exactly when the limiter becomes available.

Suppose the minimum interval is 200 ms.

If requests arrive every 200 ms:

```text
0 ms, 200 ms, 400 ms, 600 ms, ...
```

Every request can be accepted.

The accepted rate is approximately 5 requests per second.

However, suppose requests arrive every 150 ms:

```text
0 ms:   Accepted
150 ms: Rejected
300 ms: Accepted
450 ms: Rejected
600 ms: Accepted
750 ms: Rejected
900 ms: Accepted
```

Accepted requests are separated by 300 ms.

The long-run accepted rate is:

```text
1000 / 300 = approximately 3.33 requests per second
```

Although the configured rate is 5 requests per second, the actual accepted rate is lower because requests do not arrive at the ideal times.

Unused acceptance opportunities are not accumulated.

### State Stored for Each Key

For a strict-spacing implementation, the entire state of a key can be represented by one timestamp:

- The next allowed request time.

An equivalent implementation can store the timestamp of the last accepted request.

Example pseudocode:

```java
if (now >= nextAllowedTime) {
    nextAllowedTime = now + interval;
    return true;
}

return false;
```

### Why Does Leaking Require No Update?

The limiter does not need to continuously decrease a stored bucket level.

Instead, the passage of time is represented by comparing the current time with the stored timestamp.

Once the current time reaches nextAllowedTime, the key becomes eligible for another request automatically.

No background timer is required.

### (d) Choose a rate limiter for each requirement

#### Requirement 1: "1,000 calls per calendar day, reset at midnight"

Recommended version: Version 2 — Thread-safe Fixed Window Counter.

Reason:

The requirement explicitly defines a calendar-day boundary.

A fixed window counter directly represents the desired business rule.

The counter resets when the next calendar day begins.

A production implementation must use the appropriate wall clock and calendar time zone.

If multiple service instances must share the same daily quota, Version 9 or another distributed fixed-window implementation is more appropriate.

Version 1 is also sufficient if all requests are processed by a single thread.

#### Requirement 2: "5 login attempts in any minute"

Recommended version: Version 3 — Sliding Window Log.

Reason:

The phrase "any minute" requires an exact rolling 60-second interval.

A fixed window counter may allow 10 attempts across a minute boundary.

A sliding window counter may introduce estimation errors.

The sliding window log provides exact enforcement.

Because the limit is only 5, storing up to 5 timestamps per key has relatively low memory cost.

#### Requirement 3: "600 requests per minute per API key, with many keys, where a small error is acceptable"

Recommended version: Version 4 — Sliding Window Counter.

Reason:

The sliding window counter provides approximate rolling-window enforcement while using O(1) memory per key.

A sliding window log could require up to 600 timestamps per API key.

With many API keys, the log may consume excessive memory.

The sliding window counter offers a good balance between accuracy and scalability.

#### Requirement 4: "A page sends 20 calls at once when it loads, and 5 calls per second are allowed on average"

Recommended version: Version 5 — Token Bucket.

Configuration:

```text
Capacity = 20 tokens
Refill rate = 5 tokens per second
```

Reason:

The token bucket can accumulate tokens while the client is idle.

A full bucket allows the initial burst of 20 requests.

Afterward, the refill rate controls the sustainable long-term request rate.

#### Requirement 5: "A third-party API rejects a second call within 200 ms"

Recommended version: Version 6 — Leaky Bucket.

Configuration:

```text
Minimum interval = 200 ms
Maximum rate = 5 requests per second
```

Reason:

The third-party API requires a minimum separation between consecutive requests.

A token bucket could allow multiple requests simultaneously.

A fixed or sliding window limiter does not necessarily guarantee minimum spacing between requests.

The strict-spacing leaky bucket ensures that consecutive accepted requests are separated by at least 200 ms.

If requests are sent from multiple instances, the spacing must be coordinated across those instances.

### Summary

| Requirement | Version | Algorithm |
|---|---|---|
| 1,000 calls per calendar day | Version 2 | Fixed Window Counter |
| 5 login attempts in any minute | Version 3 | Sliding Window Log |
| 600 requests per minute with many keys | Version 4 | Sliding Window Counter |
| Burst of 20, average rate of 5/sec | Version 5 | Token Bucket |
| Minimum 200 ms between requests | Version 6 | Leaky Bucket |

## 4. Memory Management and Distributed Rate Limiting

### (a) What determines memory usage when map entries are never removed?

Versions 1 through 6 create a map entry whenever a new key appears.

If these entries are never removed, the memory usage depends on the total number of distinct keys that have appeared since the rate limiter was created.

Let:

```text
K = Number of distinct keys ever observed
L = Request limit per window
```

For algorithms that store a fixed amount of state per key:

```text
Memory complexity = O(K)
```

These algorithms include:

- Fixed Window Counter.
- Sliding Window Counter.
- Token Bucket.
- Strict-spacing Leaky Bucket.

For the sliding window log:

```text
Worst-case memory complexity = O(K × L)
```

The sliding window log stores timestamps in addition to the map entry.

### What Does Memory Usage Not Depend On?

For fixed-state algorithms, memory usage does not directly depend on the total number of requests processed.

For example:

```text
1 user sends 1,000,000 requests:
Only 1 map entry is required.

1,000,000 users each send 1 request:
1,000,000 map entries are required.
```

Memory usage also does not depend only on the number of currently active users.

Inactive keys remain in the map unless they are explicitly removed.

### Why Are IP Addresses and Session IDs Risky?

IP addresses and session IDs can have high cardinality.

Examples include:

- Users changing IP addresses.
- IPv6 clients using temporary addresses.
- Expired sessions.
- Frequently generated session IDs.
- Bots generating many different identifiers.
- Attackers deliberately creating unique keys.

Even if every individual key stays within its rate limit, the total number of map entries may continue growing.

This can cause:

- Excessive heap memory usage.
- Increased garbage collection.
- Reduced application performance.
- OutOfMemoryError.
- Denial of service.

Therefore, production rate limiters need a memory management strategy, such as:

- Removing expired entries.
- Periodic cleanup.
- Bounded key storage.
- Time-to-live expiration.
- External stores with appropriate memory limits.

---

### (b) When can a key be removed safely, and how does Version 7 avoid cleanup races?

A key can be removed when its stored state is equivalent to the initial state of a newly created key.

Removing the entry must not change any future rate-limiting decision.

### Safe Removal Conditions

Fixed Window Counter:

The stored window has expired, so the old counter no longer affects the current window.

Sliding Window Log:

All stored request timestamps have expired.

Sliding Window Counter:

Both stored counters are no longer relevant to the current sliding interval.

Token Bucket:

The bucket has fully refilled, assuming a newly created bucket starts full.

Leaky Bucket:

The next allowed request time has already passed.

```text
now >= nextAllowedTime
```

At that point, the key has no remaining rate-limiting restriction.

Deleting the entry is equivalent to keeping an expired timestamp.

### Race Condition Between Cleanup and Request Threads

Suppose the leaky bucket allows one request every 200 ms.

The current state is:

```text
key = user-123
nextAllowedTime = 1000 ms
```

At time 1200 ms, the cleanup thread reads the state.

```text
Cleanup thread:
get(user-123) returns nextAllowedTime = 1000

1200 >= 1000

The cleanup thread decides that the entry can be removed.
```

Before the cleanup thread removes the entry, a request thread processes a new request.

```text
Request Thread A:

Current time = 1200 ms

1200 >= 1000

Request accepted.

nextAllowedTime = 1400 ms
```

The cleanup thread then continues:

```text
Cleanup thread:

remove(user-123)
```

It removes the newly updated state rather than only the expired state it originally observed.

Another request arrives immediately afterward.

```text
Request Thread B:

Current time = 1201 ms

No entry exists for user-123.

Request accepted.

nextAllowedTime = 1401 ms
```

Two requests were accepted only 1 ms apart, violating the required 200 ms interval.

### How Version 7 Prevents the Race

Version 7 must make the expiration check and deletion atomic with respect to request updates.

One implementation uses ConcurrentHashMap.computeIfPresent().

```java
map.computeIfPresent(key, (k, state) -> {

    if (now >= state.nextAllowedTime) {
        return null;
    }

    return state;
});
```

Returning null removes the mapping.

Request processing must also use an atomic operation on the same key.

```java
map.compute(key, (k, state) -> {
    // Check whether the request can be accepted.
    // Update the state atomically.
    return state;
});
```

Because both operations are atomic for the same key, cleanup cannot delete a state that has been updated between the expiration check and removal.

There are two possible execution orders.

#### Order 1: Cleanup Runs First

```text
Cleanup checks expired state.
Cleanup removes expired entry.
Request arrives.
Request creates a new entry.
Request is accepted.
```

This is correct because the old state had expired.

#### Order 2: Request Runs First

```text
Request updates nextAllowedTime to 1400.
Cleanup reads the updated state.
Cleanup checks whether 1200 >= 1400.
Condition is false.
Cleanup keeps the entry.
```

This is also correct.

An alternative implementation can use conditional removal:

```java
map.remove(key, observedState);
```

This is safe when state objects are immutable and each update replaces the old value, provided equality cannot confuse a newer state with the observed expired state.

If the state object is mutated in place, conditional removal alone may not prevent the race.

The fundamental requirement is that cleanup must not remove a newly updated state based on an earlier expiration check.

### (c) How does Version 8 tell a rejected caller how long to wait?

Version 8 returns additional information when a request is rejected.

Instead of returning only a boolean, the rate limiter can return a result containing:

- Whether the request was accepted.
- How long the caller should wait before retrying.

For example:

```java
public record RateLimitResult(
    boolean allowed,
    long retryAfterMillis
) {}
```

The precise result type may differ in the tutorial implementation.

### Calculating the Waiting Time

For a strict-spacing leaky bucket:

```text
retryAfterMillis =
    max(0, nextAllowedTime - now)
```

Suppose:

```text
Current time = 1200 ms
Next allowed time = 1400 ms
```

The waiting time is:

```text
1400 - 1200 = 200 ms
```

For a fixed window counter, the waiting time is the remaining time until the current window expires.

For a sliding window log, it is the time until enough accepted request timestamps expire.

For a token bucket, it is the time required to refill enough tokens for another request.

### HTTP Status Code

When an HTTP request exceeds the rate limit, the server should normally return:

```http
HTTP/1.1 429 Too Many Requests
```

### Retry-After Header

The server can include the Retry-After header.

```http
HTTP/1.1 429 Too Many Requests
Retry-After: 2
```

This tells the client to wait at least 2 seconds before retrying.

The standard Retry-After header supports two formats:

1. A non-negative integer number of seconds.
2. An HTTP-date indicating when the client should retry.

For example:

```http
Retry-After: 5
```

The value represents 5 seconds, not 5 milliseconds.

### Converting Milliseconds to Seconds

If the internal rate limiter returns milliseconds, the server should round upward when converting to integer seconds.

```java
long retryAfterSeconds =
    (long) Math.ceil(retryAfterMillis / 1000.0);
```

For example:

```text
Internal wait = 1500 ms
Retry-After = 2 seconds
```

For a positive waiting time below one second:

```text
Internal wait = 200 ms
Retry-After = 1 second
```

Rounding upward prevents the server from instructing the client to retry before the limiter becomes available.

The waiting time is advisory. Other concurrent requests from the same key may consume the newly available capacity before the caller retries.

### (d) Why does running Version 8 on multiple instances violate a service-wide limit?

Version 8 maintains its rate-limiting state in local application memory.

Each service instance has its own independent map.

Suppose the service-wide limit is:

```text
100 requests per minute per user
```

The service runs on three instances.

```text
Instance A: Local limit = 100
Instance B: Local limit = 100
Instance C: Local limit = 100
```

A load balancer distributes the user's requests across the instances.

The user may send:

```text
100 requests to Instance A
100 requests to Instance B
100 requests to Instance C
```

Each instance believes that the user has stayed within its local limit.

However, the user has sent:

```text
100 + 100 + 100 = 300 requests
```

The intended service-wide limit has been exceeded.

In general, if there are N independent service instances:

```text
Potential combined allowance = N × Local limit
```

### Architecture

```text
                  Client
                     |
                Load Balancer
                     |
        +------------+------------+
        |            |            |
    Instance A   Instance B   Instance C
        |            |            |
     Local Map    Local Map    Local Map
```

The local maps do not share information.

### When Is Version 8 Still the Right Choice?

#### Situation 1: Only One Service Instance Processes the Relevant Traffic

If the service runs on a single instance, all requests are checked against the same rate-limiting state.

A local limiter can enforce the intended limit without requiring an external store.

Similarly, local state may work when each key is reliably assigned to exactly one instance, although failover and routing changes can reset or split the state.

#### Situation 2: The Limit Is Intentionally Per Instance

Sometimes the goal is to protect each individual server rather than enforce a global user quota.

For example:

```text
Each inference server can process
a maximum of 100 requests per second.
```

In this situation, every instance should maintain its own independent limit.

A local limiter is appropriate because it:

- Has low latency.
- Requires no network request.
- Has no external storage dependency.
- Protects individual instances from overload.

Local and distributed rate limiters can also be combined.

A distributed limiter enforces the global user quota, while a local limiter protects each instance's resources.

### (e) How does Version 9 implement distributed rate limiting?

Version 9 stores rate-limiting counters in a shared external store.

All service instances access the same state.

A common implementation uses Redis.

### Architecture

```text
                   Client
                      |
                 Load Balancer
                      |
         +------------+------------+
         |            |            |
     Instance A   Instance B   Instance C
         |            |            |
         +------------+------------+
                      |
                Shared Store
                   Redis
```

All instances use the same counter for the same user and time window.

### Required Atomic Operation

The shared store must provide an atomic counter operation that safely increments the counter and initializes its expiration.

For example:

```text
incrementAndExpire(key, ttl)
```

The operation should:

1. Locate the counter for the current key and window.
2. Increment the counter atomically.
3. Set the TTL when the counter is first created.
4. Return the updated counter value.

The rate limiter can then determine whether the request is allowed.

```java
long count = store.incrementAndExpire(key, ttl);

return count <= limit;
```

This design may count rejected attempts as well as accepted requests, depending on the intended counter semantics.

An alternative implementation atomically checks the limit before incrementing, so rejected requests do not modify the counter.

Both approaches can enforce a fixed-window acceptance limit when implemented correctly.

### Why Is Read Followed by Write Not Enough?

Suppose the current count is 99 and the limit is 100.

Two service instances process requests simultaneously.

```text
Instance A reads count = 99
Instance B reads count = 99

Instance A checks 99 < 100: true
Instance B checks 99 < 100: true

Instance A writes count = 100
Instance B writes count = 100

Both requests are accepted.
```

The actual number of accepted requests becomes 101, but the stored count is only 100.

This is the same lost update problem that occurs in a non-thread-safe local counter.

A shared store alone does not solve concurrency problems.

The read-modify-write operation must be atomic across all service instances.

### Redis Example

Redis provides the atomic INCR command.

```redis
INCR rate-limit:user-123:window-100
```

However, executing INCR and EXPIRE as separate operations may introduce a failure window.

For example:

```text
INCR succeeds.
Application crashes before EXPIRE.
The counter remains in Redis indefinitely.
```

A Lua script can execute the increment and expiration initialization atomically.

```lua
local count = redis.call("INCR", KEYS[1])

if count == 1 then
    redis.call("PEXPIRE", KEYS[1], ARGV[1])
end

return count
```

In this example:

- KEYS[1] is the rate-limiting counter key.
- ARGV[1] is the TTL in milliseconds.
- INCR atomically increments the counter.
- PEXPIRE sets the expiration time.
- The script returns the updated counter.

Redis executes the script atomically relative to other commands.

The expiration is initialized only when the counter is created, rather than extended after every request.

### Why Does Version 9 Use Wall-Clock Milliseconds?

A distributed fixed-window limiter needs all service instances to identify the same time window.

For example:

```java
long windowId = nowMillis / windowSizeMillis;
```

The Redis key can include the window identifier.

```java
String redisKey =
    "rate-limit:" + userId + ":" + windowId;
```

If the window size is 60 seconds:

```text
windowSizeMillis = 60,000
```

All instances should calculate the same window identifier for requests occurring within the same fixed window.

System.nanoTime() cannot be used as a shared absolute timestamp because its origin is arbitrary and may differ between JVM processes.

Instead, Version 9 uses wall-clock milliseconds:

```java
System.currentTimeMillis()
```

Wall-clock timestamps are comparable across machines, assuming their clocks are sufficiently synchronized.

However, clock skew can still cause different instances to disagree near a window boundary.

Possible mitigations include:

- Synchronizing system clocks using NTP.
- Using a shared authoritative clock.
- Calculating window identifiers using the store's clock.

For calendar-based quotas, the calculation must also respect the intended time zone and calendar boundaries.

### Why Does Every Counter Need a TTL?

Each fixed window creates a separate counter key.

For example:

```text
rate-limit:user-123:window-100
rate-limit:user-123:window-101
rate-limit:user-123:window-102
```

Once a window has expired, its counter is no longer needed for future fixed-window decisions.

Without expiration, Redis would accumulate historical counters indefinitely.

A TTL automatically removes counters after they are no longer relevant.

Benefits include:

- Preventing unbounded memory growth.
- Automatically cleaning up inactive users.
- Removing expired windows.
- Reducing manual cleanup requirements.

The TTL must be long enough to ensure that the counter cannot disappear while its corresponding window is still active.

For example:

```text
Window size = 60 seconds
TTL = 120 seconds
```

The extra retention provides a safety margin.

Another approach is to calculate expiration from the end of the current window and add an appropriate margin.

### What Does Every Request Cost Now?

A local rate limiter only performs an in-memory operation.

A distributed rate limiter requires communication with an external store.

Every rate-limited request now incurs:

- Network communication.
- Serialization and deserialization.
- Shared-store processing.
- Connection management.
- Additional latency.

The time complexity of the Redis counter operation may still be O(1), but the network round trip makes it more expensive than a local map operation.

The shared store can also become a bottleneck under high request volume.

Possible optimizations include:

- Connection pooling.
- Efficient atomic scripts.
- Redis clustering or sharding.
- Local protective rate limiting.
- Carefully designed local quota allocation.

### What Happens When the Store Is Down?

If the shared store becomes unavailable, tryAcquire() cannot determine the current global counter.

The exact behavior of Version 9 in the tutorial run cannot be verified from the question PDF because the implementation and demonstration output are not included.

The two standard behaviors are fail-open and fail-closed.

#### Fail-Open

The limiter allows the request when the shared store is unavailable.

```java
try {
    return store.incrementAndExpire(key, ttl) <= limit;
} catch (StoreUnavailableException e) {
    return true;
}
```

Advantages:

- Preserves application availability.
- Prevents a rate-limiter outage from immediately stopping legitimate traffic.

Disadvantages:

- The global rate limit is temporarily unenforced.
- Users may exceed quotas.
- The application may become overloaded.

Fail-open is often suitable for availability-sensitive APIs when temporary quota violations are acceptable.

#### Fail-Closed

The limiter denies the request when the shared store is unavailable.

```java
try {
    return store.incrementAndExpire(key, ttl) <= limit;
} catch (StoreUnavailableException e) {
    return false;
}
```

Advantages:

- Prevents requests from bypassing the rate limit.
- Protects sensitive resources.
- Maintains stricter security and quota enforcement.

Disadvantages:

- Legitimate requests may be rejected.
- A shared-store outage can affect the entire service.

Fail-closed is often appropriate for security-sensitive operations, strict financial quotas, or expensive third-party API calls.

If the request is denied because the limiter infrastructure is unavailable rather than because the caller exceeded a quota, HTTP 503 Service Unavailable may be more appropriate than HTTP 429.

### Which Decision Must Be Made in Advance?

The application must explicitly decide whether to fail open or fail closed before a store outage occurs.

This decision depends on the business requirements.

| Requirement | Preferred Strategy |
|---|---|
| Application availability is the highest priority | Fail-open |
| Strict security enforcement | Fail-closed |
| Preventing expensive external API usage | Often fail-closed |
| Best-effort public API throttling | Often fail-open |
| Availability with limited overload protection | Local fallback limiter |

A local fallback limiter can reduce overload during a shared-store outage, but it cannot guarantee the original service-wide quota.

### Which Problem of Version 2 Returns?

Version 2 is a thread-safe fixed window counter.

Version 9 distributes the counter across service instances, but it still uses fixed-window semantics.

Therefore, the fixed-window boundary burst problem returns.

Suppose the global limit is 100 requests per minute.

A user sends:

```text
100 requests at 12:00:59
100 requests at 12:01:00
```

Redis correctly maintains separate counters for the two windows.

Each counter stays within its limit.

However, the user still sends 200 requests within approximately one second.

The shared store solves the distributed coordination problem.

It does not solve the limitations of the underlying rate-limiting algorithm.

To enforce an exact rolling-window limit, a distributed sliding window log or another suitable distributed algorithm would be required.

## Final Summary

### Rate Limiter Version Comparison

| Version | Algorithm or Feature | Memory per Key | Main Purpose |
|---|---|---|---|
| Version 1 | Fixed Window Counter | O(1) | Simple single-threaded rate limiting |
| Version 2 | Thread-safe Fixed Window Counter | O(1) | Concurrent local rate limiting |
| Version 3 | Sliding Window Log | O(L) | Exact rolling-window enforcement |
| Version 4 | Sliding Window Counter | O(1) | Approximate rolling-window enforcement |
| Version 5 | Token Bucket | O(1) | Burst allowance with average rate control |
| Version 6 | Leaky Bucket | O(1) | Minimum spacing between accepted requests |
| Version 7 | Safe Expired-State Cleanup | O(1) for leaky bucket state | Prevent unbounded key accumulation |
| Version 8 | Retry Information | O(1) for leaky bucket state | Inform rejected clients when to retry |
| Version 9 | Distributed Fixed Window Counter | O(1) per active key/window | Shared rate limits across instances |

L represents the maximum number of requests allowed within a sliding window.

### Algorithm Comparison

| Feature | Fixed Window | Sliding Log | Sliding Counter | Token Bucket | Strict-Spacing Leaky Bucket |
|---|---|---|---|---|---|
| Memory per key | O(1) | O(L) | O(1) | O(1) | O(1) |
| Exact rolling-window limit | No | Yes | No | No | Not its primary semantics |
| Boundary burst problem | Yes | No | Reduced, but approximate | No fixed boundary | No |
| Accumulates idle capacity | No | No | No | Yes | No |
| Supports configurable bursts | Limited by windows | Limited by rolling window | Approximate | Yes | No |
| Guarantees minimum spacing | No | No | No | No | Yes |
| Typical use case | Calendar quotas | Security limits | Large-scale API limits | Bursty API traffic | Strict third-party API pacing |

### Key Formulas

#### Fixed Window

```text
windowId = currentTime / windowSize

Accept if:
currentCount < limit
```

#### Sliding Window Log

```text
Remove timestamps <= currentTime - windowSize

Accept if:
remainingTimestampCount < limit
```

#### Sliding Window Counter

```text
weight = 1 - elapsedTime / windowSize

estimatedCount =
    currentCount + previousCount × weight

Accept if:
estimatedCount + 1 <= limit
```

#### Token Bucket

```text
refilledTokens = elapsedTime × refillRate

availableTokens =
    min(capacity, previousTokens + refilledTokens)

Accept if:
availableTokens >= 1
```

#### Leaky Bucket

```text
minimumInterval = 1 / allowedRate

Accept if:
currentTime >= nextAllowedTime

After acceptance:
nextAllowedTime = currentTime + minimumInterval
```

#### Retry-After

```text
retryAfterMillis =
    max(0, nextAllowedTime - currentTime)

retryAfterSeconds =
    ceil(retryAfterMillis / 1000)
```

#### Distributed Fixed Window

```text
windowId = wallClockMillis / windowSizeMillis

key = userId + ":" + windowId

count = atomicIncrementAndExpire(key, ttl)

Accept if:
count <= limit
```
