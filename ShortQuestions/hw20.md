# Homework 20 – Rate Limiter

## 1. Fixed Window Counter

### (a) Window boundary bursts

A client can use the full limit just before a window ends and again just after the next starts, allowing nearly twice the limit in a short interval. This follows from counting separate fixed windows, so removing it requires changing the limiting rule. Fixed windows fit calendar quotas, such as 1,000 calls per day with a midnight reset.

### (b) Version 1 and thread safety

With a count of 4 and a limit of 5, two threads can both read 4, accept, and write 5. Two requests passed, but only one increment was recorded. The plain HashMap and unsynchronized fields also lack safe visibility. Version 1 is suitable when only one thread calls the limiter.

### (c) Version 2 and compute

ConcurrentHashMap.compute makes the read, limit check, and update atomic for one key. Competing updates for that key wait, and updates to other keys in the same map bin may also wait. Version 2 is thread-safe because all changes to a key's state happen inside compute.

### (d) Injecting time

LongSupplier makes time controllable and tests repeatable. Production passes System::nanoTime for elapsed time. Tests pass a fake clock that they advance manually, allowing boundary tests without sleeping.

## 2. Sliding Window Rate Limiters

### (a) Version 3 decisions

Remove accepted timestamps at or before now minus the window length. If fewer than the limit remain, accept and add the current timestamp. Otherwise, reject. Counting the actual trailing window prevents the extra burst at a fixed-window boundary.

### (b) Memory usage

The log keeps up to one timestamp per accepted request within the window, so it uses O(limit) state per key. A fixed-window counter keeps only a window ID and count, using O(1) state per key. The log fits small, exact limits such as five login attempts in any minute.

### (c) Version 4 estimate

Estimated count = current count + previous count × (1 − elapsed time in current window / window length).

Accept when the estimate plus one is within the limit. This assumes requests were evenly distributed throughout the previous window.

### (d) Estimation errors

The estimate is too loose when previous requests are near the end of their window and still inside the trailing window, but only a fraction is counted. It is too strict when requests are near the beginning and have already expired, but a fraction is still counted. Version 4 fits large limits and many keys when small errors are acceptable.

## 3. Token Bucket and Leaky Bucket

### (a) Bursts and average rate

An idle token bucket fills up, allowing an immediate burst up to its capacity. Capacity controls the burst size, and refill rate controls the long-term rate. Fixed and sliding windows may reject part of that burst because their window limit can be smaller than the token bucket's capacity.

### (b) Lazy refilling

On arrival, calculate tokens = min(capacity, previous tokens + elapsed time × refill rate). An accepted request consumes one token. This accounts for refilling without a timer. A short interval can spend both saved tokens and newly refilled tokens, so accepted requests can exceed refill rate × interval length.

### (c) Version 6 behavior and state

Each accepted request adds one unit of water, which leaks at a fixed rate. Requests that would overflow are rejected. With capacity 1 and a rate of 5 per second, accepted calls must be at least 200 ms apart. Larger capacities can allow bursts, much like an equivalent token bucket.

The accepted rate can fall below the leak rate because arrivals may come while the bucket is full and leave idle gaps afterward. Each key stores only emptyAt. Its remaining level is max(0, emptyAt − now), measured in draining time, so leaking requires no background update.

### (d) Choosing a version

| Requirement | Choice and reason |
|---|---|
| 1,000 calls per calendar day | Version 2 fixed window, with boundaries aligned to midnight in the required time zone. |
| 5 login attempts in any minute | Version 3 sliding log for an exact trailing-minute limit. |
| 600 requests per minute with many keys and small acceptable error | Version 4 sliding counter for constant state per key. |
| 20 calls on page load and 5 calls/second on average | Version 5 token bucket with capacity 20 and refill rate 5/second. |
| At least 200 ms between calls | Version 6 leaky bucket with capacity 1 and leak rate 5/second. |

## 4. Memory Management and Distributed Rate Limiting

### (a) Keys that are never removed

Map entries depend on the number of distinct keys ever seen, even when current traffic is zero. Repeated requests to an existing key do not create more map entries, although the sliding log also stores recent timestamps. IP addresses and session IDs are risky because new values can keep arriving, including deliberately generated values.

### (b) Safe removal and Version 7

Remove a key only when its state is equivalent to a new key. For the leaky bucket, this means emptyAt <= now.

An unsafe sweep reads an empty bucket, then a request fills it. The sweep removes that updated entry, so another request sees a new empty bucket and passes too soon. Version 7 checks and removes inside computeIfPresent, which is atomic with tryAcquire's compute for the same key.

### (c) Version 8 retry information

acquireOrWaitNanos returns zero when accepted. On rejection, it returns level − maxLevelNanos, the time until another unit fits if no other request uses that space. HTTP uses 429 Too Many Requests with Retry-After expressed as whole seconds rounded up. The wait is guidance, so a later competing request can affect the retry.

### (d) Multiple service instances

Each instance has an independent allowance, so one user can consume allowances on several instances and exceed the service-wide limit. Version 8 fits a single-instance service or a limit intended to protect each instance separately.

### (e) Version 9 shared counter

The store must atomically increment a named counter and return its new value. Separate reads and writes can lose increments when instances race.

Wall-clock milliseconds let instances calculate the same window ID; System.nanoTime has no shared cross-process origin. Clocks should be synchronized. A TTL removes old counters, and the tutorial uses twice the window length. Its in-memory test store ignores TTL, so real storage must implement expiration.

Every request now costs a store round trip and adds store load. In the tutorial's outage run, tryAcquire throws IllegalStateException with “store unavailable.” The service must choose fail-open (allow) or fail-closed (reject) behavior in advance. Version 9 uses fixed windows, so Version 2's boundary burst returns.
