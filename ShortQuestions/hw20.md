## Question 1.

A limit on the total number of in-flight requests is not enough, because one misbehaving controller that lists all pods in a loop can occupy every slot and starve the scheduler and the kubelets. **API Priority and Fairness (APF)** (stable since 1.29) divides the API server's concurrency between classes of traffic.

| Concept | Meaning |
|---|---|
| FlowSchema | A rule that matches a request by user, verb, resource or namespace and assigns it to a priority level and to a flow (usually per user or per namespace) |
| PriorityLevel | A class of traffic with its own share of concurrency and its own queues |
| Fair queuing within a level | Requests wait in queues by flow and queues are served in turn, so a noisy flow delays itself more than others |
| Borrowing | An idle level lends unused capacity to busy levels |
| Exempt traffic | A small set of critical requests is not limited at all |
| Rejection | When queues are full the server returns HTTP 429 and the client must back off |

Critical system traffic, such as node heartbeats and leader election, sits at high priority levels, so overload from a custom controller does not make the control plane lose its nodes. The tradeoff is added queueing latency for everyone in exchange for isolation.

## Question 2.

In the API server request path, **mutating admission** runs first and may change the object (inject defaults, sidecars, labels). **Validating admission** runs after schema validation, may reject the request, and never changes the object (policies, quotas). Mutation runs before validation so that validation sees the final object, and validating admission is the last chance to refuse after all modifications are done.

Risks of **external admission webhooks** (the API server calls an external HTTPS service for each matching request):

- If the service is slow or down, the request stalls or fails according to the configured failure policy. A webhook with a "fail" policy turns an outage of the webhook service into an outage of every write it matches.
- If the webhook service runs on the cluster it protects, the cluster can enter a state where the service cannot start because its own pod creation is blocked.

Platforms therefore prefer in-process policies (declarative validation policies, no network call) where they are expressive enough, limit each webhook's scope with selectors, and keep webhook services outside the objects they admit.

## Question 3.

A controller is built from a chain of pieces:

| Piece | Responsibility |
|---|---|
| Informer (reflector plus cache) | Lists once and then watches a resource type, and maintains a local copy in memory; reads cost no API calls |
| Shared informer | One informer shared by all controllers in a process, so they do not open two watches for the same type |
| Event handler | Converts an event into a **key** (namespace/name of the affected object) |
| Work queue | Holds keys waiting to be reconciled; absorbs bursts, merges duplicates and spaces out retries |
| Reconcile function | Compares desired and actual state (read from the cache) and makes API calls to close the difference |

The flow is: the API server streams changes, the informer updates the local cache, handlers put keys into the queue, and workers take one key at a time and call reconcile. The queue **de-duplicates** keys (ten thousand events for one object need one evaluation), guarantees **one worker per key**, and uses **rate-limited retry** with a delay that doubles on each consecutive failure and resets on success, so a persistent failure does not become a hot loop.

## Question 4.

The reconcile function receives a key, not an event. It reads the current desired and actual state and takes the next step, so events are only a hint that something might have changed. This makes the controller survivable: if it is down for ten minutes, it does not need to know what happened in between, it reads the state and repairs everything still different.

It must be **idempotent** because running it twice must have the same effect as running it once. Otherwise a retry or duplicate trigger creates duplicate resources. It must also work from observed state and not keep side-channel state such as an in-memory counter, because after a restart or a missed event it would be wrong forever.

Recovery from missed events: the informer **relists** if a watch breaks and resumes from the new revision, and a periodic **resync** replays every object from the cache so every key is evaluated again even if no event arrived (it costs only local CPU).

Recovery from stale caches: the cache lags the API server, so the ReplicaSet controller can see 2 of 3 pods right after creating one and create a duplicate. Mitigations are **expectations** (count creations and deletions issued but not yet seen, and wait until the informer catches up or the expectation times out), checking writes at write time with resourceVersion so a conflict leads to a requeue with fresh state, and treating "not found" on a delete as success.

## Question 5.

A **CustomResourceDefinition (CRD)** registers a new resource type with the API server. The type is then stored in etcd, served through the same request pipeline, protected by the same authorization rules, listed and watched like any other object, and versioned and validated through a schema.

An **operator** is a controller for a custom resource that encodes operational knowledge. For example, a database operator watches a "database cluster" object and creates the pods, volumes and Services needed, handles upgrades, and reports status. The user writes the custom resource (desired state), the operator's reconcile loop watches it, and it creates ordinary objects (Deployment, Service, PVC) that the built-in controllers act on.

The framework gives durable replicated storage, authentication, authorization, audit, list/watch/versioning and tooling for free. The cost is that every instance counts against etcd quota and API server memory, and the operator itself must be correct and highly available. So custom resources suit declarative, low-volume state, not high-rate data such as per-request records or metrics.

## Question 6.

| Term | Meaning | Used by |
|---|---|---|
| Request | The amount the container is guaranteed and the scheduler reserves for it | Scheduler (placement), kernel (shares under contention), kubelet (eviction ranking) |
| Limit | The maximum the container may use | Kernel, through control groups |
| Capacity | The total resources of a node | Reported by the kubelet |
| Allocatable | Capacity minus what is reserved for the OS, Kubernetes daemons and the eviction threshold | Scheduler: the sum of requests on a node must not exceed allocatable |

The scheduler never measures actual usage, it only adds up requests. At the limit, CPU is throttled (it is compressible), while memory is a hard cap and exceeding it causes an OOM kill.

QoS classes (decided by requests versus limits) set who is sacrificed first when a node runs short of memory:

| Class | Rule | Protection |
|---|---|---|
| Guaranteed | Every container has CPU and memory requests equal to limits | Least likely to be killed; lowest kernel OOM score |
| Burstable | At least one request or limit is set, but not meeting the Guaranteed rule | Middle |
| BestEffort | No requests or limits at all | Killed first |

Under node-pressure eviction the kubelet picks pods using more than their request first, then lower priority, then by how far usage exceeds the request. The kernel OOM kill uses an OOM score derived from the QoS class.

## Question 7.

The scheduler is a controller: it watches pods with no node, picks a node, and writes the node name into the pod. It does not start anything, the kubelet does. Each pod goes through a scheduling cycle (one pod at a time) and then a binding cycle.

| Step | What happens |
|---|---|
| Filtering | Removes nodes that cannot run the pod (resources, taints, volumes, affinity). The search stops once enough feasible nodes are found (default adaptive, e.g. 500 of 5,000 nodes) |
| Scoring | Ranks the feasible nodes by weighted plugin scores (spread, resource balance, image locality, ...) and the best node is picked |
| Reservation | Reserve records the pod as "assumed" on the chosen node in the scheduler's cache, so the next cycle already sees the reduced capacity |
| Binding | PreBind, Bind and PostBind run asynchronously: prepare (for example bind volumes) and write the node name to the pod. A failure triggers Unreserve |

If no node passes filtering, PostFilter tries preemption, otherwise the pod goes to the unschedulable pool. The serial cycle makes decisions see each other's effects without locking, and the parallel binding cycle keeps API latency off the serial path.

## Question 8.

| Mechanism | Declared on | Effect |
|---|---|---|
| Node affinity (and node selector) | Pod | The pod may (or prefers to) run only on nodes with certain labels; cheap label check |
| Pod affinity (and anti-affinity) | Pod | Place near, or away from, pods with given labels within a topology domain such as a node or zone; expensive, not advised on clusters larger than a few hundred nodes |
| Taint and toleration | Node and pod | A taint repels all pods unless a pod tolerates it; used to reserve nodes (for example GPU nodes) for workloads that need them |
| Priority-based preemption | Pod priority | When no node fits a pod, PostFilter looks for a node where deleting lower-priority pods makes room |

Affinity and taints are placement constraints that narrow or bias the choice of node. Preemption is different: it is not a constraint on placement but a way to decide who loses when capacity is short. The scheduler picks victims that minimize disruption, marks the node as the pod's nominated node, and the victims terminate with their normal grace period before the pod is scheduled. Priority does not divide capacity fairly between teams, which is the job of quota and queueing systems.

## Question 9.

| Component | Responsibility |
|---|---|
| Kubelet | Agent on the node and a controller: it watches pods assigned to its node and makes the runtime match them. For each pod it has the runtime create the sandbox, pull images and start containers in order, runs probes, creates cgroups, and reports status to the API server |
| CRI | A gRPC API (image service and runtime service) through which the kubelet calls a container runtime such as containerd or CRI-O. The runtime creates the pod sandbox first, then the containers (the OCI runtime, for example runc, creates the isolated process) |
| CNI | A plugin interface for pod networking. The runtime calls the plugin when the sandbox is created, and the plugin allocates an IP, creates the virtual interface that connects the sandbox to the node, and installs routes |

In short, the kubelet decides what should run and drives the process, the CRI runtime creates the sandbox and containers, and the CNI plugin gives the sandbox its network. The kubelet does not start containers itself.

## Question 10.

A **Service** gives a stable virtual IP and DNS name to a set of pods chosen by a label selector. The **EndpointSlice controller** in the control plane keeps the list of Ready pod IPs in EndpointSlices (up to 100 endpoints each by default). **kube-proxy** on every node watches them and programs local kernel rules (iptables, nftables or IPVS) that rewrite packets sent to the virtual IP to one pod IP. **CoreDNS** (the cluster DNS add-on) resolves a Service name to its virtual IP.

The virtual IP belongs to no interface and exists only as a rule in each node's kernel, so there is no proxy process in the data path. EndpointSlices replace the single Endpoints object so a change to one backend resends only a small slice (in the tutorial's example, 15 KB instead of 150 KB). Only pods whose readiness probe passes appear as ready endpoints.

| | Regular ClusterIP Service | Headless Service |
|---|---|---|
| Virtual IP | Yes | None |
| DNS answer | The virtual IP | The addresses of its ready pods |
| Use | Load balancing to any backend | Clients that need individual pods, such as stateful systems and multi-node inference groups |
