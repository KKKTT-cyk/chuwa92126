# kubernetes-ai-inference-homework-2

1. API Priority and Fairness (APF) controls how the Kubernetes API server shares its capacity among requests. It groups requests by priority and uses fair queuing within each level. If a controller keeps listing all Pods, its requests may have to wait or receive a 429 Too Many Requests response. This leaves capacity for critical requests, such as node heartbeats, even when the API server is busy.


2. Mutating admission can change an object before it is saved, such as adding a sidecar container to a Pod. Validating admission checks the final object against cluster policies and can reject it if it breaks a rule. External webhooks add a network dependency, so a slow webhook delays matching requests. If the webhook is unavailable, the API server either rejects the request or skips that webhook and continues.


3. Informer uses List and Watch to keep a local cache up to date. When something changes, an event handler adds the affected object’s key to a work queue. A worker takes the key and runs the reconcile function, which reads the cache, compares the current state with the desired state, and makes any needed changes through the API server.


4. Reconciliation should be level-triggered so the controller can compare the current state with the desired state even if it misses an event. It should also be idempotent so repeated checks don’t create extra resources once the desired state is reached. If the watch can’t resume from its last resource version, the informer lists the resources again to refresh its cache and restarts the watch. The controller can then reconcile using the updated state.


5. CRD adds a new resource type to the Kubernetes API and defines the fields users can set. Operator is a controller that watches those resources and takes action to reach the desired state. For example, ModelService CRD lets users specify a model and a replica count, and its Operator creates or updates a Deployment to run that model.


6. Requests tell the scheduler how much CPU or memory to set aside for a Pod. Limits cap how much it can use at runtime. Capacity is a node’s total resources, and allocatable is the portion available to Pods after system reservations. Under memory pressure, the kubelet considers Pods using more than their requests for eviction first. BestEffort Pods are usually more vulnerable, Burstable Pods depend on their usage, and Guaranteed Pods are generally the most protected.


7. The scheduler first filters out nodes that don’t meet the Pod’s requirements, such as its CPU request. It then scores the remaining nodes and selects one with the highest score. During reservation, it temporarily accounts for the Pod’s requests on that node so it can schedule other Pods correctly. Finally, it binds the Pod to the selected node through the API server, and the node’s kubelet starts the containers.


8. Node affinity uses node labels to specify where a Pod must or prefers to run. Pod affinity uses the location of other Pods, such as a preference to run in the same zone as a cache Pod. Taints let nodes restrict placement, and a matching toleration allows a Pod to be considered for that node. If a high-priority Pod can’t be scheduled, preemption can remove lower-priority Pods from a node when doing so would make room for it.
   

9. After a Pod is assigned to a node, the kubelet reads the Pod spec and coordinates startup on that node. It uses CRI to ask the container runtime to create a sandbox for the Pod. During sandbox setup, the runtime uses CNI to call network plugins that set up the Pod’s network interface, IP address, and routes. Once the sandbox is ready, the kubelet uses CRI again to have the runtime pull any needed images and start the application containers.


10. A Service gives clients a stable name and uses a selector to identify its backend Pods. EndpointSlices track the Pods’ IP addresses, ports, and readiness. For a regular ClusterIP Service, CoreDNS resolves the Service name to its virtual IP. kube-proxy uses the Service and EndpointSlices to set up rules that forward connections to a ready backend. A headless Service has no virtual IP, so DNS returns the ready Pod IPs directly and the client connects to one of them.
