1. API priority and fairness is a traffic control mechanism in the Kubernetes API server which could protect the API server.
It divides the server's concurrency between classes of traffic so that could prevent a misbehaving controller from 
starving critical system traffic. If a misbehaving controller floods the API server, its excess requests can be queued 
or rejected with a 429 response code. Critical system traffic in a separate priority level still has capacity to make progress.
2. Mutating admission tells us if the object should be modified, and it runs before validation so that the validation sees
the final objects. Validating admission tells if the final object satisfied the policy, and it is the last chance to
refuse after all modifications are done.
   External admission webhooks add a network dependency to the request path. If a webhook is slow, it increases latency for
matching API requests. If it’s unavailable or times out, failurePolicy: Fail rejects the request, while Ignore lets it 
continue without that webhook’s check or mutation. The trade-off is between API availability and consistent policy 
enforcement.
3. An informer uses LIST and WATCH to keep a local cache in sync with the API server. When a relevant object changes, 
an event handler puts its key on a work queue. A worker takes the key, reads the latest available state from the cache,
and reconciles it with the desired state. If a change is needed, it writes through the API server. If reconciliation 
fails with a temporary error, the work item can be retried with backoff.
4. Reconciliation should be level-triggered because events are signals to check the current state. If a controller 
misses a Pod deletion, it can still notice on a later reconcile that only two Pods remain while the desired count is 
three. Reconciliation should also be idempotent so the controller can safely process the same key again. Once it 
observes three Pods, it has no reason to create another one.
   To recover from missed events, the informer resumes its watch from the last known resourceVersion. If that version is
too old, it re-lists the objects, rebuilds the cache, and starts a new watch. If stale cached data causes an update to 
return 409 Conflict, the controller fetches the latest object, recalculates the change, and retries if it’s still needed.
5. A CRD extends the Kubernetes API by defining a new resource type, such as PostgresCluster. Users create instances of 
that resource to declare what they want, for example, a PostgreSQL cluster with three replicas. An Operator uses a 
controller to watch those resources and reconcile the actual state with the desired state. It can create the underlying 
Kubernetes objects and automate application-specific tasks like backups and upgrades.
6. Capacity is the node’s total resources. Allocatable is the portion available to Pods after system reservations. The 
scheduler uses requests to decide whether a Pod fits on a node, and limits constrain resource usage at runtime. 
Kubernetes assigns Pods a QoS class based on their CPU and memory configuration. Under memory pressure, the kubelet 
considers Pods that exceed their requests first, then uses Pod priority and usage relative to requests to rank them.
7. The scheduler first filters out nodes that can’t meet the Pod’s requirements, such as CPU requests or node selectors.
It then scores the feasible nodes and chooses one with the highest score. During reservation, it provisionally accounts 
for the Pod’s resources on that node so another scheduling decision doesn’t count the same capacity as free. If binding 
fails, the reservation is released. Finally, binding records the node assignment through the API server, and the kubelet
on that node starts the containers.
8. Node affinity uses node labels to require or prefer certain nodes. Pod affinity use the labels and locations of other
Pods to place workloads together or apart, within a node or zone. A NoSchedule taint keeps Pods off a node unless they 
have a matching toleration. That toleration makes the node eligible, and the scheduler still checks the other 
requirements. With priority-based preemption, if a high-priority Pod cannot be scheduled, the scheduler can remove 
lower-priority Pods from a node if doing so makes that node feasible.
9. The kubelet sees that a Pod is assigned to its node. It uses CRI to ask the container runtime to set up the Pod and 
start its containers. During setup, the runtime uses CNI plugins to give the Pod an IP address and connect it to the 
cluster network.
10. A regular ClusterIP Service gives clients a stable DNS name and a virtual IP. CoreDNS resolves the Service name to 
that IP. EndpointSlices track the backend Pod IPs, ports, and readiness. Kube-proxy watches Services and EndpointSlices 
and sets up rules that forward traffic from the virtual IP to a ready backend Pod.
    A headless Service is configured with clusterIP: None. For a headless Service with a Pod selector, CoreDNS returns 
the ready backend Pod IPs directly. The client chooses an IP and connects to that Pod.
