#### Conceptual Questions

1. **Fixed Window Counter**

   **(a) Why can a fixed window counter allow a burst of requests across a window boundary even when each individual window stays within its limit? Why does no change inside the class remove this effect? For which kind of limit is the fixed window still the right choice?**

   A fixed window resets its counter at each boundary. A client can send the full limit just before the reset and another full limit just afterward. For example, five requests at 900-980 ms and five at 1000-1080 ms all pass a limit of five per fixed second, giving ten accepted requests in 180 ms. Each fixed window still obeys its own limit. Synchronization or a different map cannot remove this behavior while preserving the same fixed-window rule; preventing it requires a different policy, such as a sliding window or an additional burst limit. Fixed windows are appropriate for quotas defined per calendar period, such as 1,000 calls per day resetting at midnight. Calendar quotas must use the intended time zone and calendar boundaries; the tutorial's `nanoTime` windows alone do not represent midnight.

   **(b) Version 1 keeps the window and the count in a plain HashMap. Explain how two threads can both accept a request while losing an update to the stored count. Why is Version 1 not thread-safe, and when is it still the right choice?**

   Suppose the limit is five and the stored count is four. Thread A reads four, and thread B also reads four before A updates it. Both find room, both accept, and both write five. Two requests pass while the count increases by only one. The check and increment are separate operations, and neither the plain fields nor `HashMap` provide the needed synchronization or visibility guarantees. Concurrent creation or reset of a window can also race. Version 1 is appropriate when all calls are confined to one thread, such as a batch job throttling its own outgoing requests.

   **(c) What does ConcurrentHashMap.compute(key, function) guarantee for one key, and which other keys can such a call hold up? How does this make Version 2 thread-safe?**

   `ConcurrentHashMap.compute` atomically computes and updates the mapping for one key. Competing updates to that key are serialized, so Version 2 performs the window reset, limit check and increment as one protected operation. All access to the mutable window state follows this rule. Updating a different key can also be delayed if it shares the same internal hash bin; this is not a lock over the entire map. Keep the callback short because other updates may wait. Merely replacing `HashMap` with `ConcurrentHashMap` while retaining separate reads and writes would not make the compound decision atomic.

   **(d) Why do the classes receive the time from a LongSupplier instead of reading the system clock themselves? What does production code pass, and what does a test pass?**

   Injecting a `LongSupplier` separates time measurement from the limiting algorithm. Production code for the local elapsed-time versions passes `System::nanoTime`, which measures elapsed time without depending on wall-clock corrections. Tests pass a controllable clock, such as `AtomicLong::get`, and advance it explicitly to test boundaries, refilling and expiry without sleeping. The units must match the class. Version 9 instead requires epoch milliseconds, typically supplied by `System::currentTimeMillis`, because different processes must agree on window identifiers.

2. **Sliding Window Rate Limiters**

   **(a) How does the sliding window log of Version 3 decide whether to accept a request? Why does it avoid the fixed-window boundary burst?**

   Version 3 stores the timestamps of accepted requests for each key in an `ArrayDeque`. At time `now`, it removes timestamps whose age is at least the window length `W`, leaving requests in `(now - W, now]`. If fewer than `limit` timestamps remain, it appends `now` and accepts; otherwise it rejects without adding a timestamp. The cleanup, check and append run atomically per key. Since the interval moves with each request, crossing a fixed clock boundary does not erase recent requests. In the example, the five requests at 900-980 ms still count at 1000 ms, so the next burst is rejected.

   **(b) Why does the memory usage of the sliding window log grow with the limit, while the fixed window counter uses a fixed amount of state per key? When is the log still the right choice?**

   The log retains one timestamp for each accepted request still represented in the key's queue, up to `limit` timestamps. It therefore needs O(limit) state per key, including queue and timestamp-object overhead. A fixed-window counter only stores a window identifier and a count, so its state per key is O(1), independent of the limit. The log is suitable when the limit is small and an exact rolling-window rule matters, such as five admitted login attempts in any minute. The tutorial records accepted requests only; rejected attempts do not extend the window.

   **(c) How does the sliding window counter of Version 4 estimate the number of requests in the sliding window? On which assumption does the estimate rest?**

   Version 4 keeps a current-window count, a previous-window count and a window identifier. If fraction `f` of the current window has elapsed, it estimates the existing rolling count as `current + previous * (1 - f)`. It accepts the new request only when `estimate + 1 <= limit`. At a transition to the immediately next window, the old current count becomes the previous count; after skipping more than one window, the previous count becomes zero. The estimate assumes requests in the previous window were spread uniformly through that window. It cannot recover their actual positions because it does not store timestamps.

   **(d) The tutorial shows one case in which the estimate is too loose and one in which it is too strict. Explain where the requests of the previous window lie in each case. When is Version 4 still the right choice?**

   In the too-loose example, the previous window's five requests occur near its end, at 900, 920, 940, 960 and 980 ms. At 1500 ms, all five still belong to the true rolling interval `(500, 1500]`, but Version 4 counts only half of them: `5 * 0.5 = 2.5`. With no earlier accepted request in the current window, it admits a sixth request that the exact log rejects.

   In the too-strict example, the previous window's requests occur near its beginning, at 0, 20, 40, 60 and 80 ms. At 1100 ms, all have expired from `(100, 1100]`, but the estimate still includes `5 * 0.9 = 4.5`. Adding one exceeds five, so Version 4 rejects while the exact log accepts. Version 4 remains suitable for large limits and many keys when approximation is acceptable, such as 600 requests per minute per API key. Its memory stays O(1) per key, but the error can be substantial for highly clustered traffic.

3. **Token Bucket and Leaky Bucket**

   **(a) Why can a token bucket allow a burst after a client has been idle, while fixed and sliding window limiters may reject part of that burst? Which token bucket parameter sets the burst that passes, and which one sets the long-term rate?**

   A token bucket accumulates unused tokens up to its capacity while a client is idle. Each accepted request consumes one token, so a full bucket can admit an immediate burst of up to `capacity` requests. The capacity determines the permitted burst, while `refillPerSecond` determines the sustained rate. Window limiters count requests against a window quota and do not accumulate additional credit over multiple idle windows. For example, a token bucket with capacity ten and refill rate five per second accepts eight simultaneous requests after being idle, while a five-request window quota rejects three if they fall in the same counted window.

   **(b) Why does the token bucket class need no timer that adds tokens? How does it account for refilling when a request arrives? Why can the number of requests accepted during a short interval exceed what the refill rate alone suggests?**

   Version 5 refills lazily when a request arrives. It computes `tokens = min(capacity, tokens + elapsedNanos * refillPerNano)`, updates the last-refill timestamp and consumes one token if available. No state needs to change while the key is idle because elapsed time determines the missing refill exactly when needed. A short interval can consume both stored tokens and newly generated tokens, so its accepted count can exceed `rate * duration`. The usual bound is `capacity + rate * duration`; the burst allowance is additional initial credit, not an increase in the long-term refill rate.

   **(c) How does the leaky bucket of Version 6 differ from the token bucket in handling bursts? Why can its long-run accepted rate depend on the arrival pattern even when the leak rate is fixed? What is the whole state of a key in this class, and why does the leaking need no update?**

   Version 6 is a leaky-bucket meter: it immediately accepts or rejects and does not queue requests for later delivery. With the tutorial's capacity of one and leak rate of five per second, accepted calls must be at least 200 ms apart. Unlike a token bucket with a larger capacity, it cannot accumulate enough idle credit for several simultaneous calls. A leaky-bucket meter with a larger capacity can also admit bursts; the bucket name alone does not guarantee evenly spaced calls.

   The leak rate is an upper rate constraint, not a guarantee of achieved throughput. If requests arrive every 150 ms with capacity one, calls at 0, 300, 600 ms and so on pass, while the intervening calls fail. This gives about 3.33 accepted requests per second despite a leak rate of five. There is no queued call to fill the unused opportunity at 200 ms. The entire per-key state is `emptyAt`, the timestamp when the bucket will be empty. Its level in units of leaking time is `max(0, emptyAt - now)`. Each accepted request extends that time by one unit's drain duration; advancing `now` automatically reduces the calculated level, so leaking needs no background update.

   **(d) Choose a version for each requirement and give the reason: 1. "1,000 calls per calendar day, reset at midnight" 2. "5 login attempts in any minute" 3. "600 requests per minute per API key, with many keys, where a small error is acceptable" 4. "a page sends 20 calls at once when it loads, and 5 calls per second are allowed on average" 5. "a third-party API rejects a second call within 200 ms"**

   For "1,000 calls per calendar day, reset at midnight," choose Version 2, the fixed window counter, because the quota resets at a defined calendar boundary. Use a wall-clock date in the intended time zone; Version 1 is sufficient if only one thread calls the limiter.

   For "5 login attempts in any minute," choose Version 3, the sliding window log, because it enforces an exact rolling 60-second limit and needs only five timestamps per key.

   For "600 requests per minute per API key, with many keys, where a small error is acceptable," choose Version 4, the sliding window counter. It uses constant state per key and estimates the rolling count, making it suitable when memory efficiency matters and approximation is acceptable.

   For "a page sends 20 calls at once when it loads, and 5 calls per second are allowed on average," choose Version 5, the token bucket. Set the capacity to 20 and the refill rate to five tokens per second so a full bucket permits the page-load burst while the refill rate constrains sustained traffic.

   For "a third-party API rejects a second call within 200 ms," choose Version 6, the leaky bucket. Set the capacity to one and the leak rate to five per second so accepted calls are at least 200 ms apart.

4. **Memory Management and Distributed Rate Limiting**

   **(a) Every version up to Version 6 adds a map entry for a new key and never removes it. What does the memory usage depend on, what does it not depend on, and why is a key such as an IP address or a session id a risk?**

   Versions 1-6 retain an entry for every distinct key encountered during the process's lifetime. Map size therefore depends on historical key cardinality, not just current request rate or the number of currently active users. A long idle period does not shrink the maps. Total memory also depends on key size and per-key state; the sliding log additionally depends on the configured limit. IP addresses and session IDs are risky because their population can continually grow, and clients may generate many new identities. Even keys seen only once remain stored indefinitely.

   **(b) When can the entry of a key be removed without changing any later decision, and which state is that for the leaky bucket? A sweep that calls get and then remove runs while request threads call tryAcquire. Describe an interleaving that accepts a key more often than its capacity allows, and explain how Version 7 rules it out.**

   An entry can be removed when its state is behaviorally equivalent to a never-seen key, so deleting it cannot change a future admission decision. In Version 6, this means the bucket is empty: `emptyAt <= now`.

   For an unsafe sweep, assume capacity one and an expired entry. The sweeper reads it and decides it is empty. Before deletion, request A fills the bucket and is accepted. The sweeper then removes the key using its stale decision, deleting A's new state. Request B immediately sees an absent key, starts with an empty bucket and is also accepted, although the required drain interval has not elapsed.

   Version 7 checks expiry and returns `null` to remove the mapping inside `computeIfPresent`. Request admission uses `compute` for the same key, so cleanup and admission cannot interleave inside these operations. If cleanup happens first, admission creates fresh state; if admission happens first, cleanup sees the new nonempty state and retains it.

   **(c) How does Version 8 tell a rejected caller how long to wait? Which HTTP status and which header carry a rejection, and how is the wait represented in that header?**

   Version 8 adds `acquireOrWaitNanos`. It returns zero when it accepts a request, or a positive wait when it rejects. If `level` is the current water level measured in nanoseconds and `maxLevelNanos` is the largest level at which another unit fits, the wait is `level - maxLevelNanos`. Rejection leaves the bucket unchanged, and `tryAcquire` simply tests whether the returned wait is zero. This wait reflects the current state; another request for the same key may consume the next opportunity before the caller retries.

   An HTTP adapter returns `429 Too Many Requests` and a `Retry-After` header. The tutorial uses a delay in whole seconds, rounded up: a 180 ms wait becomes `Retry-After: 1`. It must not send nanoseconds or a decimal value as delay-seconds. HTTP also permits an HTTP-date representation.

   **(d) Why can running Version 8 independently on multiple service instances allow one user to exceed the intended service-wide limit? Name the two situations in which Version 8 is still the right choice.**

   Each Version 8 instance has its own independent map, so the same user receives separate allowances when traffic reaches different instances. In the tutorial, four instances each receive that user's calls 200 ms apart and accept them all, producing an aggregate 20 requests per second despite a per-instance rate of five. The instances do not share the history needed for a service-wide decision. Version 8 remains appropriate when the service has only one instance, or when the intended policy protects each instance separately rather than enforcing a global user quota.

   **(e) Version 9 keeps the count in a store that all instances share. Which single operation must the store offer, and why is a read followed by a write not enough? Why does the class take wall-clock milliseconds, and why does every counter get a time to live? What does every request cost now, what does tryAcquire do in the run of the tutorial when the store is down, which decision has to be made in advance for that case, and which problem of Version 2 is back?**

   Version 9 requires `incrementAndGet(name, ttlMillis)`: atomically add one to the shared counter and return the new value. The name combines the user key and window identifier, and the request passes only if the returned value is at most the limit. Separate reads and writes are insufficient: two instances could both read four, both write five and both accept. The shared store must serialize the increment itself. In this version even rejected requests increment the counter; they remain rejected once its value exceeds the limit.

   The clock supplies wall-clock epoch milliseconds so all instances derive compatible window identifiers. `System.nanoTime()` has a process-specific origin and cannot define shared windows. Clock agreement still matters: skew near a boundary can split traffic between different counters. Each counter gets a TTL so obsolete windows do not remain forever. The tutorial uses twice the window length, which retains the counter beyond its active window under its clock assumptions. Its in-memory test store deliberately ignores TTL; a production store must implement expiration and reliably establish it when creating the counter.

   Every attempt now costs a network round trip and a shared-store operation, adding latency, store load and an availability dependency. In the tutorial's outage run, `tryAcquire` propagates `IllegalStateException: store unavailable`; it does not automatically return true or false. The service must decide beforehand whether an outage means fail-open, allowing requests, or fail-closed, denying them. Finally, Version 9 returns to fixed-window counting, so Version 2's boundary burst returns. Sharing state fixes coordination across instances but does not change the algorithm's window semantics.
