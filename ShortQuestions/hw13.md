# HW13 – Java Advanced Syntax

## Question 1.

A **static nested class** does not need an instance of the outer class and can only use the outer class's static members. An **inner (non-static) class** needs an outer instance (`outer.new Inner()`) and can use the outer instance's fields as if they were its own. Inside the inner class, `Outer.this` is the enclosing instance and `this` is the inner object.

The JVM has no concept of a class inside a class, so the compiler turns each nested class into a separate class file (`Outer$Inner`) and gives the inner class a **hidden synthetic field `this$0`** that points to the outer object; the constructor receives the outer instance as a hidden argument. This is the only way an inner method can write `counter++` on the outer object's field. A static nested class has no `this$0` field.

Because of that reference, an inner object keeps its outer object alive. A long-lived inner object (a cache entry, a listener, a task in a queue) therefore prevents a large outer object, such as a service with big buffers, from being garbage collected: this is the **memory leak**.

A static nested class is usually preferred because it avoids the leak, has no extra reference field (smaller objects), is easier to create and test (`new Nested()` works anywhere), and states clearly that it does not depend on an outer object. The rule of thumb is to start with `static` and remove it only when the nested class truly needs the outer instance.

## Question 2.

**Type erasure** means generics exist only at compile time. After type checking, the compiler erases the type parameters: `T` becomes its bound (`Object` if unbounded) and casts are inserted where needed. `List<String>` becomes the raw `List`, and `String s = l.get(0)` becomes `String s = (String) l.get(0)`. So `List<String>` and `List<Integer>` are the same class at runtime.

| Not allowed | Why |
|---|---|
| `new T()` | The runtime does not know what `T` is |
| `new T[10]` | An array needs its element type at runtime |
| `obj instanceof List<String>` | `List<String>` does not exist at runtime (`List<?>` is allowed) |

A **bridge method** is a synthetic method generated by the compiler so that overriding still works after erasure. For example, `Box<T>` has `T get()`, which erases to `Object get()`. `IntBox extends Box<Integer>` overrides it with `Integer get()`, whose signature is different. To make the override work, the compiler generates a bridge `Object get()` in `IntBox` that calls `Integer get()`.

## Question 3.

**PECS** means **Producer Extends, Consumer Super**. If a parameter produces values that you read, use `? extends T`. If it consumes values that you write, use `? super T`. If you both read and write, use the exact type `List<T>`. Example: `static <T> void copy(List<? super T> dst, List<? extends T> src)`.

| Type | Reading | Adding | Why |
|---|---|---|---|
| `List<? extends Number>` | Yes, as `Number` | No (only `null`) | The real list might be `List<Integer>` or `List<Double>`; adding a `Double` to a hidden `List<Integer>` would break it |
| `List<? super Integer>` | Only as `Object` | Yes, `Integer` | The real list is a list of `Integer` or a supertype, so an `Integer` always fits, but an element read out could be any supertype |

**Invariance vs covariance:** arrays are covariant (`String[]` is a subtype of `Object[]`), while generics are invariant (`List<String>` is not a `List<Object>`). If `List<String>` were a `List<Object>`, you could add an `Integer` through the `Object` view and corrupt the `String` list. Arrays tried covariance first, and the price is a runtime check: `Object[] objs = new String[1]; objs[0] = 1;` compiles but throws `ArrayStoreException`. Generics prefer a compile-time guarantee.

## Question 4.

| Retention | Where it is kept | Who can read it |
|---|---|---|
| `SOURCE` | Source only, discarded by the compiler | Compiler, annotation processors (e.g. `@Override`) |
| `CLASS` (the default) | Written to the class file, not visible to reflection | Bytecode tools |
| `RUNTIME` | Written to the class file and readable by reflection | Your code through reflection (e.g. dependency injection, validation) |

- **`@Target`** controls where the annotation may be placed (`TYPE`, `METHOD`, `FIELD`, `PARAMETER`, and so on). Without it, the annotation can be applied to almost any declaration; with it, the compiler enforces the placement.
- **`@Inherited`** makes a class-level annotation visible on subclasses (not on interfaces, methods or fields).
- **`@Repeatable`** allows the same annotation to be used more than once. It needs a container annotation that holds an array; the compiler wraps the repeated annotations into the container, and `getAnnotationsByType` reads them.

To be read through reflection at runtime, an annotation must have **`@Retention(RetentionPolicy.RUNTIME)`**. Because the default is `CLASS`, forgetting it makes `isAnnotationPresent` return `false`.

## Question 5.

**Ways to obtain a `Class` object:**

1. Class literal, at compile time: `Person.class` (also `int.class`, `int[].class`).
2. By name, at runtime: `Class.forName("pkg.Person")`, which may throw `ClassNotFoundException`.
3. From an instance: `new Person().getClass()`.

All three return the same object for the same type (`c1 == c2 == c3`).

**`setAccessible(true)`** turns off Java's access check for a reflective member, so reflection can use a private field, method or constructor. Without it, `f.get(acc)` on a private field throws `IllegalAccessException`. **The module system limits it:** since Java 9, and strongly since Java 17 (JEP 403), JDK internals are strongly encapsulated, so `setAccessible(true)` on a private member of a JDK class (such as `String.value`) throws `InaccessibleObjectException` because `java.base` does not "opens java.lang" to the unnamed module. For your own code, `opens` in `module-info.java` or the `--add-opens` command-line flag grants access.

**`InvocationTargetException`:** `Method.invoke` wraps any exception thrown by the target method in an `InvocationTargetException`, and the real error is available through `e.getCause()`. This way the exception from the target method arrives as the cause of the reflective call's own exception type, separate from the reflection errors such as `NoSuchMethodException`, `IllegalAccessException` and `IllegalArgumentException`. The caller must unwrap it, otherwise the logs show an `InvocationTargetException` with no message and the real cause is hidden.

```java
try { Boom.class.getMethod("go").invoke(new Boom()); }
catch (InvocationTargetException e) { System.out.println(e.getCause()); } // the real exception
```

## Question 6.

The complete code is in `Coding/hw13/Validator.java`. `validate` walks from the object's own class up through its superclasses (but not `Object`) and checks every non-static field that has a validation annotation:

- `@NotNull` fails when the value is `null` (`must not be null`).
- `@NotBlank` applies to `String` fields and fails when the value is `null` or only whitespace (`must not be blank`).
- `@Range` applies to `int`/`long` fields and their wrappers and fails when the value is outside `min..max` (`must be between <min> and <max>`); a `null` wrapper value is not checked.

Every violation is `<fieldName>: <message>`, a field with several annotations can produce several violations, and the list is sorted in natural `String` order. A `null` target throws `IllegalArgumentException`.

```java
public static List<String> validate(Object target) {
    if (target == null) {
        throw new IllegalArgumentException("target must not be null");
    }
    List<String> violations = new ArrayList<>();
    // Walk up from the object's own class to its superclasses, but not Object itself
    for (Class<?> type = target.getClass(); type != null && type != Object.class; type = type.getSuperclass()) {
        for (Field field : type.getDeclaredFields()) {
            if (Modifier.isStatic(field.getModifiers())) {
                continue;                                  // static fields are ignored
            }
            checkField(target, field, violations);
        }
    }
    Collections.sort(violations);                          // natural String order
    return violations;
}
```

Fields can be private, so each checked field is made readable with `setAccessible(true)`. Fields without a validation annotation are never touched.
