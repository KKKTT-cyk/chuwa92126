  #### Conceptual Questions

  1. **Explain the difference between a static nested class and an inner (non-static) class. Describe the hidden reference an inner class holds, how it can cause a memory leak, and why a static nested class is usually preferred.**

     A static nested class does not need an instance of its enclosing class and can be created with new Outer.Nested(). It can directly access the outer class's static members, but needs an explicit object reference to access instance members. An inner class is associated with an enclosing instance and is created with outer.new Inner(). It can directly access that object's instance members, including private ones. The compiler normally stores a hidden reference to the outer object in a field such as this$0. If a long-lived listener, cached object or queued task holds the inner object, the outer object may also remain in memory even when it is no longer needed. A static nested class is usually preferred when access to the outer instance is unnecessary because it avoids this implicit reference, makes dependencies clearer, and is easier to create and test. Newer javac versions targeting Java 18 or later can omit an unused outer-instance field, but declaring the class static still expresses the intended design.

  2. **Explain type erasure: what the compiler does with List<String>, why new T(), new T[10] and obj instanceof List<String> are not allowed, and what a bridge method is and why the compiler generates it.**

     Type erasure means the compiler checks generic types at compile time and then removes type arguments from executable type operations. List<String> uses the runtime List type, and the compiler inserts casts when needed, such as casting the result of get() to String. A type variable becomes its leftmost bound, or Object if it has no bound. Generic declarations can still retain signature metadata for reflection. new T() is not allowed because T does not identify a concrete class or guarantee a no-argument constructor. new T[10] is not allowed because an array needs a runtime component type, but T is erased. When obj has type Object, obj instanceof List<String> is not allowed because the JVM cannot check the list's element type argument; instanceof List<?> can check only whether the object is a list. A bridge method is a synthetic method generated to preserve overriding after erasure. For example, if Box<T>.get() erases to Object get() and StringBox overrides it with String get(), the compiler adds an Object-returning bridge that delegates to String get(), preserving polymorphism through a Box reference.

  3. **State the PECS rule. For List<? extends Number> and List<? super Integer>, say which operations (reading, adding) are allowed on each one and why, and explain why generics are invariant while arrays are covariant.**

     PECS means Producer Extends, Consumer Super. List<? extends Number> produces values that can safely be read as Number or Object, but no non-null value can be added directly because the actual list might contain Integer, Double or another specific subtype. Adding null is type-correct. List<? super Integer> accepts Integer values, including autoboxed int values, and null, because its element type is Integer or a supertype. However, its elements can only be read safely as Object without a cast, because a List<Object> might contain other types. These rules describe compile-time permissions; a particular list may still reject mutation or null values at runtime. Generics are invariant, so List<Integer> is not a subtype of List<Number>; otherwise, a Double could be inserted into an integer list through the Number reference. Reference-type arrays are covariant, so Integer[] can be assigned to Number[]. Arrays retain their component type at runtime and throw ArrayStoreException if an incompatible value is stored. Generics normally prevent the corresponding unsafe assignment at compile time.

  4. **Describe the three retention policies (SOURCE, CLASS, RUNTIME) and what @Target, @Inherited and @Repeatable do. Which retention policy must an annotation have to be read through reflection at runtime?**

     SOURCE annotations are available to the compiler and annotation processors but are discarded from the generated class file. CLASS annotations are stored in the class file for bytecode tools but are not exposed through ordinary runtime annotation reflection; CLASS is the default retention policy. RUNTIME annotations are stored in the class file and can be read through reflection at runtime. @Target restricts where an annotation may be used, such as on fields, methods or classes. @Inherited allows a class-level annotation to be found on a subclass through its superclass when the subclass does not declare it itself; it does not propagate annotations from interfaces or make field and method annotations inherited. @Repeatable allows the same annotation type to appear more than once on an element by specifying a container annotation. getAnnotationsByType() retrieves the individual annotations, including those inside the container. An annotation must use @Retention(RetentionPolicy.RUNTIME) to be read through reflection at runtime.

  5. **List the ways to obtain a Class object. Explain what setAccessible(true) does and how the module system limits it, and why a method invoked with Method.invoke wraps an exception thrown by the target in InvocationTargetException.**

     A Class object can be obtained through a class literal such as Person.class, an object's getClass() method, Class.forName() with a binary class name, or a ClassLoader's loadClass() method. Primitive and array types also have class literals such as int.class and String[].class, and Integer.TYPE is another way to obtain int.class. Reflection methods such as getSuperclass(), getInterfaces() and Field.getType() also return Class objects. The one-argument Class.forName() initializes the class if necessary, while loadClass() normally does not. setAccessible(true) requests that normal Java language access checks be suppressed for a reflective member, allowing private access when permitted. It does not bypass module boundaries: deep reflection into private members of another named module generally requires the declaring package to be opened to the caller through an opens declaration or --add-opens. Otherwise, InaccessibleObjectException can occur; exporting a package alone is insufficient for private access. Method.invoke() wraps an exception thrown by the target method in InvocationTargetException so callers can distinguish a target-method failure from reflection's own access or argument errors. The original exception can be retrieved with getCause() or getTargetException().
