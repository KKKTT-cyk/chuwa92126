
# Java Spring Batch Homework — Solutions

## 1. Why is a simple loop unsuitable for large batch jobs?

A simple loop that loads an entire file into memory, parses each line, and saves each record is unsuitable for large batch jobs because:

1. **Memory usage:** Loading the entire file may cause an `OutOfMemoryError`. Spring Batch solves this with streaming `ItemReader` implementations.
2. **Performance:** Saving records individually creates excessive database operations. Chunk-oriented processing allows batch writes through `ItemWriter`.
3. **Transaction management:** A single large transaction can be expensive and difficult to recover. Spring Batch uses chunk-based transactions.
4. **Restartability:** If processing fails, a simple loop may need to restart from the beginning. Spring Batch uses `JobRepository`, `ExecutionContext`, and restartable readers to track progress.
5. **Error handling:** A malformed record may stop the entire process. Spring Batch provides skip and retry policies.
6. **Monitoring:** Spring Batch records execution status, read counts, write counts, and failures through `JobExecution` and `StepExecution`.

Spring Batch provides streaming, chunk-oriented processing, fault tolerance, transaction management, and restartability for large-scale batch jobs.

## 2. Job, Step, JobInstance, JobExecution, and StepExecution

Consider a daily settlement job with the identifying parameter:

`runDate=2026-10-26`

- **Job:** Defines the complete batch workflow, such as `DailySettlementJob`.
- **Step:** Represents an individual unit of work within a Job, such as `settlementStep`.
- **JobInstance:** Represents a logical job run identified by the Job name and identifying JobParameters.
- **JobExecution:** Represents one execution attempt of a JobInstance. It records execution status, start time, end time, and errors.
- **StepExecution:** Represents one execution attempt of a Step within a JobExecution. It tracks read counts, write counts, skip counts, and commit counts.

Example:

```text
Job: DailySettlementJob
    |
    |-- JobInstance: runDate=2026-10-26
            |
            |-- JobExecution #1: FAILED
            |       |
            |       |-- StepExecution: FAILED
            |
            |-- JobExecution #2: COMPLETED
                    |
                    |-- StepExecution: COMPLETED
```

If the job fails and is restarted with the same identifying parameters, Spring Batch creates a new `JobExecution` for the existing `JobInstance`.

If `runDate` changes to `2026-10-27`, Spring Batch creates a new `JobInstance`.

## 3. Chunk-oriented processing

Chunk-oriented processing divides a large dataset into manageable groups.

For a chunk size of 500:

1. Begin a transaction.
2. Read up to 500 items using `ItemReader`.
3. Process each item using `ItemProcessor`.
4. Write the processed items using `ItemWriter`.
5. Commit the transaction.
6. Repeat until the reader returns `null`.

Example:

```text
ItemReader
    |
    v
ItemProcessor
    |
    v
Chunk of up to 500 items
    |
    v
ItemWriter
    |
    v
Transaction Commit
```

Each chunk normally executes within its own transaction.

If processing fails, the current chunk's transactional changes are rolled back. Previously committed chunks normally remain committed.

### Chunk size tradeoffs

- **Small chunk size:** Lower memory usage and less repeated work after failure, but more transaction overhead.
- **Large chunk size:** Potentially better throughput through fewer commits, but higher memory usage and more work repeated after failure.
- **Medium chunk size:** Balances throughput, memory consumption, and recovery overhead.

For example, a chunk size of 500 may offer a reasonable balance, depending on the workload.

## 4. Tasklet Step vs Chunk-Oriented Step

### Tasklet Step

A tasklet step performs a specific operation, usually through a single tasklet implementation.

Typical uses include:

- Deleting temporary files.
- Moving or renaming files.
- Preparing directories.
- Running maintenance operations.

Example:

```java
@Bean
public Step cleanupStep(
        JobRepository jobRepository,
        PlatformTransactionManager transactionManager) {

    return new StepBuilder("cleanupStep", jobRepository)
            .tasklet((contribution, context) -> {
                System.out.println("Cleaning files...");
                return RepeatStatus.FINISHED;
            }, transactionManager)
            .build();
}
```

### Chunk-Oriented Step

A chunk-oriented step processes a collection of records using a reader, processor, and writer.

Typical uses include:

- Processing financial transactions.
- Importing CSV files.
- Migrating database records.
- Performing ETL operations.

Example:

```java
new StepBuilder("processStep", jobRepository)
    .<Transaction, SettlementLine>chunk(
        500, transactionManager)
    .reader(reader)
    .processor(processor)
    .writer(writer)
    .build();
```

**Difference:** Tasklets are suitable for specific operations, while chunk-oriented steps are suitable for processing large collections of records.

## 5. ItemReader, ItemProcessor, and ItemWriter

### ItemReader

`ItemReader` reads one item at a time.

```java
public interface ItemReader<T> {
    T read() throws Exception;
}
```

- Returns an item when data is available.
- Returns `null` when the input is exhausted.
- May throw an exception when reading fails.

### ItemProcessor

`ItemProcessor` validates, transforms, or filters an item.

```java
public interface ItemProcessor<I, O> {
    O process(I item) throws Exception;
}
```

- Returns an output item when processing succeeds.
- Returns `null` to filter out an item.
- Throws an exception when processing fails.

Example:

```java
if (tx.amount().compareTo(BigDecimal.ZERO) == 0) {
    return null;
}
```

This filters out transactions whose amount is zero.

### ItemWriter

`ItemWriter` writes a chunk of processed items.

```java
public interface ItemWriter<T> {
    void write(Chunk<? extends T> chunk)
            throws Exception;
}
```

The writer receives a `Chunk` instead of a single item because it supports batch database operations, reduces database overhead, and aligns writes with chunk transaction boundaries.

## 6. Filtering vs Skipping, and Skip vs Retry

### Filtering vs Skipping

**Filtering** intentionally removes an item according to business rules.

The processor returns `null`.

Example:

```java
if (tx.amount().compareTo(BigDecimal.ZERO) == 0) {
    return null;
}
```

The transaction is filtered because its amount is zero.

**Skipping** handles an item that causes a configured exception.

Example:

```java
if (tx.accountId() == null) {
    throw new InvalidTransactionException(
        tx.id(), "Missing account ID");
}
```

If `InvalidTransactionException` is configured as skippable, Spring Batch skips the invalid item within the configured skip limit.

### Skip vs Retry

**Skip:** Ignore a failed item and continue processing.

Suitable for permanent data errors, such as malformed CSV records or invalid account IDs.

**Retry:** Attempt a failed operation again.

Suitable for temporary failures, such as database deadlocks or transient network errors.

Example:

```java
.faultTolerant()
.skip(InvalidTransactionException.class)
.skipLimit(100)
.retry(DeadlockLoserDataAccessException.class)
.retryLimit(3)
```

`retryLimit(3)` allows up to three total attempts for a retryable operation.

## 7. Why must a reader using jobParameters be @StepScope?

Consider:

```java
@Value("#{jobParameters['inputFile']}")
String inputFile
```

Job parameters are available when a job executes, but they may not be available when Spring initially creates singleton beans.

`@StepScope` delays creation of the reader's target bean until the step executes.

Example:

```java
@Bean
@StepScope
public FlatFileItemReader<Transaction> transactionReader(
        @Value("#{jobParameters['inputFile']}")
        String inputFile) {

    FlatFileItemReader<Transaction> reader =
            new FlatFileItemReader<>();

    reader.setResource(
        new FileSystemResource(inputFile)
    );

    // Configure the line mapper.

    return reader;
}
```

Benefits:

1. Supports late binding of job parameters.
2. Allows different job executions to use different input files.
3. Creates a separate reader instance for each step execution.

Without `@StepScope`, the job parameter expression may not be resolved correctly when the bean is initialized.

## 8. Restarting a failed job

When a failed job is restarted with the same identifying JobParameters:

1. Spring Batch locates the existing `JobInstance`.
2. A new `JobExecution` is created.
3. Spring Batch checks the previous execution metadata stored in `JobRepository`.
4. Previously completed steps are normally skipped.
5. Restartable components restore their saved state.
6. Processing continues from the appropriate checkpoint.

### Reader requirements

A restartable reader must support saving and restoring its position.

This is commonly achieved through `ItemStream` and `ExecutionContext`.

For example, `FlatFileItemReader` can save its current position and resume from a checkpoint.

### Writer requirements

The writer should be restart-safe.

This can be achieved through:

- Transactional database writes.
- Idempotent operations.
- Unique constraints.
- Duplicate-prevention mechanisms.

### JobInstanceAlreadyCompleteException

`JobInstanceAlreadyCompleteException` is thrown when an application attempts to launch an already completed JobInstance using the same identifying JobParameters.

To create a new logical job instance, use different identifying parameters.

## 9. Multi-threaded Step vs Partitioning

### Multi-threaded Step

A multi-threaded step processes chunks concurrently using multiple threads.

Example:

```java
new StepBuilder("multiThreadedStep", jobRepository)
    .<Transaction, SettlementLine>chunk(
        500, transactionManager)
    .reader(reader)
    .processor(processor)
    .writer(writer)
    .taskExecutor(taskExecutor)
    .build();
```

The reader, processor, and writer must be thread-safe or properly synchronized because they may be accessed concurrently.

A stateful reader may require synchronization or a thread-safe implementation.

### Partitioning

Partitioning divides a dataset into independent partitions.

Each partition has its own worker step execution.

Example:

```text
Manager Step
    |
    |-- Partition 1: Records 1-1000
    |
    |-- Partition 2: Records 1001-2000
    |
    |-- Partition 3: Records 2001-3000
```

Each partition processes its assigned records independently.

### Comparison

| Feature | Multi-threaded Step | Partitioning |
|---|---|---|
| Processing | Concurrent chunks | Independent partitions |
| Step executions | One worker step execution | One per partition |
| Reader | Potentially shared | Usually separate |
| Complexity | Lower | Higher |
| Scalability | Multiple threads | Local or remote workers |

Multi-threading is simpler when components are thread-safe. Partitioning is useful when the workload can be divided into independent sections.

## 10. Pitfalls of using @Scheduled with multiple application instances

### Pitfall 1: Duplicate job launches

If several application instances use:

```java
@Scheduled(cron = "0 0 2 * * *")
public void runJob() {
    jobLauncher.run(job, parameters);
}
```

Each instance may attempt to launch the same job at 2 AM.

This can cause duplicate launch attempts, resource contention, or duplicate processing if the jobs are not properly coordinated.

**Solution:**

Use distributed scheduling or locking mechanisms such as:

- ShedLock.
- Kubernetes CronJob.
- A centralized scheduler.

A shared `JobRepository` and properly configured identifying JobParameters also help enforce job-instance semantics.

### Pitfall 2: Overlapping or missed executions

A job may still be running when the next scheduled execution begins.

Additionally, if all application instances are unavailable at the scheduled time, an in-process scheduler may miss the execution.

**Solution:**

Use persistent scheduling or orchestration, configure concurrency controls, and check whether a job is already running before launching another execution.

A durable centralized scheduler provides more reliable coordination than independent in-process schedules.

## 11. Complete TransactionValidationProcessor and SettlementStepConfig

### Requirements

The processor must:

1. Filter transactions whose amount is zero.
2. Throw `InvalidTransactionException` when the account ID is null or blank.
3. Throw `InvalidTransactionException` when the currency is unsupported.
4. Convert valid amounts to USD.
5. Extract the settlement date from the transaction timestamp.
6. Return a `SettlementLine`.

The step must:

1. Process chunks of 500 items.
2. Use the provided reader, processor, and writer.
3. Skip `InvalidTransactionException`.
4. Skip `FlatFileParseException`.
5. Fail when more than 100 items have been skipped.

### Complete Java implementation

```java
import org.springframework.batch.core.Step;
import org.springframework.batch.core.repository.JobRepository;
import org.springframework.batch.core.step.builder.StepBuilder;
import org.springframework.batch.item.ItemProcessor;
import org.springframework.batch.item.ItemReader;
import org.springframework.batch.item.ItemWriter;
import org.springframework.batch.item.file.FlatFileParseException;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.transaction.PlatformTransactionManager;

import java.math.BigDecimal;
import java.time.LocalDate;
import java.time.LocalDateTime;

record Transaction(
    long id,
    String accountId,
    BigDecimal amount,
    String currency,
    LocalDateTime timestamp
) {}

record SettlementLine(
    long transactionId,
    String accountId,
    BigDecimal amountUsd,
    LocalDate settleDate
) {}

class InvalidTransactionException extends RuntimeException {

    InvalidTransactionException(long id, String reason) {
        super("Transaction " + id + ": " + reason);
    }
}

interface ExchangeRateService {

    boolean supports(String currency);

    BigDecimal toUsd(
        BigDecimal amount,
        String currency
    );
}

class TransactionValidationProcessor
        implements ItemProcessor<Transaction, SettlementLine> {

    private final ExchangeRateService rates;

    TransactionValidationProcessor(ExchangeRateService rates) {
        this.rates = rates;
    }

    @Override
    public SettlementLine process(Transaction tx) {

        // 1. Filter zero-amount transactions.
        if (tx.amount().compareTo(BigDecimal.ZERO) == 0) {
            return null;
        }

        // 2. Validate account ID.
        if (tx.accountId() == null ||
            tx.accountId().isBlank()) {

            throw new InvalidTransactionException(
                tx.id(),
                "Invalid account ID"
            );
        }

        // 3. Validate currency.
        if (!rates.supports(tx.currency())) {

            throw new InvalidTransactionException(
                tx.id(),
                "Unsupported currency"
            );
        }

        // 4. Convert amount to USD.
        BigDecimal amountUsd =
            rates.toUsd(
                tx.amount(),
                tx.currency()
            );

        // 5. Extract settlement date.
        LocalDate settleDate =
            tx.timestamp().toLocalDate();

        // 6. Return settlement line.
        return new SettlementLine(
            tx.id(),
            tx.accountId(),
            amountUsd,
            settleDate
        );
    }
}

@Configuration
class SettlementStepConfig {

    @Bean
    public Step settlementStep(
            JobRepository jobRepository,
            PlatformTransactionManager transactionManager,
            ItemReader<Transaction> transactionReader,
            TransactionValidationProcessor processor,
            ItemWriter<SettlementLine> settlementWriter) {

        return new StepBuilder(
                "settlementStep",
                jobRepository
            )
            .<Transaction, SettlementLine>chunk(
                500,
                transactionManager
            )
            .reader(transactionReader)
            .processor(processor)
            .writer(settlementWriter)
            .faultTolerant()
            .skip(InvalidTransactionException.class)
            .skip(FlatFileParseException.class)
            .skipLimit(100)
            .build();
    }
}
```

### Explanation

**Filtering zero-amount transactions**

```java
if (tx.amount().compareTo(BigDecimal.ZERO) == 0) {
    return null;
}
```

`compareTo()` compares two `BigDecimal` values.

Returning `null` filters the transaction without counting it as a skipped error.

**Validating account IDs**

```java
if (tx.accountId() == null ||
    tx.accountId().isBlank()) {

    throw new InvalidTransactionException(
        tx.id(), "Invalid account ID"
    );
}
```

This rejects missing, empty, or whitespace-only account IDs.

**Validating currency**

```java
if (!rates.supports(tx.currency())) {
    throw new InvalidTransactionException(
        tx.id(), "Unsupported currency"
    );
}
```

This rejects currencies that the exchange-rate service does not support.

**Converting amounts**

```java
BigDecimal amountUsd =
    rates.toUsd(tx.amount(), tx.currency());
```

The exchange-rate service converts the transaction amount into USD.

**Extracting the date**

```java
LocalDate settleDate =
    tx.timestamp().toLocalDate();
```

Example:

`2026-10-26T14:30:00` becomes `2026-10-26`.

**Configuring fault tolerance**

```java
.faultTolerant()
.skip(InvalidTransactionException.class)
.skip(FlatFileParseException.class)
.skipLimit(100)
```

The step allows up to 100 skippable errors.

The 101st skipped item causes the step to fail.

### Example test cases

Assume the exchange-rate service supports USD and EUR, and 1 EUR equals 1.10 USD.

|---|---|
| Amount = 0 | Filtered |
| Account ID = null | Skipped |
| Account ID = blank | Skipped |
| Unsupported currency | Skipped |
| Amount = 100 EUR | SettlementLine with 110 USD |
