## Question1:Why is a simple loop unsuitable for large batch jobs?
A simple loop that reads an entire file into memory, parses each line, and saves the results is unsuitable for large batch jobs because it introduces several problems:
1. High memory consumption: Loading millions of records into memory can cause an OutOfMemoryError. Spring Batch addresses this through streaming ItemReader implementations and chunk-oriented processing, which process manageable groups of records without loading the entire dataset.
2. Poor transaction management: A simple loop may not properly manage database transactions. Spring Batch uses chunk-based transactions, committing changes after each successfully processed chunk.
3. Difficult error recovery: If processing fails halfway through a file, a simple loop may need to restart from the beginning. Spring Batch supports checkpointing and restartability through JobRepository, ExecutionContext, and ItemStream.
4. Limited error handling: A simple loop often requires custom logic to handle invalid records or temporary failures. Spring Batch provides built-in skip and retry mechanisms.
5. Limited monitoring: A simple loop does not automatically track execution history, processing counts, or failures. Spring Batch records execution metadata through JobRepository.

## Question2:Difference between Job, Step, JobInstance, JobExecution, and StepExecution
Concept	|Description
Job: Defines the complete batch processing workflow
Step: Defines an individual processing stage within a job
JobInstance: Represents a logical job run, identified by the job name and identifying parameters
JobExecution: Represents one execution attempt of a JobInstance
StepExecution: Represents one execution attempt of an individual step

For example, consider a daily settlement job named dailySettlementJob with the identifying parameter runDate=2026-10-24.
The Job defines the settlement workflow, consisting of three Step definitions: reading transactions, validating them, and generating settlement reports.
The combination of dailySettlementJob and runDate=2026-10-24 identifies one JobInstance.
Suppose the job fails during its first execution and is restarted successfully.
Both executions belong to the same JobInstance because they have identical identifying job parameters. Each execution has its own JobExecution, and every attempted step has its own StepExecution.
If the job is started with runDate=2026-10-25, Spring Batch creates a different JobInstance.

## Question3:Explain chunk-oriented processing
Chunk-oriented processing is a Spring Batch approach that processes data in groups rather than handling every record in a separate transaction.
It consists of three main operations:
- Reading: The ItemReader retrieves input records one at a time.
- Processing: The ItemProcessor validates, filters, or transforms each record.
- Writing: The ItemWriter writes the processed records in batches.

Transaction boundaries: Under normal chunk-oriented processing, each chunk is processed inside its own transaction. Spring Batch reads and processes the items, writes the resulting chunk, updates checkpoint metadata, and commits the transaction.
If a failure occurs before a chunk commits, its transactional changes are rolled back. Previously committed chunks remain committed.

Impact of chunk size:
- Small chunks: Use less memory and require less reprocessing after a failure, but increase transaction overhead because commits occur more frequently.
- Large chunks: Reduce commit overhead and can improve throughput, but require more memory and increase the amount of work that may need to be repeated after a rollback.

## Question4:Compare a tasklet step with a chunk-oriented step
A tasklet step executes a specific operation through the Tasklet interface, while a chunk-oriented step processes collections of records through an ItemReader, ItemProcessor, and ItemWriter.
Feature	Tasklet Step	Chunk-Oriented Step
Main purpose	Execute a specific task	Process many records
Processing method	Tasklet.execute()	Read, process, write
Transaction handling	Typically per tasklet execution	Typically per chunk
Best use case	Simple operations	Large datasets
Examples	Delete temporary files, execute cleanup SQL	CSV imports, data transformation, transaction settlement

For example, a tasklet might delete temporary files before a job begins and return RepeatStatus.FINISHED.

A chunk-oriented step might then read one million financial transactions, validate their information, convert their currencies, and write the results into a database in chunks of 500.

Tasklets are most appropriate for individual operations, while chunk-oriented steps are better for repetitive record-based processing.

## Question5:Contracts of ItemReader, ItemProcessor, and ItemWriter
ItemReader: Reads one item at a time using the read() method. It returns an item when data is available and returns null when the input has been exhausted.
ItemProcessor: Receives an input item and optionally transforms it into another type. If process() returns null, Spring Batch filters out that item, so it is not passed to the writer.
ItemWriter: Receives an entire Chunk of processed items instead of a single item. This allows efficient batch operations, such as using JDBC batch inserts to write hundreds of records in one operation.

For example, a reader may retrieve 500 records, while the processor filters out 20 invalid or unwanted records. The writer then receives the remaining 480 records in a Chunk.

## Question6:Difference between filtering, skipping, and retrying
1.Filtering occurs when an ItemProcessor deliberately returns null to remove an item from further processing. This is normal business behavior rather than an error.
For example, a processor might filter out transactions whose amount is zero:
if (tx.amount().compareTo(BigDecimal.ZERO) == 0) {
return null;
}

2.Skipping occurs when an exception is thrown but is configured as skippable. Spring Batch excludes the problematic item and continues processing, provided the skip limit has not been exceeded.
For example, a malformed CSV row may throw FlatFileParseException. If the exception is configured as skippable, the row is skipped and the skip count increases.

3.Retrying occurs when a temporary failure may succeed on another attempt. Instead of immediately skipping the item, Spring Batch attempts the failed operation again according to the configured retry policy.
For example, a temporary database deadlock may be resolved by retrying the operation.

Filtering is appropriate for intentionally unwanted records, skipping for records with tolerable errors, and retrying for potentially recoverable failures.

## Question7: Why must a reader using #{jobParameters['inputFile']} be declared with @StepScope?
A reader that accesses #{jobParameters['inputFile']} should be declared with @StepScope because job parameters are available when a job executes, not necessarily when the Spring application initializes.
By default, Spring beans are singletons and are created during application initialization. However, the value of inputFile depends on the specific job execution.
The @StepScope annotation enables late binding, meaning Spring creates the actual reader when the step starts and the job parameters are available.

For example:
@Bean
@StepScope
public FlatFileItemReader<Transaction> transactionReader(
@Value("#{jobParameters['inputFile']}") String inputFile) {

    return new FlatFileItemReaderBuilder<Transaction>()
            .name("transactionReader")
            .resource(new FileSystemResource(inputFile))
            // Configure line mapping here
            .build();
}

When the job starts with inputFile=transactions.csv, Spring Batch supplies that filename to the reader.
Without @StepScope, Spring may attempt to resolve the parameter before a job execution context exists, resulting in an error.
Additionally, @StepScope gives each executing step its own reader instance, avoiding unwanted sharing of reader state between executions.

## Question8:What happens when a failed job restarts with the same identifying parameters?
When a failed job is started again with the same identifying job parameters, Spring Batch treats it as a restart of the existing JobInstance, rather than creating a new instance.
Spring Batch creates a new JobExecution and uses metadata stored in JobRepository to determine which steps need to execute.

For restartability to work correctly:
- Reader: The reader should support saving and restoring its position, typically through the ItemStream interface and ExecutionContext. This allows it to resume from the last committed checkpoint rather than rereading the entire file.
- Writer: The writer should support safe repeated execution. It should participate in transactions where possible or use idempotent operations to avoid creating duplicate records.
- JobRepository: The repository must preserve job execution metadata and checkpoint information between execution attempts.

However, if a job has already completed successfully and another execution is attempted with the same identifying parameters, Spring Batch throws a JobInstanceAlreadyCompleteException.
This prevents an already completed logical job instance from being executed again accidentally.

## Question9:Compare multi-threaded steps with partitioning
Both multi-threaded steps and partitioning improve batch processing performance by executing work concurrently, but they use different approaches.

Multi-threaded steps use a TaskExecutor to process chunks concurrently within a single step execution. Worker threads may share the same reader, processor, and writer instances.
Partitioning divides the input data into independent subsets. Each partition has its own StepExecution and can be processed by a separate worker thread or even a different application instance.

For a multi-threaded step, the reader, processor, and writer must be safe for concurrent access.
- ItemReader: Must be thread-safe or properly synchronized to prevent duplicate or missing records. For example, SynchronizedItemStreamReader can synchronize access to a non-thread-safe reader.
- ItemProcessor: Should be stateless or thread-safe so that multiple threads can process records without interfering with one another.
- ItemWriter: Must be thread-safe or appropriately synchronized to avoid corrupted output or conflicting writes.

## Question10:Two pitfalls of using @Scheduled in a multi-instance application
Pitfall 1: Duplicate job execution
The @Scheduled annotation operates independently within each application instance. If three instances run the same scheduled method, all three may attempt to launch the same batch job.
This can cause duplicate processing or unnecessary execution conflicts.
Solution: Use a distributed scheduling mechanism such as a leader-elected scheduler, distributed lock, clustered Quartz scheduler, or Kubernetes CronJob. A shared JobRepository with consistent identifying job parameters also helps prevent duplicate execution of the same job instance.

Pitfall 2: Missed scheduled executions
If all application instances are unavailable during a scheduled trigger, an ordinary @Scheduled method does not automatically guarantee that the missed job will execute after the application restarts.
For example, if a settlement job is scheduled for 2:00 AM but the application is unavailable at that time, the job may never run for that date.

Solution: Use a persistent scheduler such as Quartz with a JDBC job store, together with an appropriate misfire policy. Alternatively, implement recovery logic that identifies missing runDate values from JobRepository and launches the missing jobs.
