3. Which time-series database resources are affected?
   High cardinality negatively affects several components of a time-series database (TSDB), such as Prometheus.
   Resource	Impact of high cardinality
   Memory	Every active series requires state in the in-memory head block, increasing memory consumption and risking out-of-memory failures
   Index storage	More series require additional index entries and postings lists, increasing index size
   Ingestion	Each series becomes an independent append target, increasing ingestion work
   Query performance	Queries matching many series must inspect larger indexes and read more chunks
   Series churn	Frequently changing labels create new series while old ones remain indexed until they expire
4. Three techniques for controlling cardinality
   Technique 1: Avoid high-cardinality labels at the instrumentation layer.
Developers should not use unique identifiers, such as user_id, request_id, email addresses, or transaction IDs, as metric labels.
Instead, metrics should use stable, bounded values such as service name, HTTP method, and status code. Individual request or user details can be recorded in logs or traces.

Technique 2: Normalize dynamic label values at the instrumentation or framework layer.
Dynamic values should be replaced with stable templates.

Technique 3: Drop or rewrite problematic labels at the collector layer.
The collection infrastructure can remove unnecessary labels before telemetry enters long-term storage.

## Question2:Why percentiles cannot be averaged, and comparison of latency representations
1. Why is the average of two 99th percentiles incorrect?
   The 99th percentile, or p99, represents a latency value below which approximately 99% of observed requests fall. It is a property of the entire latency distribution, not an ordinary measurement that can be averaged across instances.
2. Comparison of client-side summaries, fixed-bucket histograms, and sketches
   Client-side summaries
A client-side summary calculates latency quantiles within an individual application instance and exports the results.
   The main advantage is that quantiles can be calculated locally without exporting every observed latency.
However, these precomputed quantiles cannot be meaningfully combined to calculate the global p99 across multiple instances. This limits their usefulness for distributed applications.

Fixed-bucket histograms
A fixed-bucket histogram counts how many observations fall within predefined latency boundaries.
The bucket counts are cumulative.
The main advantage is that histograms can be aggregated across application instances by summing the counts for matching bucket boundaries.
After aggregation, engineers can estimate global percentiles using bucket counts and interpolation.
The limitation is that percentile accuracy depends on the histogram's bucket boundaries. Wide buckets create greater uncertainty about where observations fall within a bucket.
Moreover, increasing the number of buckets creates additional time series and raises storage costs.

Sketches
Sketches, such as t-digest and DDSketch, use compact statistical data structures to approximate latency distributions.
Unlike precomputed summary quantiles, compatible sketches can be merged across instances. This allows engineers to estimate global percentiles without retaining every individual latency observation.
Sketches can achieve good accuracy with relatively compact storage. However, they require specialized algorithms and compatible backend support.
Their error guarantees depend on the particular implementation; for example, DDSketch is designed around relative-error bounds.

3. Why should histogram bucket boundaries be chosen around the latency objective?
   Histogram percentiles are estimated from bucket counts, often using interpolation within the bucket containing the target percentile.

## Question3:Tail-based sampling memory calculation and consistent hashing
1. Calculate the memory required to buffer spans
   The sampling tier needs approximately 128 MB of memory for the span payloads alone.
2. Why must all spans of a trace reach the same sampler node?
   Tail-based sampling makes its retention decision after observing enough of a trace to evaluate characteristics such as errors, latency, and operation attributes.
   For example, a distributed request may contain spans from an API Gateway, Order Service, Payment Service, and Database Service.
   If spans belonging to the same trace are distributed across different sampler nodes, no individual node has the complete trace information.
For example, one sampler might receive only the successful API Gateway span, while another receives a Payment Service span containing an error. The first sampler could incorrectly discard the trace because it never observed the failure.
Therefore, all spans sharing the same trace ID must be routed to the same sampler node so the node can evaluate the trace as a whole and make a consistent sampling decision.

## Question4:W3C traceparent header structure and sampling consistency
1. Explain the four fields of the traceparent header
   Its general structure is: traceparent: version-trace-id-parent-id-trace-flags
   The four fields in the given header are:
   Field	Value	Size	Meaning
   Version	00	1 byte (8 bits)	Specifies the trace-context format version
   Trace ID	4bf92f3577b34da6a3ce929d0e0e4736	16 bytes (128 bits)	Uniquely identifies the entire distributed trace
   Parent ID	00f067aa0ba902b7	8 bytes (64 bits)	Identifies the caller's span that is the parent of the receiving service's span
   Trace flags	00	1 byte (8 bits)	Contains flags, including the sampling decision
2. What does the last field tell the receiving service?
   The final field is:00
This represents the trace flags.
In the W3C Trace Context format, the least significant bit, represented by 01, indicates whether the trace is sampled.
The common values are:
00 = Not sampled
01 = Sampled
Since the received header ends with 00, the sampled bit is not set.
3. How is the sampling decision kept consistent?
   In head-based sampling, the sampling decision is usually made at the beginning of a trace.
The result is encoded in the trace flags and propagated with every downstream request.
   Because every service follows the same propagated sampled flag, they make consistent recording decisions for the trace.
Without propagation, different services could independently sample the same request, resulting in incomplete or disconnected traces.
This mechanism is one of the main advantages of standardized trace context propagation across microservices.
4. What parent ID should the service send to the next service?
   When the receiving service makes an outgoing request, it should propagate the same trace ID but update the parent-id field to identify the span associated with the outgoing operation.
Typically, an instrumented HTTP client creates a new client span. The ID of that outgoing client span becomes the parent-id in the header sent to the downstream service.

## Question6:Telemetry pipeline failure isolation, overload management, delivery guarantees, and watchdog alerts
1. How should a telemetry pipeline handle backend outages?
   A fundamental requirement of an observability system is that failures in telemetry infrastructure must never block or crash the applications being monitored.
   To achieve this, the telemetry pipeline must be designed with asynchronous processing, bounded buffers, failure isolation, and appropriate backpressure handling.
   A typical production telemetry architecture is:
   Spring Boot Application
   |
   | Non-blocking telemetry recording
   v
   Bounded In-Memory Queue
   |
   | Background exporter thread
   v
   Local Agent
   |
   | Batching and retries
   v
   Collector Gateway
   |
   | Processing and routing
   v
   Durable Message Broker
   |
   | Buffered telemetry
   v
   Telemetry Storage Backend
   |
   v
   Query and Dashboard Layer

The architecture separates application request processing from potentially slow or unreliable network and storage operations.
First, applications use bounded in-memory queues.
When a request generates a log or span, the application attempts to record it in a fixed-size queue.
For example, a Spring Boot application could use an asynchronous telemetry exporter with a queue capacity of 10,000 items.
The request thread should not wait for the remote telemetry backend to acknowledge the data.

Second, background threads handle telemetry export.
A separate worker periodically retrieves telemetry from the queue, batches multiple records, and sends them to a local agent or collector.
This prevents network delays and backend outages from directly affecting business-request latency.

Third, bounded buffers prevent unlimited memory growth.
If the backend remains unavailable and the local queue fills, the application should drop telemetry rather than wait indefinitely or continuously allocate more memory.
The application should also track the number of dropped telemetry items so operators can identify data loss.

Fourth, durable brokers isolate ingestion from storage failures.
Between the collection tier and storage backend, a message broker such as Apache Kafka can temporarily retain telemetry during storage outages.
Collectors can continue publishing data to the broker while storage consumers are unavailable.
Once the storage backend recovers, consumers resume processing buffered records.
This approach absorbs bursts and separates the speed of telemetry ingestion from the speed of storage operations.

2. Overload management techniques and their trade-offs
   Buffering
Buffering is useful when a downstream component temporarily processes telemetry more slowly than the upstream producer.
At the application layer, bounded in-memory queues can absorb short bursts. At the collection layer, agents may use disk-backed buffers. Between collection and storage, durable message brokers can retain telemetry through longer outages.
However, larger buffers increase memory or disk requirements and cannot absorb unlimited data.

Dropping
When buffers become full, the system may discard telemetry rather than block the application.
For example, collectors may drop DEBUG logs, low-priority traces, or older buffered items.
The main advantage is predictable resource consumption.
The disadvantage is reduced observability because some events are permanently lost.
The pipeline should expose dropped-item counters so engineers know when telemetry has been discarded.

Sampling
Sampling reduces telemetry volume by retaining only a selected subset of events or traces.
For example, head-based sampling might retain 10% of incoming traces.
Tail-based sampling can make more informed decisions by retaining traces associated with errors or high latency, while sampling ordinary successful requests at a lower rate.
Sampling can substantially reduce storage costs but may remove information needed for future investigations.
Additionally, tail-based sampling requires temporary buffering and coordinated trace routing, which introduces memory and operational overhead.

Rate limiting
Rate limiting protects shared collection infrastructure by restricting how much telemetry an application or tenant can submit.
For example, the collector could enforce an ingestion limit of 10 MB per second for a particular application team.
If the application exceeds its quota, the collector may reject or drop the excess data.
This prevents a single misconfigured application from consuming all shared ingestion capacity.
However, rejected telemetry creates data loss unless the sender can safely buffer and retry it later.

3. At-least-once versus at-most-once delivery
   Telemetry systems commonly use two delivery semantics: at-most-once and at-least-once.

At-most-once delivery
At-most-once means each telemetry item is delivered zero or one time.
The producer does not retry indefinitely when transmission fails.
The main advantage is simplicity and low overhead.
The disadvantage is that telemetry can be permanently lost during failures.
At-most-once semantics are useful near the application because protecting request processing is more important than guaranteeing that every log or span reaches storage.

At-least-once delivery
At-least-once means the pipeline retries delivery until it receives an acknowledgment, assuming the system eventually recovers and retained data remains available.
If the storage write succeeds but the consumer crashes before committing its offset, the same telemetry item may be processed again after recovery.
This can cause duplicate records.
Therefore, at-least-once systems must tolerate duplicates or implement deduplication mechanisms.

4. Why should alerting run in a separate failure domain?
   The observability platform is most important when the monitored system experiences failures.
If both the monitored application and its alerting infrastructure depend on the same cluster, network, or cloud region, a shared failure could disable both.
   Possible approaches include deploying alert evaluation and notification infrastructure in a separate Kubernetes cluster, cloud account, or region.
The alerting path should also avoid depending on the same services it monitors, such as the application's service mesh or authentication infrastructure.
This ensures that the monitoring system can still detect and report application failures even when the primary production environment is unavailable.
5. What is a watchdog or dead-man's switch alert?
   A watchdog alert, also called a dead-man's switch, is an alert designed to verify that the alerting system itself is functioning.
   Unlike an ordinary alert that activates when something goes wrong, a watchdog signal is intentionally generated continuously.
An independent external receiver expects to receive the watchdog signal regularly.

For example:
Monitoring System
|
| Sends continuous watchdog signal
v
External Watchdog Receiver
|
| Signal continues arriving?
|
+-- YES --> Monitoring path appears healthy
|
+-- NO  --> Trigger external notification

If the watchdog signal stops arriving within the expected interval, the external receiver sends an alert to the engineering team.
The absence of the watchdog may indicate that the monitoring system, alerting pipeline, notification system, or network path has failed.
The key advantage is that the watchdog detects failures that ordinary monitoring alerts cannot report because the monitoring infrastructure itself is unavailable.
