#### Conceptual Questions

1. **What is API Priority and Fairness (APF), and how does it prevent a misbehaving controller from starving critical system traffic?**

   API Priority and Fairness manages how API-server execution capacity is shared among requests. FlowSchema rules classify requests using properties such as identity, verb, resource and namespace, assigning them to a priority level and flow. PriorityLevelConfiguration objects define concurrency shares and queuing behavior. Fair queuing helps isolate different flows within a level, while separate priority levels protect capacity for important traffic such as node heartbeats and leader election.

2. **What is the difference between mutating admission and validating admission? What risks do external admission webhooks introduce?**

   Mutating admission can change a proposed object before it is stored, for example by adding labels, applying organizational defaults or injecting a sidecar. Validating admission examines the resulting object and can accept or reject it, but cannot modify it. Both operate after authentication and authorization, so an authorized request can still be rejected by admission policy. External admission webhooks add HTTPS calls to the API-server request path. A slow or unavailable webhook can delay or block matching writes, while certificate, DNS and network failures become additional dependencies. With failurePolicy set to Fail, a call failure or timeout rejects the request; with Ignore, the request can continue without that webhook's decision, potentially bypassing the intended policy. Ignore does not override an explicit rejection returned successfully by the webhook. Broadly scoped webhooks can also create recovery deadlocks if their own replacement Pods require approval from the unavailable webhook. Restrict their scope, use short timeouts and high availability, avoid unsafe side effects, and prefer in-process policies when they can express the requirement.

3. **How do informers, local caches, work queues, and reconciliation functions work together in a Kubernetes controller?**

   An informer obtains objects through List and Watch and maintains a local cache of the relevant cluster state. Event handlers normally enqueue an object's key, such as namespace/name, rather than perform expensive work directly inside the handler. A work queue deduplicates pending keys and supports retries with backoff, allowing bursts of notifications to be processed efficiently. Worker routines take keys from the queue and invoke reconciliation functions. Each reconciliation reads the current desired and observed state, commonly through the local cache, compares them, and performs the API operations needed to move toward the desired state. It may also update status or schedule another evaluation. If the same key changes while it is being processed, the queue can arrange another pass after the current one completes. The cache reduces API traffic, the queue separates event delivery from processing, and reconciliation contains the actual control logic. Because cached state can lag behind the API server, reconciliation must tolerate stale reads and conflicts.

4. **Why should Kubernetes reconciliation be level-triggered and idempotent? How can a controller recover from missed events and stale caches?**

   Level-triggered reconciliation responds to the current difference between desired and actual state, rather than assuming that every event represents an action that must execute exactly once. Idempotence means repeating reconciliation for the same state does not create unintended additional effects. These properties make controllers resilient to duplicate notifications, retries and restarts. For example, a controller should ensure that a required child object exists rather than create another child every time it receives an update notification. Stable child names, ownership checks, optimistic concurrency and expectations about pending creations help prevent duplicates while the cache catches up.

   After a watch interruption, the informer can resume from its last processed resourceVersion while history remains available. If the version has expired, it relists and rebuilds the cached view. Optional informer resynchronization or explicit timed requeues can revisit objects even without a new change notification. A resync reprocesses cached objects; it does not itself fetch fresh state from the API server. On an update conflict, the controller should obtain the latest state, recompute its change and retry. A direct API read can be appropriate when a decision requires fresher information than the cache provides. Recovery depends on another reconciliation eventually running, so the controller must arrange retries or requeues when progress remains incomplete.

5. **What are Custom Resource Definitions (CRDs) and Operators, and how do they extend Kubernetes functionality?**

   A Custom Resource Definition adds a new resource type to the Kubernetes API, defining details such as its group, versions, kind, names, scope and schema. Users can then create instances of that type and use familiar API operations, RBAC, List and Watch mechanisms to manage them. For example, a platform could define an InferenceService resource containing a model reference, replica count and GPU requirements. A CRD supplies the API and storage representation, but does not by itself deploy the model or perform operational work. An Operator combines a controller with domain-specific operational knowledge, usually using custom resources to express desired state. It can reconcile an InferenceService into Deployments, Services and other resources, report readiness, and automate upgrades or recovery. Similarly, a database Operator might manage replication, backups and failover. CRDs extend the vocabulary of the API, while Operators implement the ongoing behavior associated with that vocabulary.

6. **What are the differences between resource requests, limits, capacity, and allocatable resources? How do QoS classes affect pod eviction?**

   A resource request describes the amount used for scheduling and resource accounting. The scheduler checks whether a node has sufficient allocatable resources after accounting for existing Pod requests; low current CPU usage does not make an already fully requested node available. A limit defines a runtime usage bound. CPU limits generally cause throttling, while exceeding a memory limit can lead to an OOM kill. A request is not a maximum: a container may use more when resources and its limits permit. Capacity is the node's total reported resources. Allocatable is the portion available to Pods after configured operating-system, Kubernetes and eviction reservations are deducted.

   Under the usual container-level CPU and memory configuration, Guaranteed Pods have CPU and memory requests equal to limits for every container. BestEffort Pods have no CPU or memory requests or limits, and Burstable covers the remaining configurations with at least one such resource setting. These classes describe resource protection, but kubelet node-pressure eviction is not a simple fixed ordering by QoS name. For resources with requests, eviction ranking considers whether usage exceeds requests, Pod priority and usage relative to requests. BestEffort Pods and over-request Burstable Pods are therefore often more exposed to memory-pressure eviction, while staying within requests offers more protection. QoS does not guarantee immunity from every failure, and disk pressure has different resource accounting. Kernel OOM killing is distinct from kubelet eviction, although QoS influences the OOM score configuration.

7. **How does the Kubernetes scheduler select a node for a pod? Explain filtering, scoring, reservation, and binding.**

   The scheduler selects an unscheduled Pod from its queue and evaluates placement using scheduling plugins. Filtering eliminates nodes that cannot satisfy required conditions, such as resource requests, required affinity, taints without matching tolerations, or volume constraints. Scoring ranks feasible nodes using preferences such as resource balance, topology distribution and preferred affinity; the scheduler combines configured scores and chooses a suitable node. It may evaluate only enough feasible nodes to make an efficient decision in a large cluster. If no node fits, the Pod remains pending, and post-filter logic may consider preemption.

   Before binding finishes, the scheduler accounts for the selected placement in its local cache as an assumed Pod so subsequent scheduling decisions do not reuse the same capacity. Reserve plugins can also reserve resources or maintain scheduling state. Permit and pre-bind steps may perform additional coordination, such as waiting for approval or preparing volumes. Binding records the Pod's node assignment through the API server. The kubelet on that node then starts the workload; the scheduler does not launch containers itself. If placement fails before completion, the scheduler releases the assumed allocation and invokes relevant cleanup or Unreserve logic so the Pod can be retried.

8. **What are the differences between node affinity, pod affinity, taints and tolerations, and priority-based preemption?**

   Node affinity places constraints or preferences on node labels, such as requiring a GPU model or preferring a zone. Required rules filter eligible nodes, while preferred rules influence scoring. Pod affinity and anti-affinity express placement relative to other Pods selected by labels within a topology domain, such as placing related workloads in the same zone or keeping replicas on different hosts. These rules describe where a Pod should run relative to nodes or other workloads.

   Taints are applied to nodes to repel Pods, while tolerations on Pods allow them to pass matching taint checks. NoSchedule prevents new placement without a matching toleration, PreferNoSchedule expresses a softer preference, and NoExecute can also evict already running Pods without an appropriate toleration. A toleration permits placement but does not require or guarantee it; node affinity is often combined with tolerations for dedicated node pools. Priority affects scheduling order, and priority-based preemption can remove lower-priority Pods when doing so would make room for a pending higher-priority Pod. Preemption does not bypass required affinity, tolerations or other placement constraints, and it cannot make an impossible request fit. It is a scheduler placement mechanism, distinct from kubelet node-pressure eviction. A non-preempting priority class can influence queue order without allowing its Pods to evict others through scheduler preemption.

9. **What are the respective responsibilities of the kubelet, Container Runtime Interface (CRI), and Container Network Interface (CNI) when starting a pod?**

   The kubelet is the node agent that observes Pods assigned to its node and reconciles them with local runtime state. It coordinates volume setup, configuration and credentials, asks the container runtime to prepare the Pod and containers, manages startup order, runs health checks and reports status. It continues monitoring the workload and applies restart policies. CRI is the standardized interface through which the kubelet communicates with a compatible runtime, such as containerd or CRI-O, to pull images, create a Pod sandbox, create and start containers, and inspect or stop them. CRI is an API contract rather than the component that executes containers by itself.

   CNI provides the plugin contract used for Pod network configuration. During sandbox setup, the runtime's networking integration typically invokes CNI plugins to attach network interfaces, allocate a Pod IP through IP address management, and configure routes or other connectivity. The kubelet supplies the desired Pod configuration and coordinates startup, the CRI runtime performs sandbox and container operations, and CNI plugins implement the network attachment. CNI establishes Pod connectivity; it does not itself define the complete Service-discovery or Service-load-balancing behavior, although some networking implementations also provide those features.

10. **How do Services, EndpointSlices, kube-proxy, and CoreDNS work together to enable service discovery and traffic routing? How does a headless Service differ from a regular ClusterIP Service?**

    A regular ClusterIP Service gives an application a stable virtual IP and service ports while its backend Pods can change. For a selector-based Service, the EndpointSlice controller tracks matching Pods and publishes their addresses, ports and readiness-related conditions in EndpointSlices. kube-proxy watches Services and EndpointSlices and programs node-level forwarding rules so connections to the Service IP are routed to eligible backend Pods. kube-proxy normally configures the data path rather than forwarding every packet through its own userspace process. Some networking implementations replace it with another Service data plane, such as an eBPF-based implementation.

    CoreDNS watches Kubernetes service information and answers cluster DNS queries. For a regular ClusterIP Service, a name such as checkout.default.svc.cluster.local resolves to the Service's virtual IP. The client connects to that IP, and the Service data plane directs the connection to a backend listed in the endpoint data. Readiness changes normally affect eligibility for new traffic as updated endpoint information propagates, while special settings such as publishNotReadyAddresses can alter the usual behavior.

    A headless Service uses clusterIP: None, so it has no Service virtual IP and no kube-proxy load balancing through such an IP. For a typical selector-based headless Service, DNS returns eligible endpoint addresses directly, allowing clients to discover and connect to individual Pods. This is useful for StatefulSets, databases and distributed inference groups that need peer identities. The client or application protocol selects endpoints and handles balancing or failover, rather than relying on a ClusterIP to hide individual backends.
