## 1. API Priority and Fairness (APF)

### What Is API Priority and Fairness?

API Priority and Fairness (APF) is a Kubernetes API server mechanism that classifies, prioritizes, and manages concurrent API requests.

Its main purpose is to prevent a single client or controller from consuming excessive API server resources and starving other important components.

For example, a misbehaving controller may continuously send thousands of List or Update requests to the API server.

Without APF, these requests could consume available API server resources and prevent critical components, such as the scheduler and kubelet, from performing their operations.

### How APF Works

APF uses two main Kubernetes resources:

- FlowSchema
- PriorityLevelConfiguration

#### FlowSchema

A FlowSchema classifies incoming requests according to attributes such as:

- User identity.
- Service account.
- Namespace.
- API resource.
- Request verb, such as GET, LIST, CREATE, or UPDATE.

Each matching request is assigned to a priority level.

#### PriorityLevelConfiguration

A PriorityLevelConfiguration defines how requests belonging to a priority level are handled.

It controls:

- Concurrency allocation.
- Request queuing.
- Request rejection.
- Fairness between competing request flows.
- Borrowing and lending concurrency capacity between priority levels, when configured.

### Request Processing

```text
Incoming API Requests
          |
          v
      FlowSchema
          |
          v
PriorityLevelConfiguration
          |
          v
 Fair Queuing / Concurrency Control
          |
          v
      API Server
          |
          v
         etcd
```

### How APF Prevents Starvation

Suppose the API server receives requests from:

- kube-scheduler.
- kubelet.
- Deployment controller.
- A misbehaving custom controller.

APF can assign critical system traffic to protected priority levels and assign the custom controller to a lower-priority level.

Each priority level receives a share of API server concurrency capacity.

If the custom controller generates excessive requests:

1. Its requests consume the concurrency allocated to its priority level.
2. Additional requests may be placed in queues.
3. If the queues become full, additional requests may be rejected.
4. Rejected requests can receive HTTP 429 Too Many Requests.
5. Critical system traffic retains access to protected concurrency capacity.

APF also uses fair queuing and shuffle sharding to reduce interference between different request flows within a priority level.

### Benefits

- Prevents request starvation.
- Protects critical Kubernetes components.
- Improves API server availability.
- Provides fairness between competing clients.
- Limits the impact of misbehaving controllers.

APF is more sophisticated than a simple requests-per-second rate limiter because it primarily manages concurrent request execution and fairness.

## 2. Mutating Admission, Validating Admission, and Webhook Risks

### Admission Control

Admission control occurs after authentication and authorization but before an object is persisted in etcd.

Admission controllers can inspect, modify, or reject incoming API requests.

### Mutating Admission

Mutating admission controllers can modify an incoming Kubernetes object before it is stored.

Common use cases include:

- Injecting sidecar containers.
- Adding default labels.
- Adding annotations.
- Setting default resource requests and limits.
- Applying security configurations.

For example, a user submits the following Pod:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: inference-pod
spec:
  containers:
    - name: inference
      image: inference:v1
```

A mutating admission webhook may inject a monitoring sidecar.

The resulting object becomes:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: inference-pod
spec:
  containers:
    - name: inference
      image: inference:v1

    - name: monitoring-sidecar
      image: monitoring:v1
```

The user does not need to manually configure the additional container.

### Validating Admission

Validating admission controllers inspect an object and decide whether it should be accepted or rejected.

They cannot modify the object.

Common use cases include:

- Rejecting privileged containers.
- Enforcing resource limits.
- Rejecting images from untrusted registries.
- Enforcing namespace policies.
- Checking security requirements.

For example, a validating webhook may reject a Pod that contains:

```yaml
securityContext:
  privileged: true
```

Even if the user has permission to create Pods, the request can still be rejected because it violates cluster policy.

### Admission Request Flow

```text
Client Request
      |
      v
Authentication
      |
      v
Authorization
      |
      v
Mutating Admission
      |
      v
Object Validation
      |
      v
Validating Admission
      |
      v
Persist Object in etcd
```

### Comparison

| Feature | Mutating Admission | Validating Admission |
|---|---|---|
| Can modify objects | Yes | No |
| Can reject requests | Yes | Yes |
| Execution order | Before validating admission | After mutation |
| Main purpose | Modify or enrich objects | Enforce policies |
| Example | Inject a sidecar | Reject privileged containers |

### Risks of External Admission Webhooks

External admission webhooks introduce dependencies into the API request-processing path.

#### 1. Availability Risk

If the webhook service becomes unavailable, API requests matching the webhook configuration may fail.

For example, if a webhook validates every Pod creation and becomes unavailable, new Pods may not be created.

#### 2. Increased Latency

The API server must wait for webhook responses.

A slow webhook increases the latency of Kubernetes API operations.

Mutating webhooks are generally invoked sequentially, so multiple slow mutating webhooks can introduce cumulative delays.

#### 3. Circular Dependencies

A webhook may depend on resources whose creation requires the same webhook.

For example:

- A webhook validates all Pod creations.
- The webhook's own Pods become unavailable.
- Kubernetes attempts to create replacement webhook Pods.
- The API server cannot contact the webhook.
- Replacement Pods cannot be created.

This creates a recovery deadlock.

#### 4. Security Risk

Admission webhooks receive Kubernetes object information.

A compromised webhook may expose sensitive data or introduce malicious modifications into submitted objects.

#### 5. Incorrect Policy Enforcement

A webhook containing bugs may incorrectly reject valid resources or modify objects unexpectedly.

### Failure Policies

Kubernetes supports two webhook failure policies.

```yaml
failurePolicy: Fail
```

If the webhook cannot be contacted or encounters certain processing errors, the API request is rejected.

Advantages:

- Stronger policy enforcement.
- Prevents requests from bypassing required security checks.

Disadvantages:

- Webhook outages can affect cluster availability.

```yaml
failurePolicy: Ignore
```

If the webhook cannot be contacted or encounters certain processing errors, the API server continues processing the request.

Advantages:

- Improves availability during webhook failures.

Disadvantages:

- Requests may bypass intended policies.

An explicit rejection returned by a functioning webhook is still enforced regardless of failurePolicy.

### Recommended Practices

- Deploy multiple webhook replicas.
- Configure short timeouts.
- Limit webhook scope using selectors and matching rules.
- Avoid unnecessary external dependencies.
- Exclude critical recovery resources when appropriate.
- Monitor webhook latency and availability.
- Use built-in admission policies when possible.
- Choose failurePolicy according to security and availability requirements.

## 3. Informers, Local Caches, Work Queues, and Reconciliation

Kubernetes controllers continuously observe cluster state and attempt to move the actual state toward the desired state.

Informers, local caches, work queues, and reconciliation functions work together to implement this process efficiently.

### Controller Architecture

```text
              API Server
                   |
              List / Watch
                   |
                   v
                Informer
                   |
                   v
              Local Cache
                   |
                   v
              Event Handler
                   |
                   v
               Work Queue
                   |
                   v
            Reconciliation
                   |
                   v
              API Server
```

### Informer

An informer observes Kubernetes resources through List and Watch operations.

When an informer starts:

1. It performs a List operation to retrieve existing objects.
2. It stores the objects in a local cache.
3. It starts a Watch using the returned resourceVersion.
4. It receives subsequent object changes.
5. It updates the local cache.
6. It notifies registered event handlers.

Common event types include:

- ADDED.
- MODIFIED.
- DELETED.

Informers also handle watch reconnections and relisting when necessary.

### Local Cache

The local cache stores a controller's local view of Kubernetes objects.

Instead of sending a GET request to the API server every time the controller needs an object, the controller can read from its local cache.

Advantages:

- Reduces API server traffic.
- Reduces network latency.
- Improves controller performance.
- Allows multiple controller components to share cached data.

However, the local cache is eventually consistent.

It may temporarily contain outdated information because API server changes take time to reach the informer.

### Event Handler

An event handler receives notifications when objects are added, modified, or deleted.

The handler normally does not perform expensive business logic directly.

Instead, it places the object's identifier into a work queue.

For example:

```text
default/inference-deployment
```

This identifier usually contains the namespace and resource name.

### Work Queue

A work queue stores resource identifiers waiting to be reconciled.

Its responsibilities include:

- Decoupling event reception from reconciliation.
- Coalescing repeated pending work for the same key.
- Supporting concurrent processing of different objects.
- Retrying failed reconciliation operations.
- Applying rate limiting and retry backoff.

For example, if the same Deployment is updated multiple times, the work queue can combine pending notifications rather than requiring a separate reconciliation for every event.

If the object changes while reconciliation is running, its key can be queued again.

### Reconciliation Function

The reconciliation function contains the controller's main business logic.

It performs the following operations:

1. Retrieve the current object.
2. Determine the desired state.
3. Observe the actual state.
4. Compare the desired state with the actual state.
5. Perform necessary operations.
6. Update status when appropriate.
7. Retry or requeue if necessary.

Example pseudocode:

```text
function reconcile(namespace, name):

    deployment = getDeployment(namespace, name)

    if deployment does not exist:
        handle deletion if necessary
        return

    desiredReplicas = deployment.spec.replicas

    actualReplicas = countManagedPods(deployment)

    if actualReplicas < desiredReplicas:
        create missing Pods

    else if actualReplicas > desiredReplicas:
        delete excess Pods

    update deployment status
```

In the built-in Kubernetes implementation, the Deployment controller manages ReplicaSets, while the ReplicaSet controller manages Pods. The pseudocode illustrates the general reconciliation principle.

### Example Workflow

Suppose a Deployment requires three replicas.

One Pod is deleted.

1. The API server records the deletion.
2. The informer receives a deletion event.
3. The informer updates its local cache.
4. The event handler identifies the affected workload.
5. The workload identifier is placed into the work queue.
6. A worker retrieves the identifier.
7. The reconciliation function observes that only two replicas exist.
8. The controller creates a replacement Pod.
9. The desired state is restored.

### Summary

| Component | Responsibility |
|---|---|
| Informer | Observes resource changes |
| Local cache | Stores a local view of cluster objects |
| Event handler | Converts resource changes into work items |
| Work queue | Schedules, coalesces, and retries work |
| Reconciliation function | Moves actual state toward desired state |

## 4. Level-Triggered and Idempotent Reconciliation

### Level-Triggered Reconciliation

Level-triggered reconciliation means that a controller makes decisions based on the current state rather than relying exclusively on individual events.

For example:

```text
Desired replicas = 3
Actual replicas = 2
```

The controller determines that one additional replica is required.

It does not need to know exactly why the third replica disappeared.

An edge-triggered controller would instead depend on receiving a specific event, such as:

```text
Pod deleted
```

If that event is lost, the controller may fail to perform the required action.

### Why Kubernetes Uses Level-Triggered Reconciliation

Distributed systems cannot assume that events will always be delivered exactly once or that clients will remain continuously connected.

Events may be:

- Lost.
- Duplicated.
- Delayed.
- Coalesced.
- Missed during controller downtime.

Level-triggered reconciliation allows the controller to recover by examining the latest state.

### Idempotent Reconciliation

An operation is idempotent if repeating it produces the same intended result without introducing additional unintended side effects.

For example, suppose the desired number of replicas is three.

First reconciliation:

```text
Desired replicas = 3
Actual replicas = 2

Action: Create one Pod.
```

Second reconciliation:

```text
Desired replicas = 3
Actual replicas = 3

Action: No operation required.
```

The second reconciliation does not create another Pod.

### Non-Idempotent Example

```text
Whenever a Pod deletion event arrives:
    Create one Pod.
```

If the deletion event is delivered twice, this implementation may create two replacement Pods.

The final replica count may become four instead of three.

### Idempotent Example

```text
Whenever reconciliation runs:

    Read desired replica count.
    Read current replica count.

    If current count is below desired count:
        Create missing replicas.

    If current count is above desired count:
        Remove excess replicas.

    Otherwise:
        Do nothing.
```

In a real controller, deterministic resource names, ownership information, pending-operation tracking, and conflict handling may also be necessary to prevent duplicate creation when caches are stale.

### Recovering from Missed Events

Controllers can recover from missed events using:

#### 1. List and Watch Recovery

When a Watch connection is interrupted, the informer attempts to resume watching from its last processed resourceVersion.

If that resourceVersion has expired, the API server may return:

```text
HTTP 410 Gone
```

The informer performs a new List operation, rebuilds its local cache, and starts a new Watch.

#### 2. Periodic Resynchronization

Controllers may periodically requeue existing objects for reconciliation.

This allows them to reevaluate objects even when no new events have arrived.

An informer resync normally reprocesses objects already present in its cache. It does not necessarily perform a new API server List operation.

#### 3. Controller Restart

When a controller restarts, it initializes its informers and reconstructs its local cache from the API server.

It then reconciles the current resources.

The controller does not need to replay every historical event.

### Recovering from Stale Caches

Informer caches are eventually consistent.

For example:

```text
API server state: 3 Pods
Local cache state: 2 Pods
```

If the controller blindly trusts the stale cache, it may attempt to create an unnecessary Pod.

Techniques for handling stale caches include:

- Wait for initial informer cache synchronization.
- Use deterministic names for resources when possible.
- Track pending create and delete operations.
- Use resourceVersion for optimistic concurrency.
- Handle AlreadyExists and NotFound errors appropriately.
- Perform direct API reads when stronger freshness is required.
- Retry reconciliation after conflicts.
- Use ownerReferences to identify managed resources.

For example, if a controller attempts to create a resource that already exists, the API server may return:

```text
HTTP 409 Conflict
```

The controller should retrieve or observe the existing resource and determine whether additional action is necessary.

### Summary

Level-triggered reconciliation makes controllers resilient to missed events.

Idempotent reconciliation makes controllers resilient to duplicate processing and retries.

Together, these properties allow Kubernetes controllers to converge toward the desired state despite failures, stale caches, and temporary inconsistencies.

## 5. Custom Resource Definitions (CRDs) and Operators

### Custom Resource Definition

A Custom Resource Definition (CRD) allows users to introduce new resource types into the Kubernetes API.

Kubernetes provides built-in resource types such as:

- Pod.
- Deployment.
- Service.
- ConfigMap.
- Secret.

However, applications may require domain-specific resource types.

For example, an AI inference platform may require:

- InferenceService.
- ModelDeployment.
- ModelEndpoint.
- TrainingJob.

A CRD allows these resources to be represented as Kubernetes objects.

### Example CRD

The following CRD defines a custom resource named ModelDeployment.

```yaml
apiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition
metadata:
  name: modeldeployments.ai.example.com
spec:
  group: ai.example.com
  scope: Namespaced

  names:
    plural: modeldeployments
    singular: modeldeployment
    kind: ModelDeployment
    shortNames:
      - md

  versions:
    - name: v1
      served: true
      storage: true

      subresources:
        status: {}

      schema:
        openAPIV3Schema:
          type: object

          properties:
            spec:
              type: object

              required:
                - model
                - replicas

              properties:
                model:
                  type: string

                replicas:
                  type: integer
                  minimum: 1

                gpu:
                  type: integer
                  minimum: 0

            status:
              type: object

              properties:
                readyReplicas:
                  type: integer

                phase:
                  type: string
```

After creating this CRD, Kubernetes exposes a new API resource.

Users can create custom objects using kubectl.

### Custom Resource Example

```yaml
apiVersion: ai.example.com/v1
kind: ModelDeployment
metadata:
  name: llama-inference
spec:
  model: llama
  replicas: 3
  gpu: 1
```

The custom resource declares that three replicas of a model should exist, with one GPU requested per replica according to the intended custom controller semantics.

The CRD itself does not automatically create Pods or deploy models.

It only defines the resource type, schema, and API behavior.

### Operator

An Operator is a Kubernetes controller that automates application-specific operational tasks.

Operators commonly combine:

- Custom resources.
- Custom controllers.
- Reconciliation logic.
- Domain-specific operational knowledge.

An Operator observes custom resources and creates or modifies Kubernetes resources to achieve their desired state.

### AI Inference Operator Example

Suppose a user creates:

```yaml
apiVersion: ai.example.com/v1
kind: ModelDeployment
metadata:
  name: llama-inference
spec:
  model: llama
  replicas: 3
  gpu: 1
```

The Operator observes the ModelDeployment object and may perform the following operations:

1. Validate application-specific model configuration.
2. Create a Deployment.
3. Configure GPU resource requests.
4. Create a Service.
5. Configure model storage.
6. Configure autoscaling.
7. Monitor application readiness.
8. Update the ModelDeployment status.

For example:

```yaml
status:
  readyReplicas: 3
  phase: Running
```

### Architecture

```text
User
  |
  v
Custom Resource
(ModelDeployment)
  |
  v
API Server
  |
  v
AI Inference Operator
  |
  +---- Deployment
  |
  +---- Service
  |
  +---- ConfigMap
  |
  +---- PersistentVolumeClaim
  |
  +---- HorizontalPodAutoscaler
  |
  v
Running AI Inference Application
```

### Example GPU Resource Configuration

The Operator may generate a Pod template containing:

```yaml
resources:
  requests:
    cpu: "2"
    memory: "8Gi"
    nvidia.com/gpu: "1"

  limits:
    cpu: "4"
    memory: "16Gi"
    nvidia.com/gpu: "1"
```

The GPU resource must be advertised by a supported device plugin or equivalent resource-management mechanism.

### CRD vs. Operator

| Feature | CRD | Operator |
|---|---|---|
| Main purpose | Defines a new API resource type | Implements operational behavior |
| Contains reconciliation logic | No | Yes |
| Creates Kubernetes API resources | Defines the resource type | Creates or manages resource instances |
| Automates applications | No, by itself | Yes |
| Example | ModelDeployment definition | AI inference controller |

### Benefits

CRDs and Operators allow Kubernetes to manage complex applications using the same declarative approach as built-in resources.

Common use cases include:

- Database management.
- Kafka cluster management.
- AI model deployment.
- GPU workload management.
- Automated backups.
- Application upgrades.
- Distributed training.

Examples of Operator-based systems include:

- Strimzi Kafka Operator.
- Prometheus Operator.
- PostgreSQL Operators.
- KServe controllers.

## 6. Resource Requests, Limits, Capacity, Allocatable, and QoS

### Resource Requests

A resource request specifies the amount of a resource that a container requests for scheduling and resource allocation.

For example:

```yaml
resources:
  requests:
    cpu: "500m"
    memory: "512Mi"
```

This means:

- CPU request: 0.5 CPU cores.
- Memory request: 512 MiB.

The Kubernetes scheduler uses resource requests to determine whether a Pod can fit on a node.

CPU requests also influence CPU allocation under contention.

A resource request is not necessarily a strict reservation of physical hardware or an upper usage limit.

### Resource Limits

A resource limit specifies the maximum resource usage permitted for a container, subject to the resource's enforcement mechanism.

For example:

```yaml
resources:
  limits:
    cpu: "1"
    memory: "1Gi"
```

This means:

- CPU limit: 1 CPU core.
- Memory limit: 1 GiB.

### CPU Limit Behavior

If a container attempts to exceed its CPU limit, the operating system may throttle its CPU execution.

CPU throttling reduces application performance but does not normally terminate the container.

For an AI inference service, CPU throttling may increase request latency and reduce throughput.

### Memory Limit Behavior

If a container exceeds its enforced memory limit, the operating system may terminate a process through the out-of-memory mechanism.

The container may enter the following state:

```text
OOMKilled
```

The kubelet may restart the container according to its restart policy.

### Node Capacity

Capacity represents the total resources reported by a Kubernetes node.

For example:

```yaml
status:
  capacity:
    cpu: "16"
    memory: "64Gi"
    nvidia.com/gpu: "4"
```

This node has:

- 16 CPU cores.
- 64 GiB of memory.
- 4 GPUs.

Not all node capacity is necessarily available for application workloads.

### Node Allocatable

Allocatable represents the portion of node resources available for Pods after accounting for applicable system reservations and eviction thresholds.

For example:

```yaml
status:
  capacity:
    cpu: "16"
    memory: "64Gi"

  allocatable:
    cpu: "14"
    memory: "60Gi"
```

The difference may be reserved for:

- Operating system processes.
- Kubernetes components.
- Kubelet.
- Container runtime.
- Eviction-related reservations.

The scheduler uses allocatable resources when determining whether Pods can be scheduled.

### Resource Scheduling Example

Suppose a node has:

```text
Allocatable CPU: 14 cores
Allocatable memory: 60 GiB
```

Existing Pods request:

```text
CPU: 10 cores
Memory: 40 GiB
```

Remaining schedulable resources are:

```text
CPU: 14 - 10 = 4 cores
Memory: 60 - 40 = 20 GiB
```

A new Pod requests:

```text
CPU: 2 cores
Memory: 8 GiB
```

The Pod can fit based on these resource requests.

Another Pod requests:

```text
CPU: 6 cores
Memory: 8 GiB
```

This Pod cannot fit because only four CPU cores remain available for scheduling.

The scheduler generally evaluates declared requests rather than instantaneous CPU and memory usage.

### Comparison

| Concept | Meaning |
|---|---|
| Request | Resource amount used for scheduling and allocation |
| Limit | Maximum permitted usage according to resource enforcement |
| Capacity | Total resources reported by the node |
| Allocatable | Node resources available for Pod scheduling |

### Kubernetes QoS Classes

Kubernetes assigns Pods one of three traditional Quality of Service classes:

- Guaranteed.
- Burstable.
- BestEffort.

QoS classification is primarily based on CPU and memory requests and limits.

#### Guaranteed

A Pod receives Guaranteed QoS when every container has CPU and memory requests and limits, and each request equals its corresponding limit.

Example:

```yaml
resources:
  requests:
    cpu: "2"
    memory: "4Gi"

  limits:
    cpu: "2"
    memory: "4Gi"
```

Characteristics:

- More predictable resource allocation.
- Stronger protection against certain resource-pressure evictions.
- Suitable for critical workloads.

Guaranteed QoS does not mean that a Pod can never be evicted or terminated.

#### Burstable

A Pod receives Burstable QoS when it does not satisfy the Guaranteed criteria but has at least one CPU or memory request or limit.

Example:

```yaml
resources:
  requests:
    cpu: "500m"
    memory: "512Mi"

  limits:
    cpu: "2"
    memory: "2Gi"
```

Characteristics:

- Can consume resources above its requests when available.
- Provides flexibility.
- Suitable for workloads with variable resource usage.

#### BestEffort

A Pod receives BestEffort QoS when none of its containers has CPU or memory requests or limits.

Example:

```yaml
containers:
  - name: worker
    image: worker:v1
```

Characteristics:

- No declared CPU or memory reservation.
- Can consume available resources.
- More vulnerable to eviction during resource pressure.

### QoS and Pod Eviction

When a node experiences memory or other resource pressure, the kubelet may evict Pods to protect node stability.

A simplified eviction tendency is:

```text
BestEffort -> Burstable -> Guaranteed
```

However, actual kubelet eviction decisions depend on factors such as:

1. Whether a Pod's usage exceeds its resource requests.
2. Pod priority.
3. Resource usage relative to requests.

Therefore, QoS class is not an absolute eviction ordering.

For example, a Burstable Pod using significantly more memory than requested may be evicted before a Pod operating within its requests.

CPU pressure is generally handled through CPU scheduling and throttling rather than CPU-based node-pressure eviction.

### AI Inference Considerations

AI inference workloads often require predictable memory and GPU allocation.

For example:

```yaml
resources:
  requests:
    cpu: "4"
    memory: "16Gi"
    nvidia.com/gpu: "1"

  limits:
    cpu: "4"
    memory: "16Gi"
    nvidia.com/gpu: "1"
```

This configuration can provide Guaranteed QoS if all containers in the Pod satisfy the CPU and memory requirements.

GPU resources are generally treated as extended resources and cannot be overcommitted through standard extended-resource scheduling.

## 7. Kubernetes Scheduler: Filtering, Scoring, Reservation, and Binding

### Purpose of the Scheduler

The Kubernetes scheduler assigns unscheduled Pods to suitable nodes.

A newly created Pod usually does not have a node assigned.

The scheduler watches for Pods that require scheduling and determines where they should run.

### Scheduling Workflow

```text
Unscheduled Pod
       |
       v
Scheduling Queue
       |
       v
Filtering
       |
       v
Feasible Nodes
       |
       v
Scoring
       |
       v
Select Best Node
       |
       v
Reservation
       |
       v
Binding
       |
       v
Kubelet Starts Pod
```

### Stage 1: Filtering

Filtering eliminates nodes that cannot satisfy the Pod's mandatory scheduling requirements.

Common filtering conditions include:

- Insufficient CPU.
- Insufficient memory.
- Insufficient GPUs.
- Incompatible node affinity.
- Untolerated taints.
- Pod affinity or anti-affinity requirements.
- Volume restrictions.
- Node availability and scheduling restrictions.

Example:

A Pod requests:

```yaml
resources:
  requests:
    cpu: "4"
    memory: "8Gi"
    nvidia.com/gpu: "1"
```

Available nodes:

| Node | Available CPU | Available Memory | Available GPU |
|---|---|---|---|
| Node A | 8 cores | 16 GiB | 2 |
| Node B | 2 cores | 16 GiB | 1 |
| Node C | 8 cores | 4 GiB | 1 |
| Node D | 8 cores | 16 GiB | 0 |
| Node E | 6 cores | 12 GiB | 1 |

Filtering results:

- Node A: Pass.
- Node B: Fail because CPU is insufficient.
- Node C: Fail because memory is insufficient.
- Node D: Fail because no GPU is available.
- Node E: Pass.

Only Node A and Node E remain eligible.

### Stage 2: Scoring

The scheduler evaluates the feasible nodes using scoring plugins.

Scoring may consider:

- Resource utilization.
- Preferred node affinity.
- Preferred pod affinity.
- Image locality.
- Topology spread.
- Resource balancing or bin-packing strategies.

Example:

| Node | Illustrative Final Score |
|---|---|
| Node A | 90 |
| Node E | 75 |

The scheduler selects Node A because it has the highest score.

Actual scores depend on the configured scheduler plugins and their weights.

### Stage 3: Reservation

After selecting a node, the scheduler assumes the Pod is assigned to that node in its internal cache.

This allows subsequent scheduling decisions to account for the Pod's resource requirements before binding is completed.

Reserve plugins can also maintain scheduling-related state.

For example:

```text
Node A available GPUs: 2

Pod X is assigned to Node A.

Scheduler assumes Pod X consumes 1 GPU.

Remaining schedulable GPUs: 1
```

This prevents subsequent scheduling decisions from incorrectly treating the same GPU capacity as still available.

Reservation does not mean that the physical GPU has already been allocated to a running container.

If a later scheduling stage fails, the scheduler can undo the reservation and retry scheduling.

### Stage 4: Binding

Binding records the scheduling decision through the Kubernetes API server.

The Pod becomes associated with the selected node.

For example:

```yaml
spec:
  nodeName: node-a
```

The kubelet on Node A observes that the Pod has been assigned to its node.

It then works with the container runtime and networking components to start the Pod.

The scheduler does not directly start containers.

### Additional Scheduling Stages

The Kubernetes scheduling framework also supports extension points such as:

- PreFilter.
- PostFilter.
- PreScore.
- NormalizeScore.
- Permit.
- PreBind.
- PostBind.
- Unreserve.

These extension points allow additional scheduling behavior to be implemented through plugins.

### What Happens If No Node Is Suitable?

If no node satisfies the Pod's requirements, the Pod remains Pending.

For example:

```text
0/5 nodes are available:
3 Insufficient nvidia.com/gpu,
2 Insufficient memory.
```

The scheduler retries when relevant cluster conditions change or the Pod becomes eligible for another scheduling attempt.

A cluster autoscaler may also provision additional nodes if configured and if suitable node groups are available.

### Summary

| Stage | Responsibility |
|---|---|
| Filtering | Eliminate unsuitable nodes |
| Scoring | Rank feasible nodes |
| Reservation | Account for the selected Pod before binding completes |
| Binding | Persist the Pod-to-node assignment |

## 8. Node Affinity, Pod Affinity, Taints, Tolerations, and Preemption

### Node Affinity

Node affinity controls which nodes a Pod can or prefers to run on based on node labels.

For example, an AI inference workload may require a node containing an NVIDIA A100 GPU.

The node may have the following label:

```yaml
metadata:
  labels:
    accelerator: nvidia-a100
```

The Pod can specify:

```yaml
affinity:
  nodeAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      nodeSelectorTerms:
        - matchExpressions:
            - key: accelerator
              operator: In
              values:
                - nvidia-a100
```

This means the Pod can only be scheduled on nodes with the specified label.

Node affinity does not allocate a GPU by itself. The Pod must also request the appropriate GPU resource.

### Required vs. Preferred Node Affinity

Required affinity is a mandatory scheduling constraint.

```text
requiredDuringSchedulingIgnoredDuringExecution
```

If no node satisfies the requirement, the Pod remains Pending.

Preferred affinity is a scheduling preference.

```text
preferredDuringSchedulingIgnoredDuringExecution
```

The scheduler attempts to satisfy the preference but may select another suitable node.

The IgnoredDuringExecution suffix means that changes to matching node labels do not automatically evict an already-running Pod.

### Pod Affinity

Pod affinity controls scheduling based on the labels and locations of other Pods.

For example, an inference service may prefer to run on the same node as a model cache service.

```yaml
affinity:
  podAffinity:
    preferredDuringSchedulingIgnoredDuringExecution:
      - weight: 100
        podAffinityTerm:
          labelSelector:
            matchLabels:
              app: model-cache
          topologyKey: kubernetes.io/hostname
```

This configuration prefers nodes that already contain a matching model-cache Pod.

Benefits include:

- Reduced network latency.
- Improved data locality.
- More efficient communication between related services.

### Pod Anti-Affinity

Pod anti-affinity prevents or discourages matching Pods from being scheduled within the same topology domain.

For example:

```yaml
affinity:
  podAntiAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      - labelSelector:
          matchLabels:
            app: inference
        topologyKey: kubernetes.io/hostname
```

This configuration prevents matching inference replicas from being scheduled on the same node.

Benefits include:

- Improved fault tolerance.
- Reduced impact of node failures.
- Better workload distribution.

However, strict anti-affinity may leave Pods Pending if insufficient suitable nodes exist.

### Taints

Taints are applied to nodes to repel Pods that do not have matching tolerations.

For example, a GPU node may be dedicated to AI workloads.

```bash
kubectl taint nodes gpu-node dedicated=ai:NoSchedule
```

This prevents new Pods without a matching toleration from being scheduled on the GPU node.

### Tolerations

A toleration allows a Pod to tolerate a matching node taint.

Example:

```yaml
tolerations:
  - key: dedicated
    operator: Equal
    value: ai
    effect: NoSchedule
```

This Pod is allowed to be scheduled on nodes with the matching taint.

However, a toleration does not force the Pod to use the tainted node.

To require a particular node type, node affinity or nodeSelector should also be configured.

### Taint Effects

| Effect | Meaning |
|---|---|
| NoSchedule | Prevents new Pods without matching tolerations from being scheduled |
| PreferNoSchedule | Discourages scheduling Pods without matching tolerations |
| NoExecute | Can evict existing Pods without matching tolerations and prevent new scheduling |

### Priority-Based Preemption

Priority-based preemption allows higher-priority Pods to obtain resources by removing lower-priority Pods when necessary.

Kubernetes uses PriorityClass resources to define Pod priorities.

Example:

```yaml
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: critical-inference
value: 100000
globalDefault: false
preemptionPolicy: PreemptLowerPriority
description: "Priority for critical AI inference workloads"
```

A Pod can reference the PriorityClass:

```yaml
spec:
  priorityClassName: critical-inference
```

Suppose a GPU node is running a low-priority batch-processing workload.

A high-priority inference Pod requires the same GPU.

If the inference Pod cannot be scheduled normally, the scheduler may determine that removing lower-priority Pods would make a node feasible.

The lower-priority Pods are selected as preemption victims and terminated.

The higher-priority Pod can then be scheduled when sufficient resources become available.

### Preemption Limitations

Preemption cannot solve every scheduling problem.

For example:

- It cannot create GPUs on a node without GPUs.
- It cannot bypass mandatory node affinity.
- It cannot bypass untolerated taints.
- It cannot remove arbitrary constraints that remain unsatisfied after lower-priority Pods are removed.

The scheduler attempts to respect PodDisruptionBudgets when selecting victims, but this is a best-effort consideration rather than an absolute guarantee.

A PriorityClass can also use:

```yaml
preemptionPolicy: Never
```

This gives Pods scheduling priority without allowing them to preempt lower-priority Pods.

### Comparison

| Mechanism | Main Purpose | Based On |
|---|---|---|
| Node affinity | Select or prefer particular nodes | Node labels |
| Pod affinity | Place related Pods near each other | Pod labels and topology |
| Pod anti-affinity | Separate matching Pods | Pod labels and topology |
| Taints | Repel unsuitable Pods | Node configuration |
| Tolerations | Allow Pods onto tainted nodes | Pod configuration |
| Preemption | Make room for higher-priority Pods | Pod priority |

### Combined AI Inference Example

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: inference-pod
  labels:
    app: inference

spec:
  priorityClassName: critical-inference

  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
          - matchExpressions:
              - key: accelerator
                operator: In
                values:
                  - nvidia-a100

  tolerations:
    - key: dedicated
      operator: Equal
      value: ai
      effect: NoSchedule

  containers:
    - name: inference
      image: inference:v1

      resources:
        requests:
          cpu: "4"
          memory: "16Gi"
          nvidia.com/gpu: "1"

        limits:
          cpu: "4"
          memory: "16Gi"
          nvidia.com/gpu: "1"
```

This Pod requires an A100-labeled node, tolerates the dedicated AI node taint, requests one GPU, and receives high scheduling priority.

## 9. Kubelet, CRI, and CNI

### Kubelet

The kubelet is a Kubernetes agent running on each worker node.

Its main responsibility is to ensure that Pods assigned to its node are running according to their specifications.

The kubelet:

- Watches Pods assigned to its node.
- Retrieves Pod specifications.
- Coordinates container creation and execution.
- Coordinates volume preparation.
- Performs health probes.
- Restarts failed containers according to restart policies.
- Reports Pod and node status.
- Monitors node resource usage.
- Performs node-pressure eviction.

The kubelet does not normally implement container execution directly.

Instead, it communicates with a container runtime through CRI.

### Container Runtime Interface (CRI)

CRI stands for Container Runtime Interface.

It is a standardized interface that allows the kubelet to communicate with compatible container runtimes.

Common container runtimes include:

- containerd.
- CRI-O.

CRI uses gRPC to expose runtime and image-management operations.

Common operations include:

- PullImage.
- RunPodSandbox.
- CreateContainer.
- StartContainer.
- StopContainer.
- RemoveContainer.
- PodSandboxStatus.

### CRI Responsibilities

The container runtime is responsible for:

- Pulling container images.
- Creating Pod sandboxes.
- Creating containers.
- Starting and stopping containers.
- Managing container lifecycle.
- Configuring container isolation.
- Reporting container status.

The runtime may use a lower-level OCI runtime, such as runc, to create and execute containers.

### Container Network Interface (CNI)

CNI stands for Container Network Interface.

It defines a standard interface for configuring container networking.

Common Kubernetes networking implementations include:

- Calico.
- Cilium.
- Flannel.

CNI plugins are responsible for operations such as:

- Connecting Pods to the cluster network.
- Configuring network interfaces.
- Assigning Pod IP addresses, often through an IPAM plugin.
- Configuring routing.
- Removing network configuration when Pods are deleted.

Depending on the networking implementation, additional components may enforce network policies and provide advanced traffic-routing capabilities.

### Pod Startup Workflow

Suppose a user creates an inference Pod.

#### Step 1: Pod Creation

The API server validates and stores the Pod object.

#### Step 2: Scheduling

The scheduler selects a suitable node and binds the Pod to that node.

#### Step 3: Kubelet Observes the Pod

The kubelet on the selected node observes the assigned Pod through the API server.

#### Step 4: Prepare Resources

The kubelet coordinates preparation of required resources, such as:

- Volumes.
- Secrets.
- ConfigMaps.
- Device allocations.
- Container configuration.

#### Step 5: Create Pod Sandbox

The kubelet calls the container runtime through CRI.

For example:

```text
RunPodSandbox()
```

The runtime creates the Pod sandbox and its required namespaces.

The sandbox provides shared infrastructure for the Pod's containers, including the Pod network namespace.

#### Step 6: Configure Pod Networking

For a typical non-host-network Pod, the container runtime invokes the configured CNI plugins.

The CNI plugins:

1. Allocate or obtain a Pod IP address.
2. Configure network interfaces.
3. Connect the Pod to the cluster network.
4. Configure necessary routes.

The Pod can then communicate with other network endpoints according to the cluster's networking configuration.

#### Step 7: Pull Container Images

The kubelet coordinates image availability through CRI image-management operations.

For example:

```text
PullImage()
```

If the image is already available locally and the image pull policy permits reuse, another download may not be required.

#### Step 8: Create and Start Containers

The kubelet instructs the runtime to create and start containers.

```text
CreateContainer()
StartContainer()
```

Init containers run according to their configured ordering before regular application containers, with special handling for restartable init containers where supported.

#### Step 9: Health Checks

The kubelet performs configured probes.

- Startup probe: Determines whether the application has completed startup.
- Readiness probe: Determines whether the application is ready to receive traffic.
- Liveness probe: Determines whether the container should be restarted.

#### Step 10: Update Pod Status

The kubelet reports Pod and container status to the API server.

When the Pod becomes ready, it can normally become an eligible backend for matching Services.

### Architecture

```text
API Server
     |
     v
Scheduler
     |
     v
Pod Assigned to Worker Node
     |
     v
Kubelet
     |
     | CRI / gRPC
     v
Container Runtime
(containerd / CRI-O)
     |
     +---- OCI Runtime
     |         |
     |         v
     |      Containers
     |
     +---- CNI Plugins
               |
               v
           Pod Network
```

### Comparison

| Component | Responsibility |
|---|---|
| Kubelet | Manages assigned Pods and coordinates their lifecycle |
| CRI | Standard interface between kubelet and container runtime |
| Container runtime | Creates and runs Pod sandboxes and containers |
| CNI | Standard interface for configuring Pod networking |
| CNI plugins | Configure network interfaces, IP addresses, and connectivity |

The kubelet coordinates Pod execution, the container runtime executes containers through CRI operations, and CNI plugins configure Pod networking.

## 10. Services, EndpointSlices, kube-proxy, CoreDNS, and Headless Services

### Kubernetes Service

A Service provides a stable network identity for accessing a group of Pods.

Pods are temporary resources, and their IP addresses may change when they are recreated.

A Service allows clients to communicate with application replicas without tracking individual Pod IP addresses.

Example:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: inference-service

spec:
  selector:
    app: inference

  ports:
    - port: 80
      targetPort: 8080

  type: ClusterIP
```

This Service selects Pods containing the label:

```yaml
labels:
  app: inference
```

Clients connect to the Service on port 80, and traffic is forwarded to eligible Pods on port 8080.

### EndpointSlice

An EndpointSlice stores network endpoint information for a Service.

It contains information such as:

- Backend IP addresses.
- Backend ports.
- Readiness conditions.
- Node information.
- Zone information.

For example:

```yaml
apiVersion: discovery.k8s.io/v1
kind: EndpointSlice

metadata:
  name: inference-service-abc
  labels:
    kubernetes.io/service-name: inference-service

addressType: IPv4

ports:
  - port: 8080
    protocol: TCP

endpoints:
  - addresses:
      - "10.244.1.10"
    conditions:
      ready: true

  - addresses:
      - "10.244.2.15"
    conditions:
      ready: true

  - addresses:
      - "10.244.3.20"
    conditions:
      ready: false
```

For Services with selectors, the EndpointSlice controller automatically maintains EndpointSlices based on matching Pods and their conditions.

EndpointSlices improve scalability by distributing endpoint information across multiple objects rather than maintaining all endpoints in one large object.

### kube-proxy

kube-proxy is a node-level component that implements Kubernetes Service traffic routing.

It watches Services and EndpointSlices through the API server.

Based on this information, it configures networking rules on worker nodes.

Depending on the Kubernetes version and configuration, these rules may use mechanisms such as:

- iptables.
- IPVS.
- nftables.

Some Kubernetes networking implementations replace kube-proxy with an alternative Service data plane, such as an eBPF-based implementation.

### Traffic Routing Example

Suppose a Service has the following ClusterIP:

```text
10.96.0.100
```

Its backend Pods are:

```text
Pod A: 10.244.1.10:8080
Pod B: 10.244.2.15:8080
Pod C: 10.244.3.20:8080
```

A client sends a request to:

```text
10.96.0.100:80
```

The Service networking rules select an eligible backend and translate or route the connection to its Pod IP and target port.

For example:

```text
10.96.0.100:80
        |
        v
10.244.2.15:8080
```

kube-proxy generally configures the networking data plane rather than acting as a userspace proxy that processes every application request.

Service load balancing is generally connection-oriented rather than HTTP-request-oriented. It does not necessarily distribute individual HTTP requests evenly.

### CoreDNS

CoreDNS provides DNS-based service discovery within a Kubernetes cluster.

Instead of requiring applications to remember Service IP addresses, CoreDNS allows them to use Service names.

For example:

```text
inference-service
```

The fully qualified domain name is typically:

```text
inference-service.default.svc.cluster.local
```

The cluster domain may differ from cluster.local depending on configuration.

For a regular ClusterIP Service, CoreDNS resolves the Service name to its ClusterIP.

Example:

```text
inference-service.default.svc.cluster.local
                    |
                    v
               10.96.0.100
```

CoreDNS observes Kubernetes resource information through the API server and generates DNS responses based on the cluster state.

### Complete Service Discovery and Traffic Flow

```text
                    API Server
                         |
           +-------------+-------------+
           |                           |
        Service                  EndpointSlices
           |                           |
           +-------------+-------------+
                         |
                  Watched by CoreDNS
                  and Service Data Plane


Client Pod
    |
    | 1. DNS lookup
    v
CoreDNS
    |
    | 2. Return Service ClusterIP
    v
Client Pod
    |
    | 3. Connect to ClusterIP
    v
Service Networking Rules
    |
    | 4. Select eligible backend
    |
    +----------+----------+
    |          |          |
  Pod A      Pod B      Pod C
```

The complete process is:

1. The client resolves the Service name through CoreDNS.
2. CoreDNS returns the Service ClusterIP.
3. The client sends traffic to the ClusterIP.
4. The Service data plane selects an eligible endpoint.
5. Traffic is routed to the selected Pod.

### What Happens When a Pod Fails?

Suppose Pod B becomes unhealthy.

1. The kubelet detects a readiness probe failure.
2. The kubelet updates the Pod's readiness condition.
3. The EndpointSlice controller updates the endpoint information.
4. kube-proxy or its replacement observes the updated EndpointSlice.
5. The Service data plane stops selecting the unready Pod for normal new traffic.

The Service name and ClusterIP remain unchanged.

Existing connections may behave differently depending on the networking implementation and connection state.

### Headless Service

A headless Service is a Service configured with:

```yaml
clusterIP: None
```

Example:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: inference-headless

spec:
  clusterIP: None

  selector:
    app: inference

  ports:
    - port: 8080
      targetPort: 8080
```

Unlike a regular ClusterIP Service, a headless Service does not allocate a virtual ClusterIP.

For a typical selector-based headless Service, CoreDNS returns the IP addresses of eligible backend Pods directly.

For example:

```text
inference-headless.default.svc.cluster.local
                    |
                    v
          10.244.1.10
          10.244.2.15
          10.244.3.20
```

The client is responsible for selecting a backend and connecting directly to it.

DNS results normally reflect endpoint readiness unless the Service is configured to publish not-ready addresses.

### Regular ClusterIP Service Architecture

```text
Client
   |
   v
CoreDNS
   |
   v
Service ClusterIP
   |
   v
Service Data Plane
   |
   +--------+--------+
   |        |        |
 Pod A    Pod B    Pod C
```

### Headless Service Architecture

```text
Client
   |
   v
CoreDNS
   |
   v
List of Pod IP Addresses
   |
   v
Client Selects Backend
   |
   +--------+--------+
   |        |        |
 Pod A    Pod B    Pod C
```

### Headless Service Use Cases

Headless Services are commonly used when applications need direct access to individual backend instances.

Examples include:

- StatefulSets.
- Distributed databases.
- Kafka brokers.
- Distributed AI training.
- Distributed inference workers.
- Client-side load balancing.
- Peer-to-peer communication.

For example, a distributed inference application may need to discover specific model-serving workers rather than sending requests to an arbitrary replica.

A headless Service allows the application to discover individual worker endpoints.

When combined with a StatefulSet and appropriate configuration, it can also support stable DNS identities for individual replicas.

### Regular Service vs. Headless Service

| Feature | Regular ClusterIP Service | Headless Service |
|---|---|---|
| ClusterIP | Allocated | None |
| DNS response | Service virtual IP | Backend endpoint IPs |
| Load balancing | Service data plane | Client or application |
| Direct Pod discovery | Not through ordinary Service A/AAAA lookup | Yes |
| kube-proxy virtual-IP routing | Used in a conventional implementation | Not used for headless virtual-IP routing |
| Typical use case | Stateless web services | Stateful or distributed systems |

### AI Inference Considerations

A regular ClusterIP Service is suitable for stateless inference replicas when any healthy replica can process a request.

A headless Service may be more suitable when the client or inference router needs to:

- Select a specific model worker.
- Route requests according to model availability.
- Preserve application-level session affinity.
- Coordinate distributed inference.
- Implement custom load balancing.

For LLM inference, application-level routing may also consider:

- GPU utilization.
- Request queue length.
- Model availability.
- KV-cache locality.
- Token-generation workload.
- Expected inference latency.

Kubernetes Service routing does not automatically understand these application-specific metrics. A specialized inference router may therefore be required.
