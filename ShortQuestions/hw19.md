# kubernetes-ai-inference-homework

1. An imperative command tells the system to perform an action once, like starting three copies of checkout on specific hosts. A declarative object sets a goal, like keeping three copies of checkout running. The spec describes the desired state, and the status reports the most recently observed state.

Kubernetes controllers are level-triggered because they can compare the current state with the goal whenever they check.
- Lost event: An edge-triggered controller may miss pod deletion. A level-triggered controller sees that only two Pods remain and creates the missing one.
- Controller restart: An edge-triggered controller needs to replay missed events. A level-triggered controller reads the current state and fixes any difference.
- Duplicate event: An edge-triggered controller may create two replacements for one deleted Pod. A level-triggered controller checks the count again and takes no action if three Pods already exist.


2. Kubernetes components read and write objects through the API server to keep components independent, apply the same access rules to every request, and let components share cluster state without knowing how etcd stores it. The main cost is that the API server and etcd can become bottlenecks. If either is unavailable, components cannot save new changes.

If two controllers read the same resourceVersion, the first successful update changes the object’s version. The second controller gets 409 Conflict because its version is now out of date. It must read the latest object, check whether its change is still needed, and retry if necessary. This is called optimistic concurrency. Neither controller needs to hold a lock because the API server checks the version when it saves the update.

If the requested Watch history has been compacted, the client gets 410 Gone. It needs to run List again to get fresh snapshot, then restart Watch from the resourceVersion returned by that List.


3. Pod runs one or more containers for the application. 
   
   ReplicaSet maintains the desired number of Pods. For example, if checkout needs three Pods and one is deleted, the ReplicaSet controller creates a replacement.

   Deployment manages ReplicaSets and handles updates by gradually scaling up the new ReplicaSet and scaling down the old one. 
   
   Service gives clients a stable address and routes traffic to Ready Pods that match its selector, so clients can keep using the same address as Pods change.


4. The control plane manages the cluster’s desired state and decides where Pods should run. The data plane runs those Pods on worker nodes and routes traffic to them. If the control plane is temporarily unavailable, existing Pods on healthy nodes can usually keep running and serving requests. Scaling the application or scheduling replacement Pods has to wait until the control plane recovers.


5. When a client asks to create a Pod, the API server uses authentication to verify who sent the request and authorization to check whether that client can create Pods in the namespace. Mutating admission can modify the Pod, for example by adding a sidecar container. The API server then checks that the Pod spec is valid, and validating admission checks that the final Pod follows cluster policies, such as using an approved image. If all checks pass, the API server saves the Pod object in etcd.


6. resourceVersion identifies the version of an object that a client read. If two clients read the same version, the first successful update changes the object’s resourceVersion. When the second client submits its update with the old version, the API server rejects it with 409 Conflict. The client must read the latest object and retry if its change is still needed. This prevents it from accidentally overwriting the first client’s changes.


7. A controller first uses List to get a snapshot of the objects it tracks. It then starts a Watch from the resourceVersion returned by that list. As objects are added, updated, or deleted, the controller uses those events to keep its local copy up to date. This saves bandwidth and processing time because the API server only sends changes after the initial list.
