# Homework 19 – Kubernetes

## 1. API Priority and Fairness

APF classifies API requests into flows and priority levels, then controls how many can run concurrently. Fair queues and separate capacity shares keep a noisy controller from using all available capacity. Excess requests wait or receive 429 Too Many Requests, while critical traffic retains capacity under a suitable configuration.

## 2. Mutating and validating admission

Mutating admission can change an object, such as adding defaults or a sidecar. Validating admission accepts or rejects the resulting object based on policy. External webhooks add latency and depend on network and webhook availability. With failurePolicy set to Fail, failures can block requests. With Ignore, requests can bypass unavailable checks.

## 3. Controller components

An informer uses List and Watch to keep a local cache updated. Event handlers add object keys to a work queue, which deduplicates pending keys and supports retries. Workers take keys, read the latest cached state, and run reconciliation to move the actual state toward the desired state through API updates.

## 4. Level-triggered and idempotent reconciliation

Level-triggered reconciliation checks the current state against the goal. Idempotent reconciliation can run repeatedly without creating unwanted duplicate effects. After missed events, a controller can relist and requeue objects. For stale caches or update conflicts, it retries after refreshing state, using a direct API read when needed. Reconciliation must tolerate observing its own changes later.

## 5. CRDs and Operators

A Custom Resource Definition adds a new resource type to the Kubernetes API, including its schema. An Operator combines custom resources with controllers that automate application-specific tasks, such as database backups or upgrades. The CRD defines the API, and the controller implements the behavior.

## 6. Requests, limits, capacity, allocatable, and QoS

| Term | Meaning |
|---|---|
| Requests | Resource amounts used for scheduling and accounting. |
| Limits | Runtime usage bounds. CPU can be throttled, and exceeding a memory limit can cause an OOM kill. |
| Capacity | Total resources reported by a node. |
| Allocatable | Resources available to Pods after system reservations and eviction headroom. |

BestEffort Pods have no CPU or memory requests or limits. Guaranteed Pods have matching CPU and memory requests and limits for every container. Other Pods are Burstable. Under memory pressure, Pods using more than their requests are generally evicted first, then ranked by priority and usage above requests. This usually protects Guaranteed Pods more, but QoS alone does not determine eviction order.

## 7. Scheduler stages

1. Filtering removes nodes that fail requirements such as resource requests, affinity, or taints.
2. Scoring ranks the remaining nodes and selects a suitable one.
3. Reservation records the placement in scheduler state and lets plugins reserve resources while binding proceeds. Reservations are undone if placement fails.
4. Binding records the Pod's assignment through the API server. The selected node's kubelet then starts it.

## 8. Placement rules and preemption

| Mechanism | Purpose |
|---|---|
| Node affinity | Requires or prefers nodes with specified labels. |
| Pod affinity | Places Pods near matching Pods in a topology domain, such as a node or zone. |
| Taints and tolerations | Taints repel Pods. A matching toleration permits placement but does not guarantee it. NoExecute taints can also evict existing Pods. |
| Priority-based preemption | May evict lower-priority Pods so a higher-priority pending Pod can fit. Other scheduling constraints must still be satisfied. |

## 9. kubelet, CRI, and CNI

The kubelet watches Pods assigned to its node and manages their lifecycle. It uses CRI, a standard interface, to ask the container runtime to pull images, create the Pod sandbox, and run containers. The runtime typically invokes CNI plugins to configure the Pod's network interfaces, IP address, and connectivity. The kubelet then monitors health and reports status.

## 10. Service discovery and routing

A regular ClusterIP Service provides a stable virtual IP. EndpointSlices track its backend addresses and readiness. CoreDNS resolves the Service name to its ClusterIP, and kube-proxy watches Services and EndpointSlices to program node routing rules that forward traffic to backends.

A headless Service uses clusterIP: None. DNS returns backend Pod addresses directly, so the client chooses a backend without a Service virtual IP or kube-proxy load balancing for that Service.
