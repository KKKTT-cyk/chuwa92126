1. The imperative command tells system what to do, and declarative objects provides the desired state that the system 
should be. For an object, the spec holds the desired states and is written by users and other controllers that want a
change. While the status holds the observed state and is written by the component that observed it. Keeping the two apart
means that the component reporting reality cannot accidentally change the intent.

The Kubernetes controller is level-trigger because it reconciles based on the current state and the desired state. An 
event can trigger reconciliation, but the current state determines what action is needed.
a) an event is lost:
The level-trigger design will show the next evaluation sees the same difference; while the edge-trigger design shows the
difference is never repaired.
b) the controller restart:
The level-trigger design will read the current state and continue while the edge-trigger design must replay history it may
not have.
c) the same event is delivered twice:
The level-trigger design acts once because the state already matches while edge-trigger design may act twice.

2. kubernetes components never call each other, kubernetes is a set of small components that share a single point of
coordination that write and read shared objects through the API server. 
This keeps components loosely coupled, centralize authentication, authorization, admission checks, and auditing, and 
provides a shared source of truth while hiding storage details from components. The cost is the API server and the etcd
are shared dependencies. Under heavy load they can become bottlenecks, and if they become unavailable, operations such 
as new scheduling and status updates can stall.

Suppose both controllers read the same object with the same resourceVersion. The first update to commit succeeds and 
changes the object's version. The second update uses the old version, so the API server returns HTTP 409 Conflict. The 
second controller must re-read the latest object, decide whether its change is still needed, and retry with the new 
version if necessary. The controllers don't need to hold a lock between reading and writing because the version check 
and to write happen atomically.

If the requested resourceVersion is too old, the API server returns HTTP 410 Gone. The client should clear its local 
cache, list the resources again to rebuild it, and start a new watch from the resourceVersion returned by that list.

3. A pod is the smallest schedulable unit: one or more containers that share a network address and volumes and always
run on the same node;
A replicaSet is a target number of identical pods;
A deployment is a versioned set of pods with a rollout policy; it creates one ReplicaSet per version; and manages 
ReplicaSets and handles rolling updates by scaling up the new ReplicaSet and scaling down the old one.
A service is a stable address and name in front of a changing set of pods;
As Pods are replaced during a rollout, the EndpointSlice controller updates the backend list, and kube-proxy updates 
the forwarding rules. Clients keep using the same Service endpoint.

4. The control plane is the set of components that hold and act on the cluster's desired state. The data plane is what 
runs the workloads: the nodes, the container runtime and the network.
Keeping them separate matters for failures: the data plane can keep serving traffic while the control plane is down.

5. The client sends a POST request to the API server. The API server first authenticates the caller and then checks 
whether they’re authorized to create that type of object. Next, mutating admission can modify the object. The API 
server validates the object, and validating admission checks whether it complies with cluster policy. If all checks 
pass, the API server stores the object in etcd and returns 201 Created with the created object.

Authentication verifies who is making the request. Authorization checks whether that identity is allowed to perform the 
requested action, such as creating a Pod in a particular namespace. Admission control runs after those checks and before
the object is saved. Mutating admission can modify the object, and validating admission can reject it if the final 
object violates cluster policy.

6. Kubernetes uses resourceVersion to detect stale updates. If two clients read the same version and both try to update 
the object, the first update to commit succeeds and changes the version. The second update still carries the old version,
so the API server rejects it with 409 Conflict. The second client can re-read the object and retry its change if it’s 
still needed. This prevents one client from overwriting the other’s update.

7. LIST gives the client a snapshot of the objects and a resourceVersion. The client starts a WATCH from that version 
and updates its local cache as objects are added, modified, or deleted. This is more efficient than repeatedly 
listing everything because the server streams only the changes, reducing network traffic and repeated processing.
