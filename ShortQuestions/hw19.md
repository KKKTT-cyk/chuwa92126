# HW19 – Kubernetes

## Question 1.

An **imperative** command such as "start 3 copies of checkout on these hosts" runs once and is gone. If a node fails, nothing happens until someone issues another command, and repeating the request may start 3 more copies. A **declarative** object such as "there should be 3 copies of checkout" stays in the store. After a node fails, the difference between 3 and 2 is visible, so a copy is started, and repeating the request has no effect because the state is already as declared. The request is therefore **idempotent**, and the declaration is a **durable record** that the system can read at any time, even after a restart or a lost message.

Every object is split into two parts:

| Part | Holds | Written by |
|---|---|---|
| **spec** | Desired state (intent) | Users and other controllers that want a change |
| **status** | Observed state | The component that observes it |

Keeping them apart means the component reporting reality cannot accidentally change the intent.

Kubernetes controllers are **level-triggered**: events are only a hint that something might have changed, and the controller then evaluates the full state of the object. An **edge-triggered** design reacts to events ("pod X died"); a level-triggered design reacts to state ("there are 2 pods, 3 are wanted").

| Situation | Edge-triggered | Level-triggered |
|---|---|---|
| (a) An event is lost | The difference is never repaired | The next evaluation sees the same difference |
| (b) The controller restarts | Must replay history it may not have | Reads current state and continues |
| (c) The same event arrives twice | May act twice | Acts once, because the state already matches |

## Question 2.

Kubernetes components never call each other; they read and write objects through the **API server** and react to changes in those objects (hub and spoke). Benefits:

- **Policy in one place:** authentication, authorization, admission checks and audit logging apply to every change, whoever makes it.
- **State in one place:** only the API server talks to the store, so components do not need to know how the data is kept.
- **Loose coupling:** the scheduler never calls the kubelet; it writes the chosen node into the pod object and the kubelet sees it.
- **Replaceable parts and extensibility:** a component can be replaced as long as it speaks the API, and new object types and controllers use the same mechanism as built-in ones.

The main **cost** is that the API server and its store are on the path of every operation, so they are the shared bottleneck and the shared failure point.

Every object carries a **resourceVersion**, which comes from the etcd revision of its last write. An update must state the version it was based on, and the store rejects the update if the object has changed since (compare-and-swap). Suppose two controllers read the same object and both try to update it:

- The update that reaches the store first **succeeds**, because the version it is based on is still current.
- The other update is based on a stale version, so it receives a **409 Conflict**.
- The loser must **read the object again and retry** if its change still makes sense on the new state. The caller decides this, because the store cannot.

No locks are needed because a lock can be held by a client that crashes or is partitioned. With compare-and-swap on a version, a conflict is a normal result that the client resolves by reading again and retrying.

A watching client resumes from the last revision it saw. If that revision has been **compacted**, the API server answers **410 Gone (too old)**, because history cannot be kept forever. The client must **list again** and start watching from the new revision of that list.

## Question 3.

| Object | Role | What keeps it true |
|---|---|---|
| **Pod** | The smallest schedulable unit: one or more containers that share a network address and volumes and always run on the same node | The kubelet on the chosen node |
| **ReplicaSet** | A target number of identical pods | The ReplicaSet controller creates and deletes pods |
| **Deployment** | A versioned set of pods with a rollout policy; it creates one ReplicaSet per version | The Deployment controller shifts replicas between ReplicaSets |
| **Service** | A stable address and name in front of a changing set of pods | The EndpointSlice controller and kube-proxy |

The objects work as an ownership chain in which each controller manages only the layer directly beneath it. The Deployment controller keeps one ReplicaSet per version and moves replicas from the old one to the new one in bounded steps; the old ReplicaSet is scaled to 0 and kept for rollback. The ReplicaSet controller keeps N pods alive. The scheduler picks a node for each pod, and the kubelet runs the containers.

Pods are replaceable rather than repairable: a failed pod is not fixed in place, and a new pod is created from the same template. A Service finds its pods through a **label selector**, and a ReplicaSet counts its pods the same way, so a pod that matches the labels is included whatever created it.

## Question 4.

The **control plane** is the set of components that hold and act on the cluster's desired state: kube-apiserver, etcd, kube-scheduler, the controller managers. The **data plane** is what runs the workloads: the nodes, the container runtime and the network. Keeping them separate matters for failures, because the data plane does not depend on the control plane for running what is already running.

If the control plane becomes temporarily unavailable (API server or etcd down):

| Stops | Continues |
|---|---|
| Creating or changing objects | Containers already running |
| Scheduling new pods | The kubelet restarts failed containers from its local state |
| Replacing failed pods | kube-proxy rules stay installed, so Service addresses keep working |
| Rollouts, scaling | The pod network keeps forwarding |
| Node health and autoscaling decisions | DNS answers from the CoreDNS cache and its own running pods |

The result is no new work and no repair, but traffic to existing pods is still served. When the API server returns, controllers see the current state and repair it.

## Question 5.

A request from a client to create an object passes through the same pipeline in the API server:

1. **Authentication:** who is asking (certificate, token, OIDC identity).
2. **Authorization:** may this identity do this verb on this resource (RBAC).
3. **Mutating admission:** may change the object (inject defaults, sidecars, labels).
4. **Schema validation:** is the object well formed for its type.
5. **Validating admission:** may reject the object but never changes it (policies, quotas, webhooks).
6. **Persist:** write to etcd with a compare-and-swap on the revision, then respond and send a change event to every watcher.

| Stage | Question | Why it is placed here |
|---|---|---|
| **Authentication** | Who is asking | Authorization needs an identity |
| **Authorization** | Is this identity allowed | Cheap check that rejects most unauthorized traffic before any heavy work |
| **Admission control** | Should the object be modified, and does the final object satisfy policy | Mutating runs before validation so validation sees the final object; validating is the last chance to refuse |

## Question 6.

**resourceVersion** is a field in every object's metadata. It comes from the etcd revision of the object's last write, so it identifies which version of the object a client has seen. It is also used to resume watches from a known point.

It prevents conflicting updates through **optimistic concurrency**. An update must state the resourceVersion it was based on. The store compares it with the object's current version and rejects the update if the object has changed since. When several clients modify the same object, only one write is accepted against a given version; the others receive a conflict (HTTP 409). Each of them reads the object again and retries, so no client silently overwrites another client's change.

## Question 7.

**List** returns the current objects of a type and the revision at which that snapshot was taken. **Watch** opens a stream of changes after a given revision. A client lists, then watches from the revision of the list, and keeps its own copy in sync from the stream. If the connection drops, it resumes the watch from the last revision it saw with no gap. If that revision has been compacted, the API server returns 410 Gone and the client lists again.

This is more efficient than repeatedly listing for these reasons:

- Listing is the expensive operation: a full list of pods at 150,000 pods is about 0.9 GB. Controllers therefore list once and then watch, which sends only the changes.
- The API server keeps a **watch cache** with one watch per resource type on etcd, and serves most lists and all watches from memory, so thousands of clients do not overload the store.
- An informer keeps a local copy of the objects, so the controller's reads cost no API calls.
