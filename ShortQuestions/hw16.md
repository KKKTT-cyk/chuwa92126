# HW16 – Reactor

## Question 1.

In Spring MVC on Tomcat, every request holds **one thread from start to finish** (up to 200 threads by default). Take a
request that calls a database and an external API, about 255 ms in total:

```
[CPU 2 ms] [ waiting for the database 50 ms ] [CPU 2 ms]
[ waiting for the external API 200 ms ............... ] [CPU 1 ms]
```

The thread uses the CPU for only about 5 ms (2%), but it is **reserved for the full 255 ms (100%)**. The rest of the time it
just waits for I/O. This wastes resources in three ways:

| Consequence | Explanation |
|---|---|
| Throughput ceiling | 200 threads / 0.255 s = about 780 requests per second, even with an idle CPU |
| More threads is expensive | Each platform thread reserves stack memory (often up to 1 MB) and adds context switches |
| Slow dependencies spread | If the external API slows to 2 s, all 200 threads fill up with waiting requests and the service stops responding |

## Question 2.

The **Reactor pattern** is built on **I/O multiplexing**: one call asks the OS which of thousands of connections are ready,
so a thread only works when something is ready. Its four parts:

| Component | Role |
|---|---|
| Demultiplexer | The OS mechanism (via Java's `Selector`: select, poll, epoll, kqueue) that reports which channels are ready |
| Event loop (reactor) | A thread that loops forever: waits for ready events, then dispatches each one to its handler |
| Acceptor | Handles new connections and registers them with the selector |
| Handlers | Do the actual reading, processing and writing for one ready channel |

Blocking an event loop thread is harmful because **one loop serves many connections**. With 4 event loops serving 10,000
connections, a single `Thread.sleep()`, JDBC query or blocking HTTP call in a handler freezes every connection owned by that
loop. Four such calls freeze the whole server. That is why handlers must be fast and never block.

## Question 3.

The four interfaces of the Reactive Streams specification (also in the JDK as `java.util.concurrent.Flow`):

1. **`Publisher<T>`**: the source of data; it has one method, `subscribe(Subscriber)`.
2. **`Subscriber<T>`**: the consumer; it receives `onSubscribe`, `onNext`, `onError` and `onComplete`.
3. **`Subscription`**: the link between them; it has `request(long n)` and `cancel()`.
4. **`Processor<T, R>`**: both a `Subscriber<T>` and a `Publisher<R>`.

The sequence of signals:

```
subscriber.subscribe  ->  publisher
publisher: onSubscribe(subscription)     (called once, first)
subscriber: request(2)
publisher: onNext(item1), onNext(item2)  (0..N times)
subscriber: request(1)
publisher: onNext(item3), onComplete()   (one terminal signal: onComplete or onError)
```

**`request(n)`** means "I can handle n more items". The publisher never sends more `onNext` signals than were requested, so
items flow only as fast as the subscriber asks for them. This is how **backpressure** works. Nothing is produced until
someone subscribes and requests.

## Question 4.

A **`Mono<T>`** emits **0 or 1** item and then completes (similar to `CompletableFuture<T>` or `Optional<T>`). A
**`Flux<T>`** emits **0..N** items, possibly infinite (similar to a `Stream<T>` or `List<T>`, but asynchronous). Both can end
with an error signal.

"**Nothing happens until you subscribe**" means that operators only **describe** a pipeline. A `Flux` is like a recipe:
building it costs nothing, and `subscribe()` is the actual cooking. For example, a `Flux.range(1, 3).map(...)` that prints
inside `map` prints nothing until `subscribe()` is called, and every new subscription runs the work again.

`Mono.just(buildReport())` is **eager**: Java evaluates `buildReport()` right away, when the pipeline is assembled, even if
nobody subscribes. `Mono.just(x)` is only for values you already have. `Mono.fromCallable(() -> buildReport())` is **lazy**:
`buildReport()` runs only on subscription, and every time someone subscribes.

```java
Mono<Report> eager = Mono.just(buildReport());                 // runs NOW, even if nobody subscribes
Mono<Report> lazy  = Mono.fromCallable(() -> buildReport());   // runs on subscribe, every time
```

## Question 5.

Suppose `call(1)` takes 300 ms, `call(2)` 100 ms and `call(3)` 200 ms:

| Operator | Function returns | Inner calls | Output order | Example total time |
|---|---|---|---|---|
| `map` | A plain value | None (synchronous, one-to-one) | Same as input | - |
| `flatMap` | A `Mono` / `Flux` | Concurrent (up to 256 by default; `flatMap(fn, 8)` limits it) | As they finish: r2, r3, r1 | about 300 ms |
| `concatMap` | A `Mono` / `Flux` | One at a time | Preserved: r1, r2, r3 | about 600 ms |
| `flatMapSequential` | A `Mono` / `Flux` | Concurrent | Preserved (early results are buffered): r1, r2, r3 | about 300 ms |

`map` is for synchronous transformations. Using `map` with an async call gives a `Flux<Mono<User>>`, a stream of unexecuted
pipelines, which is almost always a bug. Use `flatMap` when order does not matter, `concatMap` when order matters or calls
must not overlap, and `flatMapSequential` when you want both speed and order.

## Question 6.

An error travels down the pipeline as an **`onError` signal** and ends the stream. A `try/catch` around the code that builds
a pipeline does not catch it, because that code only **builds** the pipeline. The error happens later, during execution
(for example, during the HTTP call), so the `catch` block is never reached.

| Operator | Effect |
|---|---|
| `onErrorReturn(value)` | Replaces the error with a fallback value (like catch and return a default) |
| `onErrorResume(e -> publisher)` | Switches to a fallback publisher (like catch and call a fallback) |
| `onErrorMap(e -> newException)` | Translates the exception into another one (like catch and throw a new one) |
| `retryWhen(Retry.backoff(...))` | Re-subscribes to retry, with exponential backoff |
| `timeout(duration)` | Signals a `TimeoutException` if nothing arrives in time |

Order matters: if `timeout` is placed before `retryWhen`, every attempt gets its own time limit. Swapping them would put one
limit on all attempts together.

## Question 7.

- **`subscribeOn`** decides where the **subscription and the source** run. Its position in the chain does not matter.
- **`publishOn`** switches the thread for **every operator after it**.

```java
Flux.range(1, 2)
    .map(n -> log("A", n))                 // runs on boundedElastic (chosen by subscribeOn)
    .publishOn(Schedulers.parallel())
    .map(n -> log("B", n))                 // runs on parallel (after publishOn)
    .subscribeOn(Schedulers.boundedElastic());
```

A blocking JDBC call should be wrapped in `Mono.fromCallable(...)` and moved to **`Schedulers.boundedElastic()`** with
`subscribeOn`. This keeps it off the event loop. Blocking code must never run on event loop threads or on
`Schedulers.parallel()`, which is meant for CPU-bound work.

```java
return Mono.fromCallable(() -> legacyCustomerDao.findById(id))   // a blocking JDBC call
        .subscribeOn(Schedulers.boundedElastic());               // run it OFF the event loop
```

## Question 8.

**Backpressure** addresses the problem of a fast producer and a slow consumer: without coordination, items pile up in memory
until the application runs out of it. With backpressure, the consumer controls how fast data flows.

A subscriber expresses demand with **`request(n)`** on its `Subscription`, and Reactor's operators propagate that demand
upstream automatically. `limitRate(100)` controls how much is requested at a time: it requests 100 items from upstream, and
refills once 75% of the batch has been consumed.

Some sources, such as `Flux.interval`, user clicks, sensor readings or broker messages, emit on their own schedule and cannot
slow down. For these, choose an overflow strategy:

| Operator | When the consumer cannot keep up |
|---|---|
| `onBackpressureBuffer(n)` | Queue up to n items, then fail |
| `onBackpressureDrop()` | Discard new items until there is demand again |
| `onBackpressureLatest()` | Keep only the most recent item |
| `onBackpressureError()` | Fail immediately (`Flux.interval` behaves like this by default: `OverflowException`) |

## Question 9.

| | Cold publisher | Hot publisher |
|---|---|---|
| Execution | Each subscriber triggers its own execution from the beginning | Emits whether or not anyone is subscribed |
| Late subscribers | Get all items from the start | Miss what was already emitted |
| Examples | `Mono.fromCallable`, `Flux.range`, every `WebClient` call | A `Sink`, `share()` |

A `WebClient` call is cold. The `Mono` only describes the request, so each `subscribe()` runs it again:

```java
Mono<User> user = webClient.get().uri("/users/42").retrieve().bodyToMono(User.class);
user.subscribe(u -> log.info("A {}", u));   // HTTP request #1
user.subscribe(u -> log.info("B {}", u));   // HTTP request #2 - the call is sent AGAIN
```

- **`cache()`** remembers the result and replays it to every later subscriber, so the HTTP call happens only once.
- **`share()`** keeps one upstream subscription shared by all current subscribers, which turns the cold source into a hot
  one. Subscribers that join late miss the items already emitted.

## Question 10.

| Aspect | Spring MVC | Spring WebFlux |
|---|---|---|
| Model | Thread per request, blocking | Event loop, non-blocking |
| Default server | Tomcat | Reactor Netty |
| Controller return types | Objects, `ResponseEntity` | `Mono`, `Flux` |
| Database access | JDBC, JPA | R2DBC, reactive MongoDB / Redis drivers |
| Interception | Servlet Filter, `HandlerInterceptor` | `WebFilter` |
| Request context | `ThreadLocal` (MDC, `SecurityContextHolder`) | Reactor `Context` |
| Debugging | Ordinary stack traces | Harder |
| Best for | Most CRUD applications, blocking libraries | High-concurrency I/O, streaming, API gateways |

Since Java 21, a virtual thread that blocks on I/O does not hold an OS thread. With `spring.threads.virtual.enabled=true`
(Spring Boot 3.2+), Tomcat runs each request on a virtual thread, so ordinary blocking code scales to many thousands of
concurrent requests. **Spring MVC with virtual threads is the better choice** for request/response services that need high
concurrency but want simple code and blocking libraries (JDBC, JPA), with easy debugging. WebFlux is better for streaming
(SSE, WebSockets), real backpressure, composing many async sources, or an existing reactive stack.

## Question 11.

The complete code is in `Coding/hw16/Question11.java`. The three calls start at the same time through `Mono.zip`, and each one has its own 2-second timeout and its own fallback:

- **Product:** no fallback. If the call fails or times out, the returned `Mono` fails with that error.
- **Stock:** if the call fails or times out, the page uses `Stock.unknown(sku)`.
- **Reviews:** `collectList()` comes first, so the timeout covers the whole call (a timeout on the `Flux` itself would only limit the gap between two items). If the call fails or times out, the page uses an empty list.

The method only builds the pipeline and never blocks.

```java
public Mono<ProductPage> productPage(String sku) {
    // No fallback: if the product call fails or times out, the page fails with that error
    Mono<Product> product = catalog.getProduct(sku)
            .timeout(Duration.ofSeconds(2));

    // If the stock call fails or times out, use Stock.unknown(sku)
    Mono<Stock> stock = inventory.getStock(sku)
            .timeout(Duration.ofSeconds(2))
            .onErrorReturn(Stock.unknown(sku));

    // collectList() first, so the timeout covers the whole call; on failure or timeout use an empty list
    Mono<List<Review>> reviewList = reviews.getReviews(sku)
            .collectList()
            .timeout(Duration.ofSeconds(2))
            .onErrorReturn(List.of());

    // All three calls run at the same time; nothing blocks
    return Mono.zip(product, stock, reviewList)
            .map(t -> new ProductPage(t.getT1(), t.getT2(), t.getT3()));
}
```
