#### Conceptual Questions

1. **Compare the data models of logs, metrics and traces: what a single record contains, how the storage volume of each signal grows (with traffic, with the number of label combinations, or with the number of services a request touches), and which kind of question each signal answers best. Explain why a telemetry pipeline is itself a high-throughput write-heavy, low-frequency-read distributed system.**

   A log record describes one event. It typically contains a timestamp, severity, service name, message and contextual fields such as an error code, request ID or trace ID. Log volume grows with the number of events, the size of each record and retention time. If each request produces several logs, increasing traffic usually increases storage proportionally. 

   A metric sample contains a timestamp and a numeric value belonging to a time series identified by a metric name and a particular set of label values. For example, http_requests_total with service="checkout" and status="500" identifies one series. Storage grows mainly with the number of active series, sampling frequency and retention time. Each distinct label combination creates another series, so adding user IDs or request IDs as labels can make storage and memory usage explode. With the same series and collection interval, higher request traffic changes the counter values rather than producing a sample for every request. 

   A trace describes the causal path of a request through a system and consists of spans. A span typically contains a trace ID, span ID, parent span ID, operation name, start time, duration, status and attributes. Trace volume grows with the number of sampled requests multiplied by the number and size of spans per request. Requests that touch more services, make more database calls or perform retries usually produce more spans. Retention and the sampling rate also affect storage.

   The telemetry pipeline is itself a distributed system because many application processes continuously send data through agents, collectors, buffers and storage services, while separate components query the data and evaluate alerts. Its ingestion rate is high because every application instance contributes writes, but most individual records are never read. Reads are relatively infrequent compared with writes and often arrive in bursts during investigations, although dashboards and alert rules also query regularly. This workload favors batching, compression, append-oriented storage, bounded buffering and retention policies. The pipeline must handle network failures, traffic bursts and storage outages without blocking or crashing the applications it observes, and expensive queries should be isolated from ingestion so an investigation does not disrupt incoming telemetry.

2. **Compare the two families of log storage: a full-text inverted index and a label index with compressed chunks in object storage. For each family describe what is paid at write time and at read time, which query patterns are fast or slow, and how each one is hurt by high cardinality. State which family you would choose for a platform with very high volume and mostly "this service, last 15 minutes" searches, and why.**

   A full-text inverted index, such as a Lucene-based Elasticsearch design, maps searchable terms to the documents containing them. At write time, the system pays for parsing and tokenizing indexed content, updating indexes, writing segments and merging those segments. These operations create CPU overhead, additional storage and write amplification. At read time, the system looks up terms and intersects posting lists to identify matching documents instead of scanning all stored log text. This makes selective searches for indexed words or fields efficient, including searches across services or longer time ranges. However, queries matching many records, expensive wildcard or regular-expression searches, and large aggregations can still be costly. Many distinct indexed values increase term dictionaries and aggregation costs, while dynamically creating many distinct field names can cause a separate mapping explosion. High-cardinality identifiers are useful for searches, but indexing them is not free.

   A label-index design, such as Loki's approach, indexes a limited set of labels and stores log content in compressed chunks, often in object storage. At write time, it groups records by label set, appends and compresses them into chunks, and maintains references from labels and time ranges to those chunks. It avoids building a full-text index for every message, reducing ingestion and storage costs. At read time, labels and the requested time range select candidate chunks, which must then be fetched, decompressed and scanned for text or other unindexed content. Queries limited to a particular service and short time window are efficient because little data needs scanning. Arbitrary text searches across all services or long time ranges can be slow and consume substantial query CPU and object-storage bandwidth. High-cardinality labels create many separate streams, a larger index and many small chunks that compress poorly and increase storage-operation overhead. Request IDs and user IDs should normally remain in log content or non-indexed metadata rather than stream labels.

   For very high log volume with mostly “this service, last 15 minutes” searches, I would choose a label index with compressed chunks in object storage. The query pattern already provides selective labels and a narrow time range, so scanning the selected chunks is reasonable. The platform avoids paying the full-text indexing cost for every incoming record and benefits from compression and economical long-term storage. I would keep labels such as service and environment bounded, control retention, and size the query tier for occasional broader searches. A full-text index would be more attractive if frequent arbitrary searches across large portions of the dataset were the main requirement.

3. **Compare pull-based and push-based metrics collection. Cover service discovery, detecting that a target is down, short-lived batch jobs, firewalls and network topology, who controls the collection rate, and what happens to the collector when an application misbehaves.**

   With pull-based collection, the collector discovers application targets through mechanisms such as Kubernetes, DNS, cloud APIs or static configuration, then periodically requests their metrics endpoints. The collector needs a current target list and network access to each endpoint. It controls scrape intervals, timeouts and collection concurrency, making ingestion load relatively predictable. A failed scrape provides an independent health signal, such as Prometheus up = 0, without requiring the application to report its own failure. However, this means the target could not be scraped, not necessarily that its process is dead: a network problem, timeout or invalid metrics response can also cause failure. If a target disappears from service discovery, detecting an unexpected disappearance requires additional absence checks or knowledge of expected targets.

   Pull is less suitable for a short-lived batch job that starts and exits between scrapes. Such a job can push its final metrics to an intermediary gateway that the collector later scrapes. Gateway metrics need lifecycle management so old results are not mistaken for a currently healthy job; the gateway being reachable does not prove the job is still running. Pull also requires inbound reachability from the collector to targets, which can be difficult across firewalls, NAT or isolated networks. Local collectors can scrape within each network and forward results when central reachability is unavailable.

   With push-based collection, applications or agents send metrics to a known collector endpoint, so the collector does not need to discover and contact every producer. Producers still need to locate the collector and identify themselves consistently. Push fits short-lived jobs because they can export before exiting, although delivery must complete or be buffered reliably. It also fits networks where outbound connections are allowed but inbound access is restricted. The application or exporter normally controls its send interval and batch size, while the collector can impose quotas or rate limits. Missing data is less explicit than a failed scrape: it may mean the application is dead, idle, disconnected or unable to export. Heartbeats, expected reporting intervals and last-seen checks are needed to distinguish these cases.

   A misbehaving push producer can flood the collector with excessive requests, large batches, retries or too many unique series, potentially harming other tenants. The collection tier therefore needs authentication, per-producer limits, bounded queues and overload handling. Pull gives the collector more control because an application cannot independently increase the scrape frequency, and slow targets can be constrained with timeouts. However, a scrape can still return an enormous response or millions of label combinations, so pull collectors also need response-size, sample and series limits. Neither model removes cardinality risk. A practical platform can combine pull for long-running services with controlled push paths for batch jobs and restricted networks.
