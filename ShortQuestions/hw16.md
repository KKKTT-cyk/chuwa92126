# java-reactor-homework

1. Using the timeline of a request that calls a database and an external API, explain why the thread-per-request model wastes resources for I/O-bound work.

In the thread-per-request model, one platform thread is occupied for the entire request. In the tutorial example, the request takes 255 ms, but only 5 ms is spent on CPU work; the rest time is spent waiting for the database and external API. During these waits, the thread cannot handle another request. Non-blocking I/O lets threads handle other work while waiting for results.


2. Describe the Reactor pattern: the roles of the demultiplexer, the event loop, the acceptor and the handlers. Explain why blocking an event loop thread is so harmful.

The Reactor pattern uses a demultiplexer to identify connections that are ready for I/O. The event loop receives these events and dispatches them to the appropriate handlers. The acceptor accepts new connections and registers them with the selector, and handlers perform reading, processing, and writing. 

Blocking an event loop thread is harmful because it serves many connections, so one blocking operation delays all other connections assigned to that loop.


3. Name the four interfaces of the Reactive Streams specification, describe the sequence of signals between a publisher and a subscriber, and explain the role of `request(n)`.

The four Reactive Streams interfaces are Publisher, Subscriber, Subscription, and Processor. Publisher provides data, Subscriber receives signals, and Subscription controls demand and cancellation. Processor acts as Subscriber and Publisher. 
After subscription, the Subscriber first receives onSubscribe, followed by onNext signals, and eventually either onComplete or onError. The Subscriber calls request(n) to request up to n additional items, allowing it to control the data flow through backpressure.


4. Explain the difference between `Mono` and `Flux`, and what "nothing happens until you subscribe" means. Explain why `Mono.just(buildReport())` behaves differently from `Mono.fromCallable(() -> buildReport())`.

Mono has zero or one item, while Flux has zero to many items and may represent an infinite stream. Both support completion and error signals. “Nothing happens until you subscribe” means that a lazy source and its processing pipeline execute upon subscription. 
`Mono.just(buildReport())` calls `buildReport()` immediately and captures its result. `Mono.fromCallable(() -> buildReport())` defers the call until subscription and executes it again for each subscription.


5. Compare `map`, `flatMap`, `concatMap` and `flatMapSequential` in terms of what the function returns, whether inner calls run concurrently, and the order of the output.

- map applies a synchronous function that returns a plain value. It preserves the source order and does not subscribe to inner publishers.

- flatMap applies a function that returns a Publisher, such as a Mono or Flux. It subscribes to multiple inner publishers concurrently, up to a concurrency limit. Their results may interleave, so the original order is not guaranteed.

- concatMap expects a Publisher, but it subscribes to one inner publisher at a time and waits for it to complete before starting the next. This preserves the source order.

- flatMapSequential subscribes to multiple inner publishers concurrently but buffers later results to preserve the original source order.


6. Explain why a `try/catch` around the code that builds a pipeline does not catch errors from that pipeline, and describe what `onErrorReturn`, `onErrorResume`, `onErrorMap`, `retryWhen` and `timeout` do.

A `try/catch` around pipeline construction cannot catch errors that occur later during execution. These errors are delivered through the pipeline as `onError` signals. It can still catch exceptions thrown synchronously while constructing the pipeline.

`onErrorReturn` replaces an error with a fallback value. `onErrorResume` switches to a fallback Publisher. `onErrorMap` converts an error into another exception. `retryWhen` re-subscribes to the source according to a retry policy, such as exponential backoff. `timeout` signals a timeout error when the expected signal does not arrive within the specified duration.


7. Explain the difference between `publishOn` and `subscribeOn`, and which scheduler should be used to wrap a blocking JDBC call.

`publishOn` changes the scheduler used for downstream signal processing. `subscribeOn` schedules subscription and source execution, regardless of where it is placed in the pipeline, unless the source has its own scheduling behavior.

Blocking JDBC call should be wrapped in `Mono.fromCallable()` and scheduled using `subscribeOn(Schedulers.boundedElastic())`, which keeps the blocking work off the event loop.


8. Explain what backpressure is, how a subscriber expresses demand, and the options available when a source such as `Flux.interval` cannot slow down.

Backpressure allows subscriber to control how many items it receives by calling `Subscription.request(n)`. The Publisher must not emit more items than the outstanding demand.

A source such as `Flux.interval` cannot slow its clock to match demand and may signal an overflow error when demand is insufficient. Possible strategies include buffering items, dropping items, keeping only the latest item, or failing with an error.


9. Explain the difference between cold and hot publishers, why subscribing twice to the same `WebClient Mono` sends two HTTP requests, and how `cache()` and `share()` change this.

Cold publisher starts its work separately for each subscriber, and hot publisher shares an active source, and late subscribers may miss earlier items. A typical `WebClient Mono` is cold, so subscribing twice sends two HTTP requests.

`cache()` shares one upstream subscription and replays the cached result and terminal signal to later subscribers. It can also use a time-to-live to expire the cache.

`share()` allows subscribers to share an upstream subscription. For a Flux, it shares live data without replaying earlier items and can reconnect after all subscribers cancel.


10. Compare Spring MVC and Spring WebFlux, and explain when Spring MVC with virtual threads is a better choice than WebFlux.

Spring MVC uses a thread-per-request model with blocking libraries such as JDBC and JPA. Spring WebFlux uses reactive pipelines and runs on an event-loop server such as Reactor Netty.

Spring MVC with virtual threads is a better choice for request/response applications that use blocking libraries and benefit from simple imperative code. WebFlux is useful for reactive streaming, backpressure, and composing many non-blocking operations.
