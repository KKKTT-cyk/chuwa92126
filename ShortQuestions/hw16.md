1. Suppose a request spends 5 ms processing, 100 ms waiting for a database, and 200 ms waiting for an external API. 
The thread does useful work for only 5 ms but stays occupied for 305 ms. With many requests, waiting platform threads 
consume memory and fill the thread pool.
2. Demultiplexer: Watches connections and reports which ones are ready for reading or writing.
Event loop: Picks up those events and dispatches them.
Acceptor: Accepts and registers new connections.
Handlers: Perform the actual work for each event.
Blocking an event loop is harmful because one thread serves many connections. One slow operation can delay all the 
others it handles.
3. Here are four interfaces:
Publisher: Produces data.
Subscriber: Receives data.
Subscription: Controls demand and cancellation.
Processor: Receives, processes, and publishes data.
The subscriber calls subscribe(), then receives onSubscribe(subscription). It calls request(n), and the publisher sends 
data through onNext(). The stream ends with either onComplete() or onError(). 
request(n) means: “I can accept up to n more items.”
4. Mono provides zero or one item. Flux provides zero to many items.
“Nothing happens until you subscribe” means the pipeline usually describes work that starts when subscribed to. 
However, normal Java expressions can still execute immediately:
   Mono.just(buildReport()); // Builds the report immediately
   Mono.fromCallable(() -> buildReport()); // Builds it upon subscription
fromCallable() delays execution; it does not automatically move it to another thread.
5. | Method              | Function returns            | Concurrent inner operations?   | Output order   |
   |---------------------|-----------------------------|--------------------------------|----------------|
   | `map`               | A regular value             | Does not introduce concurrency | Original order |
   | `flatMap`           | A publisher, such as `Mono` | Yes                            | May interleave |
   | `concatMap`         | A publisher                 | No, one at a time              | Original order |
   | `flatMapSequential` | A publisher                 | Yes                            | Original order |
flatMapSequential can start several operations but waits to emit their results in the original order. Concurrency does
not necessarily mean multiple threads.
6. The try/catch runs while building the pipeline, but the work usually runs later. Execution errors travel through the 
pipeline as error signals. The outer catch can only catch exceptions thrown directly during construction.
   onErrorReturn: Returns a fixed fallback value
   onErrorResume: Switches to a fallback operation
   onErrorMap: Converts the error into another error
   retryWhen: Resubscribes according to retry rules
   timeout: Signals an error or uses a fallback when the wait exceeds a limit
7. publishOn changes where downstream processing runs. subscribeOn schedules subscription and source execution.
For blocking JDBC calls, use boundedElastic():
   Mono.fromCallable(() -> blockingJdbcCall())
   .subscribeOn(Schedulers.boundedElastic());
The JDBC call still blocks, but it waits on a worker thread instead of blocking the event loop.
8. Backpressure lets the receiver control how much data it receives. The subscriber uses request(n) to express its capacity.
If the source cannot slow down, possible choices are:
Buffer: Store items temporarily, preferably with a size limit.
Drop: Discard items that cannot be handled.
Latest: Keep only the newest item.
Error: Fail when capacity is exceeded.
For example, Flux. interval can signal an overflow error when there is insufficient demand.
9. A cold publisher starts independent work for each subscription. A hot publisher shares an ongoing source; 
late subscribers may miss earlier data.
A normal WebClient Mono is cold, so subscribing twice usually sends two HTTP requests.
cache(): Stores the result and replays it to later subscribers, optionally until it expires.
share(): Shares the upstream work. For Mono.share(), later subscribers can also receive the completed result. If 
everyone cancels before completion, a later subscription can start a new request.
10. Spring MVC supports straightforward, blocking code. WebFlux uses non-blocking processing so a small number of 
threads can serve many requests.

MVC with virtual threads is often a better choice when the application mainly uses blocking tools such as JDBC or JPA 
and the team prefers sequential code. Virtual threads make waiting cheaper; they do not make database queries faster.
    
WebFlux fits applications with many non-blocking calls, streaming responses, or a need to control the rate of data delivery.
