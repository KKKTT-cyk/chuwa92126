# Observability Homework

## 1. What do logs, metrics, and traces tell us?

Suppose a video app creates subtitles when someone uploads a clip. A user says the subtitles for clip C17 never appeared.

| Signal | What we record | What we can learn |
| --- | --- | --- |
| Log | One event with a timestamp, level, message, and relevant fields. For example, the decoder logs that it found no audio track in clip C17. | What happened to this clip? Log storage grows with the number and size of events written as traffic increases. |
| Metric | One timestamp and numeric value for a series identified by its metric name and labels. A counter can group subtitle jobs by outcome. | Are failures becoming more common across all clips? At a fixed sampling interval, storage grows with the number of distinct label combinations. Using a unique clip ID as a label would create a series for every clip. |
| Trace | A trace follows one request. Each span records an operation, its start and end times, a trace ID, a span ID, and a parent span ID if it has a parent. | Did clip C17 spend most of its time fetching the video or decoding its audio? Storage grows with the number of requests traced and the spans per request. Calling more services usually adds more spans. |

Every worker produces telemetry while it processes clips. Collectors batch these records, and storage nodes divide the incoming writes among them. Even when nobody opens a dashboard, data keeps arriving. Alerts and investigations read selected signals and time ranges, so the pipeline handles many more writes than reads.

## 2. Which log storage design fits this app?

| Design | At write time | At read time | Effect of high cardinality |
| --- | --- | --- | --- |
| Full-text inverted index | Split messages into searchable terms and store a list of matching records for each term. Building and updating the index costs CPU and disk space. | Searching for a rare indexed word such as `codec` is fast, even across services. A search for a common word over a whole month can still return millions of matches. | Indexing a different clip ID in every message adds many distinct terms and enlarges the index. |
| Label index and compressed chunks in object storage | Group logs by a few labels, such as service and environment. Compress each group into chunks, store them in object storage, and index the labels. | A service and time filter narrows the chunks to read. Searching for `codec` across every service for a month requires reading and scanning many chunks. | A clip ID label creates a separate stream per clip. Many small chunks mean poorer compression and more index entries. |

For high volume, I would choose the **label index with compressed chunks**. Our usual query is “show the subtitle decoder’s logs from the last 15 minutes.” The service label and time window narrow the search before any text is scanned. I would keep the clip ID in the log message so I could still find C17 within those results.

## 3. How do pull and push metrics collection compare?

| Question | Pull | Push |
| --- | --- | --- |
| Who finds whom? | The collector discovers running subtitle workers through configuration or a service registry, then requests their metrics. | Each worker or agent knows the collector’s address and sends its metrics there. |
| How do we detect a failure? | A failed scrape shows that a known worker could not be scraped. Either the worker or the network could be responsible. | Silence could mean an idle worker, a crash, or a network problem. Track the last heartbeat for each expected worker. |
| What about short jobs? | A subtitle export that runs for four seconds can start and finish between two scrapes spaced 15 seconds apart. | The export can send its final duration and outcome to a gateway before exiting. |
| How does the network affect the choice? | The collector needs a route to the worker’s metrics endpoint. A firewall can block incoming connections. | A worker behind a firewall can send metrics if outbound connections to the collector are allowed. |
| Who controls the rate? | The collector sets the scrape interval and timeout. | The sender sets its reporting interval and batch size. The collector can limit what it accepts. |
| What if one worker misbehaves? | A slow response or a huge scrape consumes collector resources. Timeouts and sample limits bound that cost. | A worker that retries continuously can flood the collector. Per-sender rate limits and bounded queues protect capacity for other workers. |
