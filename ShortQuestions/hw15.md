# HW15 – Data Access

## Question 1.

ORM stands for Object-Relational Mapping. It converts between Java objects and relational database tables: it turns objects into rows when saving, and turns query-result rows back into objects when reading. Java and the database speak two different languages, and ORM maps one to the other:

| Java | Database |
|---|---|
| class (e.g. `Student`) | table (`students`) |
| object (`new Student("Lin", "lin@example.com")`) | row (`id=1, name='Lin', email='lin@example.com'`) |
| field (`name`, `email`) | column (`name`, `email`) |

Saving a `Student` makes Hibernate run SQL such as `INSERT INTO students (name, email) VALUES ('Lin', 'lin@example.com');`. Java code does not eliminate SQL; the framework generates and executes it for us.

## Question 2.

JPA (Jakarta Persistence API) is a standard for Java persistence. It is like a rulebook that defines what `@Entity`, `@Id` and `@OneToMany` mean, which methods `EntityManager` has, and how JPQL should be written. JPA by itself does not do the database work; it needs an implementation.

Hibernate is the most common JPA implementation, the engine that works according to that rulebook. It reads the entity annotations, generates SQL, converts query results into objects, manages entity state, and implements dirty checking and lazy loading.

So "JPA is the standard, Hibernate is the implementation" because JPA specifies how things should work, while Hibernate actually executes them.

## Question 3.

Hibernate already saves us from writing much JDBC, but common CRUD code is still repetitive. Spring Data JPA is a repository abstraction built on top of JPA that generates the repository implementation for us:

```java
public interface StudentRepository extends JpaRepository<Student, Long> {
}
```

We only write the interface. We do not implement `save()`, `findById()`, `delete()` or `findAll()` ourselves, because Spring Data JPA provides them when we extend `JpaRepository`.

The relationship between the three is: Spring Data JPA uses JPA, JPA is implemented by Hibernate by default, and Hibernate finally accesses the database through JDBC.

## Question 4.

An Entity is a Java object that is managed by JPA and is usually saved to a database table. It is the Java representation of one row of data.

| Annotation | Purpose |
|---|---|
| `@Entity` | Declares a JPA entity; this class is managed by JPA |
| `@Table(name = "students")` | Specifies the table the class is stored in (here `students`) |
| `@Id` | Declares the primary key; the field that uniquely identifies a row |
| `@GeneratedValue` | Specifies the ID generation strategy, i.e. who generates the ID (for example `GenerationType.IDENTITY`) |

```java
@Entity
@Table(name = "students")
public class Student {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
}
```

## Question 5.

`@Id` declares which field is the primary key, that is, the field used to uniquely identify one row. An entity needs it so JPA can tell rows apart.

A newly created entity has no ID before the INSERT, because the ID is generated when it is saved (`@GeneratedValue`):

```java
Student student = new Student("Lin", "lin@example.com");
// student.getId() is null at this point
```

This is why the ID type is `Long` rather than `long`: `Long` can be `null`, which clearly expresses "no ID yet", while `long` defaults to 0, which is easy to confuse with a real value.

## Question 6.

A student can take many courses and a course can have many students, so it looks like a many-to-many relationship. But an enrollment itself has data, such as the time and the status. With a simple `@ManyToMany` the relationship is only a line between two entities and has nowhere to keep that data. So we model the relationship itself as an association entity, `Enrollment`, and the design becomes:

```
Student 1 ----< many Enrollment many >---- 1 Course
```

Fields that belong in `Enrollment` rather than in `Student` or `Course`:

- `enrolledAt`: when the student enrolled in the course.
- `status`: whether the enrollment is currently `ACTIVE` or `DROPPED`.
- A `grade` could be added in the future.

`Enrollment` also gets a unique constraint on `(student_id, course_id)`, so the same student and course combination can appear only once. Application code can check first and return a friendly error, but the database constraint is the last line of protection.

## Question 7.

```java
public class Enrollment {
    @ManyToOne
    @JoinColumn(name = "student_id")
    private Student student;
}
```

1. **Owning side:** `Enrollment.student` is the owning side of the relationship with `Student`. The way to find it is to look at the schema: the foreign key is in the `enrollments` table, so the side that holds it is the owner.
2. **Foreign key column:** `student_id` in the `enrollments` table (it references `students(id)`). `@JoinColumn` specifies this column.
3. **Responsibility:** The owning side maintains the foreign key. Only when the value of the owning side changes does Hibernate know what to write into `student_id`. `Student.enrollments` is the inverse side, which does not maintain the foreign key, so changing only the inverse-side collection does not change the database.

## Question 8.

```java
@OneToMany(mappedBy = "student")
private List<Enrollment> enrollments;
```

`mappedBy` is written on the inverse side. It tells Hibernate that `Student.enrollments` is not a new independent relationship: it describes the same relationship as `Enrollment.student`, which is the owner, so Hibernate should use the existing `enrollments.student_id` foreign key. Without `mappedBy`, Hibernate would treat it as another relationship maintained by `Student` and might create an extra join table (such as `student_enrollments`), duplicating the existing foreign key. `mappedBy` creates no new column.

`"student"` is a Java field name because `mappedBy` points to a property of the `Enrollment` class, and that field is named `student`:

```java
public class Enrollment {
    @ManyToOne
    @JoinColumn(name = "student_id")
    private Student student;   // mappedBy refers to this field name
}
```

- Java field name: `student`, used by `mappedBy`.
- Database column name: `student_id`, used by `@JoinColumn`.

Writing `mappedBy = "student_id"` is wrong: Hibernate cannot find a Java property `Enrollment.student_id`, and mapping validation fails at application startup.

## Question 9.

- **LAZY:** the relationship is loaded only when it is actually accessed. It is like fetching the documents only when you need them.
- **EAGER:** the relationship is required to be loaded together with the entity. It is like carrying all the documents over whether you use them or not.

For example, with `@ManyToOne(fetch = FetchType.LAZY) private Course course;`, reading an `Enrollment` may leave `course` as just a proxy. Hibernate only issues the course query when we call `enrollment.getCourse().getTitle()`.

Relationships should not all be EAGER because loading one entity would then also load everything related to it, even when the data is never used. That is why the relationships in our entities are declared with `fetch = FetchType.LAZY`, for example `@ManyToOne(fetch = FetchType.LAZY)` on `Enrollment.student` and `Enrollment.course`.

## Question 10.

Example: "query the Enrollments of a student by `studentId`", i.e. `GET /api/students/1/enrollments`.

| Layer | Responsibility in this example |
|---|---|
| HTTP Request | The client (e.g. Postman) sends `GET /api/students/1/enrollments`; `1` is the `studentId`. |
| Controller | Handles only the HTTP request: receives the `studentId` and calls the Service. |
| Service | Holds the business logic and the transaction; it calls the Repository to get the student's enrollments and turns them into the response view (student and course basic information). |
| Repository (Spring Data JPA) | `EnrollmentRepository` has no hand-written SQL; the derived query `List<Enrollment> findByStudentIdOrderByEnrolledAtDesc(Long studentId)` is understood from its name: `findBy` runs a query, `StudentId` filters on `enrollment.student.id`, `OrderByEnrolledAtDesc` sorts newest first. |
| Hibernate | Uses the entity mapping to generate the SQL and converts the result rows back into `Enrollment` objects. |
| JDBC | The standard Java API that connects to the database, executes the SQL and reads the query result. |
| Database | PostgreSQL runs roughly `SELECT ... WHERE student_id = ? ORDER BY enrolled_at DESC` on the `enrollments` table and returns the rows. |

The result then travels back up the same layers and is returned as the HTTP response.
