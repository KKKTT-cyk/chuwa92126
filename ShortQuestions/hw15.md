# Homework 15 - Reactor

## 1. Why does thread-per-request waste resources for I/O-bound work?

Example timeline: 5 ms processing -> 100 ms waiting for the database -> 200 ms waiting for an external API -> 5 ms building the response.

The request takes 310 ms, but only about 10 ms is active processing. With a platform thread per request, the thread stays occupied during the 300 ms wait. It does not keep using CPU while blocked, but it still consumes thread resources and a pool slot. Many simultaneous requests can exhaust the pool. Non-blocking I/O lets a small number of threads handle other work while waiting.

## 2. What is the Reactor pattern?

- **Demultiplexer:** waits for I/O events and reports which registered connections are ready, such as a selector using `epoll`.
- **Event loop:** repeatedly receives ready events and dispatches them.
- **Acceptor:** accepts new connections and registers them for further events.
- **Handlers:** perform the work for an event, such as reading data or preparing a response.

An event loop serves many connections. Blocking it with JDBC, sleep, or a long calculation delays all the other connections assigned to that loop.

## 3. What are the four Reactive Streams interfaces?

- `Publisher<T>`: provides a stream and accepts subscribers.
- `Subscriber<T>`: receives data and terminal signals.
- `Subscription`: lets the subscriber request data or cancel.
- `Processor<T, R>`: acts as both a subscriber and a publisher.

The subscriber calls `publisher.subscribe(subscriber)`. The publisher calls `onSubscribe(subscription)`. The subscriber then uses `request(n)` to request up to `n` more items, which arrive through `onNext`. The stream may end with either `onComplete` or `onError`, never both.

Demand is cumulative, and `n` must be positive. A publisher must not emit more items than requested. Terminal signals do not require demand. `cancel()` stops interest in further data.

## 4. Mono, Flux, and subscription

`Mono<T>` emits zero or one item; `Flux<T>` emits zero to many items. Both can complete or fail.

For a lazy, cold pipeline, building it only describes the work. Subscribing starts execution. Spring WebFlux subscribes to the publisher returned by a controller.

```java
Mono<Report> first = Mono.just(buildReport());
Mono<Report> second = Mono.fromCallable(() -> buildReport());
```

In `first`, Java calls `buildReport()` immediately and `just` captures its result. In `second`, the call is deferred until subscription and demand, and is repeated for each subscription. Exceptions from the callable become error signals. `fromCallable` alone does not move work to another thread.

## 5. map, flatMap, concatMap, and flatMapSequential

For a Flux:

| Operator | Mapper returns | Concurrent inner subscriptions? | Output order |
| --- | --- | --- | --- |
| `map` | A value | No inner publisher | Source order |
| `flatMap` | A Publisher | Yes, up to the concurrency limit | Inner results may interleave |
| `concatMap` | A Publisher | No; one inner at a time | Source order |
| `flatMapSequential` | A Publisher | Yes, up to the concurrency limit | Buffers later results to preserve source order |

Concurrent subscriptions allow asynchronous calls to overlap; they do not automatically create threads or make blocking calls non-blocking.

## 6. How are pipeline errors handled?

A `try/catch` around pipeline construction only catches exceptions thrown during construction. Execution errors usually happen later and travel as `onError` signals.

- `onErrorReturn`: replaces failure with a fixed fallback value.
- `onErrorResume`: switches to a fallback publisher, possibly chosen using the error.
- `onErrorMap`: transforms the exception and keeps the stream failed.
- `retryWhen`: resubscribes according to a retry policy, such as limited retries with backoff. Side effects may repeat.
- `timeout`: fails with a timeout error, or switches to a supplied fallback, if the expected signal takes too long. On a Flux, a duration normally limits the wait for the first item and gaps between items.

An error ends the original upstream sequence; a fallback does not continue that failed sequence where it stopped.

## 7. publishOn and subscribeOn

`publishOn(scheduler)` moves downstream signal processing to that scheduler until another scheduling boundary. `subscribeOn(scheduler)` schedules subscription and source-side work; its effect is not limited to operators written after it. Sources with their own scheduling can still emit elsewhere.

Wrap a blocking JDBC call with `fromCallable` and `boundedElastic`:

```java
Mono<Student> student = Mono.fromCallable(() -> jdbcLoadStudent(id))
        .subscribeOn(Schedulers.boundedElastic());
```

This keeps the blocking call off the event loop. It does not turn JDBC itself into non-blocking I/O. Avoid `Mono.just(jdbcLoadStudent(id))`, which calls JDBC immediately.

## 8. What is backpressure?

Backpressure prevents a fast producer from overwhelming a slower consumer. The subscriber communicates demand through `Subscription.request(n)`.

A timed source such as `Flux.interval` cannot postpone its clock ticks to match demand. Without sufficient demand, it can fail with an overflow error. Possible policies include:

- Buffer a limited number of items and define what happens when the buffer fills.
- Drop items with `onBackpressureDrop()`.
- Keep only the latest pending item with `onBackpressureLatest()`.
- Fail when the system cannot keep up.

Choose based on whether losing data is acceptable. An unlimited buffer can exhaust memory; `limitRate` alone cannot make an uncontrollable source slow down.

## 9. Cold and hot publishers

A cold publisher starts independent work for each subscription. A hot publisher shares a source or previously produced data; late subscribers may miss earlier items unless replay is provided.

A normal WebClient request Mono is cold, so subscribing twice sends two HTTP requests.

- `cache()` on a Mono shares the first load and replays its value, empty completion, or error to later subscribers. A TTL overload allows expiration. Once started, the cached load continues even if subscribers cancel.
- `share()` on a Mono shares one upstream subscription and its result. In Reactor 3.7, later subscribers also receive the terminal result. If all subscribers cancel before termination, it cancels the source and a later subscription can start it again.

Reuse the same cached or shared Mono instance. Creating a new one per call does not share across calls. `Flux.share()` generally shares live emissions without replaying all earlier values.

## 10. Spring MVC and Spring WebFlux

Spring MVC uses the Servlet model and commonly runs blocking request-handling code. WebFlux uses reactive publishers and non-blocking I/O, allowing a small event-loop pool to handle many concurrent connections. MVC also supports asynchronous responses; the distinction is not simply synchronous versus asynchronous.

MVC with virtual threads is often a better choice for an existing imperative application using JDBC/JPA and other blocking libraries. It keeps straightforward code while reducing the cost of many I/O-waiting requests. Virtual threads do not remove database connection limits or make CPU work faster.

WebFlux is useful for end-to-end non-blocking applications, many concurrent I/O operations, and streaming with backpressure. It requires care to keep blocking work off event loops.
