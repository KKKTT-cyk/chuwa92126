## Question1: Explain how java.lang.reflect.Proxy works, what Proxy.newProxyInstance() generates at runtime, what an InvocationHandler receives on every call, why only interfaces can be proxied, and why the handler should rethrow InvocationTargetException.getCause().
1.How Proxy.newProxyInstance() works?

The Proxy.newProxyInstance() method dynamically generates a proxy class that implements one or more specified interfaces.
Its signature is:
Proxy.newProxyInstance(
ClassLoader loader,
Class<?>[] interfaces,
InvocationHandler handler
);
The three parameters are:
- loader: The class loader used to define the proxy class.
- interfaces: The interfaces that the generated proxy class implements.
- handler: The object responsible for intercepting and processing method calls.

2.What does InvocationHandler receive?
The invoke() method receives three arguments:
Object invoke(
Object proxy,
Method method,
Object[] args
) throws Throwable;
proxy is the generated proxy instance, method represents the invoked interface method, and args contains the method arguments (or null if there are none).

3.Why can Java dynamic proxies only proxy interfaces?
The standard JDK dynamic proxy mechanism generates a class that extends java.lang.reflect.Proxy and implements the specified interfaces. It does not generate subclasses of arbitrary concrete classes. Therefore, it cannot directly proxy a concrete class that does not expose an appropriate interface.

4.Why should InvocationTargetException.getCause() be rethrown?
When reflection invokes a method using method.invoke(), any exception thrown by the target method is wrapped in an InvocationTargetException.
For example, if the target method throws IllegalArgumentException, reflection wraps that exception. Rethrowing e.getCause() exposes the original exception to the caller rather than the reflection wrapper.

## Question2:Describe the three phases of class loading (loading, linking, initialization), the situations that trigger class initialization, and the parent delegation model: the three built-in class loaders and why delegation to the parent comes first.
1.Java uses a class-loading mechanism to load class definitions into the JVM dynamically. Class loading and initialization involve three primary phases: loading, linking, and initialization.
Phase 1: Loading
During loading, the JVM locates and reads a class's binary representation, typically from a .class file or JAR file, and creates the corresponding runtime Class object.
Phase 2: Linking
Linking consists of three operations.
Verification: The JVM checks that the class's bytecode follows JVM structural and type-safety requirements.
Preparation: Memory is allocated for static fields, which receive their default values before explicit static initializers run.
Resolution: Symbolic references to classes, fields, and methods are resolved into concrete runtime references. Resolution can occur lazily rather than entirely during initial linking.
Phase 3: Initialization
During initialization, the JVM executes static field initializers and static initialization blocks in their defined order.

2.When is class initialization triggered?
Common triggers include creating an instance with new, invoking a static method, accessing or modifying a nonconstant static field, and using reflection in ways that request initialization, such as Class.forName("com.example.UserService").
Initialization also occurs for required superclass initialization and for the class containing the application's main() method before it executes.

3.Parent Delegation Model
Java has three primary built-in class loaders:

Bootstrap Class Loader

Loads fundamental Java runtime classes, such as java.lang.String

Delegates to parent first

Platform Class Loader

Loads Java platform modules outside the core bootstrap set

Delegates to parent first

Application Class Loader

Loads application classes and dependencies from the application class path and applicable modules


Under the standard parent delegation model, a class loader first asks its parent to load a requested class. If the parent cannot find the class, the child attempts to load it itself.

Parent delegation is important because it helps prevent applications from replacing core Java classes, promotes consistent class identity, reduces duplicate loading, and improves JVM reliability.

Custom class loaders may implement different delegation strategies, but parent-first loading is the standard behavior.

## Question3:Explain the roles of serialVersionUID, transient, and readResolve() in Java serialization, and why deserializing data from an untrusted source is dangerous.
1. serialVersionUID
   serialVersionUID is a version identifier for a serializable class. During deserialization, Java compares the class's serialized version identifier with the identifier of the locally loaded class.
   If the identifiers are incompatible, Java throws InvalidClassException.
Explicitly declaring serialVersionUID avoids depending on an automatically calculated identifier that can change as the class evolves. However, a matching identifier does not guarantee that all class changes are serialization-compatible.
2. transient
   The transient keyword prevents a field from participating in Java's default serialization mechanism.
   class User implements Serializable {
   private String username;
   private transient String password;
   }
   When the object is serialized, username is saved, but password is excluded from default serialization.
When the object is deserialized, the transient password field receives its default value, which is null for a String.
This is useful for excluding sensitive data, temporary state, caches, and other fields that should not be persisted.
3. readResolve()
   The readResolve() method allows a deserialized object to be replaced with another object before being returned to the caller.
It is commonly used to maintain singleton identity during deserialization.
   Without readResolve(), deserializing a traditional serializable singleton may create a distinct object, violating the singleton guarantee. With readResolve(), the deserialized result is replaced by the existing instance.
4. Why is deserializing untrusted data dangerous?
   Java deserialization can be dangerous because reconstructing an object may invoke application or library behavior, including custom deserialization methods. An attacker may construct a malicious serialized object graph that exploits vulnerable classes or dependencies.
   Possible consequences include remote code execution through deserialization gadget chains, denial-of-service attacks, unauthorized state manipulation, and unexpected application behavior.
The safest approach is to avoid native Java deserialization for untrusted data whenever possible. Structured formats such as JSON, combined with strict validation and explicit type restrictions, are generally preferable.
When Java serialization is unavoidable, developers should restrict allowed object types using ObjectInputFilter, limit object-graph size and depth, and ensure that the data source and dependencies are trusted and appropriately secured.
