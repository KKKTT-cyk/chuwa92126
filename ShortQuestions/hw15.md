### Question 1.

In the traditional thread-per-request model, each request occupies a worker thread throughout its lifetime, including while waiting for database or HTTP responses. For I/O-bound applications, most of that time is spent waiting rather than using the CPU. This limits concurrency and creates memory and scheduling overhead. Reactive programming uses non-blocking I/O, allowing a small number of event-loop threads to handle many concurrent requests without dedicating a thread to each waiting operation.

### Question 2.

The Reactor pattern uses I/O multiplexing to handle many connections using a small number of threads. The demultiplexer identifies ready I/O events, the event loop dispatches those events, the acceptor registers new connections, and handlers process reads and writes.

Blocking an event loop is harmful because that thread serves many connections, so a single blocking operation can delay all connections assigned to it.

### Question 3.

Reactive Streams defines four interfaces: Publisher, Subscriber, Subscription, and Processor.

A subscriber receives a Subscription through onSubscribe, request data using request(n), receives items through onNext, and eventually receives either onComplete or onError.

The request(n) method implements backpressure by allowing the subscriber to control how many items the publisher may emit.

### Question 4.

Mono represents zero or one asynchronous result, while Flux represents zero to many results. Reactor publishers are generally lazy, meaning their processing starts on subscription. However, `Mono.just` evaluates its argument immediately, so `Mono.just(buildReport())` runs `buildReport` during pipeline construction. `Mono.fromCallable` defers that execution until subscription and runs it again for each new subscription.

### Question 5.

- Map applies a synchoromous transformation and returns plain values.

- flatMap maps items to publishers and merges their results concurrently, so ordering is not guaranteed.

- concatMap processes inner publishers sequentially and preserves order.

- flatMapSequential runs inner publishers concurrently but buffers results to preserve the original input order.

I would use flatMap for maximum concurrency and concatMap or flatMapSequential when output ordering matters.

### Question 6.

In Reactor, errors usually occur during subscription and are propagated as onError signals, so try/catch around pipeline construction does not catch them.

`onErrorReturn` provides a fixed callback. `onErrorResume` switches to another publisher, and `onErrorMap` transforms exceptions. `retryWhen` retries a failed subscription with configurable delays, while `timeout` emits an error when an operation takes too long. Operator ordering matters, especially when combining retries and timeouts.

### Question 7.

`subscribeOn` controls the scheduler used for subscription and upstream source execution, while `publishOn` changes the execution context for downstream operators. `subscribeOn` generally works independently of its position in the chain, while `publishOn` affects operators after it. For blocking JDBC calls, I would use `Mono.fromCallable` together with `subscribeOn(Schedulers.boundedElastic())` to keep blocking work off event-loop threads.

### Question 8.

Backpressure prevents fast producers from overwhelming slow consumers. Reactive Streams implements it through `Subscription.request(n)`, which lets a subscriber communicate how many items it can receive. Reactor propagates this demand upstream automatically.

For sources that cannot slow down, such as `Flux.interval`, Reactor provides strategies including buffering, dropping excess items, keeping the latest item, or failing with an overflow error.

### Question 9.

A cold publisher starts a new execution for each sbuscriber, while a hot publisher shares emissions among subscribers. `WebClient` publishers are cold, so subscribing twice to the same `Mono` normally sends two HTTP requests. `cache()` stores and replays results to later subscribers, while `share()` allows subscriptions to share an upstream execution. For a live `Flux`, late subscribers generally miss earlier emissions.

### Question 10.

Spring MVC typically uses a thread-per-request model with blocking APIs, while Spring WebFlux uses a reactive, non-blocking model built on Mono and Flux. WebFlux is useful for high-concurrency I/O, streaming, and composing asynchronous services. However, with Java 21 virtual threads, Spring MVC can handle many concurrent blocking requests without dedicating a platform thread to each one. I would generally choose MVC with virtual threads for traditional CRUD applications using JDBC or JPA, and WebFlux for applications that benefit from an end-to-end reactive stack and backpressure.
