## 1. Explain the difference between an imperative command such as "start 3 copies of checkout on these hosts" and a declarative object such as "there should be 3 copies of checkout", and explain what the spec and the status of an object are used for. Then explain why Kubernetes controllers are leveltriggered rather than edge-triggered: for each of these three situations, say what an edge-triggere design does and what a level-triggered design does: (a) an event is lost, (b) the controller restarts, (c) the same event is delivered twice.

An imperative command specifies actions and placement, while a declarative object states the outcome Kubernetes should maintain. The spec records the desired configuration, and the status reports observed conditions. Level-triggered controllers reconcile current state with that goal. If an event is lost, an event-only edge-triggered controller may miss the required action; reconciliation repairs the mismatch once state is observed again. After a restart, edge-triggered logic needs missed-event replay, while reconciliation rebuilds state and resumes. Duplicate events may repeat an edge-triggered action, while idempotent reconciliation sees the goal already satisfied and avoids creating extra replicas.

## 2. Explain why Kubernetes components never call each other and instead read and write objects through the API server (name at least three benefits and the main cost). Then describe how resourceVersion and optimistic concurrency handle two controllers that read the same object and both try to update it: say which update succeeds, what the other one receives, what it must do next, and why this design needs no locks. Also explain what a watching client must do when the revision it wants to resume from has already been compacted.

Controllers normally coordinate through API objects, providing loose coupling, durable shared state, and centralized security and validation. The cost is extra API latency and dependence on API-server availability. For two version-checked updates from the same read, the first accepted update changes resourceVersion; the second receives 409 Conflict, fetches the latest object, recomputes its change, and retries. An atomic version check replaces locks held between controllers. If watch history has been compacted, 410 Gone requires clearing the local cache, performing a fresh List, and restarting Watch from the returned collection version. Some direct communication still exists, such as API-server calls to kubelets.

## 3. Explain the roles of Pods, ReplicaSets, Deployments, and Services. How do these objects work together to run and maintain an application?

A Pod runs one or more containers that share networking and volumes. A ReplicaSet maintains a desired number of matching Pods, creating replacements when replicas disappear. A Deployment manages ReplicaSets to provide scaling, rolling updates, and rollbacks. A Service selects Pods by labels and gives clients a stable DNS name and, typically, a virtual IP that routes traffic to ready endpoints. Together, the Deployment and ReplicaSet maintain the application, Pods run it, and the Service keeps it reachable as Pods change.

## 4. What is the difference between the Kubernetes control plane and data plane? What happens to existing running workloads if the control plane becomes temporarily unavailable?

The control plane manages cluster state and decisions through the API server, etcd, scheduler, and controllers. The data plane runs containers and carries application traffic on worker nodes. Because node components operate locally, existing workloads generally keep running during a temporary control-plane outage, established network rules remain usable, and kubelets can still restart containers locally. However, scheduling, controller-driven scaling, deployments, and replacement of Pods on failed nodes wait for the control plane to recover.

## 5. Describe the main stages a request goes through when a client creates a Kubernetes object. What is the difference between authentication, authorization, and admission control?

A client sends the object to the API server over HTTPS. Authentication establishes the caller identity, authorization checks permission for the requested operation, and admission control applies object-level policy through mutation followed by validation. The API server also checks the object schema and required fields, persists the accepted object in etcd, and returns a response. Controllers then observe the stored object and act asynchronously, so successful creation does not mean the workload is already running.

## 6. What is the purpose of the resourceVersion field in Kubernetes? How does it help prevent conflicting  updates when multiple clients modify the same object?

resourceVersion is an opaque identifier for a stored object version. A client includes the version it read in a version-checked update. If another writer has already changed the object, the API server rejects the stale write with 409 Conflict; the client must read the latest object and retry its intended change. This prevents silently overwriting concurrent updates.

## 7. How do the List and Watch operations work together to help Kubernetes components track changes in  cluster state? Why is this approach more efficient than repeatedly listing all objects?

List retrieves an initial snapshot and its collection resourceVersion; Watch then streams subsequent additions, modifications, and deletions from that version so a component can keep a local cache current. After a disconnect, it resumes from its last version, or relists if history has expired. Sending incremental changes avoids repeatedly transferring and processing every object, reducing network traffic and API-server load.
