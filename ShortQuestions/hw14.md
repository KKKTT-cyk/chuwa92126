## Question1:Explain the difference between a static nested class and an inner (non-static) class. Describe the hidden reference an inner class holds, how it can cause a memory leak, and why a static nested class is usually preferred.
The main difference is that an inner class is associated with an instance of its enclosing class, while a static nested class is not.
The Inner object maintains a hidden reference to its enclosing Outer instance.This hidden reference allows the inner class to access the enclosing object's instance fields and methods.

How Can It Cause a Memory Leak?
If an Inner instance remains reachable through a static collection or another long-lived object, its hidden reference can keep the entire Outer instance reachable.
As a result, the garbage collector cannot reclaim the Outer object or its large data array, even if the application no longer needs them.
This can cause unintended memory retention.

A static nested class does not automatically hold a reference to an Outer instance. It can be instantiated independently.
It can access static members of the enclosing class directly, but accessing instance members requires an explicit Outer reference.

Conclusion: A static nested class is usually preferred when the nested class does not need access to an enclosing instance. It avoids unnecessary references, reduces memory-retention risks, and makes dependencies more explicit.

## Question2:Explain type erasure: what the compiler does with List<String>, why new T(), new T[10], and obj instanceof List<String> are not allowed, and what a bridge method is and why the compiler generates it.
1. What Happens to List<String>?
   During compilation, the compiler checks that the elements added to the list are String values.
   At runtime, List<String> and List<Integer> generally have the same raw runtime class.
   For an unbounded generic type parameter, the compiler generally replaces T with Object. For a bounded type parameter, it uses the erasure of the leftmost bound.
2. Why Is new T() Not Allowed?
   Because of type erasure, the actual runtime type represented by T is not available to create an instance.
3. Why Is new T[10] Not Allowed?
Java arrays know and enforce their element types at runtime, while generic type parameters are erased.
   Therefore:
   class Container<T> {
   T[] values = new T[10]; // Compilation error
   }
is not allowed because Java cannot construct an array whose runtime component type is the unknown T.
4. Why Is instanceof List<String> Not Allowed?
At runtime, Java cannot determine whether the object is specifically a List<String>, because the generic element type has been erased.
5. What Is a Bridge Method?
   A bridge method is a synthetic method generated by the compiler to preserve polymorphism after type erasure.

## Question3:State the PECS rule. For List<? extends Number> and List<? super Integer>, say which operations (reading, adding) are allowed on each one and why, and explain why generics are invariant while arrays are covariant.
PECS stands for Producer Extends, Consumer Super.
- Producer Extends: Use ? extends T when a collection primarily produces values that you want to read as type T.
- Consumer Super: Use ? super T when a collection primarily consumes values of type T that you want to add.

1. List<? extends Number>
   The wildcard means that the list holds elements of some unknown type that extends Number, which could be Integer, Double, Float, or another subtype.
   Reading is allowed:
   Number number = numbers.get(0);
Adding ordinary numeric values is not allowed:
numbers.add(10);    // Compilation error
numbers.add(3.14);  // Compilation error
The compiler does not know the exact element type. For example, the underlying list could be a List<Double>, so inserting an Integer would be unsafe.
The only value that can be added is null, because null is compatible with every reference type.
Rule: ? extends Number is suitable for reading values as Number, but not for adding non-null elements.
2. List<? super Integer>
   The wildcard means the list has an element type that is Integer or one of its supertypes.

Adding integers is allowed:
numbers.add(10);
numbers.add(20);

Reading as Integer is not guaranteed:
Integer x = numbers.get(0); // Compilation error

Instead:
Object x = numbers.get(0);

Because the actual list could be a List<Object> or List<Number>, the compiler can only guarantee that returned elements are assignable to Object.
Rule: ? super Integer allows adding Integer values and its subtypes, while reads are only guaranteed to return Object.

3. Why Are Java Generics Invariant?
   Java generics are invariant, meaning:
   List<Integer> integers = new ArrayList<>();
List<Number> numbers = integers; // Compilation error

Even though Integer extends Number, List<Integer> is not a subtype of List<Number>.

4. Why Are Java Arrays Covariant?
   Java arrays are covariant:
   Integer[] integers = new Integer[3];

Number[] numbers = integers; // Allowed
However, this can cause an exception at runtime:
numbers[0] = 3.14;
Output:
java.lang.ArrayStoreException

The actual array is still an Integer[]. Java performs a runtime element-type check and rejects the Double.
Generics instead reject similar unsafe assignments at compile time.

## Question4:Describe the three retention policies (SOURCE, CLASS, RUNTIME) and what @Target, @Inherited, and @Repeatable do. Which retention policy must an annotation have to be read through reflection at runtime?
Java annotations provide metadata that can be attached to classes, methods, fields, parameters, and other program elements.
The @Retention annotation determines how long annotation metadata remains available.
1. RetentionPolicy.SOURCE
   The annotation exists only in source code and is discarded by the compiler.
Typical uses include compile-time checking and source-code analysis.
2. RetentionPolicy.CLASS
   The annotation is recorded in the .class file but is not available through ordinary runtime reflection.
This is the default retention policy when @Retention is omitted.
3. RetentionPolicy.RUNTIME
   The annotation is included in the class file and remains accessible through reflection at runtime.
This policy is commonly used by frameworks such as Spring.
4. What Does @Target Do?
   @Target specifies where an annotation is allowed.
5. What Does @Inherited Do?
   @Inherited permits certain annotations placed on a superclass to be inherited by subclasses when annotations are queried through the Class reflection API.
6. What Does @Repeatable Do?
   @Repeatable allows an annotation to be applied multiple times to the same declaration.

## Question5:List the ways to obtain a Class object. Explain what setAccessible(true) does and how the module system limits it, and why a method invoked with Method.invoke wraps an exception thrown by the target in InvocationTargetException.
Java Reflection allows a program to inspect and interact with classes, constructors, methods, fields, and annotations at runtime.
1. Ways to Obtain a Class Object
   Method 1: Using .class
   Class<String> clazz = String.class;
This is useful when the class is known at compile time.

Method 2: Using getClass()
String value = "Hello";
Class<?> clazz = value.getClass();
This obtains the actual runtime class of an object.

Method 3: Using Class.forName()
Class<?> clazz =
Class.forName("java.lang.String");

This resolves a class by its fully qualified name. The single-argument form also initializes the class if needed.
It is useful when class names are supplied dynamically, such as by configuration.
Method 4: Using a ClassLoader
ClassLoader loader =
Thread.currentThread().getContextClassLoader();

Class<?> clazz =
loader.loadClass("java.lang.String");

This allows classes to be loaded through a particular class loader. loadClass() generally does not initialize the class immediately.

Method 5: Primitive and Array Class Literals
Class<?> primitiveClass = int.class;
Class<?> arrayClass = String[].class;
Class<?> voidClass = void.class;
Primitive class objects can also be obtained through constants such as Integer.TYPE.

2. What Does setAccessible(true) Do?
   Normally, Java access modifiers restrict access to private fields and methods.
   Reflection can suppress Java language access checks where permitted:
   Setting accessibility to true requests permission to bypass normal Java access checks for that reflective object.
3. How Does the Java Module System Limit Reflection?
   Since Java 9, the Java Platform Module System (JPMS) has introduced stronger encapsulation boundaries.
A module can expose packages using:
exports com.example.api;

or open packages for deep reflection using:
opens com.example.model;

An exported package permits ordinary access to its public API, but does not automatically permit reflective access to private members.
For deep reflection across module boundaries, the target package generally must be opened to the calling module, or another applicable access rule must permit access.
Otherwise, setAccessible(true) can fail with InaccessibleObjectException.

4. Why Does Method.invoke() Wrap Exceptions?
   When a method invoked through Method.invoke() throws an exception, Java wraps that exception in an InvocationTargetException.

This allows callers to distinguish between:
- An exception thrown by the invoked method itself.
- A problem with the reflective invocation, such as invalid arguments or insufficient access permissions.
