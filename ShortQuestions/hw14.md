### Question 1.

`java.lang.refelct.Proxy` creates a proxy class at runtime that extends `Proxy` and implements the specified interfaces. Each method call is forwarded to an `InvocationHandler`, which receives the proxy object, the reflective `Method`, and its arguments.

JDK dynamic proxies only support interfaces because Java allows single-class inheritance, and the generated proxy already extends `java.lang.reflect.Proxy`. When the handler invokes the target through reflection, it should catch `InvocationTargetException` and rethrow `getCause()` so the caller receives the original exception rather than the reflection wrapper. Dynamic proxies are commonly used for logging, caching, security and Spring AOP.

### Question 2.

Java class loading has three phases: loading, linking, and initialization. Loading locates bytecode and creates class metadata. Linking performs verification, preparation of static fields with default values, and symbolic-reference resolution. Initialization executes static initializers and blocks.

Initialization is triggered by active use, such as creating an instance, calling a static method, accessing a non-constant static field, or calling `Class.forName()` with initialization enabled.

Three build-in class loaders are Bootstrap, Platform, and Application. Java normally use parent-first delegation: a class loader asks its parent to load a class before attempting to load it itself. This protects core JDK classes, reduces duplicate definitions, and maintains consistent class identity.

### Question 3.

`serialVersionUID` identifies the serialization version of a class and is checked during deserialization. A mismatch causes `InvalidClassException`. Declaring it explicitly helps maintain compatibility across compatible class changes.

`transient` excludes an instance field from default serialization, so it receives its default value upon deserialization.

`readResolve()` allows a deserialized object to be replaced, commonly with the existing singleton instance to preserve object idendity.

Deserializing untrusted data is dangerous because crafted object graphs can execute methods during deserialization, potentially triggering gadget-chain attacks and remote code execution. We should avoid native Java deserialization for untrusted input, prefer data-only formats, and use validation and `ObjectInputFilter` where necessary.
