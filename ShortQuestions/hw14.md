# java-advanced-syntax-homework


1. Explain how `java.lang.reflect.Proxy` works: what `Proxy.newProxyInstance` generates at runtime, what an `InvocationHandler` receives on every call, why only interfaces can be proxied, and why the handler should rethrow `InvocationTargetException.getCause()`.

`Proxy.newProxyInstance()` creates proxy class and instance at runtime that implements the specified interfaces. `InvocationHandler` receives the proxy object, the called method, and its arguments on each method call.
Only interfaces can be proxied is because the generated proxy implements interfaces rather than extending a concrete class.
The handler should rethrow `InvocationTargetException.getCause()` so the caller receives the original exception instead of the wrapper.


2. Describe the three phases of class loading (loading, linking, initialization), the situations that trigger class initialization, and the parent delegation model: the three built-in class loaders and why delegation to the parent comes first.
 1. Loading: Loads the class bytecode and creates Class object.
 2. Linking: Verifies the class, prepares static fields, and resolves symbolic references.
 3. Initialization: Executes static field initializers and static blocks.

Class initialization is triggered by active uses, such as creating an instance, calling a static method, accessing or assigning a non-constant static field. 
The three built-in class loaders are Bootstrap, Platform, and Application. In parent delegation model, a class loader asks its parent to load a class first, which avoids duplicate loading and prevents application classes from replacing core Java classes.


3. Explain the roles of `serialVersionUID`, `transient`, and `readResolve` in Java serialization, and why deserializing data from an untrusted source is dangerous.

- `serialVersionUID` is used to check version compatibility during deserialization
- `transient` prevents a field from being included in default serialization
- `readResolve()` allows a deserialized object to be replaced with another object

Deserializing untrusted data is dangerous because malicious serialized objects may trigger unexpected code execution or other security vulnerabilities.
