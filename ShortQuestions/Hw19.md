## 1. What is API Priority and Fairness (APF), and how does it prevent a misbehaving controller from starving critical system traffic?

APF is API-server flow control that classifies requests into priority levels and flows, assigns concurrency budgets, and uses fair queuing with shuffle sharding. Excess requests from a noisy controller are queued or rejected with HTTP 429, while correctly classified critical system traffic retains access to its concurrency share instead of waiting behind the flood.

## 2. What is the difference between mutating admission and validating admission? What risks do external admission webhooks introduce?

Mutating admission changes an object before it is stored, such as adding defaults or injecting a sidecar. Validating admission checks the final object and accepts or rejects it without changing it. External webhooks add latency and network, TLS, and availability dependencies. Fail-closed errors can block legitimate operations, while fail-open errors can bypass policy; bugs and dependency loops can also disrupt the cluster.

## 3. How do informers, local caches, work queues, and reconciliation functions work together in a Kubernetes controller?

Informers use List and Watch to maintain an eventually consistent local cache. Their event handlers enqueue object keys into a work queue, which deduplicates pending work and can rate-limit retries. Workers read the current cached objects, run reconciliation to move actual state toward desired state, and write changes through the API server. Failed work is requeued for another attempt.

## 4. Why should Kubernetes reconciliation be level-triggered and idempotent? How can a controller recover from missed events and stale caches?

Level-triggered reconciliation compares current state with desired state, so progress does not depend on receiving every event. Idempotence makes retries safe without duplicate resources or repeated side effects. Controllers recover through List/Watch, relisting when watch history expires, and periodically resyncing or requeuing objects. They wait for cache synchronization, use fresh API reads when needed, and handle stale-write conflicts by rereading and retrying.

## 5. What are Custom Resource Definitions (CRDs) and Operators, and how do they extend Kubernetes functionality?

A CRD registers a new Kubernetes API resource type, including its schema, so users can manage custom objects through the API and kubectl. An Operator combines custom resources with controllers that encode application-specific operational knowledge. For example, a database Operator can reconcile database instances and automate backups, upgrades, and recovery without changing Kubernetes core code.

## 6. What are the differences between resource requests, limits, capacity, and allocatable resources? How do QoS classes affect pod eviction?

Requests describe resources used for scheduling; limits constrain runtime usage, such as CPU throttling or memory OOM kills. Capacity is total node resources, while allocatable excludes system reservations and eviction headroom. QoS reflects resource settings: BestEffort has no CPU or memory requests or limits, Burstable has partial protection, and Guaranteed is usually best protected. Under memory pressure, eviction ranks usage above requests, Pod priority, and relative excess usage rather than following a fixed QoS-only order.

## 7. How does the Kubernetes scheduler select a node for a pod? Explain filtering, scoring, reservation, and binding.

The scheduler filters nodes that cannot satisfy resource requests or hard placement constraints, then scores the feasible nodes and selects one with the highest weighted score. It assumes the placement in its cache, and Reserve plugins record provisional allocations to avoid races while binding is pending. Binding records the node assignment through the API server; failed later stages release reservations so the Pod can be retried.

## 8. What are the differences between node affinity, pod affinity, taints and tolerations, and priority-based preemption?

Node affinity matches node labels using required or preferred rules. Pod affinity places a Pod near matching Pods within a topology such as a node or zone. Taints repel Pods, or evict them with NoExecute, unless matching tolerations allow them to stay; tolerations do not guarantee placement. Priority-based preemption removes lower-priority Pods when that can make room for a pending higher-priority Pod, while still respecting hard placement requirements.

## 9. What are the respective responsibilities of the kubelet, Container Runtime Interface (CRI), and Container Network Interface (CNI) when starting a pod?

The kubelet coordinates startup for assigned Pods, prepares volumes, and reports health. Through CRI, it asks the container runtime to pull images, create a Pod sandbox, and start containers. The runtime invokes CNI plugins to configure the sandbox network, including interfaces, IP addresses, and routes, so containers in the Pod share networking.

## 10. How do Services, EndpointSlices, kube-proxy, and CoreDNS work together to enable service discovery and traffic routing? How does a headless Service differ from a regular ClusterIP Service?

A Service defines a stable virtual address and usually selects its backing Pods. EndpointSlices track their addresses, ports, and readiness. CoreDNS resolves Service names to ClusterIPs, while kube-proxy watches Services and EndpointSlices to program forwarding and load-balancing rules. A headless Service sets clusterIP to None: DNS returns endpoint IPs directly, and clients connect without a Service virtual IP or kube-proxy load balancing.
