# java-spring-aop-homework


1. Explain what a cross-cutting concern is, and use the `OrderService` example from class to explain "tangling" and "scattering".
   
Cross-cutting concern is  logic that many classes need but that is not their core job, such as logging, security, and metrics.

In the OrderService example, `tangling` happens when business logic is mixed with logging, permission checks, and timing code in the same method. `Scattering` happens when the same logging and timing code is repeated across multiple methods, such as `placeOrder()` and `cancelOrder()`.


2. Define aspect, join point, pointcut, advice, target and proxy, and state what a join point always is in Spring AOP.

- Aspect: A module that holds cross-cutting logic, such as logging or security.

- Join point: A point in execution where aspect can be applied. In Spring AOP, it is always a *method execution*.

- Pointcut: An expression that selects which methods should be intercepted.

- Advice: The code that runs before, after, or around selected join points.

- Target: The original object that contains the business logic.

- Proxy: An object created by Spring that is around the target and applies the advice.


3. Compare the five advice types (`@Before`, `@AfterReturning`, `@AfterThrowing`, `@After`, `@Around`): when each one runs, and which of them can change the return value or prevent the target method from running.

- `@Before`: Before the target method
  
- `@AfterReturning`: After the method returns successfully
  
- `@AfterThrowing`: When the method throws an exception
  
- `@After`: After the method finishes, whether succeeds or fails
  
- `@Around`: Wraps the entire method execution and can run before and after it. It can replace the return value or skip the target method by not calling proceed().


4. Describe three mistakes that are easy to make inside an `@Around` advice and the effect of each one.

   1. Calling `pjp.proceed()` without returning its value: The caller receives null, which can throw `AopInvocationException` for primitive return types
   2. Catching `Throwable` without rethrowing: Exceptions are swallowed, which may prevent `@Transactional` from rolling back if the aspect runs inside the transaction
   3. Forgetting `pjp.proceed()`: The target method never executes, so its business logic is skipped


5. Explain what each pointcut expression matches: `execution(* com.example.orders.service.*.* (..))`, `execution(* com.example.orders..*.*(..))`, `execution(* *(Long, ..))` and `@annotation(com.example.orders.aop.LogExecutionTime)`.

- `execution(* com.example.orders.service.*.* (..))`: any method in any class directly in service

- `execution(* com.example.orders..*.*(..))`: every method in orders and all its sub-packages

- `execution(* *(Long, ..))`: methods with exactly one Long
parameter
  
- `@annotation(com.example.orders.aop.LogExecutionTime)`: methods annotated with `@LogExecutionTime`


6. Explain how Spring AOP applies advice through proxies, at which step of the bean lifecycle the proxy is created, and how you can check that an injected bean is a proxy.

Spring AOP uses proxies to intercept method calls and apply advice before or after calling the target method. The proxy is typically created after bean initialization by a `BeanPostProcessor` during `postProcessAfterInitialization()` phase. We can check whether an injected bean is a proxy using `AopUtils.isAopProxy(bean)`.


7. Explain why calling a method annotated with `@LogExecutionTime` or `@Transactional` from another method of the same class skips the advice, and describe two ways to fix it.

When one method calls another method in the same class using `this`, self-invocation occurs and bypasses the proxy, so `@LogExecutionTime` or` @Transactional` is not applied.

To fix this:
   1. The recommended approach is to extract the method into another Spring bean by injecting new bean and calling its method through the proxy.
   2. Use `AopContext.currentProxy()` instead of `this`, with proxy exposure enabled to call through the proxy.


8. State the default rollback rules of `@Transactional`, and describe three situations in which a `@Transactional` method does not roll back even though something went wrong.

By default, `@Transactional` rolls back for unchecked RuntimeException and Error, but not for checked exceptions.

Three common situations:
   1. Calling a transactional method from the same class bypasses the proxy, so the transaction advice is skipped.
   2. Spring commits by default unless rollbackFor is configured.
   3. If an exception is caught and not rethrown, Spring may commit because it does not see the failure.


9. SecurityAspect has `@Order(1)` and `TimingAspect` has `@Order(2)`, and both use `@Around` on the same method. Describe the order in which their code runs. Then compare Spring AOP with AspectJ in terms of weaving and the join points each one supports.

The execution order:
   1. SecurityAspect (code before proceed())
   2. TimingAspect (code before proceed())
   3. Target method
   4. TimingAspect (code after proceed())
   5. SecurityAspect (code after proceed())

Spring AOP uses runtime proxies and only supports method execution join points on Spring beans.

AspectJ uses weaving at compile time, post-compile time, or load time. It supports more join points, including method calls, method execution and constructors.
