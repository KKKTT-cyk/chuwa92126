# HW11 – Spring AOP

## Question 1.

A **cross-cutting concern** is logic that many classes need but that is not their core job, such as logging, metrics, transactions, security, caching and retry.

In the `OrderService` example, `placeOrder` mixes metrics, logging, a permission check and error handling around a single line of business logic (`createAndSave(request)`). That is **tangling**: one method mixes four concerns, so the business line is hard to find. `cancelOrder` repeats the same boilerplate, and so would hundreds of other methods. That is **scattering**: the same logging/metrics code is copied everywhere, so it is easy to forget in a new method and hard to change (a new log format means editing every copy).

## Question 2.

| Term | Meaning |
|---|---|
| Aspect | A module that holds one cross-cutting concern (a class annotated with `@Aspect`) |
| Join point | A point in execution where an aspect can plug in (e.g. the call to `placeOrder()`) |
| Pointcut | An expression that selects join points |
| Advice | The code to run at the selected join points, and when (before, after, around) |
| Target | The original object being advised (your `OrderService` instance) |
| Proxy | The object Spring creates around the target to apply the advice; it is what gets injected |

In Spring AOP a join point is **always a method execution**. Short version: pointcut = where, advice = what and when, aspect = pointcut + advice packaged together.

## Question 3.

| Advice | Runs | Sees return value | Can change result | Can prevent the call |
|---|---|---|---|---|
| `@Before` | Before the method | No | No | Only by throwing |
| `@AfterReturning` | After a normal return | Yes | No | No |
| `@AfterThrowing` | After an exception (sees the exception) | No | No (it is rethrown) | No |
| `@After` | Always, like `finally` | No | No | No |
| `@Around` | Wraps the whole call | Yes | Yes | Yes |

Only `@Around` can change the return value and skip the target method (for example by returning a cached value), because it controls whether and how `proceed()` is called. `@Before` can stop the call only by throwing an exception. Rule of thumb: use the least powerful advice that does the job.

## Question 4.

| Mistake | Effect |
|---|---|
| Calling `pjp.proceed()` without returning its value | The caller always receives `null`; for a primitive return type Spring throws `AopInvocationException` |
| Catching `Throwable` and not rethrowing | Exceptions vanish silently, and if this aspect runs inside the transaction advice, `@Transactional` will not roll back |
| Forgetting `pjp.proceed()` | The target method never runs |

The correct pattern is `return pjp.proceed();`, optionally inside `try/finally`.

## Question 5.

- `execution(* com.example.orders.service.*.*(..))`: every method of every class **directly** in the `service` package (not sub-packages), with any return type and any parameters.
- `execution(* com.example.orders..*.*(..))`: every method in `orders` and **all its sub-packages**, because `..` in a package means this package and all sub-packages.
- `execution(* *(Long, ..))`: any method, in any class, whose **first parameter is `Long`**, followed by anything (`..` in parameters means any number of parameters of any type).
- `@annotation(com.example.orders.aop.LogExecutionTime)`: methods annotated with `@LogExecutionTime`.

## Question 6.

Spring never changes your class. At startup it creates a **proxy** that wraps the bean, and the proxy is what other beans receive. When a controller calls `orderService.placeOrder(req)`, the proxy runs the "before" part of the matching advice, calls the real method on the target, then runs the "after" part and returns the result. Spring uses either a JDK dynamic proxy (implements the target's interfaces) or CGLIB (generates a subclass of the target class, the Spring Boot default).

The proxy is created in `BeanPostProcessor.postProcessAfterInitialization()`, which is step 6 of the bean lifecycle.

To check that an injected bean is a proxy, print its class name:

```java
log.info(orderService.getClass().getName());
// com.example.orders.service.OrderService$$SpringCGLIB$$0
```

## Question 7.

When a method calls another method of the same class, the call is really `this.placeOrder(...)`, and `this` is the **target**, not the proxy. The call never reaches the proxy, so the advice (`@LogExecutionTime`, `@Transactional`) does not run. The same root cause breaks `@Cacheable`, `@Async`, `@Retryable` and `@PreAuthorize`.

Two fixes:

1. **Move the method to another bean** (recommended). Inject that bean; the injected reference is the proxy, so advice applies. This gives a clean design with no Spring APIs in business code, at the cost of one more class.
2. **Call through the current proxy**: use `@EnableAspectJAutoProxy(exposeProxy = true)` and `AopContext.currentProxy()`:

```java
OrderService self = (OrderService) AopContext.currentProxy();
requests.forEach(self::placeOrder);   // through the proxy
```

This is a small change but couples the code to Spring AOP.

## Question 8.

**Default rollback rules:**

| Thrown | Default |
|---|---|
| `RuntimeException` (unchecked) | Rollback |
| `Error` | Rollback |
| Checked exception (e.g. `IOException`) | **Commit** (change with `rollbackFor = Exception.class`) |

**Situations where it does not roll back although something went wrong:**

1. **A checked exception is thrown**: the transaction commits unless `rollbackFor = Exception.class` is set.
2. **The exception is caught and swallowed inside the method**: the proxy never sees an exception, so it commits. In the `transfer` example, a swallowed failure in `credit()` lets the debit commit and the money disappears. The fix is to rethrow.
3. **Self-invocation** (or a `private` method, or a class that is not a Spring bean): the call bypasses the proxy or the annotation is ignored, so no transaction exists at all and there is nothing to roll back.

## Question 9.

**Execution order.** A lower `@Order` value means higher precedence, i.e. the outermost aspect. So the code runs in this order:

1. `SecurityAspect` code before `proceed()` (outermost)
2. `TimingAspect` code before `proceed()`
3. Target method
4. `TimingAspect` code after `proceed()`
5. `SecurityAspect` code after `proceed()`

The highest-precedence aspect is first on the way in and last on the way out. This is why a security check goes outermost: it rejects the call before any other work happens.

**Spring AOP vs AspectJ:**

| | Spring AOP | AspectJ |
|---|---|---|
| Weaving | At runtime, through proxies | Compile-time, post-compile or load-time (bytecode is modified) |
| Join points | Method execution only | Method call/execution, constructors, field get/set, static initializers |
| Targets | Spring beans only | Any Java object |
| Self-invocation | Not intercepted | Intercepted |

Spring AOP borrows AspectJ's annotations and pointcut language (`@Aspect`, `@Around`, `execution(...)`) but not its weaver.
