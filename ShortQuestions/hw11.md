# Q2.
Job: the whole batch process.
Step: one independent phase of job.
Job parameters: the input.
Job instance: the logic run.
StepExecution: one attempt to run a job instance.
ExecutionContext: key-value state saved during a run.
JobRepository: persist metadata.

# Q3.
ItemReader reads one item at a time and the ItemProcessor processes one item at a time. The results are collected until the chunk size is reached, and then the ItemWriter writes the whole chunk at once   
Each chunk runs in its own transaction. The transaction covers reading, processing and writing the chunk, and it commits only after the writer finishes. In the same transaction, Spring Batch also updates the step’s execution metadata in the JobRepository, such as how many items were read and the reader’s current position. So the business data and the restart state are always consistent.   
If an error occurs, only the current chunk is rolled back; all previously committed chunks stay in the database. When the job is restarted, it resumes from the last committed chunk, so at most one chunk of work is repeated.   
A larger chunk size usually means higher throughput, because there are fewer commits and batch writes are more efficient. However, it uses more memory, since more items are held at once, keeps transactions and database locks open longer, and means more work is repeated after a failure. A smaller chunk size uses less memory and repeats less work, but commits more often and is slower. The right value is a trade-off and should be tuned by testing.

# Q4.
A tasklet step runs a single piece of custom logic through the Tasklet interface’s execute() method, returns RepeatStatus.FINISHED when the work is done. 
Each call to execute() runs in one transaction, and there is no split into reading, processing and writing. It is suited to simple, one-off actions. A typical use is a cleanup task, such as deleting a temporary file.  
A chunk-oriented step splits the work into an ItemReader, an optional ItemProcessor, and an ItemWriter. 
Items are read and processed one at a time and written in chunks, with one transaction per chunk, so a failed job can restart from the last committed chunk. It is suited to processing large volumes of data. A typical use is importing a large CSV file into a database table.

# Q5.

ItemReader: read() returns the next item each time it is called. When there is no more input, it returns null,  tells Spring Batch that the input is exhausted. The current chunk is then written and the step finishes. Because of this, a reader must never return null as a real data item.
ItemProcessor: process() takes one input item and returns one output item, possibly of a different type. If it returns null, the item is filtered out: it is not passed to the writer, and it is counted in the step’s filter count. Returning null is not an error; to signal an error, the processor should throw an exception.
ItemWriter: write() receives a whole Chunk of items instead of a single item. This allows the writer to perform efficient batch operations, such as a single JDBC batch insert, instead of one database round trip per item. It also matches the transaction boundary: all items in a chunk are written in the same transaction, so they are committed or rolled back together.


# Q6.
Filtering means the processor returns null because the item is valid but not needed, 
Skipping means an exception is thrown because the item is bad.

Skip is for permanent errors that would fail again, such as bad data. 
Retry is for temporary errors that may succeed on another try, such as a database deadlock or network timeout.

# Q7.
Job parameters only exist when a job is launched, but singleton beans are created at application startup, before any parameters are available. 
@StepScope delays creating the bean until the step runs, so the expression can be resolved then. It also creates a new reader for each step execution, so each run reads its own file with fresh state.

# Q8.
When a failed job is launched again with the same identifying parameters, Spring reuses the same JobInstance and creates a new JobExecution. 
Completed steps are skipped, and the failed step resumes after the last committed chunk, using the state saved in its ExecutionContext.
the reader must be restartable: it saves its position in the ExecutionContext and reads input in a stable order. The writer must not leave partial results from the failed chunk, for example by writing transactionally or truncating the file on restart.
JobInstanceAlreadyCompleteException is thrown when a job is launched with the same identifying parameters as a JobInstance that has already completed successfully. To run it again, new parameters must be used.

# Q9
A multi-threaded step runs chunks in parallel threads within a single step, and all threads share the same reader, processor and writer. 
A partitioned step splits the data into partitions, and each partition runs as its own step execution with its own reader and writer. 
Partitioning keeps restartability and can scale across machines; a multi-threaded step is simpler but usually not restartable.
In a multi-threaded step, the reader must be thread-safe and should not save state, the processor should be stateless, and the writer must be thread-safe. Item order is not guaranteed.

# Q10.
Duplicate runs: Each instance has its own scheduler, so the job is started once per instance at the same time, and data may be processed several times. 
Fix: use a distributed lock such as ShedLock, or trigger the job from a single external scheduler such as a Kubernetes CronJob.
Non-identifying parameters: Using a timestamp as the job parameter creates a new JobInstance on every launch, so duplicates are not detected and failed runs are never restarted. 
Fix: use a meaningful identifying parameter, such as the run date, with a shared JobRepository, so duplicates are rejected and failed runs can resume.

record Transaction(long id, String accountId, BigDecimal amount, String currency, LocalDateTime timestamp) { }
record SettlementLine(long transactionId, String accountId, BigDecimal amountUsd, LocalDate settleDate) { }
class InvalidTransactionException extends RuntimeException {
    InvalidTransactionException(long id, String reason) {
        super("Transaction " + id + ": " + reason);
    }
}
interface ExchangeRateService {
    boolean supports(String currency);
    BigDecimal toUsd(BigDecimal amount, String currency);
}
class TransactionValidationProcessor implements ItemProcessor<Transaction, SettlementLine> {
    private final ExchangeRateService rates;
    TransactionValidationProcessor(ExchangeRateService rates) {
        this.rates = rates;
    }
    @Override
    public SettlementLine process(Transaction tx) {
        if (tx.amount() == 0) {
            retuurn null;
        }
        if (tx.accountId() == null || tx.accountId().isBlank()) {
            throw new InvalidTransactionException(tx.id(), "missing account id");
        }
        if (!rates.supports(tx.currency())) {
            throw new InvalidTransactionException(tx.id(), "unsupported currency " + tx.currency());
        }
        return new SettlementLine(
                tx.id(),
                tx.accountId(),
                rates.toUsd(tx.amount(), tx.currency()),
                tx.timestamp().toLocalDate());
    }
}
@Configuration
class SettlementStepConfig {
    @Bean
    public Step settlementStep(JobRepository jobRepository,
                               PlatformTransactionManager transactionManager,
                               ItemReader<Transaction> transactionReader,
                               TransactionValidationProcessor processor,
                               ItemWriter<SettlementLine> settlementWriter) {
        return new StepBuilder("settlementStep", jobRepository)
                .<Transaction, SettlementLine>chunk(500, transactionManager)
                .reader(transactionReader)
                .processor(processor)
                .writer(settlementWriter)
                .faultTolerant()
                .skip(InvalidTransactionException.class)
                .skip(FlatFileParseException.class)
                .skipLimit(100)
                .build();
    }
}
