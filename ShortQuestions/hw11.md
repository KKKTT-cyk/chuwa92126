# Spring Batch Homework — Questions 1–10

## Question 1
A simple loop that loads an entire file into memory does not scale: memory use grows with file size and may cause out-of-memory failures. Spring Batch's streaming `ItemReader` reads items incrementally. A manual loop also lacks transaction boundaries, restart checkpoints, and built-in error policies; chunk-oriented processing commits batches, the `JobRepository` stores execution metadata, and fault-tolerant steps support skip/retry. Separating reading, processing, and writing also makes the job easier to test and maintain.

## Question 2
A job defines the batch workflow; a step defines one phase of it. A 'JobInstance' is the logical occurrence identified by a Job and its identifying JobParameters, such as `settlementJob` with `runDate=2026-10-23`. A 'JobExecution' is one attempt to run that instance, so restarting after failure creates a new JobExecution for the same JobInstance. A 'StepExecution' records the outcome, counts, and execution context of one Step attempt within a JobExecution. A different identifying `runDate` creates a different JobInstance.

## Question 3
In chunk-oriented processing, the reader fetches items one at a time, the processor transforms or filters them, and the writer receives a chunk of results. The step commits each chunk in a transaction, typically including state updates for restart. Larger chunks usually reduce transaction and write overhead but require more memory and can cause more work to be repeated after rollback; smaller chunks reduce the rollback/reprocessing window but increase overhead. The exact number of written items can be lower than the number read because of filtering.

## Question 4
A tasklet step runs a unit of work via a `Tasklet`, such as deleting temporary files or invoking a stored procedure. A chunk-oriented step repeatedly reads, processes, and writes items in transactions, such as importing a million CSV transactions into a database. Choose tasklets for bounded procedural operations and chunks for item-oriented datasets.

## Question 5
`ItemReader<T>.read()` returns the next item, or `null` to signal end of input. `ItemProcessor<I,O>.process()` returns a transformed item, or `null` to intentionally filter an item without treating it as an error. `ItemWriter<T>.write(Chunk<? extends T>)` receives a group of items so it can batch database statements or file writes efficiently and participate in the chunk transaction.

## Question 6
Filtering is an intentional business decision: a processor returning `null` for a zero-amount transaction removes it without a skip error. Skipping tolerates an exception for a bad item, such as an invalid account ID, subject to a skip limit. Retrying reattempts a transient failure, such as a temporary database deadlock or network timeout. A permanently malformed CSV row is suited to skip, not repeated retry; a temporary connection failure is suited to retry.

## Question 7
`#{jobParameters['inputFile']}` is resolved from the active job's parameters, not at application startup. `@StepScope` creates a step-scoped proxy and delays instantiation of the reader until the step runs, when those parameters are available. Without step scope, the expression may not resolve correctly and a singleton reader cannot safely receive distinct parameter values for different executions.

## Question 8
Rerunning a failed job with the same identifying parameters restarts the existing JobInstance using a new JobExecution. Completed steps are normally not repeated, and restartable readers use persisted position/state (via `ItemStream` and the execution context) to resume at a checkpoint. Writers must be transactionally consistent or idempotent so retries/restarts do not duplicate effects; external side effects require special care. Starting an already completed JobInstance with the same identifying parameters throws `JobInstanceAlreadyCompleteException` (unless a new instance is created with different identifying parameters).

## Question 9
A multi-threaded step uses multiple threads to process chunks within one step, so items may be processed out of order and components may be shared across threads. The reader, processor, and writer must be thread-safe or properly synchronized/isolated, and the design must tolerate ordering changes. Partitioning splits input into independent partitions, each with its own StepExecution and typically its own step-scoped reader/state; partitions can execute in parallel locally or remotely. Partitioning is often easier for isolating reader state and restart boundaries.

## Question 10
First, if every application instance runs the same `@Scheduled` method, each may launch the job, causing duplicate submissions or competing executions. Use a single scheduler, distributed lock, or centralized orchestrator and enforce job-instance identity through the JobRepository. Second, schedules can overlap if a previous run is still active, causing resource contention or job-execution conflicts. Prevent concurrent launches for the same logical run, check running executions, or use a scheduler/orchestrator with explicit concurrency policies. A shared persistent JobRepository is important for coordination but does not by itself replace distributed scheduling controls.

## Question 11 — Implementation

The Java files under `src/main/java/com/example/settlement/` implement the supplied records, exception, exchange-rate interface, processor, and step configuration. The processor filters zero amounts, throws `InvalidTransactionException` for blank account IDs or unsupported currencies, and creates a USD `SettlementLine` with the timestamp's date. The step uses a chunk size of 500, skips `InvalidTransactionException` and `FlatFileParseException`, and fails after more than 100 skips. It assumes a configured `ItemReader<Transaction>`, `ItemWriter<SettlementLine>`, `ExchangeRateService`, `JobRepository`, and `PlatformTransactionManager` are provided by the application.

The code targets Spring Batch 5+ / Spring Boot 3+ and Java 17+. A skip limit of 100 permits 100 skips; the 101st fails the step.
