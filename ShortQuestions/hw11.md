## Conceptual Questions

**1. Explain what a cross-cutting concern is, and use the OrderService example from class to explain "tangling" and "scattering".**

A cross-cutting concern is shared logic, such as logging, metrics, or security, that is needed in many places but is not the main business task. In the class example, OrderService.placeOrder mixes createAndSave(request) with logging, timing, and checkPermission("ORDER_CREATE"). This is tangling because several concerns are mixed into one method. Scattering happens when cancelOrder and many other methods repeat the same logging and timing code. Aspects move this shared logic into one place so the service can focus on creating and saving orders.

**2. Define aspect, join point, pointcut, advice, target and proxy, and state what a join point always is in Spring AOP.**

An aspect is a module that groups a cross-cutting concern's pointcuts and advice. A join point is a point in program execution where advice can apply; in Spring AOP, it is always a method execution. A pointcut selects the method executions, and advice defines what code runs and when. The target is the original object, such as OrderService. The proxy is the wrapper Spring creates and injects to apply advice before delegating to that target.

**3. Compare the five advice types (@Before, @AfterReturning, @AfterThrowing, @After, @Around): when each one runs, and which of them can change the return value or prevent the target method from running.**

@Before runs before the method and can stop it only by throwing an exception. @AfterReturning runs after a normal return and can inspect the result but cannot replace it. @AfterThrowing runs when the method throws a matching exception, which normally continues to propagate. @After runs after success or failure, like finally. These after advice types cannot prevent the method from running because it has already run. @Around wraps the whole call and controls proceed(), so it can skip the target method or replace its return value. The other advice types cannot supply a replacement return value, although @AfterReturning can modify a mutable returned object.

**4. Describe three mistakes that are easy to make inside an @Around advice and the effect of each one.**

Forgetting to call pjp.proceed() means the target method never runs. Calling it but returning null instead of its result makes the caller receive null and causes AopInvocationException for a primitive return type. Catching Throwable without rethrowing it hides the failure. If this happens inside the transaction advice, the transaction may commit because its interceptor never sees the exception, unless the transaction is already marked rollback-only.

**5. Explain what each pointcut expression matches: execution(\* com.example.orders.service.\*.\*(..)), execution(\* com.example.orders..\*.\*(..)), execution(\* \*(Long, ..)) and @annotation(com.example.orders.aop.LogExecutionTime).**

execution(\* com.example.orders.service.\*.\*(..)) matches methods directly in the service package, with any return type, method name, and parameters, but excludes subpackages. execution(\* com.example.orders..\*.\*(..)) includes methods in orders and all its subpackages. execution(\* \*(Long, ..)) matches methods whose first declared parameter is Long, followed by zero or more parameters of any type. @annotation(com.example.orders.aop.LogExecutionTime) matches methods annotated with @LogExecutionTime. All of these still depend on Spring's proxy interception rules.

**6. Explain how Spring AOP applies advice through proxies, at which step of the bean lifecycle the proxy is created, and how you can check that an injected bean is a proxy.**

Spring injects a proxy that intercepts calls, runs matching advice, and delegates to the target method when the advice proceeds. It can use a JDK interface proxy or a CGLIB subclass proxy. Normally, the proxy is created in BeanPostProcessor.postProcessAfterInitialization(), after dependency injection and initialization callbacks; the lesson identifies this as step 6 of the bean lifecycle. Printing orderService.getClass().getName() can reveal a generated name such as OrderService$$SpringCGLIB$$0. AopUtils.isAopProxy(orderService) can also check it directly.

**7. Explain why calling a method annotated with @LogExecutionTime or @Transactional from another method of the same class skips the advice, and describe two ways to fix it.**

In the class example, placeOrders calls placeOrder on the same OrderService object, so the call uses this and bypasses the proxy. As a result, the inner method's @LogExecutionTime or @Transactional advice does not run, although any existing outer transaction still applies. One fix is to move placeOrder into OrderPlacementService and call its injected proxy from BulkOrderService. Another is to enable @EnableAspectJAutoProxy(exposeProxy = true) and call through AopContext.currentProxy() while inside a proxied invocation. The separate-bean approach is cleaner because business code does not depend on Spring AOP APIs.

**8. State the default rollback rules of @Transactional, and describe three situations in which a @Transactional method does not roll back even though something went wrong.**

By default, @Transactional rolls back for RuntimeException and Error, but not checked exceptions. A checked exception such as IOException can therefore allow a commit unless rollbackFor = Exception.class or another matching rule is configured. A caught and swallowed exception can also allow a commit because the proxy sees a normal return, as in the tutorial's failed credit after a successful debit. This assumes the transaction has not already been marked rollback-only. Finally, self-invocation bypasses the transactional advice, so no new transaction is started by that annotation; without an outer transaction, earlier writes may already be committed.

**9. SecurityAspect has @Order(1) and TimingAspect has @Order(2), and both use @Around on the same method. Describe the order in which their code runs. Then compare Spring AOP with AspectJ in terms of weaving and the join points each one supports.**

A lower @Order value means higher precedence, so SecurityAspect is the outer aspect. If both aspects proceed and the method succeeds, the order is Security before, Timing before, target method, Timing after, and Security after. If Security rejects the call before proceeding, Timing and the target do not run. Code after proceed() requires a finally block if it must also run when an exception occurs.

Spring AOP applies advice at runtime through proxies and supports only method execution join points on Spring beans. AspectJ modifies bytecode at compile time, after compilation, or at load time. It supports method calls and executions, constructors, field reads and writes, and static initialization. It can also advise self-invocation and objects outside Spring. Using @Aspect annotations with Spring AOP does not itself enable AspectJ weaving.
