### Question 1.

A cross-cutting concern is functionality required by multiple parts of an application that is not part of their core business logic, such as logging, security, transactions, or metrics.

Tangling occurs when business logic and cross-cutting concerns are mixed in the same method, as the logging, permission, exception reporting and metrics in the original `OrderService.placeOrder()` example.

Scattering occurs when the same logging or metrics code is duplicated across many service methods, as the same logging, permission, exception reporting and metrics logic in `OrderService.placeOrder()`, `OrderService.cancelOrder()` and all methods involved with order in the `OrderService` example.

Spring AOP solves these problems by extracting shared functionality into reusable aspects, keeping business logic clean and centralized.

### Question 2.

- Aspect: A module containing cross-cutting logic, typically an `@Aspect` class.
- Join point: A point where advice can be applied; always a method execution in Spring AOP.
- Pointcut: An expression selecting which method executions to advise.
- Advice: The logic executed before, after, or around selected methods.
- Target: The original object whose methods are advised.
- Proxy: A Spring-created wrapper that intercepts method calls and executes advice.

In short, the pointcut determines where, the advice determines what and when, and the aspect packages them together.

### Question 3.

Spring AOP provides five advice types. `@Before` runs before the target method, `@AfterReturning` runs after successful completion, `@AfterThrowing` runs when the method throws exceptions, and `@After` runs on either normal or exceptional completion.

`@Around` wraps the entire invocation and is the most flexible. It can modify arguments and return values, retry the operation, or skip the target method by not calling `proceed()`.

Only `@Around` can directly replace the method's return value. `@Before` can prevent execution by throwing an exception.

### Question 4.

Three common mistakes in `@Around` advice are:

1. Not returning `proceed()` result: The caller receives an incorrect result, often `null`, and primitive returns may cause an exception.
2. Catching and swallowing exceptions: Failures become hidden and transaction rollback may be prevented.
3. Forgetting `procees()`: The target method never executes.

Normally, an around advice should return `pjp.proceed()` and propagate exceptions unless it intentionally wants to change the method's behavior.

### Question 5.

- `execution(* com.example.orders.service..(..))`: matches all methods in calsses directly inside `com.example.orders.service`, excluding subpackages.

- `execution(* com.example.orders...(..))`: matches methods throughout `com.example.orders` and all its subpackages.

- `execution(* *(Long, ..))`: matches methods with any return type and name whose first parameter is `Long`, followed by zero or more additional parameters.

- `@annotation(com.example.orders.aop.LogExecutionTime)`: matches methods annotated with `@LogExecutionTime`.

### Question 6.

Spring AOP is proxy-based. During bean initialization, Spring uses a `BeanPostProcessor`, typically during `postProcessAfterInitialization()`, to wrap eligible beans with AOP proxies.

When another bean calls an advised method through the proxy, Spring executes the matching advice before or after delegating to the target method.

Spring supports JDK dynamic proxies for interface-based proxying and CGLIB proxies for class-based proxying. Spring Boot uses CGLIB by default.

We can identify a proxy using `bean.getClass().getName()` or `AopUtils.isAopProxy(bean)`.

### Question 7.

Spring AOP uses proxies to intercept method calls. When a method calls another method within the same class, the call uses `this`, which refers to the target object and bypasses the proxy.

As a result, advice such as `@LogExecutionTIme` or `@Transactional` does not execute on that inner call.

Two solutions are to move the annotated method into another Spring bean and call it through dependency injection, which is recommended, or explicitly invoke the current proxy using `AopContext.currentProxy()` with `exposeProxy = true`.

### Question 8.

By default, Spring `@Transactional` rolls back on unchecked exceptions, including `RuntimeException` and `Error`, but commits on checked exceptions unless configured otherwise.

Three common situations where the intended rollback does not happen are:

1. A checked exception is thrown without configuring `rollbackFor`.
2. An exception is caught and swallowed, so the transaction interceptor may see a successful return.
3. A transactional method is called from another method in the same class, bypassing the Spring AOP proxy.

We can address these by configuring `rollbackFor`, propagating exceptions, and ensuring transactional methods are called through Spring-managed proxies.

### Question 9.

With `SecurityAspect` annotated `@Order(1)` and `TimingAspect` annotated `@Order(2)`, the security aspect has higher precedence and wraps the timing aspect. The execution order is: Security Before -> Timing Before -> Target Method -> Timing After -> Security After.

Spring AOP uses runtime proxies and only supports method execution join points on Spring-managed beans. AspectJ uses compile-time, post-compile, or load-time bytecode weaving and supports additional join points, including method calls, constructors, field access, and self-invocation.
