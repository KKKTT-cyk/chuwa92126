# Homework 11 - Spring Batch

These answers use Spring Batch 5.x, matching the APIs in the assignment.

## 1. Why Is a Simple Whole-File Loop Not Enough?

- Loading a large file can exhaust memory. A streaming ItemReader and chunk processing keep only a limited amount of data in memory.
- Saving one item per transaction is slow, while one huge transaction holds resources for too long. Chunk transactions and batched writes balance speed and transaction size.
- A crash can force the loop to start over. JobRepository metadata and saved ExecutionContext checkpoints support restarting from committed progress.
- One bad row can stop everything, and temporary failures may be recoverable. Configured skip and retry policies handle these cases.
- A plain loop has little execution tracking. JobExecution and StepExecution record status, counts, and failures for monitoring.

A custom loop could implement these features, but Spring Batch provides the infrastructure.

## 2. Job, Step, JobInstance, JobExecution, and StepExecution

For a daily settlement job with an identifying runDate parameter:

| Term | Meaning and example |
| --- | --- |
| Job | The whole workflow definition, such as dailySettlementJob. |
| Step | One stage in that workflow, such as importing and validating transactions. |
| JobInstance | A logical run identified by the job name and identifying parameters. runDate=2026-10-26 identifies that day's instance. |
| JobExecution | One attempt to execute an instance. A failed attempt and its restart have different executions but the same instance. |
| StepExecution | One attempt to execute a step within a JobExecution, with its own status and read/write/skip counts. |

Changing the identifying runDate to 2026-10-27 creates another JobInstance. Changing only a non-identifying parameter does not.

## 3. How Does Chunk-Oriented Processing Work?

The reader reads items one at a time until the chunk size or end of input is reached. The processor transforms or filters each item. The writer receives the remaining output items as a chunk. In a normal single-threaded chunk step, a transaction surrounds the chunk's read/process/write work and commits after a successful write, with restart state saved at the commit boundary.

For chunk size 500, 1,200 valid items normally produce writes of 500, 500, and 200 items. Filtered items can make the output chunk smaller than the input chunk.

Larger chunks reduce commit overhead and can improve throughput, but use more memory, hold transactions longer, and repeat more uncommitted work after failure. Smaller chunks commit more often and reduce rollback work, but add overhead. Previously committed chunks normally remain committed when a later chunk fails.

## 4. Tasklet Step vs. Chunk-Oriented Step

A tasklet performs an operation through execute(), returning FINISHED when done or CONTINUABLE when more work remains. Each invocation is normally transactional. It suits tasks such as deleting a temporary file or running a stored procedure.

A chunk-oriented step uses a reader, optional processor, and writer to process many records in batches. It suits importing a large CSV into a database. Chunk processing is implemented using tasklet infrastructure, but supplies the item-processing loop and commit handling for us.

## 5. Reader, Processor, and Writer Contracts

- **ItemReader:** read() returns the next item. Returning null means the input is finished, not that a bad row should be ignored.
- **ItemProcessor:** process(item) transforms an input item into an output item. Returning null filters out that item, so it is not passed to the writer. Processing then continues with other items.
- **ItemWriter:** write(Chunk<? extends T>) receives a group of output items. This enables efficient batched I/O and a shared chunk transaction instead of a commit for every item. Throwing an exception reports a write failure; the writer should not silently ignore failed writes.

## 6. Filtering, Skipping, and Retrying

**Filtering** is an intentional business decision. The processor returns null without an error, such as dropping a zero-amount transaction. It increases the filter count, not the skip count.

**Skipping** discards an item after a configured skippable exception, such as a malformed CSV row or an invalid account id. It counts toward the skip limit, which is shared across read, process, and write skips.

**Retrying** attempts an operation again because the failure may be temporary, such as a database deadlock during a write. Retrying an invalid account id usually cannot fix it. Retries must be bounded; after exhaustion, the item may be skipped if the configured policies allow it, otherwise the step fails.

## 7. Why Use @StepScope for a Parameter-Based Reader?

The value in #{jobParameters['inputFile']} belongs to a particular job execution and is unavailable when a normal singleton reader is created during application startup. @StepScope delays creating the reader until the step runs, when the parameters are available. It also gives each StepExecution its own reader instance and state.

The step-scoped proxy can be injected earlier, but its actual reader is created in the active step scope. For a stream reader, expose its ItemStream methods through a suitable bean return type, such as FlatFileItemReader<Transaction>. A suitable execution scope is needed for late binding; @StepScope is the usual choice for this reader.

## 8. Restarting a Failed Job

For a restartable job, launching the same job name with the same identifying parameters after failure creates a new JobExecution for the existing JobInstance. Completed steps are normally not repeated; the failed step restarts from its saved committed state. Uncommitted work may run again. Adding a new identifying timestamp creates a new instance instead of restarting the failed one.

A stateful reader must save and restore its position, usually through ItemStream and ExecutionContext. Its input must remain stable and be read in a consistent order. A stateful writer must also restore its state where needed. Writes should participate in the chunk transaction or safely tolerate repeated work through idempotency, such as unique transaction ids. Restart metadata alone cannot prevent duplicate external side effects.

JobInstanceAlreadyCompleteException is thrown when the same job instance has already completed successfully and is launched again. Use different identifying parameters only when a genuinely new logical run is intended.

## 9. Multi-Threaded Step vs. Partitioning

In Spring Batch 5, a multi-threaded chunk step uses a TaskExecutor to process chunks concurrently within one StepExecution. Item processing and completion order are not guaranteed. Shared readers, processors, writers, and their dependencies must be thread-safe or correctly synchronized; processors should preferably be stateless. @StepScope alone does not make a component thread-safe.

Partitioning divides input into separate ranges or files. Each partition has its own worker StepExecution and ExecutionContext, and can use its own step-scoped components. Workers can run locally or remotely. Partitions should not unintentionally overlap, and shared resources must still be safe for concurrent access.

Many readers and writers keep mutable state, so adding threads blindly is unsafe. Synchronizing a reader can protect read access, but restart checkpoint behavior still needs checking. Database connections and other resource pools also need enough capacity.

## 10. Pitfalls of @Scheduled with Several Application Instances

1. **Duplicate or overlapping launches:** Every application instance runs its own scheduler, and a later trigger can arrive while earlier work is still running. Use a distributed lock, leader election, or a clustered/external scheduler. Also use a shared persistent JobRepository and stable identifying parameters, such as the business runDate, so instances coordinate the same logical run. Different job instances can still overlap, so choose the lock scope appropriately.
2. **Incorrect parameter identity:** Reusing the same parameters after successful completion causes JobInstanceAlreadyCompleteException. Adding a fresh identifying timestamp on every trigger avoids that exception but creates new instances and can reprocess the same data instead of restarting a failure. Use business-based identifiers: the same runDate for a failed day's restart and a new date for the next day's run. Handle already-running/completed outcomes instead of blindly relaunching.

## 11. Transaction Validation and Settlement Step

The Java implementation is in org.tiff.homework11.question11.

- Zero amounts are filtered first, using BigDecimal.compareTo so 0 and 0.00 are both treated as zero.
- A null or blank account id, or an unsupported currency, throws InvalidTransactionException.
- Valid amounts are converted through ExchangeRateService.toUsd(); timestamp.toLocalDate() supplies the settlement date.
- The step uses chunks of 500, skips InvalidTransactionException and FlatFileParseException, and sets skipLimit(100). The 101st skippable error fails the step; filters do not use this limit.

The configuration also registers the processor bean. As in the assignment, the reader, writer, exchange-rate implementation, JobRepository, and transaction manager are supplied by the application. No actual exchange rates or input format are invented here. Amount and timestamp are assumed non-null because the assignment supplies no rule for missing values.
