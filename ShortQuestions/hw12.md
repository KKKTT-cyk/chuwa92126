## Question1:Explain what a cross-cutting concern is, and use the OrderService example from class to explain “tangling” and “scattering.”
A cross-cutting concern is functionality that affects multiple parts of an application but is not directly related to its core business logic. Common examples include logging, security, performance monitoring, transaction management, and exception handling.

Tangling occurs when business logic and multiple cross-cutting concerns are mixed within the same method. In this example, placeOrder() combines order creation with logging, security, and performance monitoring. This makes the method harder to read, maintain, and test.

Scattering occurs when the same cross-cutting concern is repeated throughout different classes or methods. For example, if PaymentService, UserService, and InventoryService all contain similar logging and execution-time measurement code, that functionality is scattered across the application.

## Question2: Define aspect, join point, pointcut, advice, target, and proxy, and state what a join point always is in Spring AOP.
1. Aspect
An aspect is a class that encapsulates a cross-cutting concern, such as logging, security, or performance monitoring. In Spring AOP, aspects are commonly defined using the @Aspect annotation.
2. Join Point
A join point is a specific point during program execution where additional behavior can be applied.
In Spring AOP, a join point is always a method execution. Spring AOP does not directly support constructor execution or field access as join points.
3. Pointcut
A pointcut is an expression that determines which method executions should be intercepted by an aspect.
4. Advice
Advice is the action executed by an aspect at a matching join point.
5. Target
The target is the actual object whose method execution is being advised.
6. Proxy
A proxy is an object created by Spring that intercepts method calls and applies the configured advice before delegating to the target object.

## Question3: Compare the five advice types: when each one runs, and which of them can change the return value or prevent the target method from running.
| Advice type | When it runs | Can change the return value? | Can skip normal method execution?  |
|:-----|:---:|-------:|---|
| @Before | Before the target method | No |  Only by throwing an exception |
| @AfterReturning | After successful completion | No |  No |
| @AfterThrowing | When the method exits by throwing an exception | No |  No |
| @After  |  After completion, whether successful or exceptional  | No  | No  |
|  @Around  | Before and after execution, with control over invocation   | Yes  | Yes  |

@Before: Executes before the target method. It is commonly used for logging and security checks. It cannot replace the method's return value, but throwing an exception can prevent execution.

@AfterReturning: Executes only when the advised method returns normally. It can inspect the returned value, but it cannot replace the returned reference. It may still mutate a mutable returned object.

@AfterThrowing: Executes when an exception escapes the advised method. It is commonly used for error logging and cannot normally suppress the exception simply by returning.

@After: Works similarly to a finally block. It executes after method completion regardless of whether the execution succeeds or throws an exception.

@Around: Is the most powerful advice type. It can execute code before and after the target method, modify arguments, inspect or replace the return value, handle exceptions, or skip the target method entirely.

## Question5: Explain what each pointcut expression matches.
Expression 1: execution(* com.example.orders.service.*.*(..))
This expression matches any method declared in any class directly inside the com.example.orders.service package.
- First *: Any return type.
- com.example.orders.service: Exact package.
- Second *: Any class name directly in that package.
- Third *: Any method name.
- (..): Any number and types of arguments.

Expression 2: execution(* com.example.orders..*.*(..))
This expression matches any method in classes within the com.example.orders package and all its subpackages.
The .. allows zero or more package levels.

Expression 3: execution(* *(Long, ..))
This expression matches methods whose first parameter is a Long object, followed by zero or more additional parameters.

Expression 4: @annotation(com.example.orders.aop.LogExecutionTime)
This expression matches method executions whose methods have the @LogExecutionTime annotation.

## Question6: Explain how Spring AOP applies advice through proxies, at which step of the bean lifecycle the proxy is created, and how you can check that an injected bean is a proxy.
6.1: Spring AOP applies advice using proxy objects. When Spring creates a bean that matches an aspect's pointcut, it can expose a proxy instead of the original target object to other beans.
When a client invokes a method through the proxy, the proxy executes applicable advice and delegates the call to the target method.
6.2: In the typical bean lifecycle, an AOP proxy is created by a BeanPostProcessor, commonly an auto-proxy creator such as AnnotationAwareAspectJAutoProxyCreator.

The process generally follows these steps:
1. Spring instantiates the bean.
2. Spring injects dependencies.
3. Spring runs initialization callbacks, such as @PostConstruct.
4. An auto-proxy creator evaluates whether the bean requires advice, usually during postProcessAfterInitialization().
5. If advice applies, Spring creates or exposes a proxy.
6. Other beans typically receive the proxy through dependency injection.

6.3: To check whether an injected bean is a proxy, Spring provides utility methods in the AopUtils class:
import org.springframework.aop.support.AopUtils;

@Autowired
private OrderService orderService;

@PostConstruct
public void checkProxy() {

    System.out.println(
        AopUtils.isAopProxy(orderService)
    );

    System.out.println(
        AopUtils.isJdkDynamicProxy(orderService)
    );

    System.out.println(
        AopUtils.isCglibProxy(orderService)
    );
}

AopUtils.isAopProxy() returns true if the object is a recognized Spring AOP proxy. The other two methods identify the proxy mechanism.

## Question7:Explain why calling a method annotated with @LogExecutionTime or @Transactional from another method of the same class skips the advice, and describe two ways to fix it.
Spring AOP is proxy-based, meaning advice normally runs when a method is called through a Spring-managed proxy.
When one method calls another method within the same class using this, the call directly accesses the target object and bypasses the proxy. This behavior is known as self-invocation.

Because the call does not go through the Spring proxy, the @LogExecutionTime advice and the transaction advice associated with @Transactional are skipped for that invocation.

Solution 1: Move the method into another Spring-managed bean
Solution 2: Invoke the method through the Spring proxy.
Another approach is to obtain a proxy reference to the same bean instead of using this.
For example, Spring's ObjectProvider can lazily obtain the Spring-managed instance:
@Service
public class OrderService {

    private final ObjectProvider<OrderService> selfProvider;

    public OrderService(
            ObjectProvider<OrderService> selfProvider) {
        this.selfProvider = selfProvider;
    }

    public Order submitOrder(CreateOrderRequest request) {
        return selfProvider.getObject().placeOrder(request);
    }

    @LogExecutionTime
    @Transactional
    public Order placeOrder(CreateOrderRequest request) {
        return createAndSave(request);
    }
}
Here, selfProvider.getObject() retrieves the Spring-managed OrderService, which is the proxy when Spring has proxied that bean.

## Question8:State the default rollback rules of @Transactional, and describe three situations in which a @Transactional method does not roll back even though something went wrong.
By default, Spring's @Transactional rolls back the transaction when an unhandled RuntimeException or Error escapes the transactional method.
However, checked exceptions, such as IOException and SQLException, do not trigger rollback by default unless rollback rules are explicitly configured.

Situation 1: A checked exception is thrown
@Transactional
public void placeOrder() throws IOException {

    orderRepository.save(order);

    throw new IOException("File processing failed");
}
Because IOException is a checked exception, Spring does not automatically roll back the transaction under the default rules.

Situation 2: An exception is caught and swallowed
@Transactional
public void placeOrder() {

    try {
        orderRepository.save(order);
        paymentClient.charge(order.getTotal());
    } catch (RuntimeException ex) {
        log.error("Order processing failed", ex);
    }
}
In this example, the exception is caught and not rethrown.
As a result, the transactional method returns normally, and Spring may commit the transaction instead of rolling it back.

Situation 3: The transactional method is called without passing through the proxy
@Service
public class OrderService {

    public void process() {
        this.saveOrder();
    }

    @Transactional
    public void saveOrder() {
        orderRepository.save(order);
    }
}
When process() calls saveOrder() using this, the Spring proxy is bypassed.
Therefore, the @Transactional advice on saveOrder() is not applied to that call. If no other transaction exists, the method executes without the transaction it was intended to start.

## Question9:SecurityAspect has @Order(1) and TimingAspect has @Order(2), and both use @Around on the same method. Describe the order in which their code runs. Then compare Spring AOP with AspectJ in terms of weaving and the join points each one supports.
Part 1: Advice execution order
In Spring AOP, the @Order annotation determines the priority of aspects.
A smaller order value indicates higher precedence.
Assuming the method completes successfully, the execution sequence is:
Security Before
Timing Before
Target method executes
Timing After
Security After

SecurityAspect acts as the outer interceptor, while TimingAspect acts as the inner interceptor.

Part 2: Spring AOP vs. AspectJ
Spring AOP uses runtime proxies to intercept method executions. Its main advantage is its straightforward integration with Spring-managed beans. It is well suited for common enterprise application concerns such as logging, transaction management, security checks, and performance monitoring.
AspectJ uses bytecode weaving to integrate aspects directly into application code. Weaving can occur during compilation, after compilation, or when classes are loaded. Because it modifies the effective bytecode rather than relying on external proxy calls, AspectJ can intercept a wider range of join points, including constructors, field access, and internal method calls.
