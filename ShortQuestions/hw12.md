# Java Spring AOP Homework

## 1. Cross-Cutting Concerns, Tangling, and Scattering

A cross-cutting concern is functionality that affects multiple parts of an application but is not part of the core business logic. Examples include logging, security, transaction management, and performance monitoring.

In an `OrderService`, the main business logic is processing orders. However, the service may also need to perform logging, security checks, and transaction management.

**Tangling** occurs when cross-cutting concerns are mixed with business logic in the same method. For example, an `OrderService.placeOrder()` method may contain logging statements, security checks, and order-processing code.

**Scattering** occurs when the same cross-cutting concern is repeated across multiple classes. For example, logging code may appear in `OrderService`, `PaymentService`, and `InventoryService`.

Spring AOP solves these problems by separating cross-cutting concerns into reusable aspects, keeping business logic cleaner and easier to maintain.

## 2. Core Spring AOP Concepts

- **Aspect:** A module that encapsulates cross-cutting functionality, such as logging or security.
- **Join Point:** A point during program execution where advice can be applied.
- **Pointcut:** An expression that selects which join points should be advised.
- **Advice:** The action performed at a selected join point.
- **Target:** The original object whose methods are being advised.
- **Proxy:** An object created by Spring that intercepts method calls and applies advice before delegating to the target.

In Spring AOP, a join point is always a **method execution**.

Unlike AspectJ, Spring AOP does not support constructor execution or field access as join points.

Example:

```java
@Aspect
@Component
public class LoggingAspect {

    @Before("execution(* com.example.service.*.*(..))")
    public void logBefore() {
        System.out.println("Method is about to run");
    }
}
```

Here, `LoggingAspect` is the aspect, `@Before` defines the advice, and `execution(...)` defines the pointcut.

## 3. Five Types of Advice

| Advice Type | When It Runs | Change Return Value? | Prevent Target Execution? |
|---|---|---|---|
| `@Before` | Before the target method executes | No | Yes, by throwing an exception |
| `@AfterReturning` | After the method returns successfully | No | No |
| `@AfterThrowing` | After the method throws an exception | No | No |
| `@After` | After the method completes, regardless of outcome | No | No |
| `@Around` | Before and after the method, controlling execution | Yes | Yes |

`@AfterReturning` cannot replace the return value directly, although it can modify a returned mutable object.

`@Around` is the most powerful advice type because it controls whether and when the target method executes using `proceed()`.

Example:

```java
@Around("execution(* com.example.service.*.*(..))")
public Object measureTime(ProceedingJoinPoint pjp)
        throws Throwable {

    long start = System.currentTimeMillis();

    Object result = pjp.proceed();

    long duration = System.currentTimeMillis() - start;

    System.out.println("Execution time: " + duration);

    return result;
}
```

An `@Around` advice can modify arguments, replace return values, handle exceptions, or skip target execution entirely.

## 4. Three Common Mistakes in @Around Advice

### Mistake 1: Forgetting to Call proceed()

```java
@Around("execution(* com.example.service.*.*(..))")
public Object wrong(ProceedingJoinPoint pjp) {
    return null;
}
```

**Effect:** The target method never executes because `proceed()` is not called. This causes the business logic to be skipped.

### Mistake 2: Forgetting to Return the Original Result

```java
@Around("execution(* com.example.service.*.*(..))")
public Object wrong(ProceedingJoinPoint pjp)
        throws Throwable {

    pjp.proceed();
    return null;
}
```

**Effect:** The target method executes, but its actual return value is discarded. The caller receives `null` instead, which may cause incorrect behavior or errors.

### Mistake 3: Swallowing Exceptions

```java
@Around("execution(* com.example.service.*.*(..))")
public Object wrong(ProceedingJoinPoint pjp)
        throws Throwable {

    try {
        return pjp.proceed();
    } catch (Exception e) {
        return null;
    }
}
```

**Effect:** Exceptions are hidden from the caller. This makes debugging difficult and may interfere with expected transaction rollback behavior.

A better approach is to log exceptions and rethrow them when appropriate.

## 5. Pointcut Expressions

### Expression 1

```java
execution(* com.example.orders.service.*.*(..))
```

This expression matches method executions in classes directly inside the `com.example.orders.service` package.

- First `*`: Any return type.
- `service.*`: Any class directly in the service package.
- Second `*`: Any method name.
- `(..)`: Any number and type of arguments.

It does not automatically match methods in subpackages.

### Expression 2

```java
execution(* com.example.orders..*.*(..))
```

This expression matches method executions in classes in the `com.example.orders` package and all its subpackages.

The `..` allows zero or more package levels.

For example, it can match:

```text
com.example.orders.OrderManager
com.example.orders.service.OrderService
com.example.orders.repository.OrderRepository
```

### Expression 3

```java
execution(* *(Long, ..))
```

This expression matches methods with any return type and any method name, where the first parameter is `Long` and any number of additional parameters may follow.

Examples:

```java
void findOrder(Long id);

String updateOrder(Long id, String status);
```

It does not match methods whose first parameter is primitive `long` instead of `Long`.

### Expression 4

```java
@annotation(com.example.orders.aop.LogExecutionTime)
```

This expression matches method executions where the method is annotated with `@LogExecutionTime`.

Example:

```java
@LogExecutionTime
public void placeOrder() {
    // Business logic
}
```

This is useful for selectively applying timing advice to annotated methods.

## 6. Spring AOP Proxies and Bean Lifecycle

Spring AOP applies advice through proxy objects.

When a client calls a method through a Spring-managed proxy, the proxy intercepts the call, executes applicable advice, and delegates to the target method.

The execution flow is:

```text
Client / Controller
        |
        v
Spring AOP Proxy
        |
        v
Advice Chain
        |
        v
Target Method
```

### When Is the Proxy Created?

The proxy is typically created during Spring bean initialization by an auto-proxy creator, which is a type of `BeanPostProcessor`.

Proxy wrapping commonly occurs during the `postProcessAfterInitialization()` phase, after the bean has been initialized and before it is made available for normal use.

Some beans may be proxied earlier in special situations, such as circular-reference handling.

Spring commonly uses two proxy mechanisms:

1. **JDK Dynamic Proxy:** Creates an interface-based proxy.
2. **CGLIB Proxy:** Creates a class-based proxy.

### How to Check Whether a Bean Is a Proxy

Spring provides the `AopUtils` class:

```java
import org.springframework.aop.support.AopUtils;

System.out.println(AopUtils.isAopProxy(orderService));
```

If the result is `true`, the bean is an AOP proxy.

Additional checks:

```java
AopUtils.isJdkDynamicProxy(orderService);

AopUtils.isCglibProxy(orderService);
```

## 7. Self-Invocation Problem

Self-invocation occurs when one method calls another method within the same class.

Example:

```java
@Service
public class OrderService {

    public void createOrder() {
        saveOrder();
    }

    @Transactional
    public void saveOrder() {
        // Save to database
    }
}
```

When `createOrder()` calls `saveOrder()`, the call happens internally through `this` rather than passing through the Spring proxy.

As a result, the `@Transactional` advice on `saveOrder()` is skipped for that call.

The same problem occurs with proxy-based advice such as `@LogExecutionTime`.

### Solution 1: Move the Method to Another Spring Bean

```java
@Service
public class OrderService {

    private final PaymentService paymentService;

    public OrderService(PaymentService paymentService) {
        this.paymentService = paymentService;
    }

    public void createOrder() {
        paymentService.saveOrder();
    }
}

@Service
public class PaymentService {

    @Transactional
    public void saveOrder() {
        // Database operation
    }
}
```

Because the method is called through another Spring-managed bean's proxy, the transaction advice can execute.

### Solution 2: Call Through the Current Proxy

Spring provides `AopContext.currentProxy()` to access the current proxy when proxy exposure is enabled.

```java
((OrderService) AopContext.currentProxy()).saveOrder();
```

This requires `exposeProxy = true`, an existing invocation through the proxy, and a proxy compatible with the cast.

Moving the advised method to another Spring-managed service is generally preferred because it avoids coupling business logic to Spring AOP internals.

## 8. @Transactional Rollback Rules

By default, Spring transactions roll back when an unhandled exception is:

- `RuntimeException` (unchecked exception).
- `Error`.

By default, Spring does not roll back for checked exceptions, such as `IOException` or `SQLException`, unless rollback behavior is explicitly configured.

### Situation 1: A Checked Exception Is Thrown

```java
@Transactional
public void processOrder() throws IOException {
    saveOrder();
    throw new IOException("File error");
}
```

By default, Spring does not roll back the transaction for this checked exception.

**Solution:**

```java
@Transactional(rollbackFor = Exception.class)
```

This configures the transaction to roll back for checked exceptions as well.

### Situation 2: An Exception Is Caught and Swallowed

```java
@Transactional
public void processOrder() {
    try {
        saveOrder();
        throw new RuntimeException("Failed");
    } catch (RuntimeException e) {
        System.out.println("Error handled");
    }
}
```

Because the exception is caught and the method returns normally, Spring may commit the transaction instead of rolling it back.

**Solution:** Rethrow the exception or explicitly mark the transaction as rollback-only.

### Situation 3: Self-Invocation Bypasses the Proxy

```java
public void createOrder() {
    processOrder();
}

@Transactional
public void processOrder() {
    saveOrder();
    throw new RuntimeException("Failed");
}
```

When `createOrder()` directly calls `processOrder()` within the same class, the call bypasses the Spring proxy.

Therefore, the `@Transactional` interceptor is skipped, and the annotation does not start a transaction for that invocation.

An existing outer transaction may still roll back, but the inner method's transaction annotation is not applied.

**Solution:** Move the transactional method into another Spring-managed service or invoke it through the proxy.

## 9. Advice Ordering and Spring AOP vs. AspectJ

Suppose two aspects apply to the same target method:

```java
@Aspect
@Component
@Order(1)
public class SecurityAspect {
    // @Around advice
}
```

```java
@Aspect
@Component
@Order(2)
public class TimingAspect {
    // @Around advice
}
```

Spring gives higher precedence to aspects with smaller `@Order` values.

Therefore, `SecurityAspect` has higher precedence than `TimingAspect`.

Assuming both `@Around` advices call `proceed()` and the target method returns normally, the execution order is:

```text
1. SecurityAspect - Before
2. TimingAspect   - Before
3. Target Method Executes
4. TimingAspect   - After
5. SecurityAspect - After
```

The advice execution behaves like nested function calls.

`SecurityAspect` executes first before the target and last after the target because it is the outermost advice.

If an outer advice does not call `proceed()`, the inner advice and target method will not execute.

### Spring AOP vs. AspectJ

| Feature | Spring AOP | AspectJ |
|---|---|---|
| Mechanism | Runtime proxies | Bytecode weaving |
| Weaving | Proxy creation at runtime | Compile-time, post-compile, or load-time weaving |
| Join Points | Method execution only | Method execution, constructor execution, field access, and more |
| Target Objects | Primarily Spring-managed beans | Can advise objects outside Spring |
| Self-Invocation | Bypasses proxy advice | Can be advised through weaving |
| Complexity | Simpler | More powerful but more complex |

**Spring AOP** uses proxy-based interception and is suitable for common enterprise concerns such as logging, security, and transaction management.

**AspectJ** modifies bytecode through weaving and supports a wider range of join points, including constructor execution and field access.

AspectJ can also advise internal method calls that Spring proxy-based AOP cannot intercept.

Spring AOP is generally easier to configure and maintain, while AspectJ provides more powerful interception capabilities for advanced use cases.
