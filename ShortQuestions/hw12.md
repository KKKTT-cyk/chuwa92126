## Question 1.

A loop that calls `Files.readAllLines`, parses each line and saves it has six problems. Spring Batch has a feature for each one.

| Problem with the loop | Spring Batch feature |
|---|---|
| Loads everything into memory (a 10 GB file gives `OutOfMemoryError`) | **Chunking**: read, process and write N items at a time |
| One malformed line kills the whole run | **Skip policies** for bad records, **retry** for transient errors |
| A crash at line 900,000 means starting over from 0 | **Restart** from the last committed chunk |
| One huge transaction, or none at all | **One transaction per chunk** |
| No record of what ran or what failed | **JobRepository metadata**: status, counts, failures, parameters |
| Hard to parallelize safely | **Multi-threaded steps** and **partitioning** |

## Question 3.

In chunk-oriented processing the reader and processor are called **once per item**, and the writer is called **once per chunk** with all the items of the chunk. With a chunk size of 3, one transaction reads and processes items 1, 2 and 3, writes `[1, 2, 3]` and commits. The next transaction does the same for items 4, 5 and 6. This repeats until the reader returns `null`.

The **transaction boundary is one chunk**: the transaction starts before the first read of the chunk and commits after the write. Progress is saved in the `ExecutionContext` at each commit.

The chunk size is also the commit interval:

| Chunk size | Effect |
|---|---|
| Small (e.g. 10) | Many commits (slower), little memory, little work lost on a failure |
| Large (e.g. 5,000) | Few commits (faster), more memory, a bigger chunk to roll back and redo |

A typical value is 100 to 1,000, then measure. On restart, at most one chunk of work is repeated.

## Question 5.

- **ItemReader**: `read()` is called once per item and returns one item. It **returns `null` to signal that there is no more input**, and the step then finishes. In the custom `PagedApiReader` it returns `null` after the last page has been consumed.
- **ItemProcessor** (optional): `process()` is called once per item to transform, validate, enrich or filter it. **Returning `null` means the item is filtered out**: it is not added to the chunk and not written, and it is counted in `filterCount`. It means "this item is valid but not needed", for example a zero-amount transaction.
- **ItemWriter**: `write(Chunk<? extends T> chunk)` is called once per chunk. A writer receives the whole Chunk instead of one item so that it can do **bulk operations**: one JDBC batch, one file flush, one API call per chunk instead of per item.

## Question 6.

**Filtering vs skipping**

| | Filter | Skip |
|---|---|---|
| How | The processor returns `null` | An exception is thrown and the step is configured to skip it |
| Meaning | "This item is valid but not needed" | "This item is bad" |
| Counted in | `filterCount` | `skipCount` |
| Example | A zero-amount transaction | A malformed CSV line, or a transaction with a missing account |

**Skip vs retry**

| | Skip | Retry |
|---|---|---|
| For | Permanent errors: the item itself is bad | Transient errors: trying again may work |
| Example error | `FlatFileParseException`, `InvalidTransactionException` | `TransientDataAccessException` (deadlock, lock timeout, temporary network failure) |
| Effect | The item is left out and counted in `skipCount` | The item is processed or written again |
| Limit | `skipLimit`: too many skips fails the step | `retryLimit`: after it, the error is treated as a failure (or a skip, if skippable) |

## Question 7.

Without `@StepScope`, Spring creates **one reader instance at startup**, shared by every run. Job parameters are **not known at startup**, so `#{jobParameters['inputFile']}` could not be resolved. With `@StepScope` the bean is created **for every step execution**, and the expression is resolved when the step starts. This also gives each run a clean reader; a custom reader that does not implement `ItemStream` would otherwise keep its position into the next run.

```java
@Bean
@StepScope   // created per step execution, so it can read job parameters
public FlatFileItemReader<Transaction> transactionReader(
        @Value("#{jobParameters['inputFile']}") String inputFile) { ... }
```

## Question 8.

If a job failed and is started again with the **same identifying parameters**, this is a **restart**: Spring Batch creates a **new JobExecution of the same JobInstance**. Steps that already completed are not run again, and the failed step resumes after the last commit. For example, if `settlementStep` committed 900,000 items and then failed, the second execution does not run `checkInputStep` again, the reader jumps to item 900,001, and `archiveStep` then runs.

For this to work:

- The **reader must be restartable**: it implements `ItemStream` and saves and restores its position in the `ExecutionContext`. The built-in readers do this.
- The **writer must be restart-safe**: it must not duplicate output. `FlatFileItemWriter` truncates to the last committed position, and database writers should be idempotent (an upsert or a unique key).

`JobInstanceAlreadyCompleteException` is thrown when the same identifying parameters are used and the previous execution is **COMPLETED (or ABANDONED)**, and only if the job has at least one identifying parameter. It stops the same data from being processed twice, for example the 2026-10-08 settlement being paid twice. To run again, change the parameters or use a `RunIdIncrementer`.

## Question 9.

| | Multi-threaded step | Partitioning |
|---|---|---|
| How | One step; chunks are processed by a thread pool | The data is split into ranges; each range is processed by its own worker step execution |
| When | Simple speed-up within one JVM | Large data sets with a natural key range; restart per partition |

In a multi-threaded step, the **reader, processor and writer are shared by all threads**, so they must be **thread-safe or stateless** (the race conditions from the multithreading lesson apply). `FlatFileItemReader` is not thread-safe, so it is wrapped in a `SynchronizedItemStreamReader`. Two more concerns: items are **no longer processed in file order**, and the **saved reader position is unreliable** when chunks finish out of order, so the usual choice is `saveState(false)` plus idempotent writes.

## Question 10.

Two pitfalls of `@Scheduled` batch jobs in an application with several instances:

1. **Several application instances.** With 3 pods, the scheduled method fires on each of them and the job starts 3 times. **Fix:** use a distributed lock (e.g. ShedLock), Quartz in cluster mode, or one dedicated scheduler, or run the schedule outside the application (a Kubernetes CronJob). Identifying job parameters such as `runDate` give some protection, because the second launch is normally rejected with `JobExecutionAlreadyRunningException` or `JobInstanceAlreadyCompleteException`. They are not a substitute for a real lock: this only works when both launches use exactly the same identifying parameters and the same database.
2. **One scheduler thread by default.** A 2-hour job delays every other `@Scheduled` task in that instance. **Fix:** set `spring.task.scheduling.pool.size=4` (or a suitable size).

## Question 11.

The complete code is in `Coding/hw12/Question11.java`. The two parts that were completed:

**`TransactionValidationProcessor.process`**: a zero-amount transaction is **filtered** (return `null`, it is valid but not needed); a null or blank account id, or a currency that `supports()` rejects, throws `InvalidTransactionException` (a bad item, so it can be **skipped**); every other transaction is converted to USD, and the settle date is the date part of the timestamp.

```java
@Override
public SettlementLine process(Transaction tx) {
    if (tx.amount().signum() == 0) {
        return null;                                   // FILTER: zero-amount noise, not an error
    }
    if (tx.accountId() == null || tx.accountId().isBlank()) {
        throw new InvalidTransactionException(tx.id(), "missing account");   // can be SKIPPED
    }
    if (!rates.supports(tx.currency())) {
        throw new InvalidTransactionException(tx.id(), "unsupported currency");
    }
    BigDecimal usd = rates.toUsd(tx.amount(), tx.currency());   // ENRICH: convert the currency
    return new SettlementLine(tx.id(), tx.accountId(), usd, tx.timestamp().toLocalDate());
}
```

**`SettlementStepConfig.settlementStep`**: a chunk-oriented step with chunks of 500, made fault tolerant: it skips `InvalidTransactionException` and `FlatFileParseException`, and fails once more than 100 items have been skipped.

```java
return new StepBuilder("settlementStep", jobRepository)
        .<Transaction, SettlementLine>chunk(500, transactionManager)   // 500 items per transaction
        .reader(transactionReader)
        .processor(processor)
        .writer(settlementWriter)
        .faultTolerant()
        .skip(InvalidTransactionException.class)
        .skip(FlatFileParseException.class)
        .skipLimit(100)                            // more than 100 skipped items -> the step FAILS
        .build();
```
