1. Loads everything into memory -> Chunking: read, process and write N items at a time
   One bad record kills the run -> Skip policies for bad records, retry for transient errors
   A crash means starting over -> Restart from the last committed chunk
   One huge transaction, or none at all -> One transaction per chunk
   No record of what ran or what failed -> JobRepository metadata: status, counts, failures, parameters
   Hard to parallelize safely -> Multi-threaded steps, partitioning
2. Job: The whole batch process: an ordered set of steps, such as dailyImportJob.
   Step: A stage within that job, such as importing a file.
   JobInstance: The job name plus identifying parameters, such as dailyImportJob with runDate=2026-10-25.
   JobExecution: One attempt to run that instance. Restarting after failure creates another execution.
   StepExecution: One execution attempt of a particular step, with its read/write/skip counts
3. Items are read and processed individually, and the resulting items are written as a chunk. Each chunk normally runs
within one transaction and commits after writing.
A larger chunk reduces transaction overhead but uses more memory and may require more work to be repeated after 
rollback. A smaller chunk uses less memory and limits repeated work but commits more frequently.
4. A tasklet step executes a task through Tasklet.execute(), repeating if necessary until completion. It suits 
operations such as deleting temporary files or running a stored procedure.
A chunk-oriented step reads, processes, and writes many records in transactional chunks. It suits importing a large CSV 
file into a database.
5. ItemReader: Returns one item per read() call; returning null means the input has ended.
   ItemProcessor: Transforms or validates an item; returning null filters that item out.
   ItemWriter: Receives a Chunk of output items, enabling efficient batch writes within the chunk transaction.
6. Filtering: Intentionally exclude an item by returning null, such as ignoring inactive customers.
   Skipping: Ignore an item after a configured exception, such as a malformed CSV record, subject to the skip limit.
   Retrying: Attempt a failed operation again because the error may be temporary, such as a database deadlock.
7. @StepScope delays creation of the reader until the step starts, when job parameters are available. This allows 
expressions such as #{jobParameters['inputFile']} to resolve at runtime and gives each StepExecution its own reader instance.
8. With the same identifying parameters, a restartable failed job creates a new JobExecution for the same JobInstance. 
Completed steps are normally skipped, and the failed step resumes from its last committed checkpoint. Stateful readers
and writers must save and restore necessary state, typically through ItemStream and ExecutionContext. Writes must 
support rollback or otherwise handle repeated execution safely. JobInstanceAlreadyCompleteException is thrown when the 
same JobInstance has already completed successfully.
9. In Spring Batch 5.x, a multi-threaded step processes chunks concurrently within one StepExecution. Shared readers, 
processors, and writers must be thread-safe or appropriately synchronized.
Partitioning divides the input into separate subsets, each processed by its own worker StepExecution and ExecutionContext. 
Workers can run locally or remotely, and step-scoped components can isolate each partition’s state.
Processing order is not guaranteed in a multi-threaded step.
10. Duplicate launches: Every application instance runs its own scheduler. Use a distributed lock, leader election, or 
a single external scheduler.
    Overlapping executions: A new trigger may launch while previous work is still running, especially with asynchronous 
launching or different parameters. Use execution checks or locking, meaningful identifying parameters such as runDate, 
and a shared persistent JobRepository.
