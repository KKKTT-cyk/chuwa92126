### Question 1.

A simple loop is unsuitable for large batch jobs because it may load the entire file into memory, fail on one bad record, require restarting from the beginning, and lack transaction management and execution tracking.

Spring Batch solves these problems with streaming readers and chunk processing, skip/retry policies, checkpoint-based restartability, per-chunk transactions, and `JobRepository` metadata. It also supports parallel processing through multi-threaded steps and partitioning.

### Question 2.

- A job defines the overall batch workflow
- A Step represents one phase of the overall batch workflow
- A JobInstance represents one logical run identified by the job name and identifying parameters, such as `dailySettlementJob` with `runDate=2026-10-23`.
- A JobExecution is one attempt to execute a JobInstance, so a failed instance can have multiple executions
- A StepExecution tracks an individual step attempt, including read, write, skip, and commit counts.

Spring Batch persists these records in the JobRepository.

### Question 3.

- Chunk-oriented processing reads and proceeses items individually, then writes them together as a chunk.
- Transaction boundaries: Each chunk runs within its own transaction, so successfully committed chunks are preserved if a later chunk fails.
- Chunk-size tradeoffs: A larger chunk reduces commit overhead and often improves throughput, but increases memory usage, transaction duration, and potential reprocessing after a failure. A smaller chunk has the opposite tradeoffs. It is a good strategy to start with a chunk size of a few hundred and tune it based on performance testing.

### Question 4.

- A tasklet step executes a specific task, such as checking a file, cleaning temporary files, or archiving data. It implements an `execute()` method and returns `FINISHED` or `CONTINUABLE`.
- A chunk-oriented step is designed for processing many records through an ItemReader, optional ItemProcessor, and ItemWriter. It automatically manages iteration, transactions, and checkpoints.

I'd use tasklets for setup and cleanup and chunk steps for bulk data processing.

### Question 5.

- ItemReader reads one item at a time and returns `null` to signal the end of input.
- ItemProcessor optionally validates, transfors, or filters each item; returning `null` filters the item out, while throwing an exception triggers fault-tolerance handling.
- ItemWriter receives an entire `Chunk` of processed items rather than a single item, allowing efficient bulk database operations, file writes, or API calls.

### Question 6.

- Filtering vs Skipping: Filtering is for valid but unneccesary records and happens when an ItemProcessor returns `null`. Skipping handles invalid records by allowing configured exceptions, such as a parsing or validation error, without failing the entire step.

- Skipping vs Retry: Retry handles transient failures, such as database deadlocks or network timeouts, by attempting the operation again. Skip uses a skip limit, while retry uses a retry limit. I would skip permanently invalid transactions and retry temporary infrastructure failures.

### Question 7.

`@StepScope` is required because `jobParameters` are available only when a job step is executing, while singleton beans are normally created during application startup. `@StepScope` enables late binding, so Spring creates the actual reader during the step execution and resolves `#{jobParemeters['inputFile']}` correctly. It also provides a separate reader instance for each StepExecution, which is important for stateful readers.

### Question 8.

When a failed job is launched again with the same identifying parameters, Spring Batch creates a new JobExecution for the existing JobInstance. It skips previously completed steps by default and resumes the failed step from the last committed checkpoint stored in the ExecutionContext. The reader must support saving and restoring its position, typically through ItemStream, while the writer must be restart-safe for idempotent to avoid duplicate output. If the JobInstance already completed successfully, launching it again with the same identifying parameters throws `JobInstanceAlreadyCompleteException`.

### Question 9.

A multi-threaded step processes chunks concurrently within one StepExecution using a TaskExecutor. Because the reader, processor and writer are shared across threads, they must be thread-safe or stateless. Partitioning divides the input into independent ranges, each processed by its own worker StepEXecution, allowing better state isolation and per-partition restarts. Multi-threading is useful for a simple speedup in one JVM, while partitioning is better suited to larget datasets that can be divided into independent subsets.

### Question 10.

One major pitfall of using `@Scheduled` in a multi-instance application is duplicate job launches, because every instance runs its own scheduler. I would address this with a distributed lock such as ShedLock or a centralized scheduler such as Kubernetes CronJob. Another pitfall is poor failure visibility: scheduled exceptions may be logged without triggering operational recovery. I would monitor JobExecutions and configure failure alerts using JobExecutionListener or metrics. I'd also configure the scheduler thread pool and time zone explicitly.

### Question 11.

```

import org.springframework.batch.core.Step;
import org.springframework.batch.core.repository.JobRepository;
import org.springframework.batch.core.step.builder.StepBuilder;
import org.springframework.batch.item.ItemProcessor;
import org.springframework.batch.item.ItemReader;
import org.springframework.batch.item.ItemWriter;
import org.springframework.batch.item.file.FlatFileParseException;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.transaction.PlatformTransactionManager;

import java.math.BigDecimal;
import java.time.LocalDate;
import java.time.LocalDateTime;

record Transaction(
        long id,
        String accountId,
        BigDecimal amount,
        String currency,
        LocalDateTime timestamp
) {}

record SettlementLine(
        long transactionId,
        String accountId,
        BigDecimal amountUsd,
        LocalDate settleDate
) {}

class InvalidTransactionException extends RuntimeException {
    InvalidTransactionException(long id, String reason) {
        super("Transaction " + id + ": " + reason);
    }
}

interface ExchangeRateService {
    boolean supports(String currency);
    BigDecimal toUsd(BigDecimal amount, String currency);
}

class TransactionValidationProcessor
        implements ItemProcessor<Transaction, SettlementLine> {

    private final ExchangeRateService rates;

    TransactionValidationProcessor(ExchangeRateService rates) {
        this.rates = rates;
    }

    @Override
    public SettlementLine process(Transaction tx) {

        // 1. Filter zero-amount transactions
        if (tx.amount().signum() == 0) {
            return null;
        }

        // 2. Validate account ID
        if (tx.accountId() == null || tx.accountId().isBlank()) {
            throw new InvalidTransactionException(
                    tx.id(), "Missing account ID");
        }

        // 3. Validate currency
        if (!rates.supports(tx.currency())) {
            throw new InvalidTransactionException(
                    tx.id(), "Unsupported currency: " + tx.currency());
        }

        // 4. Convert amount to USD
        BigDecimal amountUsd =
                rates.toUsd(tx.amount(), tx.currency());

        // 5. Extract settlement date
        LocalDate settleDate = tx.timestamp().toLocalDate();

        // 6. Return processed record
        return new SettlementLine(
                tx.id(),
                tx.accountId(),
                amountUsd,
                settleDate
        );
    }
}

@Configuration
class SettlementStepConfig {

    @Bean
    public Step settlementStep(
            JobRepository jobRepository,
            PlatformTransactionManager transactionManager,
            ItemReader<Transaction> transactionReader,
            TransactionValidationProcessor processor,
            ItemWriter<SettlementLine> settlementWriter) {

        return new StepBuilder("settlementStep", jobRepository)
                .<Transaction, SettlementLine>chunk(500, transactionManager)
                .reader(transactionReader)
                .processor(processor)
                .writer(settlementWriter)
                .faultTolerant()
                .skip(InvalidTransactionException.class)
                .skip(FlatFileParseException.class)
                .skipLimit(100)
                .build();
    }
}
```
