#### Conceptual Questions

1. **Explain why a simple loop that reads a whole file into memory, parses each line and saves it is not suitable for large batch jobs, and name the Spring Batch feature that addresses each problem.**

   A simple loop is not suitable for large batch jobs because reading the whole file into memory can cause an OutOfMemoryError, one bad record can stop the entire job, a crash may force the job to restart from the beginning, and there is no built-in record of what was processed. Spring Batch solves these problems with chunk-oriented processing, skip and retry support, restart from the last committed chunk, transaction management, and JobRepository metadata.

2. **Explain the difference between Job, Step, JobInstance, JobExecution and StepExecution, using a daily job that is run with a runDate parameter as the example.**

   A Job represents the entire batch process, while a Step represents one phase inside that job. A JobInstance is one logical run of a Job identified by its identifying parameters. For example, dailySettlementJob with runDate=2026-10-08 is one JobInstance. A JobExecution is one attempt to run that JobInstance, so a failed run and its restart are different JobExecutions of the same JobInstance. A StepExecution is one attempt to run an individual Step and stores information such as read, write, skip, commit and rollback counts.

3. **Explain chunk-oriented processing: how reading, processing and writing are organized, where the transaction boundaries are, and how the chunk size affects speed, memory and the amount of work repeated after a failure.**

   In chunk-oriented processing, Spring Batch reads and processes items one at a time until the configured chunk size is reached, then sends the whole chunk to the writer. One chunk is normally handled in one transaction and committed together. A small chunk size uses less memory and repeats less work after a failure, but causes more commits and can be slower. A larger chunk size reduces the number of commits and can improve performance, but uses more memory and may require more work to be repeated if the chunk rolls back.

4. **Compare a tasklet step with a chunk-oriented step, and give a typical use for each one.**

   A tasklet step performs one task and is suitable for work that is not based on processing many individual records. Typical examples are deleting temporary files, checking whether an input file exists, moving a file or calling a stored procedure. A chunk-oriented step is designed for processing many records through a reader, optional processor and writer. A typical use is reading a large CSV file, transforming each record and writing the results to a database or another file.

5. **Describe the contracts of ItemReader, ItemProcessor and ItemWriter: how a reader signals the end of the input, what it means when a processor returns null, and why a writer receives a whole Chunk instead of a single item.**

   ItemReader reads one item at a time and returns null when there is no more input. ItemProcessor receives one item at a time and can transform or validate it. If the processor returns null, the item is filtered out and is not sent to the writer. ItemWriter receives a whole Chunk instead of one item so it can perform efficient bulk operations such as a JDBC batch, one file flush or one API call for the entire chunk.

6. **Explain the difference between filtering and skipping an item, and the difference between skip and retry, with an example of an error suited to each.**

   Filtering means the item is valid but is not needed, so the processor returns null and the item is counted as filtered. For example, a transaction with a zero amount can be filtered out. Skipping is used when an item is bad and an exception is configured as skippable, such as a malformed CSV line or a transaction that fails validation. Retry is different because it is intended for temporary failures where trying again may succeed, such as a database deadlock, timeout or temporary network problem.

7. **Explain why a reader that uses #{jobParameters['inputFile']} must be declared @StepScope.**

   The inputFile job parameter is not available when Spring creates normal singleton beans at application startup. Declaring the reader @StepScope causes Spring to create a new reader for each StepExecution, so the job parameter expression is resolved when the step starts. It also gives each step execution a fresh reader instance instead of sharing the same stateful reader across runs.

8. **Describe what happens when a failed job is started again with the same identifying parameters, what the reader and the writer must support for this to work, and when JobInstanceAlreadyCompleteException is thrown.**

   Starting a failed job again with the same identifying parameters creates a new JobExecution for the same JobInstance. Completed steps can be skipped, and the failed step can continue from the last committed position using state stored in the ExecutionContext. For this to work, the reader must be restartable and save and restore its position, and the writer must be restart-safe so repeated writes do not create incorrect duplicate output. JobInstanceAlreadyCompleteException is thrown when the same identifying parameters are used for a JobInstance that has already completed successfully.

9. **Compare a multi-threaded step with partitioning, and explain what must be true of the reader, processor and writer in a multi-threaded step.**

   A multi-threaded step uses several threads to process chunks from the same StepExecution inside one step. Partitioning first splits the input into separate ranges or partitions, and each partition has its own worker StepExecution that can run in parallel and restart independently. In a multi-threaded step, the reader, processor and writer are shared across threads, so they must be thread-safe or stateless. A non-thread-safe reader such as FlatFileItemReader needs protection such as SynchronizedItemStreamReader.

10. **Describe two pitfalls of starting batch jobs with @Scheduled in an application that runs as several instances, and how to address each one.**

    One problem is that every application instance can run the same scheduled method, so a three-instance deployment may start the same batch job three times. This can be addressed with a distributed lock such as ShedLock, Quartz in cluster mode, or by moving scheduling to an external system such as a Kubernetes CronJob. Another problem is that Spring uses one scheduler thread by default, so a long-running scheduled job can delay other scheduled tasks. This can be addressed by increasing the scheduling thread pool size or by using a separate external scheduler.
