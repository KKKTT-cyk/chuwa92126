## 1. A request-duration histogram exports 8 finite buckets, one +Inf bucket, a sum and a count for every label combination. The service has 100 instances, 20 endpoints and 4 status values. Calculate the number of series. Then a developer adds a user_id label with 50,000 distinct values: calculate the worst-case series count, explain which resources of a time-series database are hurt, and list three techniques that keep cardinality under control and where each one is applied.
1.so that’s 11 series per label combination. The combinations are 100 instances times 20 endpoints times 4 statuses, which is 8,000. So the total is 11 times 8,000, or 88,000 series
2.Adding user_id with 50,000 values multiplies every combination by 50,000. In the worst case, where every user hits every instance, endpoint and status, that’s 88,000 times 50,000, or 4.4 billion series.
3.Memory goes first, because every active series sits in the in-memory head block, so the database gets OOM-killed. The inverted index also blows up, since each user_id value adds its own postings list. Ingestion slows down because every sample needs a series lookup, queries have to fan out over millions of series, and storage compresses poorly because the data is so sparse.
First, in the application code, only use bounded labels like endpoint and status, and put per-user detail in logs or traces instead. Second, at the collection layer, use Prometheus relabeling or the OpenTelemetry Collector to drop labels like user_id, and set sample_limit so one bad deploy can’t flood the system. Third, at the database layer, enforce per-tenant series limits and use recording rules to pre-aggregate away dimensions we don’t query. The cheapest fix is at the source, but defending at all three layers means one mistake can’t take down monitoring.


## 2. Instance A served 800 requests with a 99th percentile of 20 ms and instance B served 200 requests with a 99th percentile of 600 ms. Explain why the average of the two percentiles is not the 99th percentile of the combined traffic. Then compare client-side summaries, fixed-bucket histograms and sketches by whether they can be aggregated across instances, their accuracy, and their cost, and explain why bucket boundaries should be chosen around the latency objective.
Averaging percentiles
You can’t average them. Percentiles aren’t linear, and the combined P99 depends on the full distribution of both instances, not just two numbers. You have to merge the distributions first, then compute the percentile.
Summaries compute quantiles on each instance. They’re accurate locally but can’t be aggregated, and they cost client CPU.

Histograms aggregate easily by summing buckets. They’re cheap, but only exact at bucket boundaries, and each bucket adds a series.

Sketches like t-digest are mergeable with bounded error, so they’re accurate and aggregatable, but they use more memory and need backend support.

Buckets around the SLO
Histograms are only exact at boundaries, so I put a bucket right at the SLO, like 300 milliseconds, and keep buckets dense around it. That makes the SLO check exact without adding series everywhere.




## 3. A tail-based sampling tier receives 2,000 traces per second, each with 8 spans of 400 bytes on average, and holds each trace for a 20 second decision window. Calculate the memory needed to buffer the spans. Explain why all spans of a trace must be routed to the same sampler node, and compare routing by hash(trace id) modulo N with consistent hashing when the tier grows from 4 to 5 nodes, including the fraction of traces that move in each case.
The tier buffers 20 seconds of traffic, so that’s 2,000 times 20, or 40,000 traces. At 8 spans each, that’s 320,000 spans, and at 400 bytes each, about 128 megabytes. In practice I’d plan for two to three times that for object overhead and traffic spikes.
Tail-based sampling decides after seeing the whole trace, for example keeping traces with errors or high latency. If spans are split across nodes, each node sees only part of the trace, so it can make the wrong decision and store incomplete traces. So we route by trace ID, and every span of a trace lands on the same node.

## 4. The header traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-00 arrives at a service. State the meaning and size of each of the four fields. What does the last field tell the service to do, how does it keep the sampling decision consistent across all services of a trace, and what does the service put in the parent-id field of the header it sends to the next service?
The header has four fields separated by dashes. The first is the version, one byte, currently 00. The second is the trace ID, 16 bytes or 32 hex characters, and it identifies the whole trace across every service. The third is the parent ID, 8 bytes or 16 hex characters, which is the span ID of the caller. The last is trace flags, one byte, where the lowest bit is the sampled flag.




## 5. A service has a 99.95% availability objective measured over 30 days. Calculate the error budget in minutes. For burn rates of 14.4 and 6, calculate the error ratio that triggers the alert and the fraction of the budget consumed after 1 hour and after 6 hours respectively, and the number of days after which the budget would be exhausted at burn rate 6. Explain why a good alert uses a long window and a short window together, and which of the two alerts should page someone and which should create a ticket.
30 days is 43,200 minutes, and 99.95% availability allows 0.05% failure, so the error budget is 21.6 minutes. A good alert requires both windows to exceed the threshold. The long window, like one hour, shows the problem is significant and filters out short blips. The short window, like five minutes, shows it’s still happening, so the alert clears quickly once the issue is fixed instead of firing for another hour.





## 6. Explain how a telemetry pipeline is designed so that a backend outage never blocks or slows the monitored application, what the overload options are at each stage (buffering, dropping, sampling, rate limiting) and the tradeoff of each, and the difference between at-least-once and at-most-once delivery for telemetry. Then explain why the alerting path should run in a separate failure domain from the systems it monitors and what a watchdog (dead-man's switch) alert detects.
The key is decoupling. The SDK exports asynchronously into a bounded in-memory queue with timeouts, so the app never waits on the network. If the queue is full, it drops data instead of blocking. Then local agents, collectors, and something like Kafka buffer between the app and the backend, so a backend outage never reaches application threads.
Buffering, in memory, on disk, or in Kafka, absorbs bursts and short outages, but costs memory and latency, and still fills up in a long outage. Dropping protects the app and is simple, but creates blind spots, so we should count what we drop. Sampling, at the SDK or the collector, cuts volume while keeping representative data, but we lose detail and rare events. Rate limiting at the collector or gateway stops one noisy service from overwhelming the backend, but that service loses data and the limits need tuning.
At-least-once retries until acknowledged, so nothing is lost but you can get duplicates. At-most-once sends once and never retries, so it’s cheap and never duplicates but can lose data. For telemetry, I’d use at-most-once at the app edge to protect the app, and at-least-once inside the pipeline, like with Kafka.
If alerting runs on the same cluster, region, or network as the systems it monitors, a single outage takes down both, and we’re silent exactly when we need alerts most. So alerting should run in a different cluster or region, with its own notification path.
