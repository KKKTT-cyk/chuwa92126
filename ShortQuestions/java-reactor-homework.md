#### Conceptual Questions

1. **Using the timeline of a request that calls a database and an external API, explain why the thread-per-request model wastes resources for I/O-bound work.**

   For example, a request uses the CPU for 2 ms, waits 50 ms for a database, uses the CPU for another 2 ms, waits 200 ms for an external API, and uses the CPU for a final 1 ms. The request takes 255 ms, but only 5 ms is actual CPU work. With a blocking platform-thread-per-request model, a thread is occupied for the entire request even though it spends most of the time waiting. Waiting does not continuously consume CPU, but the thread still reserves memory and a slot in the request thread pool. With 200 threads, the simplified throughput ceiling is about 200 / 0.255, or 784 requests per second. Slower dependencies can exhaust the pool while the CPU still has spare capacity. Non-blocking I/O allows a thread to handle other requests while the database or API response is pending, then continue the original request when its result becomes available.

2. **Describe the Reactor pattern: the roles of the demultiplexer, the event loop, the acceptor and the handlers. Explain why blocking an event loop thread is so harmful.**

   The Reactor pattern uses I/O multiplexing to manage many connections with a small number of threads. 

   The demultiplexer reports which channels are ready for I/O. The event loop waits for these readiness events and dispatches each event to its handler.

   The acceptor accepts new connections and registers them for further events. 

   Read and write handlers perform the work associated with ready channels and must return quickly.

   Blocking an event loop with Thread.sleep(), JDBC or a blocking HTTP call prevents it from processing all the other connections assigned to that loop. One slow call can therefore delay many unrelated requests. Blocking operations should be moved to a suitable worker scheduler or replaced with non-blocking APIs.

3. **Name the four interfaces of the Reactive Streams specification, describe the sequence of signals between a publisher and a subscriber, and explain the role of request(n).**

   The four interfaces are Publisher, Subscriber, Subscription and Processor. A Publisher accepts subscribers, a Subscriber receives signals, a Subscription manages demand and cancellation, and a Processor is both a Subscriber and a Publisher. After subscribe(subscriber) is called, the publisher first sends onSubscribe(subscription). The subscriber can then call request(n) to request n additional items. The publisher delivers zero or more onNext signals without exceeding the outstanding demand, followed by either onComplete for success or onError for failure. These terminal signals do not require outstanding item demand, and no further signals follow termination. Signals to one subscriber are serialized. Positive request amounts accumulate; Long.MAX_VALUE is normally treated as unbounded demand. The subscriber can also call cancel() to stop receiving data. This demand protocol provides backpressure by allowing the consumer to control how many items it is prepared to receive.

4. **Explain the difference between Mono and Flux, and what "nothing happens until you subscribe" means. Explain why Mono.just(buildReport()) behaves differently from Mono.fromCallable(() -> buildReport()).**

   Mono represents a publisher that emits zero or one item, while Flux can emit zero to many items and may be infinite. Either can terminate with an error, and Mono<Void> represents completion without a value. Building a normal cold pipeline describes work rather than executing it; subscription activates the pipeline, and demand controls item delivery. In WebFlux, the framework normally subscribes to the publisher returned by a controller. However, ordinary Java expressions used during assembly still run immediately. Mono.just(buildReport()) calls buildReport() before Mono.just() receives its argument, then captures that result for subscribers. Mono.fromCallable(() -> buildReport()) defers the call until execution after subscription and runs it again for each subscription. It also converts an exception from the callable into an error signal. Deferring work does not automatically move it to another thread or make a blocking operation non-blocking.

5. **Compare map, flatMap, concatMap and flatMapSequential in terms of what the function returns, whether inner calls run concurrently, and the order of the output.**

   map takes a function that returns a plain value and transforms each incoming item synchronously, preserving the input order. It does not subscribe to inner publishers or introduce concurrency. flatMap takes a function that returns a Publisher, such as a Mono or Flux, and merges the inner publishers. Multiple asynchronous inner operations can be in flight concurrently, subject to the configured concurrency limit, and their results can interleave rather than follow input order. concatMap also maps each item to a Publisher, but subscribes to one inner publisher at a time and waits for it to finish before moving to the next, preserving order. flatMapSequential subscribes to inner publishers eagerly, allowing concurrent asynchronous operations, but buffers later results until earlier publishers have been drained so the output follows source order. These operators do not by themselves make synchronous blocking functions run in parallel; concurrency depends on the inner publishers and scheduling.

6. **Explain why a try/catch around the code that builds a pipeline does not catch errors from that pipeline, and describe what onErrorReturn, onErrorResume, onErrorMap, retryWhen and timeout do.**

   A try/catch around pipeline assembly catches only exceptions thrown while assembling it. Execution usually happens later, after subscription, and execution failures are delivered as onError signals rather than thrown back into that earlier try/catch. onErrorReturn replaces an error with a fallback value, while onErrorResume switches to a fallback publisher. onErrorMap transforms the error into another exception without recovering successfully. retryWhen resubscribes to the upstream publisher according to a retry policy, which can specify a retry limit, error filter and backoff; side effects can therefore happen again. timeout imposes a time limit and normally signals TimeoutException when it expires, cancelling the upstream subscription. For a Mono it limits the wait for its result; for a Flux, timeout(Duration) normally measures the wait for the first item and then the gaps between items. To limit the total duration of collecting a Flux, place timeout after collectList(). Operator order matters: timeout before retryWhen gives each attempt its own limit, while timeout after retryWhen limits the combined operation.

7. **Explain the difference between publishOn and subscribeOn, and which scheduler should be used to wrap a blocking JDBC call.**

   publishOn changes the execution context for downstream signal handling and operators after that point, until another scheduling boundary changes it. subscribeOn schedules subscription to the upstream source, so it is useful for choosing where a synchronous source or callable executes even when placed later in the chain. It does not override a source that emits on its own scheduler or a later publishOn boundary. A blocking JDBC call should be wrapped with Mono.fromCallable(() -> dao.findById(id)).subscribeOn(Schedulers.boundedElastic()). The callable defers the work, and boundedElastic runs it away from event-loop threads on a scheduler intended for blocking tasks with bounded resources. Using Mono.just(dao.findById(id)) would execute the blocking call immediately before scheduling could help. Wrapping JDBC isolates its blocking behavior; it does not turn JDBC into a non-blocking driver.

8. **Explain what backpressure is, how a subscriber expresses demand, and the options available when a source such as Flux.interval cannot slow down.**

   Backpressure coordinates a producer with a slower consumer so that the producer does not deliver more items than the consumer has requested. A subscriber expresses demand through Subscription.request(n), and Reactor operators propagate or reshape those requests upstream. For a timed source such as Flux.interval, ticks are tied to a clock rather than produced only when requested. Without enough demand and without another strategy, interval can terminate with an overflow error. onBackpressureBuffer can store items until demand arrives, preferably with a bounded capacity and an explicit overflow policy. onBackpressureDrop discards items when there is no demand, and onBackpressureLatest retains only the most recent pending item. Failing explicitly or cancelling the source can also be appropriate. Buffering trades memory for temporary tolerance, while dropping or keeping only the latest value loses data. An unbounded buffer cannot safely solve a permanently faster producer, and limitRate changes upstream request batches rather than making an uncontrollable source slow down.

9. **Explain the difference between cold and hot publishers, why subscribing twice to the same WebClient Mono sends two HTTP requests, and how cache() and share() change this.**

   A cold publisher starts its work separately for each subscription, so each subscriber gets its own execution. A hot publisher shares an ongoing production of signals, and late subscribers may miss earlier values unless replay is provided. A normal WebClient Mono describes an HTTP exchange; subscribing twice starts two independent requests, even when both subscriptions use the same Mono variable. cache() creates a shared Mono that retains the value or terminal signal for later subscribers, avoiding repeated requests while the cached signal remains valid; a time-to-live overload limits retention. share() also allows subscribers to share one upstream task, but its behavior depends on the publisher type. Mono.share() shares the task and its eventual terminal result, including with later subscribers; if all subscribers cancel before termination, it can cancel and reset the upstream task. Flux.share() normally shares live emissions among active subscribers and does not replay earlier items. The cached or shared publisher itself must be reused; constructing a new one for every caller does not share requests across callers.

10. **Compare Spring MVC and Spring WebFlux, and explain when Spring MVC with virtual threads is a better choice than WebFlux.**

    Spring MVC uses the Servlet programming model and commonly handles requests with imperative code and blocking libraries such as JDBC and JPA. Spring WebFlux uses a reactive, non-blocking model, commonly with Reactor Netty event loops, Mono and Flux pipelines, and reactive database drivers. WebFlux is useful for streaming, many concurrent I/O operations and end-to-end reactive systems, but blocking its event loops causes serious delays and reactive debugging can be more complex. Spring MVC with virtual threads is often a better choice for request-response or CRUD services that already use blocking libraries and benefit from straightforward control flow and stack traces. Virtual threads can suspend during supported blocking I/O without occupying a platform thread for the whole wait, allowing many concurrent requests while retaining imperative code. They do not remove limits such as database connection-pool capacity, and they do not provide Reactive Streams backpressure. WebFlux remains useful when streaming, demand control or extensive reactive composition is central to the application.
