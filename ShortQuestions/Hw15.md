## 1. Using the timeline of a request that calls a database and an external API, explain why the thread-perrequest model wastes resources for I/O-bound work.
A request might take 255 ms, but only 2 ms processing the result, 200 ms waiting for an external API, and 1 ms preparing the response. Only 5 ms involves CPU work. Although the waiting thread usually consumes little CPU, it still holds memory and a thread-pool slot, limiting how many requests the server can handle concurrently.





## 2. Describe the Reactor pattern: the roles of the demultiplexer, the event loop, the acceptor and the handlers. Explain why blocking an event loop thread is so harmful.
The Reactor pattern uses a demultiplexer, identify connections ready for I/O.
The event loop waits for these events and dispatches them to the appropriate handlers. The acceptor accepts new connections and registers them for monitoring, while the handlers perform reading, processing, and writing.
Blocking the event loop is harmful because one thread typically serves many connections: while it waits for a slow operation, all other connections assigned to it are delayed, increasing latency and reducing throughput.


## 3. Name the four interfaces of the Reactive Streams specification, describe the sequence of signals between a publisher and a subscriber, and explain the role of request(n).
The four interfaces are Publisher, Subscriber, Subscription, and Processo. After publisher.subscribe, the publisher calls onSubscribe, followed by zero or more requested onNext signals, and optionally a terminal onComplete() or onError(). The subscriber calls subscription.request() to request up to n additional items.


## 4. Explain the difference between Mono and Flux, and what "nothing happens until you subscribe" means. Explain why Mono.just(buildReport()) behaves differently from Mono.fromCallable(() -> buildReport()).
Mono represents a sequence of zero or one item, while Flux represents zero to many items, potentially an infinite stream. “Nothing happens until you subscribe” means that, for a cold publisher, assembling the pipeline describes the work subscribing initiates execution. In contrast, Mono.fromCallable(() -> buildReport()) stores the computation and calls buildReport() when subscribed to, normally once per subscription.


## 5. Compare map, flatMap, concatMap and flatMapSequential in terms of what the function returns, whether inner calls run concurrently, and the order of the output.
map transforms each item into a value and preserves source order.
flatMap transforms each item into a publisher, allows concurrent inner execution, and emits results as they arrive without guaranteeing source order. concatMap also returns inner publishers but executes them one at a time, preserving order.
flatMapSequential allows concurrent inner execution while buffering later results to preserve source order.





## 6. Explain why a try/catch around the code that builds a pipeline does not catch errors from that pipeline, and describe what onErrorReturn, onErrorResume, onErrorMap, retryWhen and timeout do.
A try/catch around pipeline construction only catches exceptions thrown during assembly; execution errors normally occur after subscription and travel as onError signals. onErrorReturn replaces an error with a fallback value and completes; onErrorResume switches to a fallback publisher; onErrorMap transforms the error into another exception; and retryWhen resubscribes to the upstream according to a retry policy, such as limited retries with backoff. timeout signals a timeout error if the first or next item does not arrive within the configured duration, or switches to a supplied fallback.





## 7. Explain the difference between publishOn and subscribeOn, and which scheduler should be used to wrap a blocking JDBC call.
subscribeOn controls where subscription and synchronous source execution begin, while publishOn switches downstream processing to the specified scheduler from its position in the pipeline. For a blocking JDBC call, use Mono.fromCallable(() -> jdbcCall()).subscribeOn(Schedulers.boundedElastic()) to defer execution and move the blocking work off the event loop. The JDBC call remains blocking, but it runs on a scheduler designed to accommodate blocking tasks.

## 8. Explain what backpressure is, how a subscriber expresses demand, and the options available when a source such as Flux.interval cannot slow down.
Backpressure prevents a fast producer from overwhelming a slower consumer. The subscriber calls Subscription.request(n) to express demand for n additional items. When a source such as Flux.interval cannot slow down, excess items can be buffered with onBackpressureBuffer (preferably with a limit), dropped with onBackpressureDrop, reduced to the latest value with onBackpressureLatest, or cause an overflow error. Without sufficient demand or an appropriate strategy, Flux.interval signals an error.




## 9. Explain the difference between cold and hot publishers, why subscribing twice to the same WebClient Mono sends two HTTP requests, and how cache() and share() change this.
A cold publisher starts a separate execution for each subscription, while a hot publisher shares a data-producing process among subscribers. A normal WebClient Mono is cold, so subscribing twice triggers two HTTP requests. cache() shares the initial request and replays its outcome—including errors—to later subscribers, optionally with an expiry time. Mono.share() also shares the request and its result, but cancels the upstream if everyone cancels before completion. For a Flux, share() generally shares the active execution without replaying past items.






## 10. Compare Spring MVC and Spring WebFlux, and explain when Spring MVC with virtual threads is a better choice than WebFlux.
Spring MVC uses the Servlet model and commonly handles requests with imperative, blocking code; WebFlux uses non-blocking reactive processing with Mono and Flux, typically on a small event-loop pool. MVC with virtual threads is often a better fit for applications using JDBC, JPA, or blocking SDKs: it preserves straightforward code while allowing many I/O waits without occupying a platform thread for each wait. WebFlux is attractive for reactive streaming and non-blocking pipelines. Virtual threads do not speed up CPU-heavy work or remove database connection limits.
